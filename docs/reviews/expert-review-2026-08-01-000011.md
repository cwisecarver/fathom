# Fathom Expert Panel Review

**Date:** 2026-08-01
**Panels:** Elixir/OTP & Concurrency · Storage & Durability · Distributed Systems & Fencing · Multi-Tenant Security & Shard Isolation · Performance & Hot Paths · Missing Capabilities & Operational Readiness
**Methodology:** Panel scoping → 6 parallel expert reviews → spot-checked unified ranking

## Project Profile

- **Type:** multi-tenant sharded data platform (SQLite-per-shard, Hrana, S3-bottomless)
- **Commit reviewed:** 1ce608b
- **Total Findings:** 48 unique after dedup (from 60 raw across 6 panels)
- **Focus of this audit:** performance, stability, missing features, data integrity

## Executive Summary

Four themes dominate. **First, the SQL surface is unguarded.** Every gate fathom has — the `:ro`
token scope, `:block_tenant_ddl`, the write fence, the per-shard size cap — is enforced by a
leading-keyword prefix match over client SQL, and `attach`, `vacuum`, and `pragma <x> = <y>` are in
none of the prefix lists. Two panels independently proved, by execution, that any authenticated
stream can `ATTACH` and then read *and write* every co-resident tenant's database file. That is the
one invariant AGENTS.md calls a release blocker, and it is open on `main` with a green suite.
**Second, several code paths conclude "my writes are durable" without evidence.** The terminate-path
flush settle matches a reply shape the flush task stopped producing at commit `f8ecf63`, so every
graceful stop discards the in-flight flush result and then deletes the local file; and a 412 with
the lock still ours is treated as proof the stored object contains *this* interval's bytes when it
may hold an earlier snapshot. Both end in `drop_local/1` unlinking acknowledged, never-uploaded
writes, and both are reachable on an ordinary rolling deploy — which is also when they compound.
**Third, the fence has three places where the token itself misbehaves**: `restore_lock/3` writes the
epoch *backward*, `flush_then_drop` releases with a stale `lock_etag` so the lock survives the drop,
and an expired-but-present heartbeat object marks a healthy, lock-renewing node dead. **Fourth, the
harnesses cannot see any of this** — the bench gate is six single-threaded p50s of read paths on
idle shards, the cluster suite pins only the happy fence paths, and no test anywhere issues `ATTACH`
as tenant SQL.

Fix order is not the rank order: #1 and #7 (`set_authorizer` + a read-only handle + an executor
statement gate) are a single afternoon that closes the release blocker, and #3 is a fifteen-line
diff that stops silent data deletion on the next deploy. **The single most important sentence: a
tenant on this build can read and overwrite every other tenant homed on the same node with one
`ATTACH DATABASE` statement, and a rolling deploy silently deletes acknowledged writes — both are
reachable today, on the default configuration, with no exotic timing.**

## Ranked Findings

### #1. `ATTACH DATABASE` gives any authenticated stream full read + write access to every co-resident tenant's shard file
**Severity:** Critical | **Category:** Shard Isolation | **Panels:** Security, Gaps (both verified by probe)
**Likelihood:** Certain (one statement) | **Blast Radius:** Every tenant co-resident on the node

**Problem:** Every shard lives at `<data_dir>/<shard_id>.db` in one flat directory
(`lib/fathom/shard.ex:2275`, `db_path/1`), and the per-stream handle is opened read-write with no
authorizer and no `SQLITE_LIMIT_ATTACHED` (`lib/fathom/shard/connection.ex:18-57` — confirmed: the
`with` chain sets pragmas only). `Fathom.ShardExecutor.do_execute/2`'s statement gate
(`lib/fathom/shard_executor.ex:91-142`) branches on `dml?/1` (`:802` — `insert|update|delete|replace`)
and `ddl?/1` (`:819` — `create|alter|drop`); `attach` matches neither, so it reaches
`Connection.query/4` unmodified. The attacker does not need to guess the path — `PRAGMA
database_list` is a read pragma returning the absolute path of their own file.

Verified end to end by two panels independently:

```
PRAGMA database_list         -> [[0,"main","/…/fathom_shards/evilco.db"]]
ATTACH DATABASE '/…/victimco.db' AS v  -> {:ok, …}
SELECT x FROM v.secrets                -> [["victimco-PII"]]
INSERT INTO v.secrets VALUES ('PWNED') -> {:ok, num_changes: 1}
```

**Impact:** Total cross-tenant read *and* write breach. It bypasses `:ro` scope (#7),
`:block_tenant_ddl`, `Fathom.Shard.WriteFence`, and the single-writer lease (the victim's
coordinator holds the lease; the attacker's connection never consults it). Writes to a victim shard
also bypass its `WriteCounter`, so the victim stays "clean" and its idle `drop_clean/1` either
discards the tampering or persists it on the next flush — either way the tenant's data is no longer
trustworthy. Under `HRANA_AUTH=required` — the mode whose entire purpose is per-shard isolation — a
tenant holding a *valid token for its own shard* reads every neighbour.

**Recommended Fix:** Two layers, both small.
1. `lib/fathom/shard/connection.ex:21` — add `:ok <- Sqlite3.set_authorizer(conn, [:attach, :detach])`
   to the `open/1` `with` chain. exqlite 0.37 (already pinned) ships it and documents this exact
   example. Verified working: `ATTACH -> {:error, "not authorized"}` while `CREATE TABLE`, `INSERT`,
   `SELECT`, `PRAGMA journal_mode` are unchanged.
2. `lib/fathom/shard_executor.ex:91` — add an `attach?/1`/`detach?/1` branch to the `cond`,
   returning `%Error{code: "FILO_STATEMENT_BLOCKED", status: 403}`, unconditionally (not
   config-gated: the migration engine replays through `Connection` directly, not this path).
   Defence in depth: strip leading SQL comments before classifying (see #7).
3. Ship with the cross-tenant regression test in #20. Defence in depth for later: give each shard
   its own subdirectory so a sibling's path is not derivable.

### #2. An un-sidecar'd local `.db` is trusted as this node's own warm copy — a planted file is served as authoritative, and an ordinary failover/fail-back clobbers a newer lineage
**Severity:** Critical | **Category:** Shard Isolation / Data Loss | **Panels:** Security (#2), Storage (#2)
**Likelihood:** High (attacker: trivial; no-attacker path: an ordinary failover-then-fail-back) | **Blast Radius:** Any tenant, including ones never served on the node

**Problem:** One root cause, two triggers. Cold-open treats a present local `.db` as a warm restart
and **skips the storage pull entirely**: `file? = File.exists?(path)` (`lib/fathom/shard.ex:325`),
`pull_task = if file?, do: nil, …` (`:330`), `warm? = file? and not resolve_fork(…)` (`:351-352`),
`pull_task = pull_task || if warm?, do: nil, …` (`:354`). The provenance guard returns
`fork_evidence/2 :missing -> :no_sidecar` (`:1912-1913`) and `resolve_fork(:no_sidecar, …), do: false`
(`:1947`) — i.e. "keep it, open warm". `await_pull(nil, …)` then hits `:missing` and **adopts
whatever etag the store holds now** (`:766-774`), so the first fenced flush `If-Match`es
successfully.

- **Trigger A (attacker).** SQLite's `ATTACH` *creates* the target file. Verified: from `evilco`'s
  stream, `ATTACH DATABASE '<data_dir>/neverseen.db' AS t; CREATE TABLE t.planted(a)` produces a
  structurally valid 8192-byte database, no sidecar, `Fathom.Shard.verify_integrity` → `:ok`. When
  the victim's coordinator later starts, it serves the attacker's database and uploads it over the
  genuine object. `VACUUM INTO '<data_dir>/<victim>.db'` reaches the same primitive without `ATTACH`
  (#8), so fixing only `ATTACH` does not close this.
- **Trigger B (no attacker).** A brand-new shard has no sidecar *by construction*:
  `promote_pull/2`'s else branch explicitly `File.rm(etag_sidecar(path))` (`:836-840`). So on a
  persisted `:shard_data_dir` (PVC / reattached volume): node A dies before its first flush → LB
  reroutes to B → B serves, flushes, idles, releases cleanly → A returns and the LB routes home →
  A's `file?` is true, `:no_sidecar` ⇒ warm, adopt-current-etag ⇒ `post_lease_warm_check/3`
  (`:612-641`) compares the store's etag against the etag just adopted *from the store* — always
  equal — and A's first flush overwrites B's acknowledged writes. `revalidate_touched/5`'s warm
  branch (`:523-547`) protects only the crash-steal direction; the clean-release direction has no
  sidecar to compare. The comment at `:814-826` names exactly this clobber as the hole the
  sidecar-first ordering closed — for the promote crash window only, not for the born-empty case.

**Impact:** Silent, unrecoverable substitution or destruction of a tenant's entire database. No
quarantine, no `.forked.<ts>` recovery copy, no `[:fathom,:shard,:forked]` telemetry — the clobber
looks like a normal flush.

**Recommended Fix:** Make "brand-new, no stored object" an **explicit** provenance state rather than
an absence.
1. In `promote_pull/2`'s else branch (`shard.ex:836-840`) write a sentinel sidecar (e.g. the literal
   `"-"`, "derived from: no object") instead of removing it, and have `await_pull(nil, …)` map that
   value to `expected_etag = nil` so the first flush uses `If-None-Match: *` and can only create.
2. Once every locally-created file carries provenance, make `:missing` **fail closed** —
   quarantine + cold re-pull — instead of adopting the current etag. At minimum gate the
   adopt-current fallback behind a config flag defaulting to off.
3. Additionally stamp an ownership marker (`Heartbeat.owner/0` + incarnation) at coordinator
   creation and at every promote, so a file *this incarnation did not create* is untrusted even if
   it carries a sidecar shape — that is what makes trigger A loud rather than authoritative.

### #3. `settle_flush_task/1` matches a reply shape the flush task stopped producing — every terminate discards the in-flight flush, then deletes the post-snapshot writes
**Severity:** Critical | **Category:** Data Loss | **Panels:** OTP (#1)
**Likelihood:** High — every write-active shard with a flush in flight at SIGTERM (default interval 5 s) | **Blast Radius:** Fleet-wide on a rolling deploy

**Problem:** CONFIRMED against source. `fenced_flush/2` (`lib/fathom/shard.ex:1575-1587`) replies
`{:fenced, flush_and_reconcile(...), updates}` / `:fence_superseded` / `:fence_skip`. The live
handler matches that correctly (`:993`). The terminate path does not:

```elixir
# lib/fathom/shard.ex:2188-2207
case Task.yield(task, settle_yield_ms()) || Task.shutdown(task) do
  {:ok, {:ok, new_etag}} ->   # line 2191 — UNREACHABLE, the task never replies {:ok, etag}
    ...
  _ ->
    %{state | flush_task: nil}   # always taken
end
```

`Task.yield/2` returns `{:ok, {:fenced, {:ok, etag}, updates}}`. This is a refactor regression:
`git show f8ecf63` ("run the periodic-flush fence off-process, audit #18") changed the reply shape
and updated `handle_info/2` but never touched `settle_flush_task/1`.

**Impact:** All three `terminate/2` clauses that settle (`:1325` self-fence, `:1346` idle-stop,
`:1385` SIGTERM/force-stop) proceed with a **stale `state.etag`** and **stale `flushed_through`**.
`flush_and_drop/1` (`:1457`) sees `unflushed?` true → `flush_then_drop/1` → `upload_for_drop/1`
(`:1648`) PUTs with the pre-task etag while the object is already at the task's `new_etag` ⇒
deterministic **412** → the `{:error, :superseded}` branch (`:1509-1518`) re-checks the lock, finds
it ours, logs *"flush 412 but lock still ours; object is durable, dropping"*, and runs
`drop_local(state.path)`. The object holds only the settled task's snapshot; every write committed
between that snapshot and the terminate was acked, never uploaded, and is now unlinked (`.db`,
`-wal`, `-shm`, `.etag`). Silent, unrecoverable loss with a log line asserting durability.
Secondary: the `#21` sidecar stamp is defeated, and a *transient* `check_lease` error in the same
branch (`:1519`) skips `release_lease` entirely, stranding the lock. **This is the deterministic
entry into finding #4's worst branch.**

**Recommended Fix:** Extract the verdict fold from `handle_info({ref, result}, …)` (`:989-1059`)
into one pure `apply_flush_result(state, result)` and call it from both sites, so the two can never
drift again. Minimum viable patch at `:2190`:

```elixir
{:ok, {:fenced, {:ok, new_etag}, updates}} ->
  write_etag_sidecar(state.path, new_etag)
  state |> Map.merge(updates) |> Map.merge(%{flush_task: nil,
    flushed_through: state.flush_pending, counter_gen: state.flush_pending_gen, etag: new_etag})

{:ok, {:fenced, {:reconciled, obj}, updates}} when not is_nil(obj) -> …   # see #4 for the correct semantics
```

Regression test (fails today): start a coordinator, force an in-flight flush task to complete, stop
the coordinator, assert (a) no second `Storage.flush` was issued and (b) a row written after the
task's snapshot survives a re-open.

### #4. A 412 with the lock still ours is treated as proof our writes are durable — they may not be
**Severity:** Critical | **Category:** Data Loss | **Panels:** Distributed Systems (#1)
**Likelihood:** Medium standalone; **High** combined with #3 | **Blast Radius:** Any write-active shard

**Problem:** CONFIRMED against source. `reconcile_superseded/1` (`lib/fathom/shard.ex:1625-1639`)
disambiguates a data-PUT 412 by re-reading the lock: still ours ⇒ `{:reconciled, etag}`. The handler
at `:1024-1037` then sets `flushed_through: state.flush_pending` — **marking the shard clean** —
which is only sound if the object holds *this* attempt's bytes. It need not:

1. `t0` — flush A, `flush_pending = W_A`. PUT `If-Match: E0` lands server-side, the response is lost
   (`Mint.TransportError{reason: :closed}` — documented as real on this path at
   `storage/s3.ex:108-118`, and `s3.ex:1943-1946` confirms the flush PUT is retried by nobody).
   Shard stays dirty, `state.etag` stays `E0`.
2. The tenant commits more writes; count rises to `W_B`.
3. `t1` — flush B PUTs `If-Match: E0`; object is at `E1` ⇒ 412; `check_lease` ⇒ `:ok` ⇒
   `{:reconciled, E1}`.
4. Handler sets `flushed_through = W_B`. Shard reads **clean**; the object holds only `W_A`.
5. At idle, `flush_and_drop` → `drop_clean` → `drop_local`. `W_A..W_B` gone.

The `flush_then_drop` variant (`:1509-1518`) is worse: it drops *immediately* on the terminate path,
and #3 makes reaching it deterministic on a rolling deploy.

**Impact:** Silent loss of acknowledged writes on a healthy shard with no competing owner — outside
the advertised RPO contract, which bounds loss to the flush interval on *node death*, not on an idle
drop or a deploy. Undetectable after the fact: the watermark says clean, `FlushWatermark` says
clean, and `Directory.Recorder.record_flush/1` is called (`:1036`), so `loss-report` reports the
tenant as safe.

**Recommended Fix:** A 412 is proof of nothing about content.
- Preferred: on `{:reconciled, etag}` **resync `state.etag` only** and leave `flushed_through`
  untouched (`shard.ex:1027-1032`). The shard stays dirty and the next interval re-flushes with the
  correct fence etag — one extra PUT, zero loss. Same for `flush_then_drop` (`:1509-1518`): resync
  and re-attempt the upload rather than `drop_local`.
- Or verify content: the object already carries `x-amz-meta-fathom-md5` (`s3.ex:74`); compare it to
  the md5 of the snapshot just PUT. Equal ⇒ genuinely our landed PUT ⇒ advance.
- Regression test: fake backend that applies a PUT then returns a transport error; assert
  `dirty?/1` stays true and `drop_clean` never runs.

### #5. The durability snapshot checkpoints and closes the live WAL at `synchronous=OFF` — power-loss corruption of the live shard
**Severity:** High | **Category:** Data Correctness (silent corruption) | **Panels:** Storage (#1)
**Likelihood:** Medium (needs a power cut / hard reset in the window; the window recurs every 5 s per dirty shard) | **Blast Radius:** One tenant per event, unrecoverable

**Problem:** CONFIRMED against source. `snapshot/2` (`lib/fathom/shard.ex:2224-2268`) opens a
connection to the **live** shard, sets `PRAGMA synchronous=OFF` (`:2240`, review #11 — to avoid
fsyncing the throwaway VACUUM temp), runs `VACUUM INTO` (`:2242`), then — added later by review #4 —
runs `PRAGMA wal_checkpoint(PASSIVE)` (`:2258-2259`) and `Connection.close(conn)` (`:2261`) **on
that same connection with `synchronous=OFF` still in effect**. The function's own comment at
`:2238-2239` states the rule it then violates: *"Emphatically NOT for `checkpoint/1`: a checkpoint at
synchronous=OFF can corrupt the main database on power loss."*

`synchronous` is a pager/connection property; SQLite derives checkpoint sync flags from it
(`pPager->walSyncFlags`), so at OFF a checkpoint neither fsyncs the WAL before backfill nor fsyncs
the main database after. Two checkpoints run here: the explicit PASSIVE, and SQLite's **close-time**
checkpoint, which on the last connection to a WAL database also **unlinks `-wal`/`-shm`**. This is
frequently the last connection: the periodic flush fires on a dirty shard, which is routinely a
shard with zero checked-out connections (`schedule_flush/1` keeps the timer armed while `unflushed?`,
`:2406-2408`). Main-database pages written without fsync, followed by deletion of the only recovery
source ⇒ a torn main database with no WAL.

**Impact:** Silent corruption of a tenant's live database on host power loss / hard reset — then
`quick_check`-ed (on the drop path only, see #14) and uploaded as the durable object. It also
quietly weakens `docs/durability.md`'s headline ("a process crash loses nothing —
`synchronous=FULL`"): the live shard is periodically checkpointed at OFF.

**Recommended Fix:** Scope the relaxation strictly to the `VACUUM INTO`:

```elixir
Connection.exec(conn, "PRAGMA synchronous=OFF")
result = Connection.query(conn, "VACUUM INTO '#{...}'", [])
Connection.exec(conn, "PRAGMA synchronous=FULL")   # BEFORE any checkpoint or close
if match?({:ok, _}, result), do: Connection.query(conn, "PRAGMA wal_checkpoint(PASSIVE)", [])
Connection.close(conn)
```

Equivalently, run the PASSIVE checkpoint on a separate `Connection.open/1` (FULL by default). Add a
`Connection.pragma/2` read helper and a regression test asserting `PRAGMA synchronous` reads back
non-zero at the moment the checkpoint runs.

### #6. Two prod boot guards read `:hrana_server` with a default of `false` while the listener defaults to `true`, and nothing in prod config sets it — so both are silently inert
**Severity:** High | **Category:** Security | **Panels:** Security (#4)
**Likelihood:** High — this is the default state of a single-node prod release | **Blast Radius:** Every tenant on the node

**Problem:** CONFIRMED by grep. `lib/fathom/application.ex:162` (`check_shard_base_domain!`) and
`:217` (`check_hrana_exposure!`) both read `Application.get_env(:fathom, :hrana_server, false)`,
while `hrana_listeners/0` at `:483` reads the same key with default **`true`**. No config file sets
it except `config/test.exs:36` (to `false`). So in a prod release with no `LB_BACKENDS`,
`exposed?` is `false` ⇒ the guard passes ⇒ the node boots serving Hrana with `:shard_base_domain`
unset — which makes `zone_matches?/1` (`shard_executor.ex:739-741`) return `true` unconditionally,
so the first label of any attacker-controlled `Host` selects any shard. That is precisely the
release blocker the guard was written for (expert review 2026-07-14 #6).
`check_hrana_exposure!`'s unauthenticated-wildcard-bind warning is inert for the same reason.

The existing test (`test/fathom/shard_executor_test.exs:615-666`) sets `:hrana_server` explicitly to
`true` and `false` and asserts both — it never exercises the **unset** state, which is the only
state a real prod release is in.

**Impact:** The single most likely prod topology — one node, no `LB_BACKENDS` — boots with
unanchored Host-subdomain routing, no boot failure, and no warning. With the shipped
`:hrana_auth :disabled` default, any client that reaches the port picks its tenant by `Host:`.

**Recommended Fix:** Make the default consistent — use `get_env(:fathom, :hrana_server, true)` at
`application.ex:162` and `:217`, or set `config :fathom, :hrana_server, true` in
`config/config.exs` so all three readers agree. Extract a single `Fathom.Application.hrana_enabled?/0`
so the default can never drift again. Add a test that **deletes** `:hrana_server` and asserts
`check_shard_base_domain!` still raises.

### #7. The `:ro` read-only token scope is bypassable by four trivial statement shapes; the same classifier gates `:block_tenant_ddl`
**Severity:** High | **Category:** Security | **Panels:** Security (#3), Gaps (#1, partially — the `:ro`→`ATTACH` path)
**Likelihood:** Certain (a `/* */` prefix) | **Blast Radius:** Any tenant whose `ro` credential leaks or is misused

**Problem:** CONFIRMED against source. `do_execute/2` computes `write? = dml?(sql) or ddl?(sql)`
(`lib/fathom/shard_executor.ex:94-96`) and both gates ride it — the `:ro` refusal at `:102-104` and
`block_ddl?` at `:129`. Both classifiers are
`String.trim_leading |> String.slice(0, N) |> String.downcase |> starts_with?` (`:808-813`,
`:823-828`). `trim_leading` removes whitespace, **not SQL comments**, and the prefix set has no entry
for CTE-prefixed DML, pragma assignment, `VACUUM`, or `ATTACH`. Verified against the exact logic:

```
write?=false   "/* c */ INSERT INTO t VALUES (1)"
write?=false   "-- c\nINSERT INTO t VALUES (1)"
write?=false   "WITH x AS (SELECT 1) INSERT INTO t SELECT * FROM x"
write?=false   "WITH x AS (SELECT 1) DELETE FROM t"
write?=false   "PRAGMA user_version = 99"
write?=false   "VACUUM" / "ATTACH DATABASE '/x/other.db' AS o"
write?=false   "/* c */ CREATE TABLE t(a)"
```

The comment at `:804-807` acknowledges the CTE miss but reasons only about *durability*
classification (where `changes > 0` catches it). Nothing catches it for **authorization**.

**Impact:** An export/analytics/BI `ro` credential — the whole point of review #24 — can INSERT,
UPDATE, DELETE and DDL a tenant by prefixing a comment or a CTE. `:block_tenant_ddl` (the guard that
stops a direct `manage.py migrate` from quarantining a tenant) is defeated by `/* */` before
`CREATE`. `PRAGMA user_version = N` lets a read-only credential rewrite fathom's own O(1)
schema-version gate.

**Recommended Fix:** Stop enforcing authorization with a leading-keyword heuristic.
1. For a `ro` stream, open the SQLite handle read-only — thread the scope from
   `ShardExecutor.open/2` into `Connection.open/2` and call `Sqlite3.open(path, mode: :readonly)`.
   The scope is already on the handle, so it is a small change. Verified: `ro INSERT`,
   `ro /* c */ INSERT`, `ro WITH … INSERT`, `ro PRAGMA user_version = 7` all →
   `{:error, "attempt to write a readonly database"}`; `ro SELECT 1` → `:ok`.
2. For `:block_tenant_ddl`, strip leading SQL comments before classifying, **or** drive it off
   `Sqlite3.set_authorizer/2`'s keyword-free DDL action atoms (`:create_table`, `:alter_table`,
   `:drop_table`, …).
3. Note `VACUUM INTO` survives a read-only handle (verified `:ok`) — it needs its own gate, see #8.

### #8. Tenant SQL disarms every protective PRAGMA, and `VACUUM INTO '<path>'` is an unguarded arbitrary-file-write primitive available even to `:ro` tokens
**Severity:** High | **Category:** Data Loss / Security | **Panels:** Security (#6, #8), Gaps (#2) — all verified by probe
**Likelihood:** High | **Blast Radius:** The tenant's own durability contract; the node's disk for every co-resident tenant

**Problem:** The connection-open pragmas are fathom's stated safety mechanisms and every one is
per-connection and re-settable by the tenant: `synchronous=FULL` (`connection.ex:30`),
`wal_autocheckpoint` (`:51`), `cache_size` (`:98-103`), `max_page_count` (`:129-134`).
`@control_prefixes` includes `pragma` (`shard_executor.ex:310`), and `control_statement?/1` (`:334`)
waves every pragma except the three in `@durable_pragmas` (`:321`) through as clean/control.
`vacuum` appears in no classifier list at all. Verified:

```
PRAGMA max_page_count=999999999 -> [999999999]   # the size cap defeated
PRAGMA synchronous=OFF          -> [0]           # per-commit durability off
PRAGMA journal_mode=DELETE      -> ["delete"]    # DURABLE, whole-database
VACUUM INTO '/tmp/probe.db'     -> {:ok, …}      # file created on disk
```

`journal_mode` is the sharpest: it is a **durable, database-level** change classified as control, so
`wrote? = false` and the shard is left CLEAN — an idle `drop_clean` then discards the local copy
without flushing. It also breaks the concurrency model the data path assumes and the coordinator's
WAL checkpoint path. `max_page_count` is one statement away from re-entering the permanently
un-flushable state `connection.ex:110-128` documents at length as having "no operator remedy".
`VACUUM INTO` gives a tenant — including a `ro` token — a full database dump to any path the BEAM
user can write, which is both a disk-exhaustion lever against every co-resident tenant and the
second route into finding #2's file-planting attack.

**Recommended Fix:** One new branch in `do_execute/2`'s `cond` (`shard_executor.ex:91-142`),
sharing the comment-stripping from #7:
1. Reject pragma **assignments** outside an explicit allow-list. Allow `foreign_keys`,
   `busy_timeout`, `cache_size`, `temp_store` (Django sets some of these); refuse `journal_mode`,
   `synchronous`, `max_page_count`, `wal_autocheckpoint`, `locking_mode`, `writable_schema`,
   `temp_store_directory`, and the `@durable_pragmas` set with a distinct error code. Read forms
   (`PRAGMA synchronous`) stay allowed.
2. Refuse any statement whose first token (after comment stripping) is `vacuum`. Fathom's own
   `VACUUM INTO` (`shard.ex:2242`) runs on a `Connection` directly, not through `ShardExecutor`, so
   it is unaffected.

### #9. `flush_then_drop` discards the fence-refreshed lease, so the lock is never released — a shard can be permanently stranded
**Severity:** High | **Category:** Reliability | **Panels:** Distributed Systems (#3)
**Likelihood:** Medium (requires legacy mode — reachable from any `Heartbeat` restart, see #29) | **Blast Radius:** One tenant fully offline, indefinitely; the rebalancer handoff path

**Problem:** CONFIRMED against source. `release_lease/2`'s fast path is
`DELETE … If-Match: lease.lock_etag`, where `lock_etag` is the etag of the lock **we** last wrote
(`storage/s3.ex:1615-1622`, review 2026-07-23 #6). Every other site threads the refreshed lease back
(`shard.ex:997`, `:1193`, `:1212`). `flush_then_drop` does not:

```elixir
# lib/fathom/shard.ex:1482-1483
case Fence.check(fence_ctx(state)) do
  {:ok, _updates} ->            # the refreshed lease (new lock_etag) is thrown away
    ...
    Storage.release_lease(state.id, state.lease)   # stale lock_etag — :1502, :1517, :1529
```

In **legacy mode** (`acquire_gen == nil`, `fence.ex:48`/`:96`) `Fence.check` performs a `renew_lease`
PUT which rotates the lock's etag, so the conditional DELETE `If-Match`es an etag that no longer
exists ⇒ 412 ⇒ `release_lease` returns `:ok` (`s3.ex:1618`) and **the lock object survives the
drop**. The leaked lock names `node()#<boot nonce>`; while this node's `Heartbeat` is running,
`owner_live?` (`s3.ex:1483-1493`) reports `:live` forever, so every peer gets `{:error, {:held, us}}`.

**Impact:** The shard is unopenable by any survivor for as long as the (healthy) former owner keeps
beating — the failover path is dead for that shard and waiting does not fix it. The rebalancer
handoff breaks the same way: `HandoffJob`'s step-3 drain (`handoff_job.ex:132-146` →
`command_poller.ex:263` → `Shards.drain/2` → terminate → `flush_then_drop`) leaves the lock behind,
so the target the LB was already flipped to gets `{:held, source}` forever — a 10 s
`handoff_held_retry_budget_ms` stall, then hard 503s.

**Recommended Fix:** `case Fence.check(fence_ctx(state)) do {:ok, updates} -> state = Map.merge(state, updates); …`
and use the merged `state.lease` at all three release sites (`shard.ex:1502`, `:1517`, `:1529`).
Belt-and-braces: on a 412 from the fast-path conditional DELETE, fall through to the legacy
read-then-conditional-delete (`s3.ex:1624`) instead of reporting `:ok` — a 412 there means "the lock
is not the one I wrote", exactly the case that needs a re-read. Test: drain a dirty legacy-mode
coordinator, assert `Storage.lease_holder/1 == :free`.

### #10. `restore_lock/3` rolls the fencing epoch **backward** and re-validates a dead owner's `check_lease`
**Severity:** High | **Category:** Data Correctness | **Panels:** Distributed Systems (#4)
**Likelihood:** Low-Medium (a failed `touch_object` after a landed lock PUT) | **Blast Radius:** Split-brain on one shard; the fleet-wide ordering invariant

**Problem:** CONFIRMED against source. When a steal's lock PUT succeeds (`{owner: us, epoch: N+1}`
durably written) but the subsequent `touch_object/1` fails, the code writes the **previous, dead
owner's exact lock content back** (`lib/fathom/shard/storage/s3.ex:1437-1444`):

```elixir
restore_lock(shard_id, stolen, %{owner: other, epoch: epoch, expires_at_ms: lock_exp})
```

`epoch` is documented throughout as the monotonic fencing token (`storage.ex:30-32`,
`docs/single-writer.md`), and this makes it go `N → N+1 → N`. Two consequences: (a) the zombie holds
`lease = {other, N}`, so its `check_lease/2` (`s3.ex:1644-1651`, matching owner **and** epoch)
returns `:ok` again — and combined with **#4** its next flush 412s, re-checks the lock, gets `:ok`,
and declares its unflushed writes durable while continuing to serve as owner; (b) `touch_object` can
return `{:error, _}` *after* the rotation copy landed, whenever `resolved_post/3` falls through to
`confirm_rotation/2` (`s3.ex:423`) and that HEAD errors transiently — so the data object's etag has
rotated (fencing the zombie's `If-Match`) while the lock says the zombie still owns it. Any observer
that read the lock between the two writes saw `N+1`.

**Impact:** The one invariant the design rests on — epoch is monotonic, a remapped shard's flush is
rejected — is violated on this path, and a clean crash-steal is converted into a case where the
zombie believes it is still the owner.

**Recommended Fix:** Never write a *lower* epoch. The rollback's stated goal (round-2 #20 — don't let
our own next checkout silently RECLAIM an unfenced takeover) is achieved more safely by **deleting**
the lock conditionally on our own write (`DELETE If-Match: stolen.lock_etag`): the next acquire is a
fresh conditional create and the zombie's `check_lease` correctly returns `:not_found ⇒ :superseded`.
If a rollback is genuinely wanted, write `epoch + 2`. Separately, have `touch_object` distinguish
"copy definitely did not land" from "copy landed, confirmation unreadable" and only roll back in the
first case. Test: a failed `touch_object` after the lock PUT landed.

### #12. A present-but-stale heartbeat makes a healthy, lock-renewing node's whole shard set stealable
**Severity:** High | **Category:** Data Loss | **Panels:** Distributed Systems (#8)
**Likelihood:** Medium (a `Heartbeat` process down past `ttl + steal_margin`, or a `heartbeat_server: false` config migration) | **Blast Radius:** Every shard in one node's keyspace slice, simultaneously

**Problem:** `owner_live?/3` is asymmetric. **No heartbeat object** ⇒ fall back to the lock's own TTL
(`lib/fathom/shard/storage/s3.ex:1508-1513`) — correct for a legacy-mode owner renewing its per-shard
lock. **Heartbeat object present but expired past the margin** ⇒ `:dead`, unconditionally
(`s3.ex:1483-1493`); the lock's TTL is never consulted even if the owner renewed it two seconds ago.
Meanwhile the design *intentionally* leaves a stale heartbeat object behind when the `Heartbeat`
GenServer dies abnormally (`heartbeat.ex:307-314`: "the stale-but-present object still fences
stealers") and coordinators degrade to the legacy per-shard renew fence (`fence.ex:55` → `:96`).
The comment has it backwards: a stale-but-present object is *worse* than an absent one, because
absence is the only case that falls back to the still-being-renewed lock TTL.

**Impact:** A single-process failure (or a config migration) on an otherwise-healthy, serving node
triggers a fleet-wide steal of that node's shards, with per-shard loss up to a flush interval and
`.fenced.<ts>` quarantine files, while the node keeps serving. The closest thing in the codebase to
an unforced split-brain trigger.

**Recommended Fix:** Make the expired-heartbeat branch fall through to the same lock-TTL check the
`:not_found` branch uses — an owner is dead only when **both** its heartbeat and its lock TTL have
lapsed past the margin. Strictly safer, and free (the lock was already read). Also have
`Heartbeat.init/1` refuse to start (or loudly clear) when `heartbeat_server` is off but this owner's
heartbeat object exists. Test: a legacy-mode coordinator renewing its lock + a stale heartbeat object
⇒ a peer's `acquire_lease` must return `{:held, _}`, not steal.

### #13. The write circuit-breaker arms ~⅔·TTL after the shard is already stealable
**Severity:** High | **Category:** Data Loss | **Panels:** Distributed Systems (#2)
**Likelihood:** High whenever the breaker is relevant (a one-sided storage partition; on by default in prod) | **Blast Radius:** Every write ACKed in a 20 s window, per affected shard

**Problem:** CONFIRMED by arithmetic against source. `note_not_valid/1` (`lib/fathom/shard.ex:2078-2099`)
starts `not_valid_since` at the **first `:fence_skip`**, i.e. when `Heartbeat.valid_for_write?/1`
returns `:not_valid` — which happens at `now + margin_ms >= mono_deadline_ms` with
`margin_ms: max(div(ttl, 3), 1)` (`heartbeat.ex:199`, confirmed), so at `last_renew + ⅔·ttl`. It
then waits `stealable_after_ms = state.ttl_ms + Storage.steal_margin_ms()` (`shard.ex:2110`,
confirmed) *from that point*. A peer may steal at `last_renew + ttl + steal_margin`. At defaults
(ttl 30 s, margin 5 s):

| event | time since last successful renew |
|---|---|
| coordinator stops flushing (`:not_valid`) | 20 s |
| **a peer may legitimately steal + touch** | **35 s** |
| write-fence actually publishes | 20 + 35 = **55 s** |

≈ **20 s (⅔·ttl) of continued write ACKs after another node may already own the shard**, plus a flush
interval of granularity on each end. Secondary: `:fence_skip` is also produced by `Fence.check`'s
revalidate transient-error branch (`fence.ex:92`) and the legacy `renew_lease` error branch (`:100`),
so the clock can start for a reason unrelated to heartbeat staleness.

**Impact:** `docs/single-writer.md`'s claimed RPO for a one-sided storage partition
(`~ttl + steal_margin`) is not met; the real number is `⅔·ttl` larger and every one of those acked
writes is quarantined on partition-heal.

**Recommended Fix:** Derive the threshold from the heartbeat's own state: publish `mono_deadline_ms`
(already in the `Heartbeat.Status` ETS row, `heartbeat.ex:117`/`:132`) and fence when
`now >= deadline + steal_margin_ms`. If the "time since first `:not_valid`" shape is kept, the
correct constant at `shard.ex:2110` is `Heartbeat.margin_ms() + Storage.steal_margin_ms()`
(= ttl/3 + steal_margin, 15 s at defaults), not `ttl + steal_margin`. Add a unit test asserting the
fence trips **strictly before** `last_renew + ttl + steal_margin`.

**Severity:** Medium | **Category:** Data Correctness | **Panels:** Storage (#5)
**Likelihood:** Low per-shard, but the exposure is every periodic flush of every write-active shard | **Blast Radius:** Overwrites the last good stored object for one tenant

**Problem:** CONFIRMED against source. Review 2026-07-14 #4 added a `PRAGMA quick_check` gate so a

### #16. `FlushGate` ships unbounded, the terminate path never consults it at all, and flush PUTs share the tenant-facing Finch pool
**Severity:** High | **Category:** Data Loss / Reliability (cascading) | **Panels:** OTP (#2), Performance (#7)
**Likelihood:** High on any rolling deploy or failover at density | **Blast Radius:** Node-wide; the survivor of a failover

**Problem:** Two halves of one knob.
- **The gate is off.** `FlushGate.cap/0` is `Application.get_env(:fathom, :shard_flush_max_concurrency)`
  with **no default — nil ⇒ unbounded** (`lib/fathom/shard/flush_gate.ex:19`, `:31-32`, confirmed).
  Its own moduledoc names the cascade it was written for: after a failover re-homes a burst of
  shards their flush timers phase-align, "competing with cold-open pulls for the same pool on
  exactly the survivor that's absorbing traffic". The only active mitigation is ±25% timer jitter
  (`shard.ex:77`), which decorrelates phase but not sustained rate. At the measured density and the
  default 5 s interval that is ~2,000 full-object PUTs/s per node at 10k write-active shards through
  one 200-connection pool (`storage/s3.ex:102-124`, `pool_size` 200 × `pool_count` 1) that also
  carries cold-open pulls, lease/heartbeat ops, and warm-follower revalidation, with no priority
  separation.
- **The terminate path never acquires a slot.** `FlushGate.try_acquire/0` is consulted **only** in
  `handle_info(:durability_flush, …)` (`shard.ex:1273`). `DynamicSupervisor` terminates all children
  simultaneously with one wall-clock timer per `:shutdown` value (verified empirically: 5 children ×
  1 s `terminate` completed at ~1002 ms total, not 5 s), so on SIGTERM every open coordinator
  synchronously runs `checkpoint_and_verify/1` or `snapshot_and_upload/1` at once, saturating both
  the `+SDio 10` dirty-IO pool and the Finch pool. Whatever has not finished at
  `@default_shutdown_ms 60_000` (`shard.ex:96-105`) is `:kill`ed mid-flush.
  `Fathom.Shards.drain_all/1` bounds this correctly (`shards.ex:444-462`, `max_concurrency` default
  16) but it is an **opt-in release pre-stop rpc**; a bare SIGTERM (`docker stop`, crash-adjacent
  restart, a `DataPlane.Supervisor` restart per #22) takes the unbounded path.

**Impact:** Lost acknowledged writes on rolling deploys and scale-downs at density — and because the
shutdown timer is shared by the group, the loss is not random: it is systematically the shards the
Finch pool served last. On the failover path the flush storm lengthens the RTO of the very failover
that caused it.

**Recommended Fix:**
1. Ship `:shard_flush_max_concurrency` with a non-nil default derived from the pool
   (e.g. `min(dirty_io_schedulers, div(pool_size, 4))`) — the backoff path is already built and
   safe-by-construction (the shard stays dirty).
2. Route the terminate-path flush through `FlushGate` with a **blocking** acquire bounded by the
   remaining shutdown budget, so concurrency is capped and the queue is FIFO.
3. Invoke `Fathom.Shards.drain_all/0` from `Fathom.Application.prep_stop/1` so the bounded path runs
   without the pre-stop hook; document the rpc as the earlier LB-deregistration step.
4. Give flush/upload traffic its **own** Finch pool so bulk background writes cannot consume the
   request path's connection budget.
5. Guard test: terminating K coordinators issues at most `cap` concurrent `Storage.flush` calls.

### #17. Pinned-shard failover scatters one shard across every survivor (round-robin backups, no hash)
**Severity:** High | **Category:** Reliability | **Panels:** Distributed Systems (#5)
**Likelihood:** Certain whenever a pinned node is down | **Blast Radius:** The fleet's hottest tenants — the only ones the rebalancer pins

**Problem:** CONFIRMED against source. `LbMap.render/3` emits (`lib/fathom/rebalancer/lb_map.ex:77-88`,
the string at `:87`):

```
upstream fathom_pin_X {
    server X max_fails=2 fail_timeout=10s;
    server Y backup;
    server Z backup;
    keepalive 512; ...
}
```

There is **no `hash $host consistent`** — the main pool has one (`deploy/lb/fathom.nginx.conf:61-62`),
this one does not, so nginx load-balances it **round-robin**. When X is marked down, requests for a
*single* pinned host alternate between Y and Z; both cold-open the shard, one wins `acquire_lease`,
the other gets `{:error, {:held, winner}}` → the winner's heartbeat is fresh → `holder_stealable_soon?/2`

request while X is down.

**Impact:** With a 3-node fleet, roughly **half** of a pinned shard's requests fail for the entire
duration of the pinned node's outage, and the two survivors thrash the lease/pull path against each
other. The `LbMap` moduledoc's claim that backups make a dead pin "self-heal exactly as a non-pinned
shard would re-hash on death" does not hold — the non-pinned path has a consistent hash.

**Recommended Fix:** Make the pin upstream deterministic per host. `hash $host consistent;` plus
`backup` is rejected by nginx < 1.27.3, so: (a) require nginx ≥ 1.27.3 and emit the hash directive in
the pin upstream; or (b) drop `backup` and render **one** deterministic fallback per pin (the shard's
ketama successor); or (c) drop the pin upstream on dead-node detection and fall back to
`default fathom_hrana` — `RebalanceJob.reconcile_dead_pins/1` already does this, so the fix may be as
small as shortening `@node_stale_ms` and removing the backups. Add a `LbMap.render/3` test asserting
a single deterministic target per pinned host regardless of which backends are alive.

### #26. The migration engine cannot roll out a data migration or an `atomic = False` migration; both freeze the fleet HEAD with no execution path
**Severity:** High | **Category:** Architecture | **Panels:** Gaps (#6)
**Likelihood:** Certain in month one (`AddField` + `RunPython` is the most common two-step Django migration) | **Blast Radius:** Fleet convergence stops entirely

**Problem:** The engine's model is "record the SQL Django sent to the template, replay it verbatim on
every tenant" (`migrator/copy.ex:86-94`, `replay_each/2` — verbatim replay is the only transform).
- **`RunPython` data migrations.** A backfill's ORM writes cross the wire as literal
  `INSERT`/`UPDATE`/`DELETE` carrying the *template's* row values. `data_migration_statements/1`
  detects this and sets `requires_review` (`capture.ex:475`, `alarm_on_data_migration/2` at
  `:337-356`), capping HEAD below the version. The operator's only options are: approve it (replaying
  template row values onto every tenant — the corruption the flag exists to prevent) or never
  advance. **There is no third path** — `Copy.migrate/4` takes only `[String.t()]`, so there is no
  seam for a per-tenant transform.
- **`atomic = False` migrations.** These run autocommit outside any tracked `BEGIN…COMMIT`, so
  `Capture` never sees them; the gap is detected only at the *next* capture (`migration_gap/1`,
  `alarm_gap/2` at `:377-399`), by which point the template has silently moved ahead and that next
  version is also flagged. `atomic = False` is the standard idiom for exactly the long-running
  migrations a million-shard fleet most needs to roll carefully.

**Impact:** `GET /api/migrations/status` reports `pending_review: [N]` and `converged: false` forever,
and every subsequent migration stacks behind it. Given the record that the engine was never driven by
a real `manage.py migrate` until 2026-07-30 (5 bugs found immediately), this is the same class of gap.

**Recommended Fix:** Two separable pieces, in order. (1) **Make the block legible** — surface on
`/api/migrations/status` and the admin UI *why* a version is held and what the options are. (2) **Add

module implementing `run(conn, shard_id)`, registered in the app, referenced by name from the release
row) that `Copy.migrate_chain/3` invokes in the same transaction as the replayed DDL. That is the
minimum to express "backfill per tenant" while keeping the template-literal DML path blocked; scope it
to the callback + the release column + a rollout test, and do not attempt to execute Python. For
`atomic = False`, capture cannot see it by construction — add a pre-flight check (a `manage.py`
wrapper or a documented CI gate refusing a non-atomic migration against the template) and keep the gap
detector as the backstop; document the constraint in `docs/django-migrations.md`.

### #32. `flush_now` waiters drive an unthrottled fence→VACUUM→PUT retry loop
**Severity:** Medium | **Category:** Reliability | **Panels:** OTP (#5)
**Likelihood:** Medium (a failing store during a fork/snapshot) | **Blast Radius:** Every co-tenant of the node, for up to 60 s

**Problem:** `settle_waiters(state, :flushed)` (`lib/fathom/shard.ex:2124-2132`) does a bare
`send(self(), :durability_flush)` when the shard is still dirty — no backoff, no jitter, bypassing
`schedule_flush_backoff/1`. It is reached with waiters present from three places, two of which are
*failure* paths where the shard is dirty by construction: `{:reconciled, nil}` (`:1042-1044`) and the
flush-task `:DOWN` clause (`:1078-1085`). Each iteration spawns a task doing `Fence.check` (a lock
GET, or in legacy mode a renew PUT), a whole-file `VACUUM INTO`, a full-object PUT, and on 412 a
`check_lease` GET plus an `object_etag` HEAD — then returns to `settle_waiters`, still dirty, and
sends again immediately. The loop runs until the shard goes clean or `@flush_now_timeout` (60 s,
`:83`) expires. A crash-looping flush task is the sharpest version: spawn → crash → `:DOWN` →
immediate respawn. Separately, `:fence_skip` (`:1069-1073`) does **not** call `settle_waiters` at all,
so a `flush_now` caller blocks the full 60 s during a storage partition instead of getting a
retryable error.

**Recommended Fix:** Replace the bare `send/2` at `:2126` with `schedule_flush_backoff/1` (250 ms
jittered). Track consecutive re-kicks and fail waiters with `{:error, :flush_not_converging}` past a
small threshold. Settle waiters with `{:error, :ownership_unconfirmed}` on `:fence_skip`.

### #34. `Shards.evict/2` / `drain/2` leak `{:drain_aborted, pid}` into the long-lived caller's mailbox on the timeout branch

### #38. `Directory.Recorder`'s shutdown flush has the default 5 s budget and runs after the whole data plane's flush burst
**Severity:** Medium | **Category:** Data Loss (observability) / Reliability | **Panels:** OTP (#8)
**Likelihood:** High at density on every deploy | **Blast Radius:** Post-incident loss reports are wrong in the misleading direction

**Problem:** `Fathom.Directory.Recorder` is listed bare in `control_plane_children/0`
(`lib/fathom/application.ex:265`), so `use GenServer`'s default `shutdown: 5_000` applies. Its
`terminate/2` (`directory/recorder.ex:134-138`) calls `do_flush/0`, which drains **both** buffers in
2000-row chunks (`:161`) and batch-upserts each to Postgres. Shutdown order makes this the worst
moment: top-level children stop Edge → **DataPlane** → ControlPlane → Infra, so every coordinator's
terminate-flush (#16) runs first and each successful upload calls `record_flush/1` (`shard.ex:1015`,
`:1036`, `:1500`). The `@flush_table` therefore holds a `last_flushed_at` row for every shard the node
just flushed, and the final `terminate/2` is the only chance to persist them before the process is
`:kill`ed at 5 s. At 10k–30k shards that is 5–15 chunks of 2000 upserts inside 5 s, immediately after
the node has been hammering S3.

**Impact:** `Directory.flush_lag_report/1` and `mix fathom.shard loss-report` (the review-#28 artifact
that is supposed to survive the node) systematically **under-report** the flush time for the shards
flushed last — a shard reads as flushed longer ago than it was, the misleading direction for an
operator assessing post-incident loss. The `last_active_at` half of the same buffer feeds the revert
write-age force-guard. Silent: a truncated shutdown flush logs nothing.

**Recommended Fix:** (1) Give the Recorder an explicit `shutdown:` sized like the coordinator budget
(`Supervisor.child_spec(Fathom.Directory.Recorder, shutdown: 30_000)`) — a control-plane process
holding node-wide durability metadata should outlive the data plane's flush burst. (2) Make
`terminate/2` deadline-aware: loop `flush_chunks` against a monotonic deadline and `Logger.error` the
undrained count when it gives up. (3) Flush `@flush_table` opportunistically on a size threshold, not
only on the 1 s timer.

### #39. `init_flushed_through/2` silently seeds a warm shard as *clean* if the `WriteCounter` table is momentarily absent

### #40. The heartbeat memo's safety condition is documented but never enforced
**Severity:** Medium | **Category:** Reliability | **Panels:** Distributed Systems (#9)
**Likelihood:** Low (requires an operator tuning `steal_margin_ms` down) | **Blast Radius:** ~1 s of extra wrongful-steal exposure per shard

**Problem:** `Fathom.Shard.Storage.HeartbeatCache` memoizes the *entire* heartbeat read — including
the `s3_now` clock sample — for a hardcoded 1000 ms (`storage/s3.ex:1685-1702`, `@hb_cache_ttl_ms`),
and its moduledoc (`storage/heartbeat_cache.ex:11-14`) states the safety condition as "the cache TTL
must stay well inside `Storage.steal_margin_ms/0` (default 5000 ms)". Nothing enforces or checks it;

recovers within the memo window can still be stolen from on the cached `:dead`.

assertion next to `check_storage_fence!/0` (`application.ex:127`) that
`steal_margin_ms > hb_cache_ttl_ms`. Cheaper still: cache only the *raw read* and re-stamp `ref_now`
with a fresh local clock on a hit, so a stale entry can only ever produce a more conservative
(`:live`) verdict.

**Likelihood:** Certain at the served-density ceiling | **Blast Radius:** ~2,000 no-op wakeups/s per node and the loss of heap reclamation for every served coordinator

**Problem:** Review 2026-07-24 #10 stopped the idle no-op tick with a precise argument: at 30k
coordinators the unconditional re-arm was "~6,000 wakeups/s of pure no-op … and — the bigger cost — it
made `hibernate_after` **unusable at any value**". That argument applies verbatim to a shard that is
**busy but clean** (a held stream doing only reads), and the fix does not cover it:
`schedule_flush/1`'s disarm applies only when `map_size(conns) == 0`
(`lib/fathom/shard.ex:2406-2410`), and the timer is re-armed on grant (`:894`). Each wakeup is a
no-op, and there are `held_shards / flush_interval` per second — ~2,000/s at the measured
10k-served-shards ceiling — with every one of those coordinators pinned out of `hibernate_after`
(`:142-149`) and its heap resident. This is a design cost, not a bug (the coordinator has no other way
to learn a stream wrote), but it scales on the served-density axis and is unmeasured (see #41.2).

**Recommended Fix:** Invert the signal — have the *writer* tell the coordinator once per clean→dirty
transition instead of polling. `Fathom.ShardExecutor` already tracks per-connection write state in the
process dictionary (`@txn_wrote_key`, `shard_executor.ex:367-391`), so a single `GenServer.cast` on
the **first** write of a checkout is at most one message per stream — strictly fewer than today for
read-heavy traffic, identical for write-heavy — and lets a clean served shard disarm its timer and
hibernate exactly as an idle one does.

### #43. Fleet rollout is throttled to 100 shards/hour by default with no rate metric and no ETA
**Severity:** Medium | **Category:** Reliability | **Panels:** Gaps (#9)
**Likelihood:** Certain on any large rollout | **Blast Radius:** The headline capability has no capacity-planning story

**Problem:** `ReconcileJob`'s `@default_batch_size 100` on an hourly cron

### #44. Uploads hash one pass and stream another; `Local.flush/3` returns the etag of the *source* file, not the object it wrote
**Severity:** Low | **Category:** Data Correctness / Test Gap | **Panels:** Storage (#9)
**Likelihood:** Low (the Edge plane is terminated before the DataPlane on the deploy path) | **Blast Radius:** A spurious flush failure, or a self-fence + quarantine on `Local`

**Problem:** Both backends read the flush source twice and treat the reads as identical. S3 computes
`content-length` and `content-md5` in one pass (`storage/s3.ex:292-313`, `stat_and_md5/1` at
`:679-695`) then streams the file again as the body (`flush/3` at `:250-279`) — if the file changed in
between, the store rejects the PUT (`BadDigest`) or the declared length disagrees.
`Local.flush/3` copies the source to the remote path and then hashes the **source**
(`storage/local.ex:53-77` — `file_etag(local_path)` at `:70`, after `atomic_copy` at `:69`), so the
coordinator caches a fence etag that may not describe the stored object. The window is real only where
the flush source is the **live** database rather than a VACUUM temp — `upload_for_drop/1`
(`shard.ex:1654`) — and on the rolling-deploy path the Edge plane is terminated before the DataPlane
(`application.ex:38-43`), which is correct and load-bearing and is what keeps this Low. It is **not**
guaranteed on the `Fathom.Shards.stop/1` force-stop path, which terminates a coordinator while its
streams are live.

**Recommended Fix:** Hash the *destination* in `Local.flush/3` (`file_etag(remote_path(shard_id))`
after the copy) — that is the object whose etag the fence compares. For S3, take the size/MD5 from an
fd opened once and stream the body from that same fd, or assert `mtime`+`size` are unchanged between
the passes and fail the flush loudly if not.

### #45. Compressed-upload temps (`<path>.z.<n>`) are outside every reaper glob
**Severity:** Low | **Category:** Reliability (unbounded disk leak) | **Panels:** Storage (#8)
**Likelihood:** Low (gated off by default) | **Blast Radius:** One shard-sized orphan per killed drop-flush, forever

**Problem:** With `:shard_object_encoding` set to `:zlib`, `with_body/2` (`storage/s3.ex:292-313`)
calls `Codec.compress_to_temp(local_path)`, which writes `"#{local_path}.z.#{unique}"`
(`storage/codec.ex:84-110`, name at `:85`). Its `after File.rm(tmp)` covers exceptions but **not** an
external kill — and the flush task is killed externally on the terminate path (`settle_flush_task/1`,
`shard.ex:2190`, `Task.shutdown/1`). For the periodic flush `local_path` is `<path>.snap.<n>`, so the
temp is matched by the `*.snap*` glob. For `upload_for_drop/1` (`shard.ex:1654`) `local_path` is the
**live db path**, so the temp is `<path>.z.<m>` — matching neither `reap_stale_temps/2`'s
`base <> ".{dl,snap,tmp,pull}*"` (`storage.ex:668-681`, glob at `:672`) nor `reap_named_temps/2`'s
fixed `.pull` family (`:697-709`), and therefore never reaped by the coordinator or `TempReaper`
(`shard/temp_reaper.ex:77`).

**Recommended Fix:** Add `z` to the suffix set (`".{dl,snap,tmp,pull,z}*"`) and add the `path <> ".z"`
family to `reap_named_temps/2`. A test asserting every temp name produced anywhere in
`lib/fathom/shard/` is matched by the reaper glob would prevent the next one.

### #46. `Connection.with_deadline/3`'s `after 0` peek leaks `{:timed_out, ref}` into the stream process
**Severity:** Low | **Category:** Reliability | **Panels:** OTP (#9)
**Likelihood:** Low (narrow window, and only when `:query_timeout_ms` is set) | **Blast Radius:** Slow mailbox growth in long-lived stream processes

**Problem:** `with_deadline/3` (`lib/fathom/shard/connection.ex:310-338`) runs
`result = try do fun.() after send(watchdog, {:done, ref}) end` and then peeks for `{:timed_out, ^ref}`
with `after 0` (`:327-332`). The watchdog's timeout branch does `Sqlite3.cancel(conn)` **then**
`send(parent, {:timed_out, ref})` (`:385-386`), so if the query completes naturally in the gap between
those two statements the owner reaches the peek first, returns `false`, and the message arrives
afterwards — never matched again (the next call uses a fresh `make_ref/0`). The watchdog is a
long-lived per-connection process and a stream holds its connection for the stream's life.

**Recommended Fix:** Have the watchdog send `{:timed_out, ref}` **before** `Sqlite3.cancel(conn)`, so
the message is guaranteed to be in the owner's mailbox before the cancel can let `fun.()` return — a
one-line reorder that closes the window structurally. Alternatively drain defensively for any
`{:timed_out, _}` on stale refs.

### #47. `Fathom.QueryConsole.run/3` interpolates an unvalidated shard id into the `Host` header; validation lives only in the caller

### #48. The restore drill verifies stored objects, never the restore *procedure*; and the AGENTS.md cross-version-tolerance gate has no test
**Severity:** Medium | **Category:** Test Gap | **Panels:** Gaps (#10)
**Likelihood:** n/a | **Blast Radius:** The operator procedure that runs under maximum pressure has never been executed against a real backend

**Problem:** Two gaps with one root cause — the tests exercise the pieces, never the procedure.
`RestoreDrillJob.verify/2` (`lib/fathom/restore_drill_job.ex:80-113`) pulls, `quick_check`s, and

reconcile are exercised against the real backend. (2) Extend `sample_for_drill/1` to rotate over
`@snap-` objects. (3) Add the missing cross-version-tolerance test: seed a shard at `vN-1`, release
