### #1. Uncommitted-transaction writes are counted before the snapshot but excluded from it, so the periodic flush advances the watermark past writes that later commit
**Severity:** High | **Category:** Data Loss | **Panels:** Storage
**Likelihood:** Medium | **Blast Radius:** Single shard/tenant — silent, permanent loss of an acknowledged, committed write

**Problem:** The dirty watermark assumes "every write counted in `WriteCounter` is already in the snapshot we're about to take." False for explicit multi-statement transactions. `ShardExecutor` bumps the counter on `wrote?/2`, which keys off `sqlite3_changes()` — an `INSERT` inside an open `BEGIN...COMMIT` reports `changes()=1` *before commit* (lib/fathom/shard_executor.ex:82,128-135). The periodic flush captures `flushed_to = WriteCounter.count(id)` (lib/fathom/shard.ex:976) then snapshots with `VACUUM INTO` on a *separate* connection (shard.ex:1409), which sees only committed data. Verified empirically (sqlite 3.54): an uncommitted `INSERT` bumps `changes()` to 1 yet is absent from a concurrent `VACUUM INTO`. On success the handler sets `flushed_through = flush_pending` (shard.ex:780). The subsequent `COMMIT` is a control statement (`control_statement?` matches `commit`) and does **not** re-bump. Net: `count == flushed_through` ⇒ `unflushed?/1` false (shard.ex:1227-1230) ⇒ shard reads **clean** while holding a committed write never uploaded. The next idle-drop (`drop_clean`, shard.ex:1089-1098) deletes the local copy without flushing; the stored S3 object is the pre-commit snapshot.

**Impact:** Silent, permanent loss of an acknowledged committed write — the worst durability class (system reports the data as durable). Django's `ATOMIC_REQUESTS`/`transaction.atomic()` are the primary client's default, so transactions straddling the 30 s flush interval are routine. Only busy shards (periodic flush active) are affected; idle-flush is safe (runs at `conns==0`, no open transactions). Manifests when the straddling transaction's commit is the last write before the shard idles and drops.

**Recommended Fix:** Re-dirty on commit: bump `WriteCounter` when the statement is a `COMMIT`/`END` (so `count` advances past `flushed_through` once the previously-counted-but-uncommitted writes become durable-worthy, forcing a re-snapshot). Alternatively, only count committed changes. **Regression test (folds in the Storage test-gap finding):** every existing periodic-flush durability test drives *autocommit* statements and never reproduces this window; the closest test (test/fathom/shard_durability_test.exs:232) bumps the counter *from inside* the flush — the opposite ordering. Add a test that drives `BEGIN; INSERT` through `ShardExecutor`, fires `:durability_flush`, then `COMMIT`s, and asserts the shard is still dirty / an idle-drop re-flushes and the row survives in storage.

### #2. Cold-open runs an O(resident-shards) directory scan on every open
**Severity:** High | **Category:** Performance | **Panels:** OTP
**Likelihood:** High (at the target density) | **Blast Radius:** Node-wide — every cold open / failover-warm for all tenants on the node, worst at the density the design is sold on

**Problem:** `handle_continue(:open)` calls `Storage.reap_stale_temps(path, 2 * @pull_timeout)` on every cold open (lib/fathom/shard.ex:215,221), whose body is `Path.wildcard(base <> ".{dl,snap,tmp,pull}*")` (lib/fathom/shard/storage.ex:441-453). Even though `base` is the single shard's path, `Path.wildcard` cannot prefix-optimize a `{…}*` pattern, so it does a full `readdir` of the flat shard data dir and regex-matches every entry. Measured: a 2000-entry dir takes 5.2 ms to match *zero* temps; scales linearly. The dir holds `.db`/`-wal`/`-shm`/`.etag` per shard, so at the densities the chaos rig pushed (30k–105k shards → 120k–400k dir entries) each cold open pays tens-to-hundreds of ms of pure readdir before it can serve. The following `:erlang.garbage_collect()` (shard.ex:221) is itself a mitigation for the O(N) *heap* garbage this scan produces (comment: "+68% fanout_kb_per_shard at 1000 open shards"); the O(N) *time* cost per open remains and grows with N.

**Impact:** Cold-open latency — the single headline hot path ("millions of small shards, cheap cold-open"), hit constantly by idle re-opens and failover warming — degrades linearly with resident shard-file count. The very density regime the architecture is sold on is where the scan is most expensive, turning a ~1-RTT cold open into a many-ms directory sweep, re-triggering on every re-open. Directly attacks the stated scaling story (per-shard open cost).

**Recommended Fix:** Don't scan the whole dir per open. Either (a) reap only this shard's *known* temp names (`path <> ".pull"`, the snapshot/dl names it created) with direct `File.rm`/`File.stat`, no glob; or (b) move stale-temp reaping to a single periodic sweeper (one dir scan every N minutes, amortized across opens); or (c) shard the data directory into subdirs so any readdir is bounded.

### #3. `Local` storage backend has no cross-node fence and no guard against fleet use
**Severity:** Medium | **Category:** Data Loss | **Panels:** Security
**Likelihood:** Low (misconfig) | **Blast Radius:** Catastrophic — silent split-brain corruption/loss of any co-served tenant's data

**Problem:** The single-writer lease on the `Local` backend serializes only within one BEAM node (`with_lock_mutex` uses `:global.trans({...}, fun, [node()])` — node-local scope, lib/fathom/shard/storage/local.ex:427-432). Correct for its documented dev/test single-node role, but nothing prevents `SHARD_STORAGE=local` in a multi-node fleet (e.g. `dir` on a shared NFS/EFS mount with `LB_BACKENDS` set). S3 gets a boot self-test (`check_storage_fence!`, lib/fathom/application.ex:120-125) that refuses to serve if the fence isn't enforced; `Local` gets no equivalent "this backend cannot fence across nodes" assertion.

**Impact:** With `Local` + shared mount + >1 node, two nodes can both acquire the "lease" for the same shard and both write — split-brain, last-write-wins, silent loss/corruption of a tenant's data. Passes every test (all Local-driven) and single-node runs; only surfaces in production under concurrency.

**Recommended Fix:** At boot, if `:shard_storage == Fathom.Shard.Storage.Local` and `:lb_backends` is non-empty (or `env == :prod`), raise — Local provides no cross-node single-writer guarantee. Document S3/R2/conditional-write-compatible stores as the only fleet-safe backend.

### #4. Revert's `retain`/`restore` clobber the live object unconditionally — the check-then-write TOCTOU the forward flush closed is left open on the revert path
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Distributed
**Likelihood:** Low-Medium (widened by #9) | **Blast Radius:** Per-shard cross-node — served-then-silently-discarded acknowledged writes, recoverable only from `<shard>@current` backup

**Problem:** The forward migration flush was deliberately made etag-conditional (`flush_fenced/3` → `Storage.flush(shard_id, path, expected_etag)`, lib/fathom/migrator/shard_migration.ex:335-341) *because* the read-only `fence/2` (a `check_lease`) "only proves the LOCK is ours at THIS instant, but the migrator can then stall... and a coordinator can steal + flush new bytes before this PUT lands" (comment, shard_migration.ex:321-330). The **revert path never got that fix**: `do_revert` (shard_migration.ex:123-134) guards with the same read-only `fence(shard_id, lease)` (line 124), then performs `Storage.retain(shard_id, current)` (line 129) and `Storage.restore(shard_id, to_version)` (line 130) — both **unconditional** `copy_object`s with no `If-Match` (lib/fathom/shard/storage/s3.ex:697-700; storage/local.ex:124-127). A steal landing in the window between the `fence/2` read and the `restore` copy is not caught: `restore` clobbers the stealer's freshly-flushed live object. `retain(current)` backs the stealer's bytes to `<shard>@current`, but `restore` makes the reverted version authoritative while the stealer keeps serving its own; the stealer's next flush 412s, `check_lease` still returns `:ok` (the migrator never touched the stealer's lock, only the data object), so the stealer concludes "our PUT landed, object durable" (shard.ex:1117-1126) and **drops its local copy**, discarding acknowledged post-steal writes.

**Impact:** Cross-node split-brain clobber on the revert path: served-then-silently-discarded writes plus a live-object/served-version mismatch, recoverable only by an operator from the `<shard>@current` backup. The exact hazard the forward-flush fix closed, still reachable on revert.

**Recommended Fix:** Make the revert's clobbering write etag-conditional like the forward flush — thread the live object's etag captured at pull time into `restore` (add a `restore/3` doing a conditional copy, or pull+`flush/3` the reverted bytes with `If-Match`). **Regression test (folds in the Distributed revert-fence test gap):** both existing fence tests drive only the forward migration (test/fathom/migrator/shard_migration_test.exs:369, :400). Add a revert-path analogue of :400 — with the migrator holding the lease, change the live object's etag (via FaultyStorage/steal hook) after `fence/2` passes but before `restore`, and assert the revert aborts with `:superseded` and the live object is unchanged (fails today, passes once `restore` is conditional).

### #5. Provenance sidecar is not established atomically with the pulled file, so a crash between rename and sidecar-write can later clobber a newer lineage
**Severity:** Medium | **Category:** Data Loss | **Panels:** Storage
**Likelihood:** Low | **Blast Radius:** Per-shard — clobbers a newer owner's committed writes on persistent-volume deployments

**Problem:** `promote_pull` makes the pulled file authoritative the instant `File.rename(temp, path)` lands (lib/fathom/shard.ex:666), but writes the `.etag` provenance sidecar only afterward (shard.ex:671). A crash in that two-line window leaves an authoritative warm file with **no** sidecar. On the next warm open, `quarantined_fork?` reads `:missing` and returns false (shard.ex:1319), and `await_pull(nil, ...)` treats a missing sidecar as a "legacy warm file from before provenance tracking" and **adopts the store's current etag** (shard.ex:618-626). If, in the interim, another node stole + wrote + released the shard (reachable on a persisted/remounted `:shard_data_dir`), the stale local file is now served and fenced with the *new* lineage's etag, so its first flush `If-Match`es successfully and overwrites the newer owner's acknowledged writes — precisely the clobber provenance exists to prevent; the gap is that provenance *establishment* isn't crash-atomic with file promotion.

**Impact:** Data loss (clobbering a newer owner's committed writes) in a narrow but reachable crash-plus-steal interleaving on persistent-volume deployments.

**Recommended Fix:** Write the sidecar *before* the rename (an orphan `<path>.etag` with no `<path>.db` is harmless — `warm?` is gated on `File.exists?(path)`, and the brand-new branch already `File.rm`s it), or fsync+rename the sidecar together with the db. Never let a promoted db exist without its provenance.

### #6. Unanchored Host-based tenant routing is the unguarded prod default
**Severity:** Medium | **Category:** Shard Isolation | **Panels:** Security
**Likelihood:** Low (two failures deep) | **Blast Radius:** Cross-tenant shard selection (release-blocker class) if the network boundary is also bypassed

**Problem:** `shard_from_host/1` promotes the first Host label to a shard id, anchored to the serving zone only when `:shard_base_domain` is set. When it is `nil`, `zone_matches?` returns `true` unconditionally (lib/fathom/shard_executor.ex:335-336) and routing is fully unanchored — any `Host:` first label selects that tenant's shard. Prod `runtime.exs` (config/runtime.exs:296-300) sets the anchor only if `SHARD_BASE_DOMAIN` is a non-blank env var, and there is **no boot guard** asserting it is set, unlike `check_template_default!`/`check_template_auth!`/`check_rebalancer_config!` which fail closed on exactly this class of prod misconfig (lib/fathom/application.ex:60-125). The anchor was added as defense-in-depth (expert review #13) but left optional and unenforced.

**Impact:** A prod deploy that forgets `SHARD_BASE_DOMAIN` runs the primary tenant-selection path trusting a fully attacker-controlled header with no domain anchoring. If the network trust boundary is ever bypassed/misconfigured (the only other control), `Host: victim.anything` reaches shard `victim` — the release-blocker-class cross-tenant selection the anchor exists to prevent, silently re-opened. (No *reachable* leak found; this is a config footgun lacking the boot-guard fail-safe applied to sibling risks.)

**Recommended Fix:** Add a prod boot guard (in `Fathom.Application.start/2`, matching the existing pattern): when `env == :prod` and either `:lb_backends` is configured or the Hrana server is enabled, require `:shard_base_domain` to be set (or require an explicit `ALLOW_UNANCHORED_ROUTING=true` acknowledgement), else refuse to boot.

### #7. Idle-eviction blocks the admission path on synchronous terminate-flushes (S3-coupled, up to ~8 min worst case)
**Severity:** Medium | **Category:** Reliability | **Panels:** OTP
**Likelihood:** Medium (under S3 slowdown, in the documented prod density config) | **Blast Radius:** New-tenant admission stalls up to ~8 min; defeats LB fast-503 backpressure

**Problem:** At capacity, admission calls `evicted_for_room?` in the checkout (stream) process, which walks up to 16 LRU-cold candidates and calls `drain(shard_id, 0)` on each (lib/fathom/shards.ex:257-275, :249 `@max_evict_probes 16`). `drain/2` is a *blocking* selective `receive` that waits for the evicted coordinator to fully exit (shards.ex:155-181) — and a stopped coordinator's `terminate` runs the whole synchronous flush (`checkpoint` + `Storage.flush` S3 PUT) with no supervisor timeout (it self-stopped `{:stop, :normal}`, so the 60 s shutdown budget doesn't apply). `reduce_while` treats a `{:error, :busy}` (the `drain_timeout + 30_000` = 30 s safety-net timeout) as `{:cont, false}` and tries the next candidate. Under slow/hung S3, each probe blocks up to the 30 s net, so a single new-tenant checkout can block `16 × 30s` ≈ 8 minutes before returning 503.

**Impact:** New-tenant admission latency is coupled to *other* tenants' flush-to-S3 latency; an S3 slowdown converts "refuse fast (503) so the LB backs off" into an 8-minute blocking hang on the Filo stream. Fires only with finite `:max_open_shards` + `:evict_idle_at_capacity` — exactly the documented prod density posture.

**Recommended Fix:** Make eviction non-blocking on the admission path: use a short bounded drain (e.g. `drain(id, 100)`) and/or cap total admission-path eviction budget so a checkout can't block more than a small fixed time before falling back to 503. Better: perform the flush-and-drop of the evicted shard asynchronously (hand it to a Task/queue) and admit immediately once the coordinator has released its lease, rather than waiting out the S3 upload inline.

### #8. Coordinator does synchronous S3 round-trips inside `handle_info`, reintroducing the mailbox blocking expert review #27 removed
**Severity:** Medium | **Category:** Performance | **Panels:** OTP
**Likelihood:** Medium (412/lapse paths under the S3 flakiness that also makes them slow) | **Blast Radius:** Hot-shard checkout/checkin p99 spikes 1-2 S3 RTTs

**Problem:** Expert review #27 moved the snapshot+upload off-process because "inline, the fence RTT + PUT blocked the coordinator's mailbox every interval." But several error/lapse paths still do blocking storage I/O *inline* in `handle_info`: on a durability-flush `{:error, :superseded}` (412), `reconcile_superseded/1` runs `Storage.check_lease` (S3 GET) then `Storage.object_etag` (S3 HEAD) synchronously in the flush-result handler (lib/fathom/shard.ex:796-800, :1163-1190); `Fence.check`'s `:revalidate` branch (reachable from `:durability_flush` and `:revalidate_lapse`) does a synchronous `Storage.check_lease` (shard.ex:968; lib/fathom/shard/fence.ex:82-94). While these run, every `:checkout`/`:checkin`/`:DOWN` for the shard queues behind the round-trips — the exact hot-shard p99 spike #27 eliminated, relocated to the 412/lapse paths.

**Impact:** On a write-active hot shard experiencing S3 retries or a heartbeat lapse, checkout/checkin latency spikes by 1-2 S3 RTTs because the coordinator mailbox is blocked mid-handler — the pathology #27 fixed for steady-state, unaddressed on error paths.

**Recommended Fix:** Move the `check_lease`/`object_etag` reconciliation off-process the same way the flush was (a monitored task whose result is applied via a message), or perform the ownership re-check before deciding to write rather than inline in the completion handler, so the coordinator mailbox never blocks on storage I/O.

### #9. Migrator lease renewer stops permanently on a single *transient* renew error, conflating it with supersession
**Severity:** Medium | **Category:** Reliability | **Panels:** Distributed
**Likelihood:** Medium (any S3 blip during a long migration) | **Blast Radius:** Spurious migration failure + widens #4's revert-clobber window (mid-migration steal)

**Problem:** The renewer keeping the migrator's lock TTL fresh for the whole unbounded copy uses `renewed? = match?({:ok, _}, Storage.renew_lease(...))` then `if renewed?, do: renew_loop(...), else: :ok` (lib/fathom/migrator/shard_migration.ex:225-241, :239) — it exits on **any** non-`{:ok,_}`, treating a transient `{:error, reason}` (a store blip; the behaviour contract at lib/fathom/shard/storage.ex:213-222 explicitly says "retry, don't fence — a transient blip is not loss of ownership") identically to `{:error, :superseded}`. The coordinator's own path distinguishes them (shard.ex:907-933: `:superseded` → self-fence; transient → `schedule_renew` and continue). A single S3 hiccup during a long migration silently ends lock renewal for the rest of the copy; the lock TTL (default 30 s) lapses and a client checkout can steal the shard mid-migration.

**Impact:** On its own: spurious migration/revert failure after a transient blip (the pre-flush `fence/2` aborts, work wasted, ReconcileJob retries). Worse, it is the realistic trigger that opens the #4 revert-clobber window — the renewer dying is exactly what lets a steal race the unfenced `restore`.

**Recommended Fix:** Match on the result: continue the loop on `{:ok, _}` **and** on transient `{:error, reason}` (retry after the interval), stop only on `{:error, :superseded}` — mirroring shard.ex:907-933.

### #10. Dead-pin reconciler can unpin a shard mid-handoff (no in-flight-HandoffJob or pin-recency guard) on a `:free` lease during the drain gap
**Severity:** Medium | **Category:** Reliability | **Panels:** Distributed
**Likelihood:** Low (partial `alive` set + handoff drain gap + target not yet beating) | **Blast Radius:** A handoff silently undone; hot shard bounces to the wrong node, rebalancer thrash. No data loss (lease still enforces single-writer)

**Problem:** Each tick the reconciler unpins any non-failed override whose `pinned_node` is not in the Postgres `alive` set (nodes beating within `node_stale_ms`, default 60 s) **when `Storage.lease_holder/1` returns `:free`** (lib/fathom/rebalancer/rebalance_job.ex:105-141, :122-123). The `MapSet.size(alive) > 0` guard (line 106) only rejects the *totally empty* fleet; a **partial** `alive` set (rolling deploy, or a handoff target not yet beating within the window) still makes that target's pins reconcile candidates. HandoffJob ordering is flip → **drain source (releases lease)** → target acquires; there is a real window where the source has released and the target hasn't yet acquired, so `lease_holder` reads **`:free`**. If in that window the target isn't in `alive`, the reconciler **unpins the shard a HandoffJob is actively moving to it** — no check for an in-flight handoff or a recent pin `updated_at`. The drain "completes," handoff reports success, but the pin is gone, so the shard routes back to its hash home. Guarded only by the operational assumption that every node beats, not by construction.

**Impact:** A handoff is silently undone; the hot shard bounces back / to the wrong node, and the rebalancer may re-propose and thrash. Control plane and actual placement diverge.

**Recommended Fix:** Before unpinning on `:free`, exclude shards with a live `HandoffJob` (Oban `executing/available/retryable/scheduled` for that `shard_id`) and/or a pin `updated_at` newer than a handoff's worst-case lifetime; only reconcile pins older than that grace window.

### #11. A blank/failed Prometheus scrape resets the rate baseline, causing a false all-time spike on recovery
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Admin
**Likelihood:** Medium (any single flaky/slow scrape, reporter restart, or the 5 s call timeout) | **Blast Radius:** Admin dashboard only — false all-time rate/latency spikes for one tick

**Problem:** `safe_scrape/0` returns `""` on any reporter error/timeout (rescue/catch → `""`), which `PrometheusScrape.parse` turns into `[]` (lib/fathom/admin/metrics_collector.ex:139-146, 177-185). The tick unconditionally stores that empty result as the next baseline: `prev_query_buckets: query_buckets` (=[]) and `prev_counters: counters` built from `counter_group/4` over the *static* `@s3_methods` list, so every S3 key is present but `0.0` (metrics_collector.ex:204-223, 254-255). On the next tick, when the scrape recovers, `rate_group/4` does `rate(cur, Map.get(prev, {:s3_ops,"get"}, cur), window)` (metrics_collector.ex:259-265) — because the key *is* present in `prev` (as `0.0`), the fallback-to-`cur` guard doesn't fire, so it computes `rate(N, 0.0, ~1.0) = N` (the entire cumulative op count since boot / one 1 s window). Worked: after one blank scrape with lifetime GETs = 480,000, the Storage panel shows `480,000.0 GET/s` for one tick. Same class hits `query_p50/p95/p99_ms`: `prev_query_buckets` becomes `[]`, so `diff_buckets(real, [])` returns the full cumulative histogram and the percentile is over all-time.

**Impact:** Transient but dramatic false spikes in S3 op/byte rates and query-latency percentiles on the live dashboard whenever the in-process reporter hiccups. Erodes trust and could trip an operator's eyeballed thresholds.

**Recommended Fix:** On a failed/blank scrape, do **not** advance the baselines — keep the last-good `prev_counters`/`prev_query_buckets` (and emit the previous rates or `nil`). Have `tick/1` detect `scrape == []` (or thread a `scrape_ok?` flag) and skip the `prev_*` updates for scrape-derived series that tick. **Regression test (folds part of the Admin test gap):** `test/fathom/admin/metrics_test.exs:190-221` only asserts the broadcast map's *shape*, never numerical correctness. Add a collector test that seeds `prev_counters`/`prev_query_buckets`, runs `tick/1` twice with controlled scrape text (including a tick where the scrape returns `""` followed by a real scrape), and asserts exact rates/percentiles and **no** recovery spike; also cover the `rate/3` reset clamp (`curr < prev`).

### #12. Per-shard p50/p95/p99 are cumulative-for-the-coordinator's-life, shown beside 1-second rates
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Admin
**Likelihood:** High (true for any shard with a past slow query) | **Blast Radius:** Admin dashboard only — misleading per-shard tail latency, misdirects rebalancing/triage

**Problem:** `ShardLatency.record/2` bumps ETS histogram buckets that accumulate for the entire lifetime of a shard's coordinator — the only reset is `forget/1` at `Fathom.Shard.terminate` (lib/fathom/shard_latency.ex:84-95, 132-145, no windowing). `MetricsCollector` computes `ShardLatency.percentiles(s.shard_id)` per hot shard (lib/fathom/admin/metrics_collector.ex:137) and renders those as per-shard `p50`/`p99` columns directly next to `q/s`, `rows read/s`, `rows written/s` — all **1-second windowed rates** — and next to the node-wide hero chart whose `p50/p95/p99` are **windowed diffs** (lib/fathom_web/live/admin_shards_live.ex:84-85). A shard that saw a slow scan an hour ago but is fast now shows a permanently elevated p99 that never decays until it churns out of residency, while the node-wide chart shows the true current p99. The two disagree by construction.

**Impact:** An operator drilling into "which shard is slow" gets an all-time-since-open number that misrepresents current tail latency and contradicts the node-wide chart on the same page. Misleads rebalancing/triage decisions.

**Recommended Fix:** Either (a) window the per-shard percentiles like the node-wide series — diff two histogram snapshots per shard across the tick (the collector already keeps a `prev_load` map; add a `prev_latency` histogram map for the hot set) — or (b) relabel the columns "lifetime p99" so the semantics are explicit.

### #13. KPI-tile sparklines are frozen at mount — `@history` is never updated on the realtime path
**Severity:** Medium | **Category:** Reliability | **Panels:** Admin
**Likelihood:** High (every session) | **Blast Radius:** Admin dashboard only — broken-looking realtime UI

**Problem:** `mount` assigns `:history` once from `MetricsCollector.snapshot().history` (lib/fathom_web/live/admin_overview_live.ex:32-33). `handle_info({:metrics, m}, ...)` reassigns `:metrics` and pushes the two uPlot charts via `push_event`, but never touches `:history` (admin_overview_live.ex:44-56, 104-108, 308-309). The KPI-tile sparklines are server-rendered from `@history` (`<.sparkline values={spark(@history, :qps)} />`, `spark(@history, :p99)`), so they display a static ~5-minute window captured at page load and never move for the life of the session, even though every other number on the tile updates each second. The big uPlot charts update (client ring); the tile sparklines are dead.

**Impact:** On a dashboard whose header shows a pulsing "live" dot, the "Queries/sec" and "Query p99" sparklines silently freeze — a confusing, broken-looking realtime UI.

### #14. A committed WAL write can be dropped by `drop_clean` if the stream dies between the SQLite commit and `WriteCounter.bump`
**Severity:** Low | **Category:** Data Loss | **Panels:** OTP
**Likelihood:** Very Low | **Blast Radius:** Single shard — one committed (not yet client-acked) write dropped

**Problem:** (Same watermark-ordering family as #1, but a distinct bug with the *opposite* fix.) In `do_execute`, the SQLite write commits inside `Connection.query` (WAL, `synchronous=FULL` — fsync'd, durable on local disk) and only *afterward* does `if wrote?(...), do: WriteCounter.bump(shard_id)` (lib/fathom/shard_executor.ex:73-82). Dirtiness is `count(id) > flushed_through` (lib/fathom/shard.ex:1227-1230). If the executing stream process is killed in the gap between the commit and the bump, the write is durably in the local WAL but *uncounted*. If it was the clean→dirty transition write (`count == flushed_through`), the coordinator later sees the shard as clean, and on idle `flush_and_drop → drop_clean` (shard.ex:1085-1098) deletes the local db/-wal without uploading — silently discarding a committed, fsync'd write.

**Impact:** Narrow (the write is not yet client-acknowledged — the `{:ok, …}` reply follows the bump), but it violates the intuitive "committed to the fsync'd WAL ⇒ survives" property on the idle-drop path. Only bites on stream death mid-statement for the transition write.

**Recommended Fix:** Bump the write counter *before* issuing the commit (over-counting is the documented safe direction — an extra flush, never lost data), or fold the dirty-marking into the same critical section as the write so a killed stream can never leave a committed-but-uncounted write that `drop_clean` deletes. (Note: this fix is bump-*before*-commit; #1's fix is bump-*on*-commit — apply both; they address different points in the statement lifecycle.)

### #17. The steal-touch rotates the data object to a multipart etag, silently disabling download MD5 verification exactly at failover
**Severity:** Low | **Category:** Data Correctness | **Panels:** Storage
**Likelihood:** Very Low (actual transfer corruption on a non-MD5-etag store, at the failover pull) | **Blast Radius:** Unverified promote of a corrupt just-stolen shard; self-heals on next flush

**Problem:** Download integrity (#37) verifies the streamed body's MD5 against the object's etag only when the etag is MD5-shaped (`md5_etag?` requires 32 hex chars; `verify_md5` returns `:ok` for anything else — lib/fathom/shard/storage/s3.ex:545-558). But the steal-time fence deliberately converts a single-part (MD5) etag into **multipart form** via `single_copy_touch`/`multipart_copy_touch` (`rotate_etag`, s3.ex:335-339). **Impact:** A window with no download-corruption detection on precisely the failover pulls the integrity check protects. Narrow (requires actual transfer corruption on a store whose etag isn't the MD5) and self-healing on the next flush.

**Recommended Fix:** Carry an explicit `content-md5`/`x-amz-meta-fathom-md5` on flush and verify against that on download instead of relying on the etag being MD5-shaped, so verification survives etag-form rotation.

### #20. Eviction probing a busy shard flips it to `draining`, spuriously 503-ing concurrent checkouts on healthy bystanders
**Severity:** Low | **Category:** Reliability | **Panels:** OTP
**Likelihood:** Low (at-capacity churn with busy LRU-cold candidates) | **Blast Radius:** Transient spurious 503s on healthy bystander shards

**Problem:** `evicted_for_room?` probes candidates with `drain(id, 0)` (lib/fathom/shards.ex:261-262). When a candidate is *busy* (conns > 0), the coordinator's `handle_cast({:drain, 0, reply_to})` sets `draining: true` and arms a 0 ms `:drain_timeout` (lib/fathom/shard.ex:757-762); the shard resumes only when it next processes that timer message. In the window between those two message-handlings, `handle_call({:checkout, _op}, _, %{draining: true})` returns `{:error, :draining}` → a 503 to the client (shard.ex:709-711). **Impact:** Under sustained at-capacity churn where LRU-cold candidates are busy, healthy bystander shards emit transient 503s caused by unrelated admissions — spurious client errors not attributable to any real fault. **Recommended Fix:** Make the eviction probe non-mutating for busy shards: check conn count / peek before flipping `draining`, or add an "evict-if-idle" cast that only stands the coordinator down when `map_size(conns) == 0` and otherwise leaves state untouched (never entering `draining`).

### #21. The idle-drop flush never updates the etag sidecar before dropping, producing a spurious "FORKED" quarantine on a crash after upload
**Severity:** Low | **Category:** Reliability | **Panels:** Storage
**Likelihood:** Low (crash after S3 flush success, before `drop_local`) | **Blast Radius:** False FORKED operator alarm + leaked `.forked` file + diluted fork telemetry; no data loss

**Problem:** Every other successful-flush path updates the provenance sidecar (`write_etag_sidecar` at lib/fathom/shard.ex:776, 1168, 1437). The idle drop path deliberately discards the new etag — `{:ok, _new_etag} -> drop_local(...)` (shard.ex:1100-1137, esp. 1107-1110) — because it's about to delete everything. But if the node crashes after `Storage.flush/3` succeeds (S3 object now at the *new* etag) and before `drop_local` completes, the local db survives with its `.etag` sidecar still holding the *old* etag. On the next warm open, `quarantined_fork?` sees sidecar(old) ≠ object(new) and quarantines the file as a fork (shard.ex:1342-1343 → 1355), emitting an ERROR log and `[:fathom,:shard,:forked]` telemetry — for what is actually a clean crash recovery of *identical* bytes (the local db equals the object just uploaded), which it then re-pulls redundantly.

**Impact:** False data-integrity alarms (operator paged for a nonexistent fork), a leaked duplicate `.forked.<ts>` file per occurrence, and spurious fork-rate telemetry that dilutes the real split-brain signal. No data loss.

**Recommended Fix:** Update the sidecar to `new_etag` before `drop_local` on the success branch (cheap, and closes the crash window so recovery is an ordinary clean warm restart).

### #22. The storage-usage poll runs in an unlinked, un-timed `Task.start` that can stack on a slow S3 LIST

### #23. Prometheus label parser breaks on commas or escaped quotes inside label values
**Severity:** Low | **Category:** Reliability | **Panels:** Admin
**Likelihood:** Very Low (latent — needs a future free-form label value) | **Blast Radius:** Collector GenServer crashes for the tick instead of degrading to a blank panel

**Problem:** `parse_labels/1` does `String.split(braces, ",", trim: true)` then `String.split(pair, "=", parts: 2)` and `String.trim("\"")` (lib/fathom/admin/prometheus_scrape.ex:57-66). A Prometheus label value may legally contain a comma (`{path="a,b"}`) or an escaped quote (`\"`); the comma-split shatters such a value across two "pairs", one with no `=`, so the `[k, v] = String.split(...)` pattern-match raises `MatchError`. Not rescued inside `parse_line` (only `Regex.run`'s no-match and `parse_value`'s `:error` are handled), so a single malformed line propagates out of `parse/1` and — via `MetricsCollector.tick/1` — crashes the collector GenServer for that tick.

**Impact:** Latent. Today's reporter only emits simple atom-valued tags (`outcome`, `op`, `warm`, `result`, `command`), so no value contains a comma — safe in practice. But any future metric tag carrying a free-form string (a path, name, error message) would crash the collector on scrape rather than degrade to a blank panel (the parser's stated "never a crash" contract).

**Recommended Fix:** Make `parse_labels/1` total: match `String.split(pair, "=", parts: 2)` with a `case` that drops malformed pairs, and/or wrap `parse_line/1`'s body so a bad line yields `[]`. Honor the "never a crash" contract the moduledoc promises.
