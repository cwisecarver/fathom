## Ranked Findings

### #1. A busy self-fence abandons committed-but-unflushed writes with no quarantine, log, or telemetry
**Severity:** Critical | **Category:** Data Loss | **Panels:** Durability (S1) + OTP (O4) | **Disposition:** FIX
**Likelihood:** Medium-High (any steal/failover of a *busy* shard) | **Blast Radius:** one tenant per event, silent + effectively unrecoverable

**Problem:** Every self-fence path (`{:stop, {:shutdown, :lease_lost}, state}` at `shard.ex:917-919`, `1029-1033`, `1049-1056`, `1124-1131`) stops unconditionally regardless of `state.conns`. `terminate/2` has a `lease_lost, conns==0` clause that quarantines the dirty local to `.fenced.<ts>` with `Logger.error` + telemetry, and a `conns==0` flush clause — but a self-fence with **connections still checked out** falls to the catch-all (`shard.ex:1181`), which only forgets ETS rows: no flush, no quarantine, no log, no telemetry. A self-fence is likeliest exactly when a shard is *busy* (load → GC/missed-heartbeat), and streams hold independent SQLite handles until their monitor fires async, so writes keep landing in the local WAL after the fence decision.

**Impact:** A steal/self-fence under active write load silently strands committed (fsynced) writes in a plain `<shard>.db` on the old node — invisible to the fleet (the new owner pulled a different lineage), often never reopened on that node (LB home moved), with zero operator signal. `shard_durability_test.exs:258` explicitly comments "Requires conns == 0 so the lease_lost clause runs" — the busy case is untested.

**Fix:** Extend the `lease_lost` quarantine clause to `conns > 0` too (quarantine-rename `.db`/`-wal`/`-shm` regardless of connection count; streams tear down safely against a renamed file) and emit the same `Logger.error` + `[:fathom,:shard,:fenced_quarantine]` telemetry. Ship the busy-terminate regression test (S5).

### #2. `Snapshots.restore/3` is an unconditional write fenced only by a stale read — TOCTOU clobbers concurrent writes
**Severity:** Critical | **Category:** Data Loss | **Panels:** Distsys (D1) + Durability (S2) | **Disposition:** FIX
**Likelihood:** Medium (operator restore + a racing write) | **Blast Radius:** one tenant, silent loss of acknowledged writes

**Problem:** `restore/3` (`snapshots.ex:69-84`) drains the local coordinator, reads `Storage.lease_holder/1` once, and if `:free` calls `Storage.restore_snapshot/2` — an **unconditional** server-side copy (no `If-Match`, no `expected_etag` in the callback signature: `storage.ex:392-399`, `local.ex:201-204`, `s3.ex:837-840`). Between the `lease_holder` read and the copy, any node (including this one, via a client request on the Host subdomain) can `checkout` → cold-open (the lock is free, `If-None-Match:*` succeeds) → accept + flush writes durably. `restore_snapshot` then silently overwrites them. Reachable over the control plane at `POST /api/tenants/:id/restore` (`tenant_controller.ex:150-171`) with **no quiescing** required.

**Impact:** Operator-invoked PITR silently discards acknowledged commits from a request that raced in during the drain→copy window; restore reports success. This is the exact hazard the migration engine already fenced: `Storage.restore/3` (`storage.ex:160-172`) exists specifically because "an UNCONDITIONAL restore would clobber those acknowledged writes... A 412 → :superseded aborts here, no clobber." The snapshot path reintroduced it.

**Fix:** Add a fenced `restore_snapshot(shard, snapshot_id, expected_etag)` (both backends) mirroring `Storage.restore/3`'s `If-Match`/`{:error, :superseded}`. In `Snapshots.restore/3`, capture `Storage.object_etag(id)` at the same instant as the `lease_holder` check, pass it through, and abort on `:superseded`. Add the racing-write regression test (`snapshots_test.exs` has none).

### #3. Read-only Hrana token scope is unenforced over HTTP (and only the first WS stream is protected)
**Severity:** Critical | **Category:** Security | **Panels:** Isolation (I1 + I2 + I3) | **Disposition:** VERIFY→FIX
**Likelihood:** High where ro tokens are used | **Blast Radius:** every ro-scoped credential on the HTTP path

**Problem:** `HranaAuth.verify/2` stashes the token's `ro`/`rw` scope in the **calling process's** dictionary (`Process.put`, `hrana_auth.ex:90-92`), and `ShardExecutor.open/1` reads it via `Process.delete` (`take_scope`, `shard_executor.ex:40-49`). Over **HTTP**, `authorize/2` runs in the Plug process while `open/1` runs in a brand-new `Filo.Stream` GenServer (init runs in the child, not the caller — `../filo/lib/filo/stream.ex:92-116`), so the process-dict value is never visible and `take_scope` falls through to `|| :rw`. Over **WebSocket**, `authorize/2` runs once at `hello` in the socket process, so the *first* `open_stream` consumes the `:ro` scope via `Process.delete` but every subsequent stream on the connection defaults to `:rw` (`../filo/lib/filo/socket.ex:172-191`). The feature's tests (`read_only_scope_test.exs:35-40`) call `authorize`+`open` in one process, masking both.

**Impact:** A `ro` export/analytics/BI token (`token_for(id, scope: :ro)`, `docs/auth.md`) gets **full read-write** on every Hrana-over-HTTP stream, and can write through any WS stream after the first — the `403 FILO_READONLY` never fires, silently. (Applies only when `HRANA_AUTH=required` and ro tokens are issued.)

**Fix:** Verify the Filo process boundary first-hand, then stop relying on process-local state across `authorize→open`: thread the token/scope through the `open_arg` Filo already passes to `open/1`, and re-derive scope from the token in `open/1` (extract scope-decoding from `verify/2` into a pure function). Add a real-transport integration test (HTTP via `Filo.Plug`; WS opening `open_stream(1)`+`open_stream(2)`).

### #4. Pending `flush_now` waiters are dropped when the coordinator terminates mid-flush → false `:ok` → keystone-fork copies stale bytes
**Severity:** High | **Category:** Data Correctness | **Panels:** OTP (O1) | **Disposition:** FIX
**Likelihood:** Medium (raised by the 30s→5s change) | **Blast Radius:** a forked tenant born from stale bytes

**Problem:** `handle_call(:flush_now, ...)` (`shard.ex:789-799`) appends `from` to `flush_waiters` and kicks an async task, but never calls `cancel_idle` (the checkout handler does). If the idle timer / a zero-conn drain / a supervisor shutdown fires while a `flush_now` is outstanding, the coordinator stops with `flush_waiters` non-empty, and no `terminate/2` clause calls `settle_waiters/2` — the caller's `GenServer.call` gets a `:DOWN` and raises `exit`. `Shards.flush/1` catches that exit as `:ok`, so a genuinely failed flush reports success. `Tenants.fork/2`'s `flush_source: true` (the keystone-fork path built earlier tonight) then forks a possibly-stale stored object — contradicting its own doc ("A flush error fails the fork").

**Fix:** `cancel_idle(state)` in the `:flush_now` handler; every `terminate/2` clause calls `settle_waiters(state, outcome)` before returning. Test: `flush_now` outstanding when idle/shutdown fires.

### #5. Retirement scheduling isn't crash-safe — a Postgres blip after cutover permanently leaks the old version's storage object
**Severity:** High | **Category:** Reliability | **Panels:** Migration (M1) | **Disposition:** FIX
**Likelihood:** Low-Medium | **Blast Radius:** unbounded storage leak, no self-heal

**Problem:** After cutover, `ShardMigrationJob.perform/1` calls `schedule_retirement/2` (`Oban.insert`) with no rescue. If Postgres is unreachable at that instant, `perform/1` crashes and Oban retries; on retry `ShardMigration.run/3` short-circuits to a bare `:ok` (cutover already landed, `shard_migration.ex:47-51`), which `perform`'s `:ok -> :ok` clause handles **without** re-scheduling retirement. Same in `RevertJob` (`shard_migration.ex:99-101`). No reconcile/telemetry detects "cutover done, retirement never scheduled."

**Impact:** The retained `<shard>@<prev>` object is never scheduled for deletion — silent, indefinite storage leak (cost + retention/compliance) unless an operator-configured S3 lifecycle rule happens to catch it.

**Fix:** Rescue `schedule_retirement`'s `Oban.insert` → return `{:error, reason}` so the whole job retries in a non-terminal state until retirement is actually enqueued. Test both fwd + revert crash-forward paths.

### #6. `Migrator.Capture`'s Postgres-outage retry buffer is in-memory only — a restart during the outage silently forks the template from the fleet
**Severity:** High | **Category:** Data Correctness | **Panels:** Migration (M5) | **Disposition:** FLAG (needs design) + minimal guard
**Likelihood:** Low-Medium | **Blast Radius:** corrupts the whole rollout going forward, not one shard

**Problem:** When recording a captured version to Postgres fails, `Capture` keeps the already-committed-on-template statements in GenServer `state` and retries every 5s (`capture.ex:126-166`) — pure in-memory, no persistence. A crash or (realistically) a rolling deploy/node restart *while Postgres is down* wipes the buffer; every later captured version then assumes DDL the fleet never received.

**Fix (design decision — FLAG):** persist the pending buffer durably (an Oban job in the same rescue path, or a disk/DB queue). **Minimal autonomous guard I can ship now:** expose `Capture`'s pending-count and refuse/alert a clean shutdown while pending > 0, so a deploy during an active outage is loud rather than silent.

### #7. A `WriteCounter` crash/restart can make a dirty shard misread as clean → `drop_clean` loses data
**Severity:** Medium | **Category:** Data Loss | **Panels:** OTP (O3) | **Disposition:** FIX
**Problem:** `unflushed?/1` guards a table restart via a generation compare, but `WriteCounter.init/1` creates the fresh ETS table **before** bumping the `:persistent_term` generation (`write_counter.ex:94-119`). In the window between the old owner dying and the bump, `count/1` returns `0` (table gone, rescued) while `generation/0` still returns the old value → the guard reads "unchanged" → `unflushed?/1` returns false for any watermark ≥ 0 → an idle-stop/drain in that window `drop_clean`s un-flushed writes.
**Fix:** Bump the `:persistent_term` generation **before** `:ets.new/2` in `init/1`. Test the ordering invariant.

### #8. Ownership-unconfirmed (`:skip`) durability-flush outcomes don't feed the RPO-alerting path that PUT failures do
**Severity:** Medium | **Category:** Reliability | **Panels:** Distsys (D2) | **Disposition:** FIX
**Problem:** `record_flush_failure/2` (consecutive counter + `[:fathom,:shard,:flush,:failed]` telemetry + escalation) is called from the PUT-failure and task-crash branches but **not** the `:skip` branch (`shard.ex:1133-1137`), which fires when `Fence.check` can't confirm ownership (heartbeat `:not_valid` / transient check_lease error). That branch only logs a bare warning every interval — a persistent heartbeat/lease outage grows RPO exactly like a PUT failure but produces none of the alertable signal.
**Fix:** Route `:skip` through `record_flush_failure/2` with a distinct reason (`:ownership_unconfirmed`). Test via telemetry.

### #9. Durability alert thresholds weren't recalibrated when the flush interval tightened 6× (30s→5s)
**Severity:** Medium | **Category:** Reliability | **Panels:** Durability (S3) | **Disposition:** FIX (consequence of `269a22c`, tonight)
**Problem:** `FathomUnflushedAgeHigh` fires at `> 120000ms` and `FathomManyDirtyShards` at `> 300000ms` (`deploy/observability/alert-rules.yml:51-61`) — hardcoded, unchanged by the default drop to 5s. At 5s these are ~24×/~60× the cadence, so an S3 outage on a busy shard blows the intended ~5s RPO by ~24× before paging.
**Fix:** Recalibrate proportionally to the new default; note the coupling in `docs/durability.md`'s dials so a future interval change doesn't desync them.

### #10. `requires_review` is enforced only in `head()`, not in the functions that gate replay
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Migration (M2) | **Disposition:** FIX
**Problem:** `Migrator.statements/1` (`migrator.ex:61-67`) checks `yanked` but not `requires_review`; `enqueue_migration/2` takes an explicit target with no gating. Any direct `ShardMigration.run(shard, N)`/`enqueue_migration(shard, N)` at/above a flagged version bypasses the review floor and replays the flagged DML. Automated paths are safe only because they route through `head()`.
**Fix:** Make `statements/1` (or `statement_chain/2`) refuse a `requires_review` version the way it refuses `yanked` — a structural gate. Test.

### #11. `reclaim_stale_migrating` has no liveness signal — a genuinely running long migration can be falsely reclaimed
**Severity:** Medium | **Category:** Reliability | **Panels:** Migration (M3) | **Disposition:** FIX
**Problem:** `mark_migrating` stamps `migrating_since` once; `ReconcileJob` reclaims any shard `migrating` > 1h back to `active` (`directory.ex:243-277`). Nothing renews `migrating_since` while a single attempt runs (contrast the actively-renewed S3 migration lease), so a >1h copy gets its status flipped while still running (no corruption — the lease still blocks a double-write — but the status is wrong and the "never reclaimed out from under itself" claim is false).
**Fix:** Renew `migrating_since` alongside the lease renewer, or derive staleness from the Oban `executing` job row. Test.

### #12. `Directory.shards_at_version/1` is an unbounded `Repo.all` — a fleet-wide revert can materialize millions of rows
**Severity:** Medium | **Category:** Reliability | **Panels:** Migration (M7) | **Disposition:** FIX
**Problem:** No limit/stream; loads every active shard at a version as full structs (`directory.ex:378-382`). `Migrator.revert/3` (the emergency path) calls it directly; `revert_status/1` materializes the full set just to `length()` it. Fleet tested elsewhere at 3.1M rows.
**Fix:** Add `count_at_version/1` (aggregate) for `revert_status`; `Repo.stream`/chunk for the revert path. Test.

### #13. `Connection.query/3`'s deadline watchdog isn't cancelled when the query raises → spurious interrupt on a later query
**Severity:** Medium | **Category:** Reliability | **Panels:** OTP (O2) | **Disposition:** FIX
**Problem:** `query/3`'s `rescue ArgumentError` wraps the whole `case` including `with_deadline`, so if `do_query` raises (e.g. `Sqlite3.bind` on a bad value) the exception unwinds before `send(watchdog, {:done, ref})` runs, leaving the watchdog alive; after `ms` it interrupts the same connection — now running a later, unrelated statement in the stream (`connection.ex:70-146`). (Off by default → limited exposure.)
**Fix:** `try/after` around `fun.()` in `with_deadline/3` so the watchdog is always stopped. Test.

### #14. `Tenants.fork` / `Storage.fork_shard` has no lease/atomicity guard on the destination — TOCTOU clobber
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Isolation (I4) + Distsys (D5) | **Disposition:** FIX
**Problem:** `fork` checks `refuse_if_taken(dst)` in Postgres, then `Storage.fork_shard` checks-then-copies at storage (`s3.ex:811-828` two HEADs + unconditional copy; `local.ex:183-191` `File.exists?` + `atomic_copy`) — neither lease/mutex-guarded, unlike the sibling `Migrator.ShardMigration.fork` (`with_lease/3`). A `dst_id` concurrently minted organically or by a second fork can be overwritten, or the organic coordinator's first flush 412s + self-fences real writes.
**Fix:** Mirror `ShardMigration.do_fork`: acquire the dst lease + conditional write (`If-None-Match:*` S3 / `with_lock_mutex` Local) → `{:error, :dst_exists}` for the loser. Test.

### #15. `flush: true` on snapshot creation silently ignores a failed force-flush
**Severity:** Low | **Category:** Data Correctness | **Panels:** Distsys (D4) | **Disposition:** FIX
**Problem:** `create_snapshot/2` (`tenant_controller.ex:118-119`) does `if truthy?(...), do: Shards.flush(id)` then unconditionally proceeds; the `{:error, reason}` return is discarded, so a caller asking for a guaranteed-current snapshot gets a silently-stale one on flush failure.
**Fix:** Match `Shards.flush/1` and short-circuit with an error (or a warning field). Test.

### #16. Admin query console accepts a free-text shard id with no `ShardId` validation
**Severity:** Low | **Category:** Data Correctness | **Panels:** Isolation (I5) | **Disposition:** FIX

## Findings that need your decision (FLAG)

### #18. Legacy-mode (heartbeat down) durability flush reintroduces synchronous mailbox-blocking I/O that #27 removed
**Severity:** Medium | **Category:** Reliability | **Panels:** Distsys (D3) | **Disposition:** FLAG (moderate refactor)
The `Fence.check` gating each flush runs synchronously in the coordinator; in legacy mode it calls `Storage.renew_lease` (a full PUT) in `handle_info` (`shard.ex:1101-1122`, `fence.ex:96-102`). For heartbeat-down shards, every 5s interval blocks the mailbox a storage RTT — the p99 checkout spike #27 removed, for the degraded mode. Fix is a non-trivial refactor (move the legacy renew off-process into the flush task). Worth doing, but a bigger change — flagging rather than doing blind overnight.

### #19. The hourly reconcile enqueues at most 100 shards — undermines "bounded mixed window" at fleet scale
**Severity:** Medium | **Category:** Architecture | **Panels:** Migration (M4) | **Disposition:** FLAG (knob vs bug)
`ReconcileJob` calls `rollout()` (limit 100) hourly = 2,400/day; a cold tail in the 100k–millions takes months to converge, conflicting with the docs' "bounded" claim. Fix is a config knob (`:reconcile_batch_size`) or paging within the run — an easy change, but "how aggressive should the default be" is a fleet-sizing decision. I'll make it *configurable* (safe) unless you'd rather set a specific default.

### #20. The 30s→5s default shipped `[skip-bench]`; the PUT/VACUUM cost side is unmeasured
**Severity:** Medium | **Category:** Performance / Test Gap | **Panels:** Durability (S4) | **Disposition:** FLAG (measure or re-tune)
Tonight's change measured the RPO benefit but not the cost: `VACUUM INTO` (a long-lived reader that holds back the passive WAL checkpoint) runs 6× more often, and the 6× PUT rate shares the S3 Finch pool with cold-opens. Options: (a) I add a cost benchmark and record it; (b) reconsider a middle value (e.g. 10s) as the default. Your call on whether 5s stands.
