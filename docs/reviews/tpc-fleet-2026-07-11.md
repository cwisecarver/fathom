>

> overhead**, not fathom: an nginx `Connection: close` upstream-keepalive bug made the driver
> reconnect constantly. Root cause and fix: [`lb-502-fix-2026-07-23.md`](lb-502-fix-2026-07-23.md).
>
> **Current measurement:** 4,096 concurrent tenant shards at **3,414 txn/s, zero errors** —
> [`tpc-fleet-elixir-driver-2026-07-24.md`](tpc-fleet-elixir-driver-2026-07-24.md). Re-run sweep:
> [`tpc-fleet-2026-07-23.md`](tpc-fleet-2026-07-23.md).
>
> **What still holds** is this report's *shape* finding, which the re-runs confirm: query load
> follows the shard partition across nodes, and per-txn p50 stays flat as tenants scale (no convoy).
> The "moderate concurrency by design" caveat is retired with the bug.

**2026-07-11, Apple M5 Max (18 cores), macOS 27.0.** The 3-node chaos rig (`fathom1/2/3` behind
nginx + MinIO + Postgres, all in one colima VM — 12 vCPU / 94 GB, prod-release nodes). Driven by
`deploy/chaos/chaos.sh tpc-fleet` (a real dep-free libSQL/Hrana remote client, `tpc_driver.py`,
through the LB). This is the **throughput-across-nodes** run the [fleet-density
report](fleet-density-2026-07-10.md) carried as Remaining Work #2.

Two prior runs frame this one:

- The [2026-07-10 TPC run](tpc-run-2026-07-10.md) measured the real-stack **latency shape** (per-txn
  cost over the wire) and the single-shard **write convoy** (many threads on one shard serialize on
  the `BEGIN IMMEDIATE` lock). It deliberately did **not** claim a throughput number — "throughput is
  not a rig-meaningful number here (single host, loopback client→LB)."
- The [fleet-density run](fleet-density-2026-07-10.md) proved **capacity** partitions across the
  fleet: the LB keyspace-partition spreads N shards ~N/nodes each at the single-node per-shard cost.

This run is the throughput analog of density: drive many tenant shards — **one single-writer file
each** (fathom's real model, so no intra-shard convoy) — through the real LB so they partition
across the nodes, and read back both the aggregate txn/s **and** the per-node load split. The claim
under test: the *work* partitions across the fleet the same way *capacity* does, so a busy fleet's
throughput is horizontal — each node serves its share of tenants independently.

## What it does

`deploy/chaos/chaos.sh tpc-fleet [tenants_csv per_client accounts]` (this run: `"6,12,24" 150 1000`):

1. **Sweep the tenant count.** For each `C`, run TPC-B with `C` clients = `C` distinct tenant shards
   (`tfleet<C>_0..`), **one writer per shard**, each doing `per_client` 7-statement bank txns through
   the LB. Each step gets its own shard namespace so nothing is re-seeded; ids route by Host subdomain,
   so the LB consistent-hash spreads them across the nodes exactly as in prod.
2. **Read aggregate throughput + per-txn latency** per step (the driver's `tpcb_tps` over the union
   span, plus p50/p95/p99).
3. **Read the per-node distribution.** With `SHARD_LOAD` on (docker-compose sets it), read
   `Fathom.ShardLoad.snapshot()` per node filtered to the `tfleet` set — how many tenant shards each
   node held and the total query load it absorbed. The rebalancer is quieted and idle-drop frozen for
   the run so no shard moves or is forgotten mid-measure (restored after).

## Results

Cross-LB warm `SELECT 1` RTT p50: **574 µs** (consistent with the 2026-07-10 run's 559 µs — the
per-statement network floor every txn pays).

## Findings

- **The work partitions across the fleet, and query load follows the shards.** All three nodes carry
  the load; each node's query count tracks its shard count (fathom2 holds the most shards **and**
  absorbs the most queries, 17 shards / 15.9k queries; fathom1 the fewest, 10 / 10.3k). No node is hot
  beyond its share — there is no cross-tenant coupling, because each tenant is an independent
  single-writer file on whichever node the LB hashed it to. This is throughput's version of the
  density result: **capacity partitions, and so does work.**
- **Per-txn latency stays tight as tenants scale — no convoy.** p50 moves only 4.67 → 4.80 → 5.80 ms
  while the tenant count goes 4× (6 → 24). That is the whole point of one-writer-per-shard: adding
  tenants adds independent writers, not contention. Contrast the [single-shard TPC-C
  convoy](tpc-run-2026-07-10.md#the-finding--chatty-writes-convoy-on-a-single-shard) where 8 threads on
  **one** shard drove p99 to 1–2 s. Same box, opposite outcome — the architecture is the difference.
- **Aggregate txn/s rises with concurrency to a single-host plateau — and that plateau is the *rig*,
  not fathom.** tps roughly doubles 6 → 12 tenants (17.8 → 39.1), then flattens 12 → 24 (39.1 → 40.4):
  the one 12-vCPU VM saturates around ~12 concurrent chatty writers, because that VM simultaneously
  runs all three nodes, MinIO, Postgres, **and** the GIL-bound Python driver, and every TPC-B commit
  fsyncs under `synchronous=FULL` on one shared disk. The per-txn p50 (5.8 ms) is fast; the aggregate
  is low because everything shares one machine. On N separate machines the partitioned work is ~N×
  additive (each node's ~1/3 of the tenants runs on its own CPU + disk) — that is the horizontal
  "millions" throughput axis, and this run's evidence for it is the **even-ish per-node split**, not
  the single-host aggregate.

## Limits (read before citing)

- **Absolute throughput is NOT a fathom number.** Single host, loopback client→LB, a GIL-bound
  threaded Python driver, and `synchronous=FULL` fsync serialization on one shared disk all cap the
  aggregate well below what the software costs. The trustworthy signals here are the **shape** (tps
  rises with concurrency; p50 stays flat) and the **partition** (the per-node split), not the txn/s
  magnitude. The reproducible software-cost throughput trend is the in-process `mix fathom.tpcc`
  (~11k tpmC, [companion table](tpc-run-2026-07-10.md#companion--loopback-spec-scale-tpc-c-the-reproducible-throughput-trend)).
- **Small-N hash variance.** 42 shards over 3 nodes spread 1.70× (min 10 / max 17). The consistent
  hash is even only in the large-N limit — the [density run](fleet-density-2026-07-10.md) measured
  1.22× at 30 000 shards with the *same* hash. At N=42 the spread is the sample size, not a load
  imbalance; the load-follows-shards result holds regardless of the exact split.
- **Errors are the rig's LB keepalive races, not lost data.** Transient nginx↔node upstream 502s rise
  with concurrency (22 → 56 → 332 over the sweep); the driver reconnects and skips the txn (a fresh
  stream open), so they cost throughput, not correctness — and they inflate the p95/p99 tails at 24
  tenants. Same artifact characterized in the 2026-07-10 run.
- **Moderate concurrency by design.** Pushed to 64 tenants the rig enters a 502 + reconnect storm that
  dominates wall-clock and buries the signal; the 6/12/24 sweep keeps the box out of that regime so the
  partition and the no-convoy latency read clean. Relative, single-host — a trend + a partition proof,
  not an absolute or peer-certifiable TPC result.

## Reproduce

```bash
cd deploy/chaos && ./chaos.sh up
./chaos.sh tpc-fleet "6,12,24" 150 1000   # sweep tenants; aggregate txn/s + per-txn p50 + per-node split
# needs SHARD_LOAD=true (docker-compose sets it); rebalancer/idle-drop auto-quieted for the run
```
