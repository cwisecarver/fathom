# Fathom Expert Panel Review — Phase-2 B1 Dynamic Rebalancer

**Date:** 2026-07-07
**Scope:** the Phase-2 B1 dynamic rebalancer (`Fathom.Rebalancer.*`), built across commits `16764e9..455ce2f`. Reviewed adversarially for correctness + safety **before it is ever enabled in production** (all gates off by default today).
**Panels:** (1) Distributed systems / single-writer & handoff safety · (2) Control plane / Ecto / Oban / data correctness · (3) Multi-tenant security & shard isolation / LB injection · (4) Elixir/OTP & concurrency · (5) Rebalance policy / numerical correctness
**Methodology:** panel scoping → 5 parallel expert reviews → unified dedup + ranking
**Commit reviewed:** `455ce2f`
**Total findings:** 18 unique (from 44 raw across panels)

## What is CONFIRMED SAFE (do not "fix")

- **Single-writer / no-double-write holds.** Every handoff interleaving is arbitrated by the S3 `{owner, epoch}` lease mutex + drain-before-release ordering; the LB flip/ordering is *not* what protects correctness — the lease is. The async-reload windows below are **availability/thrash**, not leaks. (Panels 1, 4)
- **Shard isolation holds.** A pin sets `$fathom_target` to a node/pin-upstream only; nginx preserves `Host`, the target re-derives the shard via `ShardId.cast`, and the lease binds the file to that canonical id. `unique_index(:shard_overrides,[:shard_id])` guarantees ≤1 map entry per host; a wrong `base_domain` fails safe (falls through to the hash pool). No cross-tenant path found. (Panels 3, 1)
- **Verified correct as-built:** the improvement guard (a lone hotspot correctly never moves), the `threshold > 0.0` empty-list guard (load-bearing), `plan_moves` running-load accounting (no double-count), the int/float `q_per_s` handling (no `Float.round` recurrence), all three migrations reversible, the cron inert when disabled + in test, `node_load` no double-count, `RebalanceJob` is a true fleet singleton (Oban Postgres peer leadership), and `warm_now/1` genuinely works with the follower down. (Panels 2, 4, 5)

## Ranked Findings

---

### #1. Pinned hot shards lose automatic failover; nothing reconciles a pin against a dead node
**Severity:** High | **Category:** Availability / cluster contract | **Panels:** 1 (+ prompt-confirmed)
**Likelihood:** High (nodes die) | **Blast radius:** the hottest shards — the ones that matter most

**Problem:** `LbMap.render` (`lib/fathom/rebalancer/lb_map.ex:45-50`) renders each pin as a **single-server** upstream (`upstream fathom_pin_<node> { server <addr> ...; }`). When the pinned node dies, nginx has no other server → 502 indefinitely. A non-pinned shard rides `upstream fathom_hrana { hash $host consistent; ... }` and re-hashes to a survivor on death (lease-arbitrated). `RebalanceJob` only *adds* moves — there is no reconciler that reads heartbeats and unpins a dead node's shards. `render` drops overrides whose `pinned_node` isn't in `:lb_backends`, but that needs an operator config edit *and* something to re-run `apply!` (nothing re-renders periodically — see #10).

**Impact:** The rebalancer converts its hottest shards from "self-healing on node death" to "down until an operator intervenes" — an asymmetry that gets **worse the more successful the rebalancer is.** This is the single strongest reason not to enable B1 as-is.

**Recommended fix:** Render the pin upstream with the pinned node primary and the rest of the fleet as `backup` servers (`server <target>; server <other> backup; ...`) so nginx fails a dead pin over to a survivor (the lease handles the remap) while still concentrating normal traffic on the target. **And** a leader-run reconciler (each `RebalanceJob` tick) that unpins any override whose `pinned_node`'s heartbeat is stale, then re-applies.

### #2. The p99-relative hot rule is effectively inert in production; `nil floor ⇒ p99` silently does nothing
**Severity:** High | **Category:** Data Correctness | **Panels:** 5
**Likelihood:** High (fires whenever `:rebalance_hot_qps_floor` is unset — the documented default) | **Blast radius:** the whole rebalancer is a silent no-op

**Problem:** Two compounding defects mean the policy's documented default (`nil floor ⇒ p99-relative, K×p99`) doesn't function:
- **Head-only p99** (`policy.ex:58-59,133`): the moduledoc claims it mirrors `scale.ex`'s threshold logic, but `scale.ex` computes p99 over the *full fleet incl. the cold tail*, while the `Reporter` publishes only each node's **top-N hottest** shards (`:load_report_top_n`, default 50). So `rates` is a pre-filtered *head*; its p99 is systematically far higher than the fleet p99 the `mult=20` calibration was validated against → under-flags.
- **Small-N p99 = max** (`policy.ex:166`): `round(0.99·(N-1)) == N-1` for all `N ≤ 51`, so `percentile(rates,99)` returns the **maximum** and `threshold = mult×max ≥ max` flags nothing, even for one mega-hot shard. Combined with the truncation making N small, the p99 path is inert for any deployment that isn't both large and tail-heavy.

**Impact:** An operator relying on the documented p99 default gets a **silently inert** rebalancer (no moves, no error). Only the absolute `:floor` path actually works. Fail-safe (nothing breaks) but the feature's headline detection mode is non-functional. The `--hotspots` harness masked this because it sees the full tail.

**Recommended fix:** Have the `Reporter` also publish a fleet-wide p99 (or enough of the tail) so the policy's bar is fleet-relative; use a percentile method that biases to the upper element / interpolates for small N; require a minimum sample count before trusting the p99 path (else fall back to floor). Add a test with a sharp head at N∈[5,30] asserting it *is* flagged. Stop claiming it mirrors `scale.ex` until it does.

### #3. `LbApply.apply!` writes the LB include with no `nginx -t` and no atomic rename → latent fleet-wide outage
**Severity:** High | **Category:** Availability (blast radius = ALL shards) | **Panels:** 3
**Likelihood:** Medium (needs a malformed render) | **Blast radius:** every shard's routing

**Problem:** `lib/fathom/rebalancer/lb_apply.ex:25` writes the rendered snippet **directly** to `:lb_map_path` (the file nginx `include`s at http level), then reload is best-effort. No config-test before promotion and no atomic temp+rename. A live `nginx -s reload` keeps old workers on a bad config, so a malformed file degrades to "stale LB" while running — but the **broken file stays on disk** and the next nginx cold start (deploy, crash, OOM, reschedule) pulls it and **fails to start** → all routing down. The non-atomic write also races the sidecar's mtime-triggered reload (can HUP against a half-written file).

**Impact:** Any malformed render — from #14 (raw `shard_id`), a bad `base_domain`/backend addr, or an `upstream_name` collision — becomes a fleet-wide LB outage that surfaces *later*, decoupled from the change that caused it. This is the containment for several lower findings.

**Recommended fix:** Render to a temp file in the same dir, run a config test (`nginx -t -c …` / an operator `:lb_test_cmd`), and only `File.rename/2` (atomic) on success; abort + log + keep the last-good file on failure.

### #4. A failed handoff deletes the cooldown record, so an un-drainable hot shard thrashes every tick
**Severity:** High | **Category:** Control-loop stability | **Panels:** 2 (+ 1)
**Likelihood:** High (the hottest shards are exactly the ones that don't drain in time) | **Blast radius:** repeated LB reloads, warm pulls, DB/map churn per tick

**Problem:** The cooldown keys on `overrides.updated_at` (`policy.ex:155-160`), but on final drain failure `HandoffJob` `unpin`s — deletes the `shard_overrides` row (`handoff_job.ex:57` → `overrides.ex:37-40`). The next `RebalanceJob` tick recomputes the same shard as hot, finds no override → not in `cooling_shards` → re-proposes → new HandoffJob → warm + pin + LB flip + drain-fail + revert, on repeat. There is no failure backoff.

**Impact:** The hottest shards — precisely the intended targets — are the ones whose connections don't drain within the window, so this thrash is their *expected* path: repeated `apply!` writes/reloads, warm pulls, exception-map churn, for a shard that can never be moved.

**Recommended fix:** Record a failure cooldown that survives the revert (a short-lived `shard_overrides` row with a `failed` reason, a dedicated cooldown table, or a recently-`failed` `rebalance_commands` check) that `cooling_shards` also honors, so a wedged shard backs off.

### #5. `HandoffJob` uniqueness silently defaults to a 60s window → duplicate handoffs for slow handoffs
**Severity:** High | **Category:** Concurrency / Oban | **Panels:** 1 (+ 2)
**Likelihood:** Medium-High under a hotspot storm | **Blast radius:** two concurrent handoffs for one shard

**Problem:** `handoff_job.ex:33-36` sets `unique: [keys, states]` but **no `:period`** → Oban's default `period: 60`. Uniqueness is "a matching job with `inserted_at ≥ now − 60s`." A handoff easily outlives 60s (warm await 30s + drain await 30s + retry backoff across `max_attempts: 3`). Once the first job's `inserted_at` ages past 60s, a second `HandoffJob` for the same `shard_id` is **not** deduped even though the first is still `executing`/`retryable`. The `Policy` cooldown doesn't cover the gap — the override's `updated_at` only exists *after* `pin_and_flip` (~30s in), so a cron tick before pinning re-proposes. Two handoffs then pin the same shard (last-writer-wins) and both drain the source (no double-write — lease arbitrates — but "at most one handoff in flight" is violated).

**Recommended fix:** `period: :infinity` on the unique clause (with the existing live `states`, that's exactly "one handoff per shard until terminal"). One line.

### #6. Rate math clamps a counter reset to a spurious 0 → a churned shard under-reports for a window
**Severity:** Medium | **Category:** Correctness (rate signal) | **Panels:** 2, 4, 5 (three panels)
**Likelihood:** High (idle→evict→reopen churn is routine here) | **Blast radius:** one-window blind spot + resets the confirm streak

**Problem:** `reporter.ex:113` computes `rate = max(curr - prev, 0) / window_s`. A shard's coordinator stopping+reopening between snapshots deletes then re-creates its `ShardLoad` row (counters reset to 0). When `curr < prev` (only possible after a reset) the delta clamps to 0 and the shard is dropped by `Enum.reject(&(&1.q_per_s <= 0.0))`. The correct rate on a reset is `curr / window_s`. Because this system LRU-evicts idle shards and cold-re-opens them (per AGENTS.md), the churn is routine, not exceptional — so a moderately-hot shard that briefly idles + reopens under-reports as 0 and resets its `confirm_windows` streak, systematically biasing against churny shards.

**Recommended fix:** `if curr < prev, do: curr / window_s, else: (curr - prev) / window_s`. (The clamp is only wrong for reopen; a stop-and-stay-stopped shard already drops out by being absent from `curr`.)

### #7. Revert-on-drain-failure doesn't cancel the outstanding `drain` command → a stale drain fires after traffic returns to the source
**Severity:** Medium-High | **Category:** Command lifecycle / availability | **Panels:** 1, 2
**Likelihood:** Medium (needs poller lag > await window) | **Blast radius:** the just-restored shard goes briefly unavailable

**Problem:** `Commands.await` timing out leaves the row `pending` (`commands.ex:58-74`); it is never tombstoned. On the final failed attempt `HandoffJob` `unpin`s + reverts the LB (`handoff_job.ex:55-61`), but a still-`pending` `drain` remains and the source node's `CommandPoller` executes it whenever it next catches up — draining the now-actively-serving source right after the revert restored it. Each of the ≤3 attempts also issues a *fresh* warm+drain, so earlier attempts' commands pile up as `pending`. The `{owner,epoch}` fence prevents double-writes but not this availability hole.

**Recommended fix:** On revert, mark the outstanding drain command terminal (`cancelled`) before returning; and/or have the poller re-check `Overrides.for_shard(id)` immediately before a `drain` and skip if the pin is gone.

### #8. `CommandPoller` executes commands serially + synchronously; one slow drain head-of-line-blocks the node, and the timeout budget is mis-ordered
**Severity:** Medium | **Category:** Concurrency / liveness | **Panels:** 4, 1
**Likelihood:** High under a hotspot storm | **Blast radius:** a node's whole command queue (incl. warms it needs as a target)

**Problem:** `command_poller.ex:56-66` maps `execute/1` over all pending commands inside the single GenServer; a `drain` blocks up to `Shards.drain`'s safety net (`drain_timeout + 30_000` = ~40s, `shards.ex:175`). Everything behind it — other shards' drains, and the **warm** commands the node needs when it's simultaneously a handoff target — waits. Worse, the budgets are mis-ordered: `HandoffJob`'s `await` (30s) and `poll_now` (30s) are **shorter** than the poller's worst-case drain (40s), so a legitimately-slow drain gets mislabeled `busy`/timed-out → premature Oban retry re-issues a **duplicate drain** (feeding #5, #7) or a spurious revert (#4).

**Recommended fix:** Run drain/warm execution off the poller with a bounded `Task.async_stream` (so a warm never queues behind a drain and poll liveness decouples from drain duration); and order the timeouts so `handoff_drain_timeout_ms ≥ command_drain_ms + shard_shutdown_ms`, with `Shards.drain`'s safety net a function of the shutdown budget rather than a flat +30s.

### #9. `confirmed_hot?` (anti-flap) counts raw rows, not distinct windows per serving node
**Severity:** Medium | **Category:** Reliability / control-loop | **Panels:** 5
**Likelihood:** Medium | **Blast radius:** transient/relocating shards get moved → ping-pong

**Problem:** `policy.ex:135-140` does `samples |> filter(shard_id == x and q_per_s >= threshold) |> length >= confirm`. With a 120s horizon and a 10s interval there are ~12 rows per shard from one node, so `confirm_windows: 2` is met by 2 of ~12 windows — no requirement they're distinct/recent/consecutive; a shard that spiked twice and is now cold "confirms." And during an LB remap the same `shard_id` appears from two `node_key`s (old+new serving node), so `confirmed_hot?` double-counts a single hot window across nodes to reach `confirm: 2`. A naturally-rehashed hot shard isn't in `cooling`, so nothing else catches it.

**Recommended fix:** Filter to `s.node_key == candidate.node_key`, `Enum.uniq_by(& &1.sampled_at)` (or bucket by window), then `>= confirm`; optionally require the windows be recent + reasonably consecutive.

### #10. Concurrent `apply!` renders race → the rendered map drifts from the override table (lost pin)
**Severity:** Medium | **Category:** Consistency | **Panels:** 1
**Likelihood:** Medium (HandoffJob runs on any node, `rebalance` queue concurrency 3) | **Blast radius:** a dropped pin → that shard drained but never routed to target

**Problem:** `lb_apply.ex:18-29` does read-all-overrides → render → `File.write!` → reload with no serialization. Two handoffs on different nodes race: A commits pin(X) + renders {X}; B commits pin(Y) + renders {Y}; last writer wins and the other pin is missing from the *file* though present in the DB. Nothing re-renders the full table, so the drift is permanent until a coincidental future `apply!`.

**Recommended fix:** Serialize `apply!` behind a Postgres advisory lock (render+write+reload as one critical section), **and** have the leader periodically re-render the whole override table each tick — the periodic re-render also self-heals #1 (dead-node pins) and #11 (a flip that failed to reload).

### #11. `LbApply.apply!` swallows reload failure and returns `:ok`; the handoff drains even when the flip never went live
**Severity:** Medium | **Category:** Error handling / handoff integrity | **Panels:** 1
**Likelihood:** Medium | **Blast radius:** silent handoff no-op that still pays the drain cost

**Problem:** `lb_apply.ex:18-46` returns `:ok` when `:lb_reload_cmd` is unset (file written, nginx never told), when the reload command exits non-zero (only a `Logger.warning`), or when `:lb_map_path` is unset. `pin_and_flip` ignores this and proceeds to `drain` — so the source is drained while traffic still routes to it (flip not live); post-drain it re-acquires on the next request (reload never took effect). Combined with #1/#10 the map can permanently disagree with the override table.

**Recommended fix:** Have `apply!` surface reload success/failure; gate `drain` on a confirmed live flip (abort before draining if it can't be applied) in modes where the flip is required.

### #12. No Oban Pruner + `rebalance_commands` never pruned → unbounded table growth
**Severity:** Medium | **Category:** Operational | **Panels:** 2, 1
**Likelihood:** High (time) | **Blast radius:** Oban/Postgres degradation over time

**Problem:** (a) Oban `plugins:` has only `Cron`, no `Pruner` (`config/config.exs:50-59`), so completed job rows are retained forever — and the new `{"* * * * *", RebalanceJob}` inserts+completes a row **every minute in every env** (~1,440/day) even while inert. (b) `rebalance_commands` has no prune anywhere (contrast `LoadSample`, which the reporter prunes): `done`/`failed` rows accumulate, and commands for an off/absent node stay `pending` forever (also a correctness hazard, #7).

**Recommended fix:** Add `{Oban.Plugins.Pruner, max_age: …}`; add a retention sweep for terminal `rebalance_commands` (fold into the reporter's prune or a small cron) plus an age cap that marks very old `pending` commands `failed`; consider a partial unique index `(shard_id, node, command) WHERE status='pending'` so `issue` is idempotent.

### #13. `Reporter` / `CommandPoller` catch `rescue` but not `:exit`, unlike the `Directory.Recorder` pattern they cite
**Severity:** Medium | **Category:** Resilience | **Panels:** 2
**Likelihood:** Low-Medium (Postgres outage) | **Blast radius:** ControlPlane restart budget

**Problem:** `reporter.ex:82-86` and `command_poller.ex:61-66` only `rescue e`. `Repo.insert_all`/`delete_all` usually *raise* `DBConnection.ConnectionError` (caught), but pool / `:noproc` / shutdown conditions surface as an **exit**, which `rescue` misses. `Directory.Recorder` explicitly catches both (`rescue e` + `catch :exit, reason`) — the moduledocs here promise "a Postgres outage drops a window, never crashes the node," which the missing `:exit` clause breaks.

**Recommended fix:** Mirror `Directory.Recorder`: `try/rescue/catch :exit`, log, continue.

### #14. `shard_id` is not re-validated at the `Override` write boundary; the renderer interpolates it raw
**Severity:** Medium | **Category:** Injection (defense-in-depth) / isolation doctrine | **Panels:** 3
**Likelihood:** Low today (upstream `ShardId.cast` makes live ids safe) | **Blast radius:** if bypassed, arbitrary nginx directive injection (→ #3)

**Problem:** `Override.changeset` (`override.ex:24-29`) validates only presence + uniqueness — never `Fathom.ShardId.valid?/1`. `LbMap.render` (`lb_map.ex:42`) then emits `#{o.shard_id}.#{base_domain} …` **raw**, while `pinned_node` is sanitized via `upstream_name`. Today the id is safe only because `ShardId.cast` validated it far upstream — but AGENTS.md's isolation gate says any *new* place a shard_id enters routing must enforce the rule, and `Overrides.pin/2` is a public function. A future caller / ops insert / refactor could write `evil; } server { ... } #` and inject nginx directives.

**Recommended fix:** `validate_format(:shard_id, ~r/^[a-zA-Z0-9_-]{1,64}$/)` (or `ShardId.valid?/1`) in `Override.changeset`; and have `LbMap.render` defensively skip entries whose `shard_id`/`pinned_node` fail validation (mirror the existing "skip unknown backend" filter). Handle the `{:error, changeset}` branch in `HandoffJob` (`handoff_job.ex:79` hard-matches `{:ok, _}` — a rejected pin would `MatchError`-crash the job).

### #15. Cross-node clock skew corrupts owner attribution + can mis-prune a node's samples
**Severity:** Medium | **Category:** Distributed correctness | **Panels:** 2
**Likelihood:** Low-Medium (NTP skew) | **Blast radius:** mis-targeted / oscillating moves

**Problem:** `sampled_at = DateTime.utc_now()` is each reporter's wall clock (`reporter.ex:91`), but `latest_per_shard` resolves a shard seen by two nodes (mid-remap) by max `sampled_at` (`load_samples.ex:24-29`), and `since`/`prune` compare cross-node `sampled_at` to a single reader's `utc_now`. A few seconds of NTP skew vs a 10s window can (a) attribute a shard's load to the wrong `node_key` (wrong `from_node`), and (b) let a fast-clock node's rows survive longer / prune a slow-clock node's early so it looks *cold* and the policy piles load onto it. The reporter's monotonic clock fixes the *window* math but not this cross-node comparison.

**Recommended fix:** Order/prune on DB `inserted_at` (one server clock) rather than the reporters' `sampled_at`, or use a per-(node,shard) monotonic sequence; at minimum document the NTP dependency.

### #16. A mis-set `:rebalance_hot_qps_floor` silently degrades to the (inert) p99 path; the env parse boot-crashes on an integer
**Severity:** Medium | **Category:** Reliability / operability | **Panels:** 5
**Likelihood:** Medium (operator footgun) | **Blast radius:** silently-disabled or crash-looping rebalancer

**Problem:** `policy.ex:132` treats `0.0`, negatives, or any non-number floor by silently falling through to the p99 path (which #2 shows is often inert) — a mis-set floor turns the rebalancer into a silent no-op. Separately `config/runtime.exs:146` does `String.to_float(floor)`, which **raises at boot** on `"500"` (needs `"500.0"`). And `p99_multiple` parsing (`policy.ex:51`, `… / 1.0`) *raises* on a non-number rather than degrading — inconsistent with `floor`.

**Recommended fix:** Validate the floor explicitly (log/raise on a configured-but-unusable value rather than silently ignoring); accept integer env values; make `p99_multiple` parsing symmetric.

### #17. Request-path load can steer control-plane pins (bounded; document the assumption)
**Severity:** Medium | **Category:** Cross-tenant abuse | **Panels:** 3 | **DEFENSIBLE-AS-BUILT**
**Likelihood:** Low (network boundary) | **Blast radius:** an induced drain-window blip on a victim shard

**Problem:** The pin decision trusts `q_per_s`, a signal a tenant fully controls from the data path (`policy.ex:57-72` ← `record_query`). Under the default posture (`:hrana_auth` disabled, trust = network), any LB-reachable caller can drive any `<shard>.<zone>`'s rate over the bar and induce a `HandoffJob` (with a brief drain interruption of the *victim* shard) for a shard they don't own. Bounded by `confirm_windows`, `cooldown_ms`, `max_moves` (1/tick), and the improvement guard.

**Recommended fix:** Accept as designed, but document that `REBALANCER_ENABLED` presumes the network boundary (or `HRANA_AUTH=required`) is enforced. Consider a per-tenant `q_per_s_at_pin` sanity clamp and a fleet-rate alert (steering detector).

### #18. Minor / low-severity cluster (batch these)
**Severity:** Low | **Category:** various | **Panels:** 2, 3, 4, 5 | mostly DEFENSIBLE-AS-BUILT

- **Reporter `init` baseline is dead** (`reporter.ex:48-54`): Reporter (ControlPlane) starts before the `ShardLoad` table (DataPlane), so the seeded baseline is always `[]` and the first window over-reports; `confirm_windows` masks it. Seed lazily on the first tick or drop the misleading comment. (Panel 2)
- **`max_moves <= 0` still emits one move** (`policy.ex:102-106`): bound checked after appending. Short-circuit at ≤0. (Panel 5)
- **Tie-breaking depends on map iteration order** (`policy.ex:120-124,70`): equal-load targets / equal-hot shards resolve arbitrarily (deterministic per tick, not canonical). Sort ties by `node_key`/`shard_id`. (Panel 5)
- **Unused composite index** `(shard_id, sampled_at)` on `shard_load_samples` (migration `…025842:24`): no query uses it; pure insert overhead. Drop, or push `latest_per_shard` into SQL (`DISTINCT ON`). (Panel 2)
- **`cooling_shards` raises on nil `updated_at`** (`policy.ex:155-160`): latent (persisted rows always set it), but a nil crashes the whole `propose` (→ dropped tick under `max_attempts: 1`). Guard nil. (Panel 5)
- **Warm `.db` + `.etag` are two non-atomic writes** (`warm_follower.ex` `pull_one`): body/sidecar can momentarily disagree; safe only because the coordinator revalidates the etag at promotion. A `warm_now`-created file isn't in the follower's `cached` set (not refreshed/evicted). (Panel 4)
- **Reporter rescue re-scans ShardLoad + re-reads the clock** instead of reusing `curr`/`now_mono`; `prune` fires every window. Micro-efficiency. (Panel 4)
- **`base_domain` / backend `addr` rendered unsanitized** (operator env, `lb_map.ex:42,49`): a stray `;`/`{`/space breaks nginx for all shards (misconfig-robustness, not attacker-reachable). Validate at config load; covered by #3's `nginx -t`. (Panel 3)
- **`upstream_name/1` is lossy** (`lb_map.ex:70-72`): distinct node_keys (`10.0.0.1` vs `10-0-0-1`) collide to one upstream name → duplicate `upstream` block → reload fails. Detect collisions or constrain `:node_key` charset. (Panel 3)
- **`{:ok, _} = Overrides.pin(...)` hard-match** (`handoff_job.ex:79`): a changeset error (esp. after adopting #14) `MatchError`-crashes the job. Handle `{:error, _}` → `{:cancel, …}`. (Panel 3)
- **`HandoffJob.apply!` runs on any node** (`handoff_job.ex:48-58`): assumes every node can write `:lb_map_path` + reload the LB; a node that can't silently no-ops the flip (→ #11). Pin `apply!` to the leader / route the flip through a command, or boot-guard + document. (Panel 1)
- **Sidecar prod-analog notes** (`docker-compose.yml` lb-reloader): picks the nginx master as lowest-PID-named-`nginx` (fragile vs PID reuse) and triggers on raw mtime (races #3's non-atomic write). For a prod reloader use a pidfile + explicit signal/sentinel. (Panel 3)

## Recommended fix order (for `/iterate`)

**Before enabling B1 in any real fleet (correctness + availability):**
1. **#1** pin-upstream `backup` servers + dead-node unpin reconciler (the failover asymmetry)
2. **#3** `LbApply` render → `nginx -t` → atomic rename (contains #14, base_domain/addr, upstream collisions)
3. **#2** make the p99 bar fleet-relative + fix small-N percentile (the core detection doesn't work)
4. **#5** `period: :infinity` on `HandoffJob` unique (one line)
5. **#4** failure-cooldown so a wedged hot shard backs off
6. **#6** `curr < prev ⇒ curr/window_s` (three-panel rate-reset bug)
