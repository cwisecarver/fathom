# Fathom Expert Panel Review

**Date:** 2026-08-24
**Panels:** Elixir/OTP & concurrency · Storage & durability · Distributed systems & fencing · Multi-tenant security & shard isolation · Migration engine & control plane
**Methodology:** Panel scoping → 5 parallel expert reviews → unified ranking

## Project Profile

- **Type:** multi-tenant sharded data platform (SQLite-per-shard, Hrana, S3-bottomless)
- **Expert Domains:** Elixir/OTP & concurrency · Storage & durability · Distributed systems & fencing · Multi-tenant security & shard isolation · Migration engine & control plane
- **Commit reviewed:** 5222ee4
- **Total Findings:** 28 (from 31 raw across panels)

## Summary

The most urgent defects are in the tenant-facing statement gate, and four of them were **confirmed by
execution** against a real `Fathom.ShardExecutor` and a real shard, not by reading. The PRAGMA
allow-list is defeated by putting whitespace around the schema-qualifier dot
(`PRAGMA main . writable_schema = ON` executes), `describe/2` runs no gate at all — not the blocked-
statement check, not the `:ro` refusal, not the token-revocation re-check — and several pragmas take
effect at *prepare* time, so `describe` alone mutates connection state. A `:ro` stream on a shard
with no local file silently receives a read-write handle guarded only by `query_only`, which the
first bug turns off. Chained, those three are a complete read-only-scope escape, and `max_page_count`
makes one tenant a node-wide disk-fill outage for every co-tenant. Fix #1–#3 before anything else;
they are cheap, reachable by any client, and on the default path.

Below that sit the durability defects. The shutdown write fence is lifted *before* the shutdown flush
it exists to cover — found independently by three of the five panels — so every rolling deploy of a
busy shard ACKs writes that land in no uploaded object. The periodic durability flush is starved on
exactly the write-active shards it protects, because `:became_dirty` re-arms a full interval per
*stream* and django-libsql opens a stream per request. Neither has any test.

One theme recurs across four panels and is worth more than any single fix: **the test doubles do not
express the real backend's contract, so entire bug classes are structurally invisible to `mix test`**.
`Storage.Local.renew_lease/3` matches on `{owner, epoch}` where S3 fences on `If-Match`, so the
legacy-renew self-fence race cannot be written as a test. `Local.write_lineage(_, nil)` honours the
"leave the previous value alone" contract that S3's full `PUT` structurally cannot, so the lineage-
erasure bug reads as covered. `FaultyStorage` delegates to `Local` and inherits both gaps. Closing
those gaps is the highest-leverage single investment in the list.

Read the **Recommended Fix** paragraphs literally, including their hedges: several findings carry an
explicit "the finding is settled, the mechanism is open" flag, and AGENTS.md's rule is that a
recommended fix is a hypothesis, not a spec.

## Ranked Findings

### #1. PRAGMA allow-list is bypassed by whitespace around the schema-qualifier dot
**Severity:** Critical | **Category:** Security / Shard isolation | **Panels:** Multi-tenant security & shard isolation (**verified by execution**)
**Likelihood:** Certain (works today on any `:rw` stream; on any stream at all in the default `:hrana_auth: :disabled` posture) | **Blast Radius:** Node-wide — one tenant can fill the node's disk and break every co-tenant on it

**Problem:** `split_at_pragma_delim/2` (`lib/fathom/shard_executor.ex:1254`) stops the pragma name at
the first `=`, `(`, `;` or whitespace. For `PRAGMA main . writable_schema = ON` it returns
`name_raw = "main"` and `tail = " . writable_schema = ON"`. `pragma_assignment?/1`
(`lib/fathom/shard_executor.ex:1263`) trims leading whitespace and sees `"."` — not `"="` or `"("` —
so it concludes "bare read, always allowed" and returns `nil`. `blocked_pragma/1`
(`lib/fathom/shard_executor.ex:1225`) therefore never fires, and the statement is handed to the
engine, where the tenant authorizer (`[:attach, :detach]`) has nothing to say about pragmas.

VERIFIED through `ShardExecutor.execute/2` on a real shard:

```
"PRAGMA writable_schema = ON"                -> FILO_PRAGMA_BLOCKED   (baseline holds)
"PRAGMA main . writable_schema = ON"         -> {:ok, ...}   writable_schema now 1
"PRAGMA main . max_page_count = 999999999"   -> {:ok, ...}   max_page_count now 999999999
"PRAGMA main . synchronous = OFF"            -> {:ok, ...}   synchronous now 0
```

`PRAGMA main. writable_schema = ON` (space after the dot) and tab/newline variants work identically.

Same defect class as expert review 2026-08-20 #19 (the `String.slice(6, 200)` window), reintroduced
by its replacement parser. The suite reports full coverage because
`test/fathom/shard_isolation_attach_test.exs:275` pins only the unspaced
`PRAGMA main.journal_mode=DELETE`, and the padding test at `:293` pads only between `PRAGMA` and the
name — never around the qualifier dot.

**Impact:** Any tenant with a `:rw` token (or any client at all in the default `:hrana_auth: :disabled`
posture) defeats every protective pragma:

- `max_page_count` breaks `:shard_max_bytes` — the shard keeps ACKing writes past the cap and can
  never upload again, which is unbounded RPO for that tenant **plus a node-wide disk-fill outage for
  every co-tenant**.
- `synchronous=OFF` breaks the per-commit durability `docs/durability.md` promises.
- `writable_schema=ON` opens `UPDATE sqlite_master` — arbitrary schema/rootpage corruption.
- `wal_autocheckpoint=0` / `locking_mode=EXCLUSIVE` are levers against the coordinator's flush path.

**Recommended Fix:** Parse the qualified name structurally instead of stopping at whitespace: after
`PRAGMA`, skip whitespace, read an identifier (bare, `"…"`, `[…]`, or backtick-quoted), then skip
whitespace; if the next non-space char is `.`, consume it, skip whitespace, and read the second
identifier as the name. Strip quoting from the identifier before the allow-list comparison — the
probe also shows `PRAGMA "writable_schema" = ON` and `PRAGMA [writable_schema] = ON` currently
produce names `"\"writable_schema\""` / `"[writable_schema]"`, which fail **closed** today but will
fail **open** the moment someone adds unquoting without also fixing this. Safer belt: if the tail
contains an `=` or `(` anywhere and the name is not in the allow-list, refuse. *Uncertainty flagged
by the panel:* the parser rewrite's hot-path cost is **unmeasured**; it runs per statement, so bench
it.

### #2. `describe/2` is a completely ungated statement path, and pragmas execute at prepare time
**Severity:** High | **Category:** Security / Shard isolation | **Panels:** Multi-tenant security & shard isolation (**verified by execution**)
**Likelihood:** Certain — `describe` is reachable on both transports with no precondition | **Blast Radius:** Every stream, including `:ro` streams and streams whose token has been revoked

**Problem:** `execute/2` and `execute_sequence/2` both run `blocked_statement/1`, the `:ro` write
refusal, and the per-statement `HranaAuth.version_current?/2` revocation re-check. `describe/2`
(`lib/fathom/shard_executor.ex:783`-`798`) runs **none** of them — it goes straight to
`Connection.describe/2` -> `Sqlite3.prepare/2` (`lib/fathom/shard/connection.ex:674`). SQLite
implements several pragmas outside the VDBE, so they take effect during *prepare*, with no `step`.

VERIFIED through `ShardExecutor.describe/2` on a real shard with the tenant authorizer set:

```
before:                               writable_schema = 0, synchronous = 2
describe "PRAGMA writable_schema=ON"  -> {:ok, %Filo.Describe{is_readonly: true}}
describe "PRAGMA synchronous=OFF"     -> {:ok, %Filo.Describe{is_readonly: true}}
after:                                writable_schema = 1, synchronous = 0
```

`describe` is reachable on the HTTP pipeline and the WebSocket (`Filo.Request.handle/4`,
`%{"type" => "describe"}`), on `:ro` streams, and on streams whose token has been revoked.

**Impact:** Three separate gates voided on one request type. A `:ro` credential mutates connection
state it is scoped out of; a revoked credential holding a live socket keeps enumerating the tenant's
schema (column names, parameter counts) indefinitely — precisely the hole expert review 2026-08-20
#22 was written to close for `execute`; and `synchronous=OFF` set via `describe` silently downgrades
the durability contract for that stream's writes. It also makes finding #1 reachable **without any
parser trick**.

**Recommended Fix:** Run the same three checks at the top of `describe/2` — `version_current?/2`
first, then `blocked_statement/1`. Do **NOT** add a `:ro` write refusal to `describe` (a `:ro` client
legitimately describes SELECTs); `blocked_statement/1` is what stops the pragma. *Uncertainty flagged
by the panel:* refusing `describe` of any statement whose lead is `pragma` outright is also worth
considering, but that is a guess about client behaviour **unvalidated against django-libsql**.

### #3. A `:ro` stream on a shard with no local file gets a read-write SQLite handle
**Severity:** High | **Category:** Security / Scope escape | **Panels:** Multi-tenant security & shard isolation (**verified by execution**)
**Likelihood:** High — fires for every brand-new tenant and every shard dropped clean with nothing stored | **Blast Radius:** Complete read-only-scope escape when chained with #1: an export/analytics/BI credential writes and creates schema

**Problem:** `open_handle(path, :ro)` (`lib/fathom/shard/connection.ex:54`-`59`) tries
`Sqlite3.open(path, mode: :readonly)` and, on **any** error, falls back to a read-write handle
guarded only by `PRAGMA query_only=ON` (`:130`-`132`, `maybe_query_only/2`). The moduledoc justifies
the fallback as "the narrow case where a read-only open cannot proceed — a database whose `-wal`
needs recovery." The far more common trigger is that **the file does not exist**:
`Sqlite3.open(missing, mode: :readonly)` returns `{:error, :database_open_failed}`, and
`Fathom.Shard`'s own comment at `lib/fathom/shard.ex:1809` records that "exqlite only creates the
file on first connection open." So every brand-new tenant with no stored object, and every shard
whose local copy was `drop_clean`ed while storage holds nothing, hands a `:ro` token a read-write
handle.

VERIFIED: `ShardExecutor.open(id, {:ro, nil})` on a never-opened shard returned scope `:ro` with
`query_only = 1`; `PRAGMA main . query_only = OFF` (the bypass in finding #1, which the executor's
own gate lets through) set it to 0, and `CREATE TABLE written_by_ro(x)` then returned `:ok` on that
handle.

**Impact:** The documented "SQLite's own enforcement has no such holes" guarantee for `:ro` degrades
to the leading-keyword heuristic the fallback exists to compensate for — and chained with the pragma
bypass it is a complete read-only-scope escape.

**Recommended Fix:** Two independent changes. (1) Make the `:ro` open create-or-nothing rather than
falling back: if the readonly open fails because the file is absent, either create an empty database
first (open rw, close, reopen `mode: :readonly`) or refuse the stream with a distinct error — the
shard has no data to read anyway. (2) Keep `query_only` out of reach unconditionally: add it to a
hard deny-list checked **before** `extra_pragma_allow()`, so `:tenant_pragma_allow` cannot be
configured to re-open it. *Uncertainty flagged by the panel:* whether the WAL-recovery case the
comment names still needs the rw fallback is **unchecked**; if it does, that path should at minimum
log loudly, since it is the one place the scope rests on a defeatable pragma.

### #4. `PRAGMA schema_version` is tenant-settable — SQLite's schema cookie confused with the Postgres column
**Severity:** High | **Category:** Data Correctness (silent wrong results) | **Panels:** Multi-tenant security & shard isolation (**verified by execution**)
**Likelihood:** High — ordinary `:rw` token, no precondition | **Blast Radius:** One tenant's queries return silently wrong columns; also reachable from migration replay and the coordinator's own snapshot connections

**Problem:** `schema_version` sits in `@tenant_pragma_allow` (`lib/fathom/shard_executor.ex:1160`-`1164`),
justified by the rationale comment at `:1148`-`1155` as "fathom's own three-place version stamp."
AGENTS.md defines that stamp as `django_migrations`, `PRAGMA user_version`, and
`shards.schema_version` in Postgres — **a database column, not a SQLite pragma**. `PRAGMA
schema_version` is SQLite's internal schema cookie, which the engine compares on every statement to
decide whether a cached prepared statement must be recompiled; SQLite's own documentation says
"Misuse of this pragma can result in database corruption."

VERIFIED: with the tenant authorizer set, `PRAGMA schema_version = 999` succeeds, persists to the
file header, and a second connection reads back 999.

**Impact:** A tenant with an ordinary `:rw` token can freeze or rewind the schema cookie. That
defeats the engine half of the fix from review 2026-07-24 #17 — the executor purges its statement
cache on DDL it sees, but a schema change made on **another stream** is caught only by `prepare_v2`
recompilation, which keys on this cookie. Frozen, a cached statement keeps its pre-ALTER column list,
so `SELECT *` returns pre-ALTER columns for post-ALTER rows. Same class as the already-recorded
`Copy.migrate/4` "no such table: app_thing" incident, and reachable from the migration replay and the
coordinator's snapshot connections, not just the tenant's own.

**Recommended Fix:** Remove `schema_version` from `@tenant_pragma_allow` and correct the comment so
the next reader does not re-add it — it is not fathom's stamp, `user_version` is. `application_id` is
a header field with no engine semantics and can stay. *Uncertainty flagged by the panel:* confirm
before shipping that Django's SQLite backend never issues `PRAGMA schema_version =` — a read of
`django/db/backends/sqlite3` says it does not, **but this was not run against a real
`manage.py migrate`**.

### #5. Suspension and deletion never reach an already-open stream; the gate is per-checkout, and a checkout lasts hours
**Severity:** High | **Category:** Security / Tenant lifecycle | **Panels:** Multi-tenant security & shard isolation
**Likelihood:** Certain for any client that already had a stream open — the exact posture an abusive or compromised client is in | **Blast Radius:** "Suspend takes a tenant offline" and "delete is GDPR Article 17 erasure" are both false; on a multi-node fleet the deny never crosses nodes at all

**Problem:** The tombstone and suspension denies live in `Shards.ensure/1`
(`lib/fathom/shards.ex:649`-`665`), which runs **once per checkout**. A checkout is taken in
`ShardExecutor.open/2` and released in `close/1` — once per Hrana stream, not per statement.
`HranaAuth.version_current?/2`'s docstring (`lib/fathom/hrana_auth.ex:134`-`136`) asserts
"`Fathom.Shards.ensure/1` already re-checks the tombstone and suspension gates on every checkout, so
those two lifecycle denies did reach a live connection." That is exactly the reasoning error the same
review corrected for token revocation: AGENTS.md and this module's own comments record that "a
django-libsql stream lives for hours between requests," so per-checkout is per-**session**, not
per-request.

Two concrete sequences:

- (a) An attacker opens a WS stream on tenant `acme`; an operator suspends `acme`;
  `Tenants.suspend/1` (`lib/fathom/tenants.ex:313`-`320`) calls `Shards.drain(id, 5_000)` and
  **discards its return value**, so a stream held past the 5 s window leaves the coordinator serving,
  and the attacker reads and writes indefinitely.
- (b) On a multi-node fleet the API call lands on whichever node the control-plane LB picked;
  `Shards.drain/2` and `Shards.stop/1` are pure local-`Registry` lookups (`[] -> :ok`), so a suspend
  or a delete issued on node A never touches the coordinator on node B — node B only adds the id to
  its ETS deny set, which gates new opens. For a deleted tenant on a remote node the only stop is the
  fenced-flush self-fence, which a purely-reading stream never triggers, so **a deleted tenant's data
  stays readable through the open stream**.

**Impact:** Both lifecycle levers are ineffective against exactly the clients they exist for. The
suite does not discriminate: `test/fathom/tenants_test.exs:347` asserts only
`Shards.checkout(id) == {:error, :shard_suspended}` after suspend, i.e. the new-stream path.

**Recommended Fix:** Add the two ETS membership checks to the same per-statement `cond` in
`do_execute/2` and `execute_sequence/3` that already carries `version_current?/2` — both are O(1)
`:ets.member` off the Postgres path, the same cost argument that justified the revocation re-check.
Return the existing `FILO_TENANT_SUSPENDED` (403) / `FILO_TENANT_DELETED` (410) codes. Separately,
`Tenants.suspend/1` should not swallow `{:error, :busy}` from `drain/2` — either surface it to the
operator or escalate to `Shards.stop/1` as `purge/1` does. The cross-node coordinator problem is
already tracked as the `rebalance_commands` follow-up in `docs/component-notes.md`; the per-statement
check makes it moot for correctness, so it is the cheaper fix.

### #6. The shutdown write fence is lifted *before* the shutdown flush it exists to cover — and is not published at all on the busy self-fence path
**Severity:** High | **Category:** Data Loss | **Panels:** **TRIPLE-DETECTED** — Elixir/OTP & concurrency · Storage & durability · Distributed systems & fencing (found independently by all three)
**Likelihood:** Certain on every rolling deploy / SIGTERM / `Shards.stop/1` of a busy shard | **Blast Radius:** Every write-active shard on a draining node; ACKed writes land in no uploaded object

**Problem:** The `conns > 0` `terminate/2` clause publishes `WriteFence.fence(state.id)` at
`lib/fathom/shard.ex:1715`, with a comment stating the reason precisely: streams do not learn the
coordinator is going away until its `:DOWN` fires (after `terminate/2` returns), so without the fence
they keep committing through "a checkpoint + VACUUM INTO + PUT that has already snapshotted past
them" — "for the whole duration of checkpoint + VACUUM INTO + a full-object PUT — budgeted up to
`:shard_shutdown_ms`, and seconds at real S3 latency — live streams keep committing writes that are
neither in the snapshot we just uploaded nor … anywhere at all."

Seven lines later, at `lib/fathom/shard.ex:1722`, the same clause calls `WriteFence.forget(state.id)`
— which is a literal alias of `unfence/1` (`lib/fathom/shard/write_fence.ex:57-58`) and `:ets.delete`s
the row — and only **then**, at `lib/fathom/shard.ex:1725`, runs `flush_and_drop(state)`. The fence
therefore covers only `settle_flush_task/1`, `settle_waiters/2` and four ETS deletes, and is **down**
for the entire checkpoint + `VACUUM INTO` + full-object PUT window it exists to cover.

The mechanism itself works — `Fathom.ShardExecutor` consults `WriteFence.fenced?/1` unconditionally on
writes (`lib/fathom/shard_executor.ex:169`); it is switched off at the wrong moment.

**Separately (found by the fencing panel only, same mechanism and same one-clause fix area):** the
`lease_lost: true` clause (`lib/fathom/shard.ex:1631-1656`) documents that it "covers a self-fence
with connections STILL CHECKED OUT… which is the likely case", yet **publishes no fence at all**
before `quarantine_fenced!/1` renames the live file out from under the open fds.

**Impact:** On every rolling deploy / SIGTERM / `Shards.stop` force-stop of a busy shard, writes
committed during the shutdown upload are ACKed to the client and are in neither the uploaded object
nor — once `drop_local_unless_serving/1` takes its `conns == 0` branch, or on a failover, or on
ephemeral container disk, or when the object's etag has moved — anywhere else. On the busy
self-fence path, writes ACKed during `terminate/2` land in the renamed `.fenced.<ts>` inode and are
invisible to the tenant. Both are exactly the "acked, then not in the object" outcome the fence was
added to convert into a retryable `FILO_STALE_LEASE` 503.

**Recommended Fix:** Move `WriteFence.forget(state.id)` to **after** `flush_and_drop(state)` in the
`conns > 0` clause (between the current lines 1725 and 1726), and add a `WriteFence.fence/1` call to
the top of the `lease_lost: true` clause. Leaving the row set at the end of terminate is safe by the
clause's own argument at `lib/fathom/shard.ex:1713-1714`: `open_with_lease/8` clears the fence
unconditionally on every successful lease acquire (`lib/fathom/shard.ex:670`), so a row stranded by a
brutal-kill mid-flush is lifted by the next open — and `test/fathom/shard_kill_cleanup_test.exs:99`
already pins that. Clearing it at all is belt-and-braces.

*Note a tension between panels for the implementer:* the OTP panel wrote that "the other two
`terminate/2` clauses do not need the change (`conns == 0` has no writers; the `lease_lost` clause
never flushes)" — that statement is about **`forget` placement** and remains true. The fencing
panel's point is about a **missing `fence`** on the `lease_lost` clause, which is a different call.
Both changes are compatible; do not read the OTP sentence as a reason to skip the fencing one.

*Test:* no test pins the fence's **lifetime** today — `heartbeat_fence_test.exs` only checks arming
timing, and `shard_kill_cleanup_test.exs` only asserts a stale row is eventually cleared, which
passes both ways. The regression test must assert `WriteFence.fenced?(id)` is **true while a slow
`Storage.flush` is in flight inside `terminate/2`** — i.e. write through a stream while a coordinator
is in `terminate/2` and assert the write is refused, not ACKed.

### #7. Periodic durability flush is starved on write-active shards: `:became_dirty` restarts the flush countdown on every stream's first write
**Severity:** High | **Category:** Data Loss | **Panels:** Elixir/OTP & concurrency
**Likelihood:** High — the default django-libsql posture (`CONN_MAX_AGE=0`, one stream per request) triggers it | **Blast Radius:** Precisely the hottest, most write-active shards; RPO becomes the whole session instead of 5 s

**Problem:** `handle_cast(:became_dirty, state)` (`lib/fathom/shard.ex:1238`) unconditionally calls
`schedule_flush(state)`. For a dirty shard both `schedule_flush/1` clauses route to
`do_schedule_flush(state)` (`lib/fathom/shard.ex:3825-3851`), whose first act is `cancel_flush(state)`
— it cancels the pending `:durability_flush` timer and arms a brand-new full interval.

`ShardExecutor.signal_dirty_once/2` (`lib/fathom/shard_executor.ex:241` and `:458-467`) keys its
"already signalled" flag on the **CONNECTION** (`{__MODULE__, :dirty_signalled, conn}` in the stream
process's dictionary), and each Hrana stream is its own `Filo.Stream` process with its own connection
(one GenServer per stream, started via `DynamicSupervisor.start_child`). So the cast fires **once per
writing stream, not once per shard**. A tenant whose streams turn over faster than
`:shard_flush_interval_ms` (5 s default — django-libsql with Django's default `CONN_MAX_AGE=0` opens
a fresh connection/stream per request) resets the timer before it can ever fire.

The checkout path was written with exactly this hazard in mind — `lib/fathom/shard.ex:1179` re-arms
only `if state.flush_timer == nil`, with the comment "never per stream cycle." The `:became_dirty`
handler, added later by review #42 to lift a clean shard off the 10x slow poll, has no such guard, so
it also resets an already-fast timer.

**Impact:** The periodic durability flush — the mechanism the moduledoc says "closes that gap … the
data-loss window is bounded to the interval" — **never runs** on the shards that need it most. Those
shards flush only at idle-drop (requires `:shard_idle_ms`, 60 s default, of zero streams), at drain,
or at a clean `terminate`. On node death the RPO for a continuously busy tenant is the whole session,
not 5 s. Silent: `[:fathom, :shard, :flush, :failed]` only fires for a flush that ran, and
`flush_p50_us` / the RPO harness drive a shard from one process, so they never reproduce the stream
turnover that triggers it. No test anywhere references `became_dirty` or `signal_dirty` — grep
returns only the two `lib/` files.

**Recommended Fix:** Make `:became_dirty` an **edge** signal rather than a reschedule: only re-arm
when the timer is absent or was armed at the slow cadence. Track the multiplier in state (e.g.
`flush_timer_slow?`) and make the handler
`if state.flush_timer == nil or state.flush_timer_slow?, do: do_schedule_flush(state), else: state` —
mirroring line 1179's guard. *Uncertainty flagged by the panel:* **unrun**; the thing to verify is
that the slow→fast transition still happens on the first write of a clean served shard (the whole
point of #42), which a test asserting "N `:became_dirty` casts spaced under the interval still
produce a flush" would pin. The naive fix of dropping `cancel_flush` from `do_schedule_flush` is
**wrong** — it would leak timers everywhere else.

### #8. Legacy-mode lease renewal races the flush fence's renewal and self-fences against itself
**Severity:** High | **Category:** Data Loss | **Panels:** Elixir/OTP & concurrency
**Likelihood:** High in legacy mode — "tens of percent per tick" for a large shard, so a busy legacy-mode shard self-fences within minutes | **Blast Radius:** The shard drops itself, quarantines every un-flushed ACKed write, and emits a false split-brain alarm with no peer involved

**Problem:** In legacy mode (`acquire_gen == nil`) the coordinator has **two independent producers**
of `renew_lease` PUTs against the same cached `lock_etag`:

1. The `:renew_lease` timer (`lib/fathom/shard.ex:1500-1506`), which spawns
   `Task.async(fn -> Storage.renew_lease(id, lease, ttl) end)` using `state.lease`.
2. The durability flush task (`lib/fathom/shard.ex:1583` + `:1605-1616`), whose `Fence.check(fence_ctx)`
   takes `Fence.legacy/2` (`lib/fathom/shard/fence.ex:116-122`) and **also** calls
   `Storage.renew_lease(ctx.id, ctx.lease, ctx.ttl_ms)` with the same `state.lease`.

The flush task performs its fence first and only replies `{:fenced, verdict, updates}` after the whole
`VACUUM INTO` + full-object PUT completes, so the refreshed lease (new `lock_etag`) is held **inside
the task** and `state.lease` stays stale for the entire flush duration — seconds at real S3. Any
`:renew_lease` tick landing in that window PUTs `If-Match: <old etag>` and gets a 412.

`put_lock/3` then re-reads the lock and returns `{:error, {:held, owner}}`
(`lib/fathom/shard/storage/s3.ex:1889-1895`) where `owner` **IS this node's own owner string**, and
`renew_lease/3` maps `{:held, _}` to `{:error, :superseded}` (`:2157-2161`) without comparing the
owner or epoch to its own — the comment there ("a 412 means the lock changed under us, which can only
be another writer") is false for a node racing itself. The coordinator then treats this as a real
steal: `apply_renew_result` (`lib/fathom/shard.ex:3758-3767`) logs "lease superseded by another node;
self-fencing" and stops with `{:shutdown, :lease_lost}`, whose `terminate/2` clause runs
`quarantine_fenced!/1` — renaming the dirty local copy to `.fenced.<ts>` **WITHOUT flushing it**. The
mirror case (the flush's fence loses instead) yields `:fence_superseded` and the same stop.

**Impact:** In the degraded mode that exists so "a heartbeat outage degrades gracefully instead of
dropping shards," a dirty shard instead drops itself, quarantines every un-flushed ACKed write, and
emits a false split-brain alarm (`[:fathom, :shard, :lease, :superseded]`) — with no peer involved.
With a 10 s renew interval and a multi-second flush the collision probability per tick is tens of
percent for a large shard. The same collision is reachable **in heartbeat mode** when the `Heartbeat`
process is down: `handle_info(:revalidate_lapse, …)` runs `Fence.check` inline, which falls through to
`legacy/2`, concurrently with a flush task doing the same.

**Recommended Fix (the panel labelled this a hypothesis — unverified against a live store):** In
`S3.renew_lease/3`, disambiguate the 412 the way `acquire_lease` already does: if the re-read lock
still names our `owner` **AND** our `epoch`, our own concurrent write won — adopt the current etag and
return `{:ok, lease_with_new_etag}` rather than `:superseded` (a genuine steal always bumps the epoch,
and `owner` carries the boot incarnation, so this cannot mask a real takeover). Pair it with a
coordinator-side guard that skips the `:renew_lease` tick while `state.flush_task != nil`, since the
fence is already renewing.

**This bug is structurally invisible to `mix test`:** `Storage.Local.renew_lease/3`
(`lib/fathom/shard/storage/local.ex:790-806`) matches only on `{owner, epoch}` so two concurrent
same-lease renews both succeed, and `Fathom.Test.FaultyStorage.renew_lease/3`
(`test/support/faulty_storage.ex:96-109`) rotates the etag but never checks the incoming one — it
enforces If-Match on **release** only. **Closing that double gap is worth more than the one fix.**

### #9. The warm-cache promotion renames un-fsynced bytes onto the authoritative live path
**Severity:** High | **Category:** Data Loss | **Panels:** Storage & durability
**Likelihood:** Low per-event (needs a power loss in the window) but **the consequence is unrecoverable** | **Blast Radius:** One tenant served an empty database, then that empty database is PUT over the good stored object
**Gate:** `:warm_follower` — **OFF by default**. Less urgent than the default-path findings above, but do not treat the gate as a mitigation for anyone who has turned it on: this is the failover path the follower exists to accelerate.

**Problem:** Every other path that materializes a shard file goes through `Storage.promote_temp/2` /
`with_atomic_temp/2`, which fsync the temp before the rename. `lib/fathom/shard/storage.ex:895-903`
states why: "rename-without-data-fsync is atomic against process crash but not power loss — after a

The warm-standby 304 fast path breaks that: `promote_warm_cache/4` (`lib/fathom/shard.ex:959-967`)
fills the pull temp with a bare `File.cp/2` at `:960`, and `promote_pull/2` (`lib/fathom/shard.ex:1100`)

so only the warm path is exposed.

**Impact:** A power loss in that window can leave `<id>.db` zero-length or partial with a sidecar that

zero-length file is a valid empty SQLite database and `PRAGMA quick_check` returns `ok`**, so
`verify_snapshot/2`'s integrity gate does not fire: the tenant is served an empty database, and the
next periodic flush PUTs that empty database over the good stored object with a valid If-Match.

**Recommended Fix:** Replace `File.cp(WarmFollower.cache_path(shard_id), temp)` with
`Storage.atomic_copy(WarmFollower.cache_path(shard_id), temp)`, which copies into a sibling temp,
fsyncs, and renames — restoring the crash contract the cold path already has. The existing
inode/etag TOCTOU re-check after the copy is unaffected and should stay.

### #11. S3's `flush/5` ERASES the shard's stored lineage when `lineage == nil`; only the Local double honours the contract
**Severity:** High | **Category:** Data Loss / Data Correctness | **Panels:** **DOUBLE-DETECTED** — Storage & durability · Distributed systems & fencing (found independently)
**Likelihood:** Certain on real S3 for every flush that passes `nil` — which includes every non-replicating coordinator, every per-shard schema migration, every migration revert, every snapshot restore, and the A2 promote publish | **Blast Radius:** The lineage counter silently resets fleet-wide; a stale pre-migration replica can later outrank the migrated object
**Gate:** the counter is erased on the **default path** (a coordinator with replication off passes `nil`); the *consequence* — a stale replica winning a promotion — requires A2 shipping, which is **off by default**.

**Problem:** The `c:flush/5` callback doc (`lib/fathom/shard/storage.ex:199-200`) states the
asymmetry on purpose: "`nil` writes no lineage … the backends take `nil` as
leave-any-previous-value-alone. Erasing a shard's lineage would reintroduce exactly the reset the key
exists to prevent" and "the lineage describes ownership history and must only ever go up."

`Storage.Local` implements that — the lineage is a separate sidecar file and
`write_lineage(_shard_id, nil), do: :ok` (`lib/fathom/shard/storage/local.ex:123`) is a no-op.

`Storage.S3` **cannot**: it stores the lineage as user metadata on the object itself,
`lineage_meta_header(nil)` returns `[]` (`lib/fathom/shard/storage/s3.ex:302` and `:859-860`), and an
S3 `PUT Object` replaces the object wholesale — every `x-amz-meta-*` key not re-sent is gone. So
every `Storage.flush/3` and `flush/4` against S3 deletes `x-amz-meta-fathom-lineage`. **The two
backends implement opposite behaviours for the same argument.** This is the same failure class
already fixed for the touch path with `S3.carry_meta/1` — `carry_meta/1` was hardened to carry every
user key across a touch, but a PUT still drops what it is not explicitly told to write, and the flush
path never got the equivalent.

Callers that pass `nil`:

- `lib/fathom/shard.ex:3244` (`lineage_to_store/1`) — `lineage_to_store(:disabled) -> nil` (a
  non-replicating node's coordinator), and the `:unknown` case when the coordinator's `open_lineage/1`
  HEAD failed.
- `lib/fathom/shard/replication/promote.ex:203` — `Promote.install_and_publish/3` (the 3-arity
  `Storage.flush`).
- `lib/fathom/migrator/shard_migration.ex:578` — every per-shard schema migration (`flush_fenced/3`)
  and every migration revert.
- `lib/fathom/shard/storage/s3.ex:1201` (`restore/3`) and `:1333` (`restore_snapshot/3`) — every
  snapshot restore.

**Impact:** After any of those, `Fathom.Shard.open_lineage/1` (`lib/fathom/shard.ex:2475`) reads
`object_head` with lineage `nil` and position `nil`, so `Storage.next_lineage/1` returns 1 — the reset
the lineage counter was introduced to eliminate. Where the position stamp survives, `next_lineage/1`
falls back to `position.epoch`, which under `:disabled` is the **lock epoch** — so a shard at lineage
50 can be reseeded at 2 by one drain onto a node with replication off, or by toggling the gate. A peer
`Follower` still holding a pre-migration replica stamped at lineage N > 1 then outranks the shard's
post-migration flushes in `Promote.fresher?/2`, and a later failover promotes the stale pre-migration
replica over the migrated object — **silently rolling a tenant's schema and data back**.

**Test gap that hid it:** `test/fathom/shard/lineage_test.exs` asserts "nil LEAVES the previous
lineage in place — the asymmetry with position" against `Storage.Local` **only**; `grep lineage` over
`shard_storage_s3_test.exs` and `shard_storage_touch_meta_test.exs` returns nothing but a comment.
`Fathom.Test.FaultyStorage` delegates to `Local`, which implements the contract as written, so the gap
is structural — the contract is enforced only where it cannot fail.

**Recommended Fix:** In `S3.flush/5`, when `lineage == nil`, carry the object's existing
`x-amz-meta-fathom-lineage` forward — the cheapest correct form is to read it from the fence HEAD the
caller already has, or to make the coordinator/migrator pass the current lineage explicitly instead of
`nil`. **The position stamp being erased here is correct and must stay.**

*Uncertainty flagged by both panels — the finding is settled, the mechanism is open:* it is
**unmeasured** whether adding a HEAD to the `nil` path costs a round trip on the coordinator's hot
flush, and whether an extra HEAD per migrated shard is affordable at fleet scale. If it is not, the
alternative is to make `lineage_to_store/1` never answer `nil` for a **live-object** flush (resolve it
at open even when replication is off) and keep `nil` meaning "no object history at all" for the
migration/snapshot callers. Either way, **move the asymmetry assertion into the S3 backend's own
test** — a `carry_meta`-style pure function assertable without a store, or a
`FATHOM_S3_TEST_*` integration assertion.

### #12. `Promote.fresher?/2` compares the replica's LOCK epoch against the object's LINEAGE — two different counters
**Severity:** High | **Category:** Data Loss | **Panels:** Distributed systems & fencing
**Likelihood:** Certain from a shard's second replicating open onward | **Blast Radius:** A2 promotion goes **inert** fleet-wide — the survivor cold-opens from S3 and the replicated tail is lost, exactly as if A2 were disabled
**Gate:** A2 replication — **OFF by default**. Ranked below the default-path findings for that reason, but it silently nullifies the entire A2 feature for anyone who has enabled it.

**Problem:** The 2026-08-20 #8 fix split one number into two and only migrated one side.

- The **object's** position stamp now carries the lineage: `open_lineage/1` (`lib/fathom/shard.ex:2475`)
  -> `Storage.next_lineage/1` -> `max(stored_lineage, stored_position.epoch) + 1`, monotonic across a
  release. Stamped by `stamp_epoch/1` (`lib/fathom/shard.ex:3230`).
- The **replica's** `epoch` still comes from `Session.with_epoch/1`
  (`lib/fathom/shard/replication/session.ex:450`) -> `Fathom.Shard.epoch/1`
  (`lib/fathom/shard.ex:239` / `:1196`) -> `state.lease.epoch` — the **lock** epoch, which
  `release_lease` resets to **1** on every clean idle-drop, drain and handoff.

`fresher?/2` (`lib/fathom/shard/replication/promote.ex:108`, and `:106`) then compares
`{lock_epoch, wal_gen, next_offset} > {lineage, wal_gen, offset}` as if they were one scale.
`Recovery.rank/1` (`lib/fathom/shard/replication/recovery.ex:145`) inherits it.

**Impact:** The lineage increments once per replicating open and never resets, while the lock epoch is
1 on any shard whose last ownership ended cleanly. So from a shard's **second** replicating open
onward, `fresher?/2` is false for every replica regardless of how far ahead it actually is —
`promote_on_open` and `Recovery.best_replica/3` both go inert, the survivor cold-opens from S3, and
the tail is lost. Same silent shape as "the touch erased the stamp": nothing fails, nothing logs, the
shard recovers to its last flush exactly as if A2 were disabled.

**The unsafe direction is reachable too:** on a mixed / gate-toggled fleet, a flush with
`lineage: :disabled` stamps the **lock epoch** into the position slot, so a replica stranded at a
higher lock epoch from an earlier crash-steal generation can **outrank a newer object** — the hazard
`lib/fathom/shard/storage.ex:96-117` names and still describes as unfixed.

**Test gap that hid it:** every promote-on-open test hand-installs the replica at the object's own
number — `promote_on_open_test.exs:109` seeds `Follower.seed(Follower, id, position.epoch, …)` with
`position.epoch = stamp.epoch` (`:182`, `:222`, `:326`, `:340`, `:354`, `:368`, `:403`, `:429`),
forcing the two scales to agree. The one test using a real shipped position
(`ownership_cycle_position_test.exs:227`) lands on `stamp == nil` (its own comment at `:243` says so),
so the `refute` passes **vacuously**. Nothing anywhere lets a real push-derived epoch meet a real
lineage stamp.

**Recommended Fix:** Ship the **lineage**, not the lock epoch, as the replica's ordering key — add the
coordinator's `lineage` to `Push`/`SeedBegin` as a separate field and have `FollowerLog` record it,
keeping `epoch` for the fencing check (`decide/2`'s `pushed < epoch`) where the lock epoch is correct.
*Uncertainty flagged by the panel:* a wire field means the `@version 2` additive-frame argument has to
be **re-made** for a field the decoder must tolerate missing from an older peer. A cheaper interim
that is **NOT a fix** but stops the wrong-direction case: assert in `fresher?/2` that both sides came
from the same counter and answer `false` otherwise. Add a test driving acquire -> write -> real
`Session.commit` -> real flush -> compare, with `assert is_integer(stamp)` as a **precondition** so it
cannot go vacuous.

### #14. `attach_transform/2` on an already-rolled-out version silently splits the fleet
**Severity:** High | **Category:** Data Correctness (silent divergence) | **Panels:** Migration engine & control plane

**Problem:** `attach_transform(version, module)` (`lib/fathom/migrator.ex:202-219`) checks that the

### #15. Yanking a middle version quarantines the entire cold tail below it
**Severity:** High | **Category:** Reliability | **Panels:** Migration engine & control plane

`warm? == true`, `fork_evidence` returns `:match`, and the coordinator serves the corrupt database to
the tenant instead of cold-pulling the last-good stored object.

**Recommended Fix:** Have `verify_snapshot/2` return a **distinct tag** (e.g.

before releasing when it sees that tag — safe there, because this is the drop path where the
coordinator is terminating. **Do NOT make `verify_snapshot/2` quarantine directly**; that is the
live-serving data-loss path review #2 closed. Assert the precondition in the test
(`assert {:error, _} = verify_integrity(path)`) so a fixture that corrupts nothing fails loudly.

### #18. `recheck_before_put/1` turns a heartbeat-process outage into a crashing flush instead of the designed legacy degradation
**Severity:** Medium | **Category:** Reliability / Data Loss | **Panels:** Distributed systems & fencing
**Likelihood:** Low-to-moderate — the supervisor normally restarts the heartbeat within milliseconds, which bounds it in the common case (hence Medium, not High) | **Blast Radius:** For as long as the heartbeat is down, the shard stays dirty, ACKs writes, and never flushes — unbounded RPO on a node that looks healthy

**Problem:** Every other caller of `Heartbeat.valid_for_write?/1` and `Heartbeat.generation/0` wraps
the call so a dead heartbeat process degrades gracefully — `Fence.heartbeat_valid/2` catches `:exit`
and returns `:legacy`, `Fence.generation/1` catches `:exit` and returns `nil`
(`lib/fathom/shard/fence.ex:72-76`). `recheck_before_put/1` (`lib/fathom/shard.ex:3350-3361`), added
later by review 2026-08-01 #28, calls `Heartbeat.valid_for_write?(gen)` **bare**. When the heartbeat
process is down the named ETS status table dies with it, `status/0` answers `:down`, and the fallback
is `GenServer.call(__MODULE__, …)` (`lib/fathom/shard/heartbeat.ex:124-138`), which exits `:noproc`.

**Impact:** A coordinator opened in heartbeat mode keeps `acquire_gen` as an integer for its whole
life (`Fence.revalidate/2` deliberately preserves it — see `lib/fathom/shard/fence.ex:88-108`). So
while the heartbeat is down, `Fence.check/2` correctly degrades to `:legacy` and renews the lock, and
**then the flush task dies inside `recheck_before_put/1`**. The result lands on
`handle_info({:DOWN, ref, …}, %{flush_task: …})` at `lib/fathom/shard.ex:1358`, which records a
transient failure and reschedules — but never reaches `note_not_valid/1`, so the write
circuit-breaker cannot arm on that path either. The entire point of the `:legacy` branch is the case
where the heartbeat does **not** come back quickly.

**Recommended Fix:** Wrap the call the way `Fence` does — either `catch :exit, _ -> :ok` (proceed; the
legacy renew PUT that `Fence.check/2` just performed is the ownership proof in that mode) or
`-> {:error, :ownership_unconfirmed_before_put}` to fail closed. *Uncertainty flagged by the panel:*
the panel leans `:ok`, because `Fence.check/2` already renewed the lock in legacy mode and failing
closed would stop durability for a reason the fence did not object to — **but that is a judgement
between two safe directions**, settled by a test that kills `Heartbeat` under a heartbeat-mode
coordinator and asserts the next durability flush still uploads.

### #19. The write circuit-breaker's clock starts at the first *dirty* flush tick, not when liveness was actually lost
**Severity:** Medium | **Category:** Data Loss | **Panels:** Distributed systems & fencing
**Likelihood:** Moderate — needs a read-mostly shard on a node cut from object storage, then a write | **Blast Radius:** Every write in the trailing window is ACKed on a node provably stealable for minutes, and is quarantined on partition-heal

**Problem:** `not_valid_since` is initialised as `state.not_valid_since || now` inside
`note_not_valid/1` (`lib/fathom/shard.ex:3030-3051`), and `note_not_valid/1` is reachable from exactly
one place: the `:fence_skip` branch of the durability-flush result (`lib/fathom/shard.ex:1335-1342`).
`handle_info(:durability_flush, …)` short-circuits at `not unflushed?(state)`
(`lib/fathom/shard.ex:1536`) **before any fence check**, and `do_schedule_flush/2`
(`lib/fathom/shard.ex:3833-3851`) arms no timer at all when `:shard_flush_interval_ms` is non-positive.
So the "how long have I been not-valid" clock only begins once the shard is **dirty and a flush
interval has elapsed**.

**Impact:** A read-only-then-written shard on a node cut from object storage: the heartbeat lapses,
and after `ttl + steal_margin` a peer may legitimately steal. The cut node has no dirty shard, so
nothing observes `:not_valid`. Minutes later a client writes: `WriteFence.fenced?/1` is false, the
write is ACKed, `not_valid_since` is set to **now**, and the breaker does not arm for a further
`margin + steal_margin`. `docs/single-writer.md` states the breaker "collapses the loss window back to
~`ttl + steal_margin`"; on this path the window is `margin + steal_margin` measured from the **first
write**, unbounded relative to when ownership was actually lost.

**Recommended Fix:** Derive `since` from the heartbeat's own published deadline rather than the first
observed `:fence_skip` — `Heartbeat`'s ETS row already carries `mono_deadline_ms` and `margin_ms`, so
`since = min(state.not_valid_since || now, deadline - margin)` is a lock-free read with no extra I/O
and no new timer. *Uncertainty flagged by the panel:* that expression is only correct while the
deadline belongs to the **current lapse episode**, so it likely needs gating on the generation the
coordinator recorded at acquire, and it is **untraced** whether a stale `deadline` can survive a
heartbeat restart in a way that would arm the fence too early. The alternative — consulting
`valid_for_write?/1` on the checkout/execute path — was already **rejected in the design** as a
hot-path cost.

### #20. `NOVEL_SHARD_RATE=0` crash-loops the admission limiter and can take the data plane down
**Severity:** Medium | **Category:** Security (admission-control bypass → remotely-triggerable outage) / Reliability | **Panels:** Multi-tenant security & shard isolation
**Likelihood:** Low (requires a misconfiguration) but the misconfiguration is the **natural operator spelling** of "disabled" | **Blast Radius:** Node-wide data-plane outage, triggerable by 31 novel-shard requests in 10 seconds

**Problem:** `rate/0` (`lib/fathom/shards/novel_limiter.ex:90`-`95`) is a two-clause `case` —
`nil -> 1_000_000` and `rate when is_number(rate) and rate > 0 -> rate` — with **no catch-all**.
`config/runtime.exs:975` accepts whatever `String.to_integer/1` returns from `NOVEL_SHARD_RATE`, and
the documentation says "unset = off", so `NOVEL_SHARD_RATE=0` is a natural operator spelling of
"disabled". With `0`, `Shards.start_if_capacity/1` (`lib/fathom/shards.ex:693` and `:967`) still sets
`rate_gated?` (it tests `!= nil`), so every novel-shard open calls `NovelLimiter.allow/2`,
`handle_call(:allow, …)` raises `CaseClauseError`, and the GenServer dies. `limiter_refused?/1`
catches the exit and fails closed, so every novel shard 429s — but the process is restarted by the
plane supervisor on each call, and that supervisor runs `max_restarts: 30` in `max_seconds: 10`
(`lib/fathom/application.ex:569` and `:138`-`141`).

**Impact:** 31 novel-shard requests in 10 seconds — precisely the signup spray this limiter exists to
absorb — exhaust the supervisor's restart intensity and **bring down the data plane**, converting a
silent misconfiguration into a remotely-triggerable node outage. Before that point, every new tenant
is refused with no diagnosable signal beyond a `CaseClauseError` in the log.

**Recommended Fix:** Add a catch-all clause to `rate/0` treating any non-positive or non-numeric value
as "off" (`1_000_000`) and logging once, and make `Shards.start_if_capacity/1` gate on `rate > 0`
rather than `!= nil` so a zero rate costs nothing on the cold path. *Alternative the panel considered
and rejected:* rejecting `0` at boot in `runtime.exs` — the lenient reading is preferable, because `0`
unambiguously means "no rate limiting", and a boot refusal turns a benign typo into a deploy failure.

### #21. The bounded flush re-kick's backoff is dead code — the enclosing `schedule_flush/1` overwrites it with a full interval

### #22. The retained backup is labelled with the directory's version but holds the file's bytes
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Migration engine & control plane
**Likelihood:** Low — requires stamp skew (a flush landing while `cutover_with_retirement/3`'s Postgres transaction failed, or a Postgres PITR) | **Blast Radius:** A later revert produces a three-way divergence the operator believes was undone

**Problem:** `do_run/3` treats the file as authoritative — `current = live_version(old)`

switching changes which object is retired — check that the orphaned `@prev` still gets collected by
the S3 lifecycle backstop.

### #24. Inline `Fence.check` on the lapse-revalidation path is the last blocking storage call left in the coordinator process
**Severity:** Medium | **Category:** Performance (cascading failure) / Reliability | **Panels:** Elixir/OTP & concurrency
**Likelihood:** Certain on any lapse broadcast at documented density | **Blast Radius:** 5k–15k storage round-trips per second through the one shared Finch pool, each blocking its own coordinator, fired exactly when the node has just proven unhealthy — landing on the survivor absorbing failover traffic

**Problem:** Reviews #27, #29 and #18 systematically moved every `Storage` call out of the
coordinator's own process — the flush, the 412-reconcile, the flush fence, and the legacy renew all
run in monitored tasks. `handle_info(:revalidate_lapse, state)` (`lib/fathom/shard.ex:1458-1486`,
alongside `handle_info({:heartbeat_lapsed, gen}, …)`) still calls `Fence.check(fence_ctx(state))`

`:revalidate` (the generation moved), which routes to `Fence.revalidate/2` -> `Storage.check_lease/2`

second.

already fixed: `:checkout` queues behind the RTT (p99 cold-open), and `Fathom.Shards.evict/2`'s 2 s
probe budget expires against a merely-blocked coordinator, which is review #34's mailbox-leak trigger.
The cost lands on the survivor absorbing failover traffic.

**Recommended Fix:** Run the revalidation in the same monitored-task shape the flush fence uses
(`fenced_flush/2`), applying the resulting `updates` in a reply handler, and reserve a
`FlushGate`-style slot (or scale `lapse_revalidate_jitter_ms` off `Registry.count(Fathom.ShardRegistry)`)
so the fan-out is bounded by concurrency rather than by phase alone. *Uncertainty flagged by the
panel:* **unmeasured**; the cheapest falsifying experiment is to force a lapse broadcast on a rig node
with a few thousand open coordinators and watch `dir_resolve` / `hrana_open` p99 during the jitter
window.
