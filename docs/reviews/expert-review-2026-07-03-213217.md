# Fathom Expert Panel Review (Round 2 — fix-regression re-audit)

**Date:** 2026-07-03
**Panels:** Elixir/OTP & concurrency; Storage & durability; Distributed systems & fencing; Multi-tenant security & shard isolation; Migration engine & control plane
**Methodology:** Re-audit of the 39 first-round fixes → 5 domains (3 run twice) → unified ranking
**Focus:** Did the fixes introduce new bugs? (fixes that are themselves broken are weighted up)

## Project Profile

- **Type:** multi-tenant sharded data platform (SQLite-per-shard, Hrana, S3-bottomless)
- **Commit reviewed:** 3dcf07b
- **Total Findings:** 37 unique (from 38 provisional candidates across 8 panel reports; round 1 found 41, all fixed)
- **Headline:** The dangerous pattern this round is **fixes that pass the Local test-double but are silently inert on the real S3 backend** — C1 (retry appends a corrupt body that the per-attempt MD5 still certifies), C2 (the `#` incarnation nonce is stripped as a URI fragment), H3 (a single-PUT self-copy yields the *same* MD5-etag so the #3 steal fence never rotates), H5 (the migrator flushes unconditionally, bypassing the fence entirely), and H6 (a "200 OK with `<Error>` body" CopyObject is read as success). Each means a **known, previously-ranked risk is not actually mitigated in production**, while the Local backend and every Local-driven regression test go green. The connective tissue is **L8**: the Local double runs the conditional data-flush and the lock read *outside* the per-shard mutex and still uses a truncating lock write, so the very tests written to prove the etag-fence fixes can pass or flake without exercising the race. The second theme is the **fenced-flush / drop-local machinery over-reacting to benign S3 signals** (H1, H2, H4, H7–H9, M1, M5, M7, M8, M12) — a lost-but-applied PUT, a killed settle task, or a torn sidecar makes a coordinator self-fence off a shard it legitimately owns and `drop_local` acknowledged, un-uploaded writes *unrecoverably*.

## Ranked Findings

### #1. Streaming download + Req default retry appends the retry body after a partial first attempt; the per-attempt MD5 certifies the corrupt result
**Severity:** Critical | **Category:** Data Loss / Data Correctness (silent durable corruption) | **Panels:** Storage ×2 (both, independently verified against deps/req 0.6.2)
**Likelihood:** High (routine S3 idle-conn reset mid-body; `retry: :safe_transient` is Req's default and is left on) | **Blast Radius:** Any shard pulled during a dropped connection; propagates to warm-follower caches | **Regresses:** #20 (streaming rewrite) / #37 (integrity check)

**Problem:** `download/4` (lib/fathom/shard/storage/s3.ex ~279-326) opens the temp fd once, then calls `Req.get(..., into: into)` with Req's default `retry: :safe_transient` still on (deps/req/lib/req/steps.ex:2336-2347, finch.ex:88-124). A `Req.TransportError{reason: :closed|:timeout}` mid-200-body re-runs the whole request against the **same still-open fd**, so the retry's body is appended after the first attempt's partial bytes. Each retry builds a fresh `Req.Response`, so `resp.private[:fathom_md5]` restarts empty and the digest covers only the **final** attempt's chunks — it matches the etag and `verify_md5` passes on a file of `partial₁ ++ full₂`. The MD5 is never re-read from the file, so the divergence is invisible. The old buffer-whole-body path was retry-safe; this defeats the #37 integrity check for exactly the torn-transfer case it was built for.

**Impact:** One dropped connection installs a corrupt oversized SQLite file that passes checksum, is fsynced + promoted, served, marked warm-dirty, and eventually flushed back as the durable object with a valid If-Match. A warm-follower cache poisoned this way passes the H2 304 freshness check and is promoted at failover. **Local double never exercises this** (no retry-on-partial path).

**Recommended Fix:** `retry: false` on downloads and retry the whole `download/4` with a fresh temp at the caller; OR on the first chunk of each 200 (`resp.private[:fathom_md5] == nil`) `:file.position(fd, 0)` + `:file.truncate(fd)` and reset the hash. **Test gap:** add a `req_plug`/`Req.Test` stub that half-streams then errors once, asserting the promoted file's on-disk MD5.

### #2. A 412 on the conditional data PUT is unconditionally read as "a stealer flushed" → self-fence + `drop_local`, destroying acknowledged post-snapshot writes unrecoverably
**Severity:** High | **Category:** Data Loss (unrecoverable) | **Panels:** Storage ×2 (settle-task variant) + OTP ×2 — **4-panel convergence**
**Likelihood:** High (fires on slow-S3 rolling-deploy shutdowns — the exact scenario the machinery targets) | **Blast Radius:** Every write after the last snapshot on the affected shard | **Regresses:** #27 (off-process flush / settle) × #5 (drop-flush durability)

**Problem:** A 412 can come from **our own** earlier PUT that landed server-side while the response was lost (Req transport timeout after body sent — routine S3), or from `settle_flush_task`'s `Task.shutdown` killing a task whose fully-transmitted PUT lands anyway (shard.ex:1076-1087). In both, `state.etag` is never advanced (shard.ex:591-593 keeps the stale etag on transient error), so the next If-Match PUT deterministically 412s → `{:error, :superseded}` → self-fence. The lease_lost / `:superseded` terminate branches then `drop_local` the db/wal/shm (shard.ex:583-586, :765-773, :862-869) — even though the heartbeat is valid and **no steal occurred**, and the local copy holds acknowledged post-snapshot writes absent from the object. `settle_flush_task`'s comment ("still dirty ⇒ drop-flush uploads everything") is falsified by the stale fence etag.

**Impact:** A single lost-but-applied PUT response permanently destroys every write after that snapshot and self-fences the coordinator off a shard it legitimately owns.

**Recommended Fix:** On a 412 (or before retrying after a transient flush error) disambiguate: compute the attempted snapshot's MD5 and HEAD the object etag — a match means "our own PUT landed"; adopt the etag and advance the watermark instead of self-fencing. At minimum, change the drop-on-`:superseded` branches to **keep** the local copy (the #1 quarantine machinery then arbitrates recoverably at next open); `drop_local` is unrecoverable. **Test gap:** a flush task that outlives settle with a landed PUT.

### #3. The S3 heartbeat object key silently drops the incarnation nonce (`#` parsed as a URI fragment) — #6 boot-scoped identity is a no-op on S3
**Severity:** Critical | **Category:** Split-brain / failure-detector identity (fencing) | **Panels:** Distributed ×2 (both, independently verified Req/URI.parse behavior)
**Likelihood:** High (every crash-restart on S3) | **Blast Radius:** Every shard the node held at crash; fleet-wide steal-back wedge | **Regresses:** #6 (boot-scoped incarnation identity, commit 35073ab)

**Problem:** `heartbeat_path(owner)` builds `prefix() <> "heartbeats/" <> owner` (s3.ex:668) where `owner` is `"#{node()}##{incarnation()}"` (heartbeat.ex:52). Req parses the URL with `URI.parse`; `#` delimits a fragment and is never transmitted, so `renew`/`read`/`clear` for **every** incarnation of a node name collide on `heartbeats/<node>` with the nonce stripped. Compounding: `owner_live?` (s3.ex:481-495) never checks `hb.owner == other`. The Local backend uses the owner as a filename where `#` is legal, so the whole suite (incl. cluster tests) passes while prod S3 is broken.

**Impact:** (a) **Permanent unavailability** — after a crash-restart the new incarnation's own renewals keep the shared object fresh, so `owner_live?("node#OLD")` returns `:live` forever; the node can never steal back its dead predecessor's locks, and every shard held at crash is wedged. (b) The exact #6 guarantee ("a lingering same-name zombie renews its *own* per-incarnation object") is void — a zombie pod is shielded by the successor's heartbeat, re-enabling zombie double-write. (c) `clear_previous_incarnation` deletes the **shared** object, transiently killing the current node's own liveness. (Migrator `migrator@node@token` owners have no `#`, unaffected.)

**Recommended Fix:** Percent-encode the owner in `heartbeat_path` (`URI.encode_www_form/1`) on write/read/clear (one choke point); mirror in Local for parity; add `hb.owner == other` verification in `owner_live?` as defense-in-depth. **Test gap:** a `Req.Test` stub asserting the request path carries the encoded nonce.

### #4. Steal-time `touch_object` self-copy produces the SAME etag on MD5-etag stores → the #3 zombie-flush fence is a no-op in production
**Severity:** High | **Category:** Data Loss / Fencing (double-writer) | **Panels:** Storage (self-copy-same-etag) + Distributed (laundering)
**Likelihood:** High (deterministic — every single-PUT object's etag *is* its content MD5) | **Blast Radius:** Any steal of a stalled owner; the whole #3 fence | **Regresses:** #3 (steal-touch zombie-flush fence, commit 554e628)

**Problem:** For a non-multipart, non-KMS object the S3 etag **is** the content MD5, deterministic in the bytes. A CopyObject self-copy of identical bytes (even with `x-amz-metadata-directive: REPLACE`) produces the **same** etag on AWS S3 (SSE-S3/plaintext) and MinIO (s3.ex:194-227). Fathom uploads exclusively via single PUTs (`@max_single_put` guard) — exactly the MD5-etag class — so the steal-time etag invalidation #3 relies on does not happen. The test (test/fathom/shard/storage/s3_steal_touch_test.exs:60-73) hand-returns a changed etag, proving only request *shape*, not that the etag actually rotates.

**Impact:** The zombie-flush hole #3 was meant to close is **still open on real S3**: the stalled old owner's late If-Match PUT still lands after the stealer's pull; the new owner serves a copy missing acknowledged writes and self-fences away its own first flush. Works only under SSE-KMS/SSE-C, which nothing requires or verifies.

**Recommended Fix:** Force a genuinely new etag — a multipart copy (UploadPartCopy + Complete; multipart etags are `hash-N` shaped, never MD5), OR maintain a separate generation/lineage object the flush fence If-Matches and bumps on steal. At minimum, extend `verify_conditional_writes!` to probe that a self-copy actually changes the etag on the configured store and refuse boot / alarm when it doesn't.

### #5. The migrator's data flush is UNCONDITIONAL (`Storage.flush/2`), bypassing the etag fence the steal-touch depends on
**Severity:** High | **Category:** Data Loss / Fencing | **Panels:** Distributed
**Likelihood:** Medium (migrator pause between fence and PUT under load) | **Blast Radius:** The stealing coordinator's object, with zero error signal | **Regresses:** #3 (steal-touch fence — migrator never evaluates If-Match)

**Problem:** The #3 steal-touch only makes a superseded writer's late PUT 412 for `flush/3` (etag-conditional) callers. The migrator fences with a read-only `check_lease`, then does an **unconditional** PUT: `fence(lease)` then `Storage.flush(shard_id, new)` (shard_migration.ex:276-277, 2-arity, no conditional headers); the restore path (s3.ex:363-365) is also unconditional. The fence-to-PUT gap is unbounded under a pause: migrator passes `fence/2`, stalls, its lease expires (the renewer loop merely stops, it does not fence the PUT), a coordinator steals + touches + serves + flushes… then the zombie migrator's unconditional PUT lands anyway, replacing the new owner's object with a migrated copy of the **old** lineage.

**Impact:** Acknowledged-write loss for the stealing coordinator with **zero error signal** (every request returned 2xx) — worse than the coordinator-zombie case, which at least 412s to self-fence on.

**Recommended Fix:** Have `pull_live` keep the object etag it already receives and discards (shard_migration.ex:298) and use `Storage.flush/3` with If-Match, aborting on `:superseded`. Make `restore/2` conditional the same way.

### #6. Warm-takeover adopts the post-touch etag without verifying the touch's SOURCE lineage → a genuine fork is laundered into a silent clobber with a valid If-Match
**Severity:** High | **Category:** Data Loss (unrecoverable, double-write past fence) | **Panels:** Distributed ×2
**Likelihood:** Medium (same-machine fast restart with a crash-time in-flight flush) | **Blast Radius:** The stolen shard's acknowledged durable writes | **Regresses:** #1 (fork quarantine) / #3 (steal-touch)

**Problem:** The warm branch (`{:ok, current} when warm? -> write_etag_sidecar(path, current)`, shard.ex:313-315) assumes any etag change since the provenance HEAD is "our own touch, moved no bytes." But if the dead prior owner's in-flight fenced flush lands between `quarantined_fork?`'s HEAD (s3.ex:203) and the steal's touch (s3.ex:200-227, incl. its 412-retry that re-adopts an intervening write), the touched object **contains the zombie's acknowledged durable writes** while the local warm file is a diverged lineage. The warm branch stamps the local file's sidecar with the new etag (forged provenance); the next flush If-Matches successfully and overwrites the zombie's durable flush. `revalidate_takeover` also uses a separate HEAD instead of the touch's own returned etag, widening the window. The cold path re-pulls and is safe; only warm keeps old bytes under a new etag.

**Impact:** Silent loss of acknowledged, already-durable writes on same-machine fast restart with a crash-time in-flight flush — the correct outcome per #1 is quarantine.

**Recommended Fix:** `touch_object` returns the pre-copy source etag it If-Matched; thread it into the lease. In `revalidate_takeover`, adopt the post-touch etag for a warm file **only if** `pre_touch == etag0` (local provenance); else quarantine + re-pull. Removes the extra HEAD and closes the laundering window.

### #7. Steal-touch 404 branch: on a never-flushed shard the zombie's `If-None-Match: *` flush CREATES the object, then the stealer self-fences and discards its own acknowledged writes
**Severity:** High | **Category:** Data Loss / Fencing (brand-new-shard path) | **Panels:** Distributed
**Likelihood:** Medium (steal of a created-but-never-flushed shard) | **Blast Radius:** All post-steal writes on a new shard | **Regresses:** #3 (steal-touch 404 branch)

**Problem:** The 404 comment (s3.ex:196-198) claims "nothing a zombie flush could clobber that a nil-etag fence doesn't refuse" — wrong direction. The zombie's fence for a brand-new shard is `If-None-Match: *`, which **succeeds precisely when no object exists**. Trace: shard S created on A, never flushed; A passes Fence.check, spawns a flush task, stalls > TTL+margin; B steals, `touch_object` sees 404 and no-ops (s3.ex:203-205), B serves and accepts writes with `state.etag == nil`; A unpauses and its `If-None-Match:*` PUT **creates** the object with A's lineage; B's first flush (`etag: nil` → `If-None-Match:*`) 412s → self-fence → lease_lost terminate drops B's local copy without flushing (shard.ex:584-586, :765-774).

**Impact:** B's acknowledged post-steal writes are deleted; the store durably holds the zombie's pre-steal lineage — the double-writer clobber on the brand-new-shard path.

**Recommended Fix:** On the 404 branch, create a fence placeholder (`If-None-Match:*` sentinel) threaded into the takeover lease so the zombie's create-only PUT 412s; teach revalidate/pull to recognize the sentinel as brand-new. OR treat a 412-on-`If-None-Match` as "revalidate lock; if still ours, retry with current etag" instead of unconditional self-fence.

### #8. CopyObject's "200 OK with `<Error>` body" is treated as success: steal-touch, retain, and restore can silently no-op; no 5 GB copy guard
**Severity:** High | **Category:** Data Loss / Reliability / Fencing | **Panels:** Storage
**Likelihood:** Medium (CopyObject failure after headers sent; any object > 5 GB) | **Blast Radius:** The steal fence and the migration revert backup | **Regresses:** #3 (steal-touch) + the revert retain/restore backup

**Problem:** AWS S3 returns 200 OK then streams an `<Error>` XML body when CopyObject fails after headers are sent. Both helpers match `{:ok, %{status: s}} when s in 200..299 -> :ok` without inspecting the body (`touch_object` s3.ex:218; `copy_object` s3.ex:378-386). A failed-but-"200" touch → data etag **not** rotated → the whole #3 fence evaporates. A failed-but-"200" retain → the pre-migration backup doesn't exist → revert restores nothing. Separately, CopyObject caps at 5 GB/request: `flush` got a guard but touch/retain/restore hard-fail (or 200-with-error) past 5 GB with no multipart-copy path.

**Impact:** The single-writer guarantee and the migration revert backup both hinge on these copies happening; a silent no-op is split-brain / lost-backup with zero signal.

**Recommended Fix:** Parse the copy response body — require `<CopyObjectResult>`/`<ETag>`, treat `<Error>` as failure (touch already fails closed on error, restoring the fence). Add the 5 GB guard (or multipart copy) to all three copy sites. **Test gap:** a stub returning 200 + `<Error>`.

### #9. Multi-step migrations skip intermediate versions: a shard 2+ behind jumps straight to HEAD applying only HEAD's statements
**Severity:** Critical | **Category:** Data Correctness (silent per-shard schema corruption) | **Panels:** Migration (latent, not fix-introduced, surfaced now)
**Likelihood:** High (routine — one fleet version per Django migration txn; cold tail lags multiple) | **Blast Radius:** Fleet-wide, every laggard 2+ behind; unrecoverable if a middle version is yanked | **Regresses:** latent/new (surfaced by this audit, not introduced by a fix)

**Problem:** `do_run` fetches only `statements(target)` and stamps `user_version = target` (shard_migration.ex:242-247); `rollout`/`lazy_migrate` enqueue laggards straight to HEAD (migrator.ex:126-136; copy.ex:21-30). Capture records one fleet version per Django migration transaction (a single `manage.py migrate` of 3 migrations = 3 versions), so a cold-tail shard 2+ behind is routine — it jumps v3→v6 applying only v6's DDL, silently missing v4/v5 CREATE TABLE/ALTER and their `django_migrations` rows, while directory and `user_version` claim HEAD. All migrator tests are single-step v1→v2.

**Impact:** Silent per-shard schema corruption at fleet scale; shards stamped HEAD missing intermediate DDL; later replays fail/half-apply; invisible because all three version stamps agree. Yanking a middle version makes it unrecoverable.

**Recommended Fix:** In `do_run` replay the chain `(current+1)..target`, erroring if any intermediate is missing/yanked. **Test gap:** a v1→v3 two-release test asserting both versions' DDL landed.

**Placement note:** ranked at #9 (above the data-loss medium tier) because its likelihood × blast radius — every multi-step laggard, fleet-wide, unrecoverable when a middle version is yanked — dominates the narrower steal-timing races below it, despite being "correctness" rather than "loss."

### #10. Capture wedge: `head/0` excludes yanked releases but `Capture.record/1` allocates `head()+1`, colliding on the unique index forever after any yank
**Severity:** Critical | **Category:** Data Correctness / Fleet-state (control plane) | **Panels:** Migration
**Likelihood:** High (any fleet revert yanks the from-version by default) | **Blast Radius:** All future fleet schema capture (control-plane-wide); recoverable via DB surgery | **Regresses:** reintroduces #19 (template/fleet schema fork) via the revert-yank path

**Problem:** `revert/3` yanks the from-version by default. The yanked row still occupies its version number, but `head/0` (= `max(version) where not yanked`, migrator.ex:62-64) no longer counts it — so the next `record/1` computes `Migrator.head() + 1` = a version that permanently collides on `unique_index(:shard_migrations, [:version])` (capture.ex:159-179). `release/3` → `{:error, changeset}`, `stash_pending` queues it, the 5 s retry recomputes the same colliding number forever; `drain_pending` stops at the first failure so every later capture also wedges — the pending queue grows unbounded and the template schema forks from fleet schema (the exact #19 failure).

**Impact:** After the first fleet revert, schema capture is silently and permanently broken; no new fleet version can be recorded without manual DB surgery.

**Recommended Fix:** Allocate version numbers from `max(version)` **including** yanked rows (a dedicated `next_version/0`); keep `head/0`'s yank-exclusion for rollout targeting only. A yanked version is a tombstone, not a free slot. **Test:** yank HEAD, capture, assert it records at `yanked+1`.

### #11. `:write_counter_reset` leaves `flush_pending` stale; combined with an in-flight off-process flush, the shard reads clean and `drop_clean` deletes un-uploaded writes
**Severity:** High | **Category:** Data Loss (interaction of #14 × #27) | **Panels:** OTP ×2
**Likelihood:** Low-Medium (WriteCounter restart while a flush task is in flight) | **Blast Radius:** Up to ~1000 acknowledged writes on a busy shard | **Regresses:** #14 (write-gated dirty flag) × #27 (off-process flush window)

**Problem:** The reset handler clears `flushed_through` (→ `-1`) but not `flush_pending` (shard.ex:642-644). If a flush task is in flight when WriteCounter restarts, the ordering "task launched → reset (`-1`) → task reply" ends with `flushed_through: state.flush_pending` (shard.ex:575-579) — a watermark from the **old dead table** (e.g. 1000) while the fresh table restarts near 0. `unflushed?` (`count > flushed_through`) then reads clean until ~1000 new writes; durability flushes skip; idle stop takes `drop_clean` — local copy deleted without upload. `settle_flush_task` has the identical stale-restore on terminate (shard.ex:1082). The #14 test has no flush in flight, so it misses this.

**Impact:** Silent loss of acknowledged writes on a busy shard whenever WriteCounter restarts while a flush task is in flight.

**Recommended Fix:** Reset handler also sets `flush_pending: -1` (or `-1` iff a task is in flight). **Better** (also fixes the terminate/message-cannot-reach-terminating-process variant): make `unflushed?` compare a WriteCounter generation captured at watermark time vs `:persistent_term.get({WriteCounter, :generation})`; any mismatch ⇒ dirty. **Test gap:** kill WriteCounter while a flush task is parked, assert still dirty after settle.

### #12. Sidecar torn-to-EMPTY defeats fork quarantine → legacy adopt-current clobbers the newer lineage
**Severity:** Medium | **Category:** Data Loss (crash-consistency; hole in the #1 fix's own safe-direction argument) | **Panels:** Storage
**Likelihood:** Medium (power loss / crash mid-`File.write` — ext4 delalloc / APFS classically yield a 0-length file) | **Blast Radius:** A stolen-and-diverged shard's newer durable lineage | **Regresses:** #1 (fork quarantine / sidecar)

**Problem:** The sidecar is a plain `File.write` justified by "a torn value reads as mismatch ⇒ quarantine (safe)" (shard.ex:976-995). That covers a **partial** value but not an **empty** one: `File.write` is O_TRUNC, and power loss classically yields a zero-length file. `read_etag_sidecar` maps `{:ok, ""}` → `:missing` → `quarantined_fork?` returns false (shard.ex:1002-1005) → `await_pull(nil, ...)` falls to the legacy branch that **adopts** the store's current etag (shard.ex:416-429). A crashed node whose shard was stolen/written/released elsewhere, sidecar torn to empty, adopts the current etag and its next flush clobbers the newer lineage with a valid If-Match — the exact #1 clobber.

**Impact:** Silent loss of acknowledged, already-durable writes on the crash-consistency path the #1 fix believed it covered.

**Recommended Fix:** Distinguish `{:ok, ""}` / non-etag-shaped garbage as `:corrupt` and route to quarantine (a spurious quarantine is recoverable). True `:enoent` keeps legacy adopt-once.

### #13. Warm-promotion TOCTOU: the follower atomically replaces the cache file between the coordinator's 304 and its `File.cp`, so the coordinator serves newer bytes under an older etag and later self-fences
**Severity:** Medium | **Category:** Data Loss (race) | **Panels:** Storage
**Likelihood:** Low-Medium (failover overlap with a dying owner's final flush + a follower poll) | **Blast Radius:** The promoted shard's post-open writes | **Regresses:** warm-follower A1 / #1 (warm promotion)

**Problem:** The coordinator reads `cached_etag` E1, gets a 304, then `File.cp`s the cache file (`warm_or_cold_pull`/`promote_warm_cache`, shard.ex:363-401) — during the overlapped-with-lease-acquire window in which the dying old owner lands a final flush E2 and the follower's poll `promote_temp`-renames E2 bytes into the cache path (warm_follower.ex:162-192). A `cp` in that window copies E2 bytes while the coordinator records provenance E1. Its first fenced flush `If-Match: E1` → 412 → self-fence → terminate drops the local copy without flushing — acknowledged post-open writes discarded though no other node owns the shard.

**Impact:** Data loss on the warm-promotion race even with no competing owner.

**Recommended Fix:** After the `File.cp`, re-read the follower sidecar and require it still equals `etag` (mismatch ⇒ fall back to `Storage.pull`); or validate the copied file's identity against the pre-304 sidecar.

### #14. `quarantine_fork!` uses a fixed `.forked` name and rm's it first → a second fork destroys the first fork's recovery copy; swallowed rename errors let a failed quarantine be overwritten by promote_pull
**Severity:** Medium | **Category:** Data Loss (recovery artifact) | **Panels:** Storage + OTP ×2 — **3-panel**
**Likelihood:** Medium (crash-looping stolen/written/released — the environment that produces forks) | **Blast Radius:** The recovery copy of acknowledged writes | **Regresses:** #1 (fork quarantine)

**Problem:** `dest = path <> ".forked"` and the function begins with `File.rm(dest)` (shard.ex:1028-1042) — a node that forks the same shard twice silently rm's the first quarantine, whose sole purpose is preserving acknowledged writes. `Enum.each(&File.rename/2)` swallows errors: a failed main-db rename still returns `true` from `quarantined_fork?`, so the cold-open `promote_pull` `File.rename(temp, path)` overwrites the never-moved forked file.

**Impact:** The recovery artifact the #1 quarantine exists to preserve is destroyed by a second fork or a swallowed rename error.

**Recommended Fix:** Unique names (`.forked.<system_time>-<uniq>`); match on the main-file rename — on failure, keep serving warm fenced by the provenance etag rather than clobbering. **Test gap:** a second fork over an existing `.forked`.

### #15. Heartbeat RESTART bumps the persisted generation but never broadcasts → the #34 proactive fence doesn't fire for the restart-lapse episode #8 explicitly models
**Severity:** Medium | **Category:** Data Correctness / Failure detection | **Panels:** OTP ×2 + Distributed — **3-panel**
**Likelihood:** Medium (heartbeat crash+restart is a real steal window) | **Blast Radius:** All subscribed coordinators sit on stale acquire_gens until the next flush | **Regresses:** #8 (restart lapse) × #34 (proactive fence broadcast)

**Problem:** #8 makes a restart bump the generation ("every re-boot = a lapse episode"); #34 subscribes coordinators to the lapse broadcast. But `init` only logs the bump — no `broadcast_lapse` (heartbeat.ex:114-121) — whereas `mark_lapse` does broadcast (heartbeat.ex:266-280). A heartbeat crash+restart is a real steal window; subscribed coordinators (shard.ex:652) keep stale acquire_gens and discover the mismatch only lazily at the next flush — unboundedly with `:shard_flush_interval_ms = 0` (idle-only mode). The gap #34 closed for lapses is reopened for restarts.

**Impact:** A restart-driven steal window is not proactively fenced; a remapped shard can double-write until a lazy flush notices.

**Recommended Fix:** In `init` (or from `handle_continue(:renew)` after the first successful renew), `broadcast_lapse(generation)` when `generation > 0`. **Test gap:** `{:heartbeat_lapsed, _}` delivery + all three fence branches.

### #16. `clear_previous_incarnation` equates "shares the local .incarnation file" with "predecessor is dead" → on a shared/PV/NFS data dir it deletes a LIVE node's heartbeat
**Severity:** Medium | **Category:** Split-brain / spurious steal window | **Panels:** Distributed ×2

### #20. A failed steal-touch leaves an epoch+1 lock the same node later RECLAIMS with no `took_over` flag, skipping the touch and revalidation entirely
**Severity:** Medium | **Category:** Fencing / incomplete steal state | **Panels:** Distributed
**Likelihood:** Low (touch failure followed by reclaim by the same node) | **Blast Radius:** Stale reads + accepted-write loss (etag fence backstops the clobber) | **Regresses:** #3 (steal-touch lock state)
