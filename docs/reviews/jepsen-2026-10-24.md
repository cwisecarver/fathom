# Jepsen: fathom under faults (2026-10-24)

**Answer, up front:** Jepsen found **six real problems that lost or forked acknowledged writes**.
All six are fixed, each with a regression test that fails on the old code. Five were bugs; one
(finding 3, two owners when clocks disagree) was a design limit, closed by making the steal
clock-free. A seventh finding is **open, a design decision**: a write that fails to reach a quorum
is still visible to later reads on its node, so a client can read a value that later vanishes
(finding 7, first seen 2026-10-25). No acknowledged write was lost in any run after the fixes.
That is strong evidence, not proof. The gaps at the end are what this rig cannot test, and they
matter for production.

| # | Problem | Fault that found it | Status |
|---|---|---|---|
| 1 | A brand-new shard lost quorum-acked writes when its owner died before the first periodic flush | Direct clients, owner SIGKILL | fixed, `068ab044` |
| 2 | Two nodes acked writes to one shard at once (split-brain) after an S3 outage longer than the steal window | MinIO paused 22 s | fixed, `1ee50d97` |
| 3 | Two nodes owned a shard at once when every node's clock fell ~35 s behind the store's | VM clock stepped forward | fixed, `4aab687a` (option A) + `d9ce4308` |
| 4 | A takeover whose replica promotion failed on an S3 error served the older object and lost the acked tail | MinIO pauses | fixed, `e0529dbc` |
| 5 | A takeover that stole from a live node trusted its own warm local copy and skipped recovery, losing the other node's acked writes | MinIO pauses, 16 shards | fixed, `e0529dbc` |
| 6 | A follower that installed a timed-out seed late absorbed a reset 31 WAL generations ahead, was promoted, and lost the acked writes in between | All faults, 30 min | fixed, `db81db43` |
| 7 | A read saw a write that had failed its quorum; the value later vanished | All faults, 30 min | **open: design decision** |

## Method

The test lives in [`jepsen/fathom`](../../jepsen/fathom/README.md). It is a standard Jepsen test
(Jepsen 0.3.15, Elle 0.2.8) that runs against the `deploy/chaos` rig: five fathom nodes behind the
nginx LB, MinIO as S3, toxiproxy in front of S3 and (with `REPL_VIA_TOXI=1`) in front of every
follower port, Postgres as the control plane. A2 replication is on (quorum 2 of 4), the flush
interval is production's 300 s.

- **Workload:** Elle list-append. Each transaction is one Hrana batch inside one shard: `BEGIN
  IMMEDIATE`, reads and appends, then `COMMIT` only if every step before it succeeded and
  `ROLLBACK` only if `COMMIT` did not. Every shard is its own Elle history, checked against
  **strict serializability**, which is what one SQLite file with one writer should give.
- **Clients:** through the LB (like a real client), straight to one node each (so non-owners get
  traffic and the lease refusal and steal paths run), or a mix of both.
- **Outcome classification is conservative:** `:fail` only when the batch result proves nothing
  committed (BEGIN refused, or ROLLBACK ran and succeeded); every HTTP error, timeout or ambiguous
  batch is `:info`. Unit tests pin this (`jepsen/fathom/test`).
- **Final reads:** after the faults heal, every key each shard ever touched is read back, as
  Jepsen's Bufstream test rewound consumers to offset 0. A lost append on a retired key is
  otherwise invisible.

### Choosing the faults: the closest Jepsen analogues

Jepsen has not analysed a SQLite-per-tenant system. The closest designs it has tested:

- **[Datomic Pro 1.0.7075](https://jepsen.io/analyses/datomic-pro-1.0.7075)** — one active
  writer (the transactor), failover by a standby that decides the writer is gone, safety resting
  on a compare-and-set in shared storage. That is fathom's shape: one owner per shard, a peer
  steals when the owner's heartbeat goes stale, the S3 lock and data object are fenced by
  `If-Match`. Jepsen used process pauses and crashes on the writers, partitions between nodes and
  between nodes and storage, and clock errors.
- **[Bufstream 0.1.0](https://jepsen.io/analyses/bufstream-0.1.0)** — object storage (MinIO in
  the test) holds the data, a coordinator tracks liveness with leases. Jepsen targeted faults at
  one subsystem at a time (pause only the coordinator, crash only the agents) and mixed them "in
  shifting combinations over time"; both of its lost-write bugs needed pauses of the agent or the
  coordinator.
- **[Amazon RDS for PostgreSQL 17.4](https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4)**
  — primary plus WAL-shipping replicas, checked with list-append. Its finding (replicas apply
  commits in a different order than the primary made them visible) is the reason fathom's clients
  here only ever read from the owner.

### Faults (`jepsen/fathom/src/jepsen/fathom/nemesis.clj`)

| fault | what it does |
|---|---|
| `kill` | disconnect from the network, then SIGKILL; revived with `docker start` |
| `pause` | SIGSTOP the container: the zombie owner |
| `isolate` | disconnect from the compose network: no LB, peers, S3 or Postgres |
| `flap` | cut and restore one node's network every 1-3 s |
| `s3-cut` / `s3-blackhole` / `s3-slow` | one node's S3 path refuses / hangs / adds 1-3 s |
| `s3-reset` / `s3-truncate` | one node's S3 connections are reset / closed after 4-64 KB |
| `repl-cut` / `repl-blackhole` / `repl-slow` | the link into one node's follower port refuses / hangs / adds 200-1000 ms |
| `kill-majority` | kill 3 of 5 nodes: no follower quorum is reachable |
| `rolling-restart` | kill and revive every node in turn, like a bad deploy |
| `minio-pause` / `postgres-pause` | SIGSTOP the object store / the control plane |
| `lb-restart` | restart nginx |
| `clock-jump` / `clock-back` | step the VM clock 20-60 s forward / back (every node and MinIO at once) |

`--hard` mixes them: start a fault, maybe pile on more 0-10 s later, hold 3-30 s (some heal before
the 15 s steal threshold, some after), heal everything, rest 0-15 s.

## Bug 1: a brand-new shard lost acked writes on owner death (fixed in `068ab044`)

**Found by:** `--target direct --faults pause,kill`, 5 minutes. Shard 5, key 8: reads returned
`[2 3]` until 16 s; `fathom1`, the owner, was SIGKILLed at 20 s; at 76 s a read through `fathom2`
returned `[]`. The appends of 2 and 3 had been acked.

**Cause:** the shard was created by its first request and had never been flushed, so no S3 object
existed. A2 replicated the writes to a quorum, but recovery only overrides a stored object it can
rank against: with no object, `Promote.fresher?(_, nil)` is false and `Recovery.rankable_stamp?(nil)`
skips the fleet ask (`promote_on_open.ex:316`). The new owner served an empty shard while three peers
held the writes. `stamp_on_open/3` (expert review 2026-10-15 #7) already closed this for an object
with no stamp; it skipped the no-object case. The window was up to one flush interval (300 s).

**Fix:** on a replicating shard with no object, the first write sends an immediate durability flush
(`Fathom.Shard.stamp_first_write/1`). The publish carries this lineage's stamp, so every later frame
outranks it. It runs at the first write, not at open, so a read-only probe of an id that never
existed writes nothing. The remaining window is one object-store round trip after the first acked
write.

**Evidence:** `test/fathom/shard/first_write_stamp_test.exs` (real three-follower fleet, both
liveness modes) fails on the old code with no object after the acked write. Four more 5-minute
direct pause/kill runs: 52,654 transactions, all shards valid. `./chaos.sh rpo` passes.

## Bug 2: two writers on one shard after a long S3 outage (fixed in `1ee50d97`)

**Found by:** `--hard --target mixed`, 10 minutes, every fault, steady clock. Shard 9, key 173
forked: one set of clients read `[3 4 5 6 7 8 9 …]`, another `[3 4 10 13 14 15 16]`, both sides
acked. Elle: G0, G-single and incompatible-order. It happened as MinIO came back from a 22 s pause
(01:51:48 to 01:52:10), longer than the lease TTL plus the steal margin (15 s).

**Cause:** `fathom4` owned shard 9. It could not renew its heartbeat during the pause and correctly
fenced its writes. When MinIO came back it renewed the heartbeat, revalidated the shard with a
**read-only** `check_lease` (the lock still named it) and resumed acking. Meanwhile a peer had read
the lock and `fathom4`'s stale heartbeat; its steal is `put_lock If-Match <the etag it read>`, and a
read does not move the etag, so the steal also succeeded. Nothing serialized the owner's resumption
against the thief's steal.

**Fix:** `Fence.revalidate/2` renews the lock (a fenced PUT) instead of reading it. A thief that read
the lock before the renew gets a 412; one that reads it after also reads the heartbeat after the
owner renewed it and finds the owner live. One of the two wins, never both. This is the same shape
Datomic relies on: one compare-and-set on storage decides. A second, smaller fix rode along: the S3
renew always advances `expires_at_ms`, because the etag is the body's MD5 and a byte-identical renew
in the same millisecond left it unchanged (the new test caught that as a flake).

**Evidence:** `test/fathom/shard/revalidate_cas_test.exs` runs the real S3 backend over
`S3EtagStore` (the local double takes a lease under a mutex and cannot express this race): fails 5
of 5 on the old code, passes 20 of 20 on the new. Bench gate OK (worst metric +3.7%).

## Finding 3: lease safety depended on clock agreement (fixed in `4aab687a`)

**Found by:** the 30-minute run with every fault (`--faults all`, up to 3 at once): 189,245
transactions across 16 shards, 79 faults. 15 shards valid; shard 0 forked. Key 370: one client
appended 1, 2, 3, 4, then 7 and 8, all acked with quorum; at the same moment other clients appended
5, 6, 9, 14, 15, 16, 18 on another node, every one refused with `write not replicated to a follower
quorum`. The final read was `[1 2 3 4 5 6 9 14 15 16 18]`: the refused branch survived and the acked
7 and 8 were lost.

**When:** 1.7 s after a `clock-jump` stepped the VM clock forward ~35 s. MinIO shares the VM's clock,
so its clock jumped at once; each node's BEAM keeps its own system time and only slews toward the new
OS time, so every node was ~35 s behind the store. Within a second `fathom1` and then `fathom5` took
the shard over (each logged `PROMOTED a local replica`), while the original owner went on acking.

**Cause:** a steal decides "is the owner's heartbeat expired?" against the **store's** clock (S3's
`Date`), and the heartbeat's expiry is written in the owner's clock, so a 35 s gap makes every live
owner look dead at once. The owner judges its own lease on its monotonic clock, which did not jump, so
it kept acking until its next renew noticed `clock lags the store` and self-lapsed, too late. Its
frames still reached a quorum because the thieves' new epoch had not reached the followers yet (their
seeds failed). The design states the assumption: the steal margin (5 s, `Storage.steal_margin_ms`)
"absorbs inter-node clock skew". This run broke it by 35 s.

**How real is the trigger?** On AWS the store's clock does not step, so this exact trigger is mostly
a rig artifact (MinIO shares the clock the fault moves). The exposure that remains in production: any
node whose clock falls more than the steal margin behind S3 *between two heartbeat renews* can be
stolen from while it is still acking. Bounded clock skew is the classic weak point of lease designs;
Datomic's safety, by contrast, rests on a compare-and-set in storage on every commit.

**Options (decision needed):**

- **A. Make stealing clock-free.** A peer steals only after watching the owner's heartbeat object stay
  unchanged for TTL + margin on its *own monotonic clock*. A live owner renews every few seconds, so
  that proves death without comparing clocks. Cost: a takeover that was not already watching waits up
  to ~15 s longer (rig failover is already lease-floor-bound at ~15 s).
- **B. Keep clocks, shrink the window.** Check the store-vs-local clock gap more often (on every
  renew it already does; more often costs S3 calls). Reduces exposure, does not remove it.
- **C. Keep the assumption and enforce it operationally.** Document "node clocks within 5 s of S3,
  never stepped", run chrony with slewing only, and page on any `clock lags the store`.

Recommendation: **A**. It removes the dependence on clocks, which is the property Jepsen tests for,
at a bounded RTO cost.

**Fix (option A, `4aab687a`):** a stealer records the lock's `{epoch, expires_at_ms, etag}` and the
owner's heartbeat expiry the first time it sees them, and steals only once it has seen that pair
unchanged for TTL + margin on its own monotonic clock (`Storage.steal_watch_window_ms/0`, 35 s with
production defaults, 15 s on the rig). This is an AND with the old store-clock rule, so it can only
make a steal later, never earlier. The fast path for a provably dead previous incarnation of the
same node is exempt. Cost: a takeover that was not already watching waits up to one more window; the
`failover_rto` bench turns the watch off so its series stays comparable. Evidence:
`test/fathom/shard/storage/steal_watch_test.exs`, 3 of 8 fail on the old code. Every 30-minute run
below includes clock jumps, and none showed two owners.

**A mistake in that fix, caught by `./chaos.sh rpo` (fixed in `d9ce4308`):** the watch also gated a
*released* marker, the lock a holder leaves when it lets go cleanly. So every clean cross-node
handoff (rebalance, idle drop, rolling deploy) answered "shard temporarily owned by another node"
for a whole window: 15 s on the rig, 35 s in production. A release is the holder's own statement,
not a clock reading, so it is now taken on the first look. The 30-minute runs below were made
before this fix, which is the likely reason they made about 80,000 transactions instead of
~180,000 (not re-measured).

## Bug 4: a failed promotion served the older object (fixed in `e0529dbc`)

**Found by:** the 30-minute run with every fault except clock steps, then reproduced with MinIO
pauses alone (3 of 8 shards in 5 minutes). Temporary decision logging on the takeover path showed
`replica promotion declined (%Req.TransportError{reason: :timeout}); opening from the stored object`.

**Cause:** a takeover chose a replica strictly ahead of the stored object, then one of the
promotion's S3 calls (the pre-promotion snapshot, or the publish) timed out because MinIO was paused.
`promote_replica` then served the stored object, on the moduledoc's argument that the stored-object
path "is still correct, it just recovers less". "Less" was the quorum-acked tail, and the new owner
then wrote at a higher lineage that outranked every replica still holding it.

**Fix:** a promotion that fails takes the same path as an unreadable decision head
(`Recovery.error_window/3`, expert review 2026-10-13 #15): refuse the open inside the under-quorum
window, so the client retries and the retry runs recovery again; fall back to the object, logged as
an error, only after the window.

**Evidence:** `promote_on_open_test.exs` "a promotion that fails on a store error refuses the open
instead of serving the object": fails 5 of 5 on the old code, passes 10 of 10 on the new.

## Bug 5: a takeover trusted its warm local copy over a newer replica (fixed in `e0529dbc`)

**Found by:** MinIO pauses with 16 shards, on an image with decision logging, after several clean
runs (it is timing-dependent).

**Cause, from the decision log:** fathom4's flush landed and it released the shard. fathom3 took it
over, promoted exactly those bytes, and acked 5,044 writes it never managed to flush (MinIO kept
pausing). fathom4 then stole the shard back. Its local copy was byte-identical to the stored object,
so `Fork.resolve` correctly found no fork and the open went WARM, and promote-on-open skips a warm
local on the argument that no replica can be ahead of this node's own file. One was: fathom4's own
replica table held fathom3's writes (lineage 4, ordinal 76). They were never served. The code's own
comment said to revisit the warm skip "if a Fork.resolve gap is ever actually found"; this is it.

**Fix:** when the lease was stolen from another node (`:prev_owner` names one), the promotion decision
runs even over a warm local. It only promotes a replica strictly ahead of the object, so a local
equal to the object loses nothing. A takeover of a *released marker* keeps the warm skip, because a
clean marker records that the visitors since wrote nothing (`RefusedOpenUnderQuorumTest` pins
serving that warm copy). **Known gap:** a holder that wrote and then released *dirty*, over an
object whose bytes still equal this node's flush, is not covered.

**Evidence:** `promote_on_open_test.exs` "a takeover from another holder promotes past a warm local
that equals the object": fails 5 of 5 on the old code, passes 10 of 10 on the new.

## Bug 6: a late seed let a follower skip 31 WAL generations (fixed in `db81db43`)

**Found by:** the first 30-minute all-faults run after the finding 3 fix (2026-10-24 23:21): shard 6
lost 38 acked writes. A run on an image with decision logging reproduced it on shard 13 (58 lost).

**Cause, from the decision log (shard 13):**

1. 05:34:24 `fathom2`, the primary, sends a full seed to `fathom3`.
2. 05:34:54 the seed times out on the primary (30 s), which then keeps **no record** of `fathom3`.
3. 05:34:56 the seed lands anyway: `fathom3` installs it, at WAL ordinal 1.
4. 05:35:34 the next reset push arrives at ordinal **33**. With no record of the follower, the
   primary stated `prev_extent` 0, which the protocol reads as "no statement", and the follower took
   that as "the old generation is complete". It absorbed, cleared `torn`, and so became promotable.
5. 05:37:11 `fathom3` is promoted while missing generations 2 to 32. Keys 129 to 132 lost their
   acked appends.

**Fix:** two guards, either of which closes it. The follower treats a reset whose `wal_ordinal`
skips past `held + 1` as `:short` and asks for a seed instead of absorbing
(`Follower.reset_verdict`). The primary, when it holds no record of a follower, now states an
**unknown** extent (all ones) instead of 0 (`Session.outgoing_extent`).

**Evidence:** `replication_short_reset_test.exs`: the two new fix tests fail with both guards backed
out. On the rig, every replica a node installed by seed or promoted was copied at that moment, and
each copy was checked for every append acked more than 3 s before it. The check flags the bad
promotion on the failing run (positive control). With the fix, two 30-minute all-faults runs: 181
promotions checked, 0 missing an acked write. (Two flags on the first run fell inside a clock jump
that moved the node's timestamps by 32 s; the "missing" values were in later reads, so they were
written after the copy.) The fix did not raise the seed rate.

## Finding 7: a read can see a write that failed its quorum (open)

**Found by:** the second 30-minute all-faults run with the bug 6 fix (2026-10-25 05:19). 15 of 16
shards valid. Shard 9, key 214:

- 860.6 s: `[:append 214 6]` on `fathom4` returns `write not replicated to a follower quorum`. The
  client is told it may not have happened, and Elle records it as `:info`.
- 868.1 s: a read on `fathom4` returns `[6]`.
- 914 s onward, after a takeover: the key restarts at `[24]` and ends at `[24 … 38]`. 6 is gone.

**No acked write was lost.** Every append the database acknowledged (24 to 38) is in the final read.
Elle flags it (`incompatible-order` `[6]` vs `[24]`, G-single-item-realtime) because a value a
client saw then disappeared, which no serializable history allows.

**Cause:** this was already listed under "what this rig cannot test" below. A write that misses its
quorum gets a 503, but the SQLite commit is local and stays visible, so later reads on that node
can see it. If ownership then moves, the new owner never had it.

**Options (decision needed):**

- **A. Fence the shard after an under-quorum commit.** Refuse reads and writes on that node until the
  frames reach a quorum, or until it gives up ownership. Readers never see a write that can vanish.
  Cost: the shard is unavailable on that node during a replication outage (it already refuses
  writes then).
- **B. Document it.** State that a failed write may be visible until failover, like reading
  uncommitted data. No code change; clients must treat a 503 write as "may be visible, may vanish".

Recommendation: **A**, because Django does not expect to read a row that later disappears.

## Operational findings

- **Postgres connection exhaustion after node crashes.** A SIGKILLed or partitioned node never closes
  its ~30 Repo connections, and with Linux's default TCP keepalive (2 h) Postgres keeps them. A few
  dozen kills used all 300 slots three minutes into the first 30-minute run, and every node's control
  plane (directory, Oban, rebalancer commands) then failed with `too many clients already` for the
  rest of that run and the next. The rig now sets `tcp_keepalives_idle=10`, interval 5, count 3; the
  next 30-minute run saw none. **Production Postgres needs the same, or an equivalent idle-session
  timeout.** The first two 30-minute runs below therefore also ran with the control plane down.
- **The rig runs the rebalancer** (`REBALANCER_ENABLED=true`), which production does not by default,
  so shard handoffs ran alongside the faults.
- **Jepsen needs more than 4 GB to check a 30-minute history** (~186,000 transactions); the analysis
  ran out of heap once. `project.clj` now asks for 24 GB, and `lein run analyze` re-checks a stored
  run.

## Runs that do not count

- **The first clock-jump run** stepped the clock with `date -s`, and the VM's `systemd-timesyncd`
  stepped it back within a second. It passed, but it tested nothing. The fault now stops
  `systemd-timesyncd` while a step lasts.
- **A hard shakedown at 01:39** reported anomalies on 6 of 8 shards. During it the Mac (lid closed)
  was entering Maintenance Sleep about 43 s of every minute; the VM froze and its clock stepped
  forward each time, and every node logged `clock lags the store` at once. Plain `caffeinate -dims`
  does not stop this; `caffeinate -s` does. A whole-VM freeze is the same shape as the MinIO pause
  that exposed bug 2 (every heartbeat goes stale together), so it was probably bug 2, but that run
  cannot show it. `run.sh` marks a run invalid when any node logs `clock lags the store` (unless the
  run injects clock faults on purpose).

## What this rig cannot test (read before trusting this for production)

- **Per-node clock skew.** Every container shares the VM's kernel clock, and the containers have no
  `CAP_SYS_TIME`. The clock faults move every node and MinIO together. Skew between nodes, the case
  the steal margin exists for, is untested.
- **Real network partitions between nodes.** The containers have no `iptables`. The partitions here
  are a node's whole network, its S3 path, or the inbound link to its follower port (toxiproxy). A
  partition that splits the fleet into two halves that can each reach S3 is untested.
- **Disk faults and power loss.** `docker kill` keeps the VM's page cache, so an "un-fsynced" write
  survives. Lost fsyncs, torn pages and power loss are untested.
- **Real S3.** MinIO does not enforce a conditional DELETE (the rig runs with
  `allow_weak_conditional_delete`), so the lock-release fence is not exercised.
- **Scale and duration.** One host, five nodes, up to 16 shards, at most 30 minutes. Jepsen's
  Bufstream campaign ran single tests for up to an hour.
- **Reads of not-yet-acked writes.** Seen once, in the last 30-minute run: finding 7. Nothing here is
  aimed at it, so how often it happens is unmeasured.
- **One workload, one protocol.** Elle list-append over Hrana HTTP. No bank or register workload, no
  WebSocket clients, no Django.
