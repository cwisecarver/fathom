## #12 — `Promote.fresher?/2` compares the replica's LOCK epoch against the object's LINEAGE

**Status:** BLOCKED on a decision that is not mine. The test-gap half is shipped (see below).

**What the finding claims.** The 2026-08-20 #8 fix split one number into two and migrated only one
side. The object's position stamp now carries the **lineage** (`open_lineage/1` →
`Storage.next_lineage/1`, monotonic across a release, never reset). The replica's `epoch` still
comes from `Session.with_epoch/1` → `Fathom.Shard.epoch/1` → `state.lease.epoch` — the **lock**
epoch, which `release_lease` resets to 1 on every clean idle-drop, drain and handoff.
`fresher?/2` (`lib/fathom/shard/replication/promote.ex:108`) compares
`{lock_epoch, wal_gen, next_offset} > {lineage, wal_gen, offset}` as if they were one scale, and
`Recovery.rank/1` inherits it.

Confirmed by reading: the two values do come from different counters, and the lock epoch does
reset to 1 on a clean release. From a shard's second replicating open onward `fresher?/2` is false
for every replica however far ahead it is, so promote-on-open and `Recovery.best_replica/3` go
inert — silently, recovering to the last flush exactly as if A2 were off. The unsafe direction is
also reachable: on a gate-toggled fleet a flush with `lineage: :disabled` stamps the lock epoch
into the position slot, so a replica stranded at a higher lock epoch from an earlier crash-steal
can outrank a newer object.

**Gate:** A2 replication, off by default. That is why this is parked rather than escalated — but
it silently nullifies the whole feature for anyone who has turned it on.

**The fix I would make.** Ship the lineage, not the lock epoch, as the replica's ordering key: add
the coordinator's `lineage` to `Push`/`SeedBegin` as its own field, have `FollowerLog` record it,
and keep `epoch` for the fencing check (`decide/2`'s `pushed < epoch`), where the lock epoch is the
correct value.

**The decision that is not mine.** That is a **wire-format change**, and it re-opens an argument
this project already settled once: the `@version 2` additive-frame contract, and whether a decoder
must tolerate the field missing from an older peer. It is a rolling-upgrade compatibility question
about a protocol, not a local correctness fix, and getting it wrong on a mixed fleet is worse than
the bug.

**Options, with consequences.**

1. **Add the field (the panel's recommendation).** Correct, and restores A2 promotion. Costs a
   protocol revision plus the mixed-fleet decode story, and needs a test that drives
   acquire → write → real `Session.commit` → real flush → compare, with `assert is_integer(stamp)`
   as a precondition so it cannot go vacuous the way the existing coverage did.
2. **The panel's interim guard** — assert in `fresher?/2` that both sides came from the same
   counter and answer `false` otherwise. The panel labelled this explicitly **NOT a fix**. Worse,
   it does not mean what it sounds like: the two sides are *never* the same counter today, so this
   makes `fresher?/2` unconditionally false — i.e. it would deliberately and permanently disable
   A2 promotion rather than fix it. Safe, and honest about being inert, but it turns a silent
   feature outage into a designed one. That is a product call.
3. **Leave it.** The status quo: promotion is inert from the second open onward and the unsafe
   direction stays reachable on a gate-toggled fleet.

I did not pick, because 1 and 2 differ on whether A2 promotion is a feature you want working now,
and 2 is a deliberate capability removal.

**What WAS shipped for this finding.** Per AGENTS.md ("if a test genuinely cannot discriminate, say
so in its moduledoc — plainly, in the file"), `test/fathom/shard/promote_on_open_test.exs` now
carries a section stating that every test in it seeds the replica from the object's own stamp
(`install_replica/2` passes `position.epoch`), so both sides of the comparison come from one number
and the tests pass whether or not the two counters agree in production. It also warns against
"closing" the gap by adding another test that seeds the same way — the seeding *is* the gap.

**Note on the panel's supporting claim.** It also cited `ownership_cycle_position_test.exs:227` as
passing vacuously on `stamp == nil`. True, but that file already documents this itself, in detail,
including an `assert is_nil(stamp)` guard that fires with an explanation if the path stops taking
the ambiguous branch. No change was needed there.
