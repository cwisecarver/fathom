### #1. `snapshot_id` bypasses the `ShardId` validation gate — path traversal / arbitrary file read-write-delete from the control plane
**Severity:** Medium (High confidence) | **Category:** Shard Isolation / Security | **Panels:** D
**Likelihood:** Low (requires the admin credential) | **Blast Radius:** Node-local arbitrary file R/W/delete + arbitrary bytes smuggled into a tenant DB

**Problem:** `ShardId.cast` is documented (`lib/fathom/shard_id.ex:1-13`) as *the* one path-traversal/isolation gate, and every shard code path validates through it. The sibling `snapshot_id` is threaded straight from request params into storage keys with **no validation**. `Snapshots.restore/3` (`lib/fathom/snapshots.ex:73`) and `drop/2` (`:103`) cast only the shard id; the raw `snapshot_id` reaches `Local.snapshot_path/2` (`lib/fathom/shard/storage/local.ex:597-598`) = `Path.join(dir(), "#{shard_id}@snap-#{snapshot_id}.db")`. A traversal `snapshot_id` (e.g. `../../../../../etc/hosts`, which `Path.join` collapses) makes `restore_snapshot/3` `File.read` an arbitrary file and `atomic_write` it into the shard's live object — then downloadable via `/admin/tenants/:id/export`. `drop_snapshot` becomes `File.rm` of an arbitrary `.db`. On S3 the value escapes the key prefix. Controller entry at `lib/fathom_web/controllers/api/tenant_controller.ex:166` (`restore`), `:190` (`drop_snapshot`). `create_snapshot` is safe (it generates its own id via `new_snapshot_id`).

**Impact:** An operator (or anything that obtains the single admin credential — see #8) turns the tenant control plane into an arbitrary-file read/write/delete primitive on the node and can smuggle arbitrary bytes into a tenant's database. Violates the codebase's stated invariant that *all* storage-key construction is gated by `ShardId`. Ranked first because shard isolation is fathom's release-blocker class and this is a concrete, cheaply-fixable existing bug.

**Recommended Fix:** Add `Snapshots.valid_snapshot_id?/1` (conservative `^[a-zA-Z0-9._-]{1,128}$`, no `/`, no `..`) and reject in `restore/3`, `drop/2`, and at the controller boundary — mirroring `ShardId.cast`. Since `new_snapshot_id` only emits `[a-z0-9-]` plus the `@snap-` context, the validator can be strict. Regression test: a traversal `snapshot_id` returns `:invalid_snapshot_id`, not a file read.

### #2. A supervisor shutdown with connections still open silently skips the final durability flush AND abandons the in-flight flush task
**Severity:** High | **Category:** Data Loss | **Panels:** A
**Likelihood:** High (every clean deploy of a write-active shard with lingering streams) | **Blast Radius:** Up to one flush interval of acked writes per busy shard on ephemeral disk, plus spurious fork-quarantines

**Problem:** `terminate/2` (`lib/fathom/shard.ex:1197-1210`) has three clauses: `lease_lost` (settles the flush task, quarantines), `conns == 0` (settles the flush task, `flush_and_drop`), and a catch-all for "connections still open (or pre-open)". The catch-all only forgets ETS rows — it does **not** call `settle_flush_task/1` and does **not** upload. On a rolling deploy, `terminate` is entered on the supervisor EXIT signal *without processing pending mailbox messages*, so `:DOWN`s from streams Bandit just killed are frequently still queued and `conns` is non-empty. A dirty, busy shard on clean SIGTERM therefore: (a) loses up to a full flush interval of acked writes on ephemeral disk (containers) despite the 60s `@default_shutdown_ms` budget existing precisely to flush; (b) if a periodic flush task was in flight, its conditional PUT may land server-side while the linked task is killed — the sidecar is never advanced, so the next warm open reads `sidecar(old) != object(new)` and **false-quarantines a fork** (the exact spurious-quarantine window review 2026-07-14 #21 closed for the drop-flush path). Note: the delete path (`Fathom.Shards.stop/1`) deliberately routes through this clause and *wants* no flush — the clause is load-bearing for two opposite intents. The existing regression test (`shard_durability_test.exs:1022`) only pins the `conns == 0` path.

**Impact:** Silent loss of the last write window on every clean deploy of a write-active shard with lingering streams; spurious `.forked.<ts>` quarantines, error logs, and operator alarm on the subsequent open.

**Recommended Fix:** In the catch-all clause: (1) always `settle_flush_task(state)` first (its result-fold updates the sidecar, closing the false-quarantine window); (2) when the shard is dirty and *not* being force-stopped for deletion (tombstone check is O(1) ETS), run `snapshot_and_upload/1` behind the same fence (`VACUUM INTO` is writer-safe — it's what the periodic flush does under live connections). Regression test: supervisor-shutdown a dirty coordinator with a held connection; assert the stored object contains the last committed write and the next warm open does not emit `[:fathom, :shard, :forked]`. See #28 (node-level drain) for the structural companion that routes deploys away from this path entirely.

### #3. The RPO contract is partition-duration-bounded, not flush-interval-bounded — a cut-from-S3 node keeps ACKing writes it will later quarantine
**Severity:** High | **Category:** Data Loss | **Panels:** B
**Likelihood:** Medium (one-sided S3 partition) | **Blast Radius:** Unbounded loss window (= partition duration) per busy shard on the cut node + client-visible split-brain across two live serving nodes

**Problem:** `docs/single-writer.md:93-99` states loss is "bounded by the flush interval, which *is* the RPO window." That holds for node *death*, not for the **one-sided partition**: a node reachable by the LB and clients but cut from S3. In that state, heartbeat renewals fail → heartbeat lapses → `valid_for_write?` returns `:not_valid` → every durability flush skips (`lib/fathom/shard.ex:946`, `:fence_skip`) and `record_flush_failure` (`:1734`) only escalates a log — but the coordinator **keeps accepting and ACKing writes indefinitely**. Nothing in `handle_call({:checkout, ...})` (`:763`) or the executor consults heartbeat validity. Meanwhile, after TTL + steal-margin a peer legitimately steals the shard and serves it (correctly — the fence prevents a double-*flush*). On heal, the old owner self-fences and `quarantine_fenced!`s **every write ACKed since its last successful flush** — a loss window equal to the partition duration, not the 5s interval. There is also a double-*serve* window (both nodes ACKing the same tenant) for the whole post-steal partition remainder — no double-write to storage, but split-brain at the client-visible layer.

**Impact:** A 10-minute S3 partition on one node silently converts the advertised 5s RPO into 10 minutes of ACKed-then-quarantined writes per busy shard, plus divergent reads/writes across two live serving nodes. The escalating log is the only signal.

**Recommended Fix:** Add a write circuit-breaker keyed off the signal already computed: when `Heartbeat` has been `:not_valid` longer than `ttl + steal_margin` ("we are provably stealable"), coordinators refuse **new write-bearing work** — reject checkouts (or have `Fathom.ShardExecutor` refuse writes) with a distinct 503, config-gated (`:fence_writes_when_stealable`, default on in prod). Existing read streams may continue. This restores "an ACKed write is lost only within one flush interval" and collapses the double-serve window to ~TTL. Update `docs/single-writer.md` either way — the doc overstates the bound. Test coverage for this window lands in the same region as #30.

### #4. Backups are a manual primitive: no scheduled snapshots, no retention, no PITR — default deployments have zero logical-corruption protection
**Severity:** High | **Category:** Data Loss / Missing Capability | **Panels:** C, E
**Likelihood:** High (logical corruption is the most common DB-platform incident) | **Blast Radius:** Total loss of pre-incident state for any tenant with no manual snapshot — i.e. most tenants

**Problem:** `docs/durability.md:120-142` itself says logical corruption (bad deploy, mass `UPDATE`, accidental `DELETE`) is "the far more common incident" and "propagates to the one durable object within a flush interval and overwrites the last good state." The answer built for it — `Fathom.Snapshots` / `@snap-<id>` (`lib/fathom/snapshots.ex:43`) — is invoked only by an operator (mix task, console, or `POST /api/tenants/:id/snapshots`). There is no Oban cron that snapshots active tenants (`config/config.exs:70` schedules only `ReconcileJob`/`RebalanceJob`), no per-tenant snapshot policy, and no retention sweep: `list/drop` are manual, so a customer who scripts periodic creates accumulates snapshots unboundedly, and a customer who doesn't has **nothing** between the incident and total loss (within one 5s flush interval). The bad state also becomes the durable object *and* every warm-follower copy fleet-wide within one poll. Turso's headline recovery feature is point-in-time restore; fathom's actual recovery point for logical corruption is "whenever an operator last ran `mix fathom.snapshot create`" — for most tenants, never. Two panels independently flagged this as the single biggest DR gap vs the RDS/Turso incumbent the finance demo targets.

**Impact:** The realistic recovery posture for the most likely incident class is "hope the operator manually snapshotted this tenant recently." The first support ticket every DB platform gets is "I deleted my data, restore it" — and today the honest answer for a tenant with no manual snapshot is "gone," even though the durability contract was perfectly upheld.

**Recommended Fix:** An Oban cron `Fathom.Snapshots.SweepJob`: for each directory-`active` tenant written since its last snapshot (reuse the `last_flushed_at` recorder signal / `Directory.active_recent/1`), `Storage.snapshot/2` + enforce retention (keep-N or GFS: hourly×24 / daily×7), dropping expired ids. Config-gated (`:snapshot_schedule`, off by default), per-tenant overridable. Snapshots are server-side CopyObject — one copy per written tenant per period, no body transfer. Emit `[:fathom, :snapshots, :swept]` and surface last-snapshot-age in the loss report. Cheaper interim worth documenting even if the job is deferred: S3 bucket versioning on the live object + a documented restore-from-version procedure (near-zero code, PITR at flush-interval granularity — dovetails with #5).

### #5. Bucket-level disaster hardening is documentation-only; the code that *deletes* is fully built while the code that *recovers from deletion* doesn't exist
**Severity:** High | **Category:** Missing Capability / Reliability | **Panels:** C
**Likelihood:** Low per-event, but catastrophic | **Blast Radius:** Fleet-extinction (every tenant) on a single bucket-level mistake or leaked node credential

**Problem:** The defense-in-depth against bucket deletion, lifecycle misconfig, compromised credential, or fat-fingered `rm --recursive` is a list of *recommendations* in `docs/durability.md:144-158` (versioning, Object Lock, replication, least-privilege). Nothing in code checks any of it: no boot-time `GetBucketVersioning` probe (contrast the excellent `verify_conditional_writes!` at `lib/fathom/shard/storage/s3.ex:109`, which refuses boot on an unenforced fence — the same fail-closed philosophy applies), no helper to restore a shard from a noncurrent S3 version (an operator is on raw `aws s3api list-object-versions`), and the data-plane credentials that serve traffic are the same ones `purge_shard`/`drop_live`/`drop_snapshot` use for permanent deletes (`s3.ex:883-943`) — one leaked node credential can erase every tenant, versioning permitting. `DeleteJob`'s purge is a hard delete with no soft-delete window: `retain_until` exists for migration versions, but tenant deletion goes straight to `DeleteObject`.

**Impact:** A single bucket-level mistake or credential compromise is currently an unbounded-blast-radius, unassisted-recovery event. With versioning silently off (the default on new buckets), it is fleet-extinction, discovered only at restore time.

**Recommended Fix:** (1) Extend the boot self-test: probe bucket versioning and log/refuse per `:require_bucket_versioning` (warn-by-default, required in prod); (2) an `undelete`/`restore-from-version` helper (`mix fathom.shard undelete <shard> [version-id]`) so noncurrent-version recovery is a runbook step; (3) document (and support via separate config keys) a split-credential deployment — data plane without `s3:DeleteObject` on the live prefix, deletes via the control plane only (see #26); (4) an optional grace period on `DeleteJob` (schedule the purge `retain_until`-style) so tenant deletion has an undo window like everything else.

### #6. No cross-store DR coherence: a Postgres directory restored to an earlier point in time resurrects deleted tenants and revoked tokens
**Severity:** High | **Category:** Missing Capability / Security / Data Correctness | **Panels:** C
**Likelihood:** Medium (Postgres PITR is a routine RDS operation) | **Blast Radius:** Fleet-wide — GDPR erasure, auth revocation, and migration convergence all silently broken

**Problem:** Durability thinking stops at the S3 bucket, but correctness state is split across **two** stores: S3 (shard bytes, locks, snapshots) and Postgres (tombstones, suspensions, `schema_version`, `token_version`/rotation state, migration registry, outboxed retirements). There is no documented or coded story for restoring them to *coherent* points in time. Concretely: the tombstone re-mint guard `Fathom.Tenants.Tombstones` is ETS loaded **from the directory** (`lib/fathom/tenants.ex:12-14`); a Postgres PITR to T−1h (routine after a directory-side incident) silently un-tombstones every tenant deleted in that hour — the next request for an erased subdomain re-mints it (the exact GDPR failure `Tombstones` exists to prevent; the ETS set also periodically *refreshes* from the restored directory, overwriting in-memory knowledge). Same shape for `token_version` (revoked tokens verify again) and `schema_version` (the laggard sweep replays migrations onto already-migrated shards — the quarantine trap, fleet-wide).

**Impact:** The directory's own recovery procedure — the store most likely to be point-in-time-restored, since it's ordinary Postgres — actively breaks erasure guarantees, auth revocation, and migration convergence. Nobody has written down that restoring Postgres is dangerous here.

**Recommended Fix:** Make S3 the durable backstop for the small set of irreversible facts: on delete, additionally write a tiny `<shard>@tombstone` object (*after* the purge), and have the tombstone boot-load/refresh union the directory rows with a storage-prefix scan (or at minimum verify-on-miss before minting a novel shard whose id has a tombstone object). Add `mix fathom.directory reconcile` cross-checking directory rows against storage (rows without objects, objects without rows, version stamps vs `user_version`) — doubling as the DR-completion step. Write the DR runbook: order of restore, reconcile pass, invariants to verify before re-opening traffic. The S3-tombstone backstop also hardens #33 (the transient deny-set drop).

### #7. Snapshot restore across a schema-migration boundary silently forks the three-place version stamp
**Severity:** High | **Category:** Data Correctness | **Panels:** C
**Likelihood:** Medium (any restore near a rollout window) | **Blast Radius:** One tenant permanently version-skewed, silent — directory swears everything is fine

**Problem:** The migration engine keeps the version stamp coherent in three places (`_fathom_migrations` in the file, `PRAGMA user_version`, `shards.schema_version` in Postgres), and the fork path carefully registers a fork at the source's schema version so the laggard sweep won't re-migrate it. `Snapshots.restore/3` (`lib/fathom/snapshots.ex:73-99`) does neither: it copies bytes back over live and never reads the restored file's `user_version` nor reconciles the directory row (snapshot type is `id` + `bytes` only — `lib/fathom/shard/storage.ex:204-227`). A snapshot captured at `vN-1` restored after the fleet cut to `vN` leaves the file at `vN-1` while the directory says `vN` — so `ReconcileJob`'s laggard query (`schema_version < head`) believes it's migrated and never converges it, and vN-expecting app code reads a vN-1 schema indefinitely. Snapshot metadata doesn't even record the schema version at capture, so an operator can't tell a cross-boundary restore is happening.

**Impact:** A routine "undo the bad deploy's data damage" restore performed near a rollout window silently produces a permanently version-skewed tenant — the exact divergence the migration gate exists to prevent, entered through the DR side door. Symptoms surface later as application errors on one tenant.

**Recommended Fix:** (a) Record `user_version` (and byte-level `schema_version`) in the snapshot key or object metadata at `create` time; (b) in `restore/3`, after the fenced copy-back, read the restored object's `user_version` and reconcile `shards.schema_version` — or, better, refuse a cross-version restore without `force: true` (mirroring `RevertJob`'s write-age guard), and on force re-flag the row so the laggard sweep re-migrates it forward. Ship the migration-gate regression: seed vN-1, snapshot, migrate to vN, restore, assert the directory/laggard behavior.

### #8. A single static, unrotatable, shared credential guards the entire control plane (including full-tenant export)
**Severity:** High | **Category:** Security / Missing Capability | **Panels:** D, E
**Likelihood:** Medium (secret leak via CI logs, shell history, shared password manager) | **Blast Radius:** Every tenant's complete database exportable + every tenant erasable + every data-plane token mintable, with no attribution

**Problem:** One `ADMIN_USER`/`ADMIN_PASS` pair, read from env (`config/runtime.exs:262-277`), gates `/admin` (all LiveViews), `/admin/metrics`, `/admin/tenants/:id/export`, and the full `/api/tenants` control plane (`lib/fathom_web/router.ex:81-94`, `require_admin_auth`) — create, delete (irreversible GDPR erasure), fork, suspend, restore (overwrites live data), and token mint/rotate/revoke for *every tenant*. It is shared across all operators, has no rotation story (change it and every operator is logged out simultaneously; no grace like the Hrana `rotate/1` path), no per-operator identity, no second factor, and no attempt throttling (#34). The data-plane token auth got a full lifecycle treatment (rotation grace, ro scope, revocation — review #24); the control plane, which is strictly more powerful, got none of it. `Plug.BasicAuth.basic_auth` uses a constant-time compare and fails closed (503) when unset — those parts are right; the problem is the credential *model*.

**Impact:** The blast radius of that one secret is the entire fleet's data (export downloads any tenant's complete SQLite file). Two platform customers can't be given API access without each being able to delete the other's tenants. This is the gap between "internal tool" and "product."

**Recommended Fix:** Move the operator surface to real authenticated sessions with per-operator accounts (`phx.gen.auth`-style) behind the existing `:browser` pipeline, and issue scoped API keys (an `api_keys` table, hashed at rest, per-key scope `read`/`manage`/`destroy`, revocable per-key without a restart) for `/api`, checked by a plug alongside BasicAuth. Delete/restore/token endpoints require the `destroy`/`manage` scopes. At minimum interim: support multiple named credentials, document rotation, and separate the *export* capability behind a distinct credential/role. Pairs with the audit log (#9) and the throttle (#34); enables the real `on_mount` check (#27).

### #9. No audit trail for control-plane or admin actions
**Severity:** High | **Category:** Missing Capability / Security | **Panels:** D, E
**Likelihood:** High (every incident/compliance review needs it; it never exists) | **Blast Radius:** No forensic answer to "who exported/deleted tenant X" across the whole fleet

**Problem:** The control plane performs irreversible, high-blast-radius, cross-tenant operations — delete/erase a tenant, export a tenant's *entire database*, fork one tenant's data into a new id, mint/rotate/revoke credentials, restore over live data — and **none emit an audit record** (who, when, which tenant, from where). Choke points: `lib/fathom_web/controllers/api/tenant_controller.ex` (all actions), `lib/fathom/tenants.ex` (`delete/1`, `fork/3`, `suspend/1`, `provision/1`), `lib/fathom/hrana_auth.ex` (`token_for/2`, `rotate/2`, `revoke/1`), `lib/fathom_web/controllers/admin_tenant_controller.ex` (`export`). There is telemetry for *counts* (`[:fathom,:tenants,:deleted]`), but that is an operational metric, not an attributable audit log. BasicAuth also carries no operator identity, so even the HTTP layer can't attribute an action to a person.

**Impact:** For a platform holding many tenants' data, there is no forensic answer to "who exported tenant X's database?" or "who deleted tenant Y?" — a compliance blocker (SOC2/GDPR accountability) and an incident-response blind spot. A compromised admin credential leaves no trail.

**Recommended Fix:** Add an append-only `audit_events` table (actor, action, shard_id, source IP, request id, outcome, timestamp) written from `Fathom.Tenants` and `Fathom.HranaAuth` control-plane functions (the natural choke points, not the controllers) — ideally in the same transaction as each mutating action. Give BasicAuth per-operator usernames (arrives with #8) so `actor` is meaningful. Emit a distinct `[:fathom,:audit,...]` telemetry event alongside the row. Export especially should always be logged; failed-auth events (from #34) should be audited too.

### #10. No per-tenant encryption boundary; S3 PUTs set no explicit server-side-encryption
**Status:** ⏸️ DEFERRED (decided 2026-07-20) — envelope/per-tenant-crypto is overkill for fathom's single-company internal-use model; per-tenant blast-radius containment has little value when all tenants belong to one company. The cheap half (explicit SSE header + boot check) may be revisited standalone if a compliance driver appears, but the finding as ranked is not pursued.
**Severity:** High | **Category:** Missing Capability / Security | **Panels:** D
**Likelihood:** Medium (S3-compatible stores vary; one IAM/bucket-policy slip) | **Blast Radius:** "Someone can read the bucket" == "someone has every tenant's data," no per-tenant key to contain it

**Problem:** Every tenant's database is stored as an opaque SQLite object with **no cryptographic tenant isolation** and no envelope/per-tenant encryption. The flush PUTs (`lib/fathom/shard/storage/s3.ex:191-236`, `flush/2`, `flush/3`) set `content-md5` and integrity metadata but **no** `x-amz-server-side-encryption`/SSE-KMS header, and there is no per-tenant key. Tenant isolation is entirely key-name discipline (good — #1 aside — but not a crypto boundary). On AWS, buckets have default SSE-S3 since 2023, so "plaintext at rest" isn't automatic there; but fathom explicitly targets S3-compatible stores (MinIO/R2/Tigris) where defaults vary, and a single over-broad IAM principal or bucket-policy slip exposes *every* tenant's full database at once with no per-tenant key to contain the breach.

**Impact:** No defense-in-depth between "someone can read the bucket" and "someone has every tenant's data." For a platform pitching millions of tenants, the absence of any per-tenant crypto boundary (or even explicit SSE) is a material gap for regulated customers and for blast-radius containment.

**Recommended Fix:** Short term — set `x-amz-server-side-encryption` (and, where used, the KMS key id) on all data/lock/snapshot/version PUTs, and add a boot check that the bucket enforces encryption. Medium term — design an envelope-encryption layer (per-tenant data key wrapped by a KMS master key) applied to the shard file before flush, so a bucket compromise yields ciphertext and tenant keys are independently revocable. Name this as a roadmap capability in the docs alongside the durability/lease design.

### #11. No billing-grade per-tenant usage metering — the counters that exist evaporate
**Status:** ⏸️ DEFERRED (decided 2026-07-20) — fathom is a single company's internal platform, not a usage-billed SaaS; there is no invoicing/tiered-plan use case, so billing-grade metering is out of scope. (Operational load visibility already exists via `ShardLoad`/`--hotspots`/the rebalancer.)
**Severity:** High | **Category:** Missing Capability | **Panels:** E
**Likelihood:** High (needed the moment there's a paying customer) | **Blast Radius:** Cannot invoice, enforce plans, or answer "why is my bill big" — and historical usage is unrecoverable

**Problem:** Every platform in the comparison class bills on exactly the numbers fathom already *computes*: rows read, rows written, storage bytes per tenant. `Fathom.ShardLoad` (`lib/fathom/shard_load.ex`) tracks checkouts/queries/`rows_read`/`rows_written` per shard — but it's a volatile ETS table, gated off by default, reset on restart, consumed only by the rebalancer and `--hotspots`. Storage usage is exported only as node-wide gauges (`lib/fathom/telemetry.ex:194-204`, `fathom.storage.objects/bytes`). There is no durable, per-tenant, monotonic usage record anywhere, and no `GET /api/tenants/:id/usage`. This is also the tenant-facing observability gap: a platform customer can't see their own query volume or DB size (the `/admin` dashboard is operator-only).

**Impact:** Fathom cannot be operated as a paid platform — no invoicing, no usage-based plans, no answer to a tenant's "why is my bill/db big." Retrofitting metering after customers exist is far harder: historical usage is unrecoverable (the counters die with each deploy).

**Recommended Fix:** A `tenant_usage` Postgres rollup: a periodic job diffs `ShardLoad.snapshot/0` (the churn-safe pattern `Rebalancer.Reporter` already uses) and upserts per-shard cumulative counters + per-shard stored bytes, flushed through the existing `Directory.Recorder` machinery to stay off the hot path. Expose `GET /api/tenants/:id/usage`. Note this forces `:shard_load` on in any metered deployment — bench that as the default-on path.

### #12. The steal-time etag touch strips the `x-amz-meta-fathom-md5` metadata, disabling the download-integrity gate for exactly the post-steal failover pull it protects
**Severity:** Medium | **Category:** Data Correctness | **Panels:** C
**Likelihood:** Medium (every crash-steal that crosses the single→multipart form boundary) | **Blast Radius:** Corruption becomes durable truth on a failover pull, silent, failover-only

**Problem:** The #17 fix (review 2026-07-14) added `x-amz-meta-fathom-md5` so integrity verification survives etag-form rotation. Both touch directions **discard** it: `single_copy_touch` (`lib/fathom/shard/storage/s3.ex:355-364`) self-copies with `x-amz-metadata-directive: REPLACE` and re-sends no metadata; `multipart_copy_touch`/`create_multipart` (`:383-416`) send none, so the completed object has empty metadata — contradicting the claim at `s3.ex:558-566` that the metadata "survives the rotation." In the single→multipart direction the resulting etag is multipart-form (`…-1`), so `verify_integrity/3` falls through *both* checks (`meta_md5` nil → `verify_md5` → non-MD5 etag → no-op): the stealing node's first pull — a failover of a possibly-multi-MB shard over a possibly-degraded network, the highest-risk pull in the system — runs with **no content verification at all** until the next single-part flush restores it.

**Impact:** A torn/corrupted transfer during a steal-takeover pull is promoted, adopted as authoritative, and flushed back with a valid If-Match — the corruption-becomes-durable-truth path the whole integrity chain (#37/#17/#24) exists to close, open at its most critical link. Silent, and only in the failover regime, so happy-path tests never see it.

**Recommended Fix:** `touch_object` already HEADs the object first; thread the existing `@md5_meta` value through — `single_copy_touch` re-sends it alongside the `REPLACE` directive, and `create_multipart` sets it on the multipart upload. ### #13. The steal decision still trusts wall clocks — a clock step becomes a data-loss event
**Severity:** Medium | **Category:** Reliability (split-brain guard) | **Panels:** B
**Likelihood:** Low (VM live-migration, bad NTP step, hypervisor pause with jumped RTC) | **Blast Radius:** A single mis-clocked node sheds ACKed writes fleet-wide (steals shards; victims fence and quarantine)

**Problem:** `owner_live?` (`lib/fathom/shard/storage/s3.ex:1156-1157`) compares the *reader's* wall clock to an expiry the *owner* stamped with its own clock; the 5s `steal_margin_ms` is the entire skew budget, enforced only by "run NTP and watch a tripwire." A node whose clock steps forward by more than the heartbeat's remaining life + 5s (VM live-migration, bad NTP step, hypervisor pause resumed with a jumped RTC — precisely the environments that also cause the GC-pause zombies this system defends against) will **wrongfully steal from a live owner**. The steal-touch means the victim self-fences rather than double-writes — safety holds — but the victim quarantines its un-flushed ACKed writes: a skew event becomes a data-loss event. The codebase already contains the clock-free alternative: `judge_previous` (`lib/fathom/shard/heartbeat.ex:391-418`) decides liveness by reading the heartbeat **twice** and checking frozen-vs-advancing expiry — pure observation of progress, immune to skew — but only for this node's own prior incarnation.

**Impact:** A single mis-clocked node can shed ACKed writes fleet-wide while every individual component behaves "correctly."

**Recommended Fix:** Generalize the double-read: in `acquire_existing`, when `owner_live?` says `:dead` purely by wall-clock margin, confirm with a second heartbeat read after a short delay (or on the next acquire attempt, memoizing the first observation) — steal only if the expiry is *frozen*. Cost: one extra GET + delay on the already-≥35s steal path. Cheaper complement: derive `now` from the S3 response's `Date` header so both sides read the same clock. Add a skew gauge (heartbeat PUT response Date vs local time) to telemetry.

### #14. `Fathom.Shards.flush/1` maps a `flush_now` call *timeout* to `:ok` — the flush-before-fork primitive can report success on a non-durable shard
**Severity:** Medium | **Category:** Data Correctness | **Panels:** A
**Likelihood:** Medium (degraded storage or a live-writer livelock) | **Blast Radius:** A fork/export "after flush" silently clones stale bytes

**Problem:** `flush/1` (`lib/fathom/shards.ex:267-281`) wraps `Fathom.Shard.flush_now/1` in `catch :exit, _ -> :ok`. The comment justifies this for "the coordinator stopped mid-call" — and review 2026-07-18 #4 correctly made every `terminate` clause settle `flush_waiters` with an explicit error, so that direction is safe. But the blanket catch **also** swallows `:exit, {:timeout, _}`: a hung/slow store past the 60s `@flush_now_timeout` (or a live writer keeping the shard re-flushing, the documented livelock) returns `:ok` while the shard is *not* durably clean. ### #15. The steal-touch defeats the warm standby exactly on crash failover — and the failover-RTO bench never exercises the steal path
**Severity:** High (impact) / Medium (it's a perf+honesty regression, not data loss) | **Category:** Performance / Reliability (failover RTO) | **Panels:** B
**Likelihood:** High (every data-bearing crash failover) | **Blast Radius:** The warm-follower fleet cost buys nothing in its headline scenario; the published warm-RTO number measures a scenario that never occurs

**Problem:** Every crash-steal calls `touch_object` (correctly — expert review #3), which **rotates the data object's etag** (`lib/fathom/shard/storage/s3.ex:1089`). The warm follower's cache is keyed on the *pre-touch* etag. On crash failover — the warm standby's design scenario — the survivor's speculative `pull_if_changed` either (a) races ahead of the touch, 304s, promotes the cache… then `revalidate_touched` (`lib/fathom/shard.ex:423-462`) sees `etag != touch_post_etag` with `warm? == false` and falls into `true -> repull` (`:459-461`) — an **unconditional full-body pull**, discarding the promoted warm copy; or (b) runs after the touch and gets a 200 full-body transfer outright. Either way the crash path pays the full pull the warm standby exists to avoid. The 2.3× win only materializes on *planned* handoffs (clean release → fresh `create_lock`, no touch). Worse, `Fathom.Bench.failover_rto` (`lib/fathom/bench.ex:284-306`) seeds the object with **no dead owner's lock**, so its "warm" measurement takes the no-steal, no-touch path — `failover_warm_s3_p50_us` measures a scenario that never occurs on real crash failover.

**Impact:** Crash-failover RTO for data-bearing shards is silently cold (~body transfer + RTTs), the warm-follower fleet cost (O(cached) conditional GETs per poll per standby) buys nothing in its headline scenario, and the bench overstates the win.

**Recommended Fix:** The lease already carries the proof: in `revalidate_touched`'s cold branch, add `etag == lease[:touch_pre_etag] -> {:ok, post}` — if the pulled/promoted bytes carry the exact etag the touch If-Matched, they are byte-identical to the touch's source (a self-copy moves no bytes), so adopt the post-touch etag with **no re-pull** (the same provenance argument the warm branch makes via the sidecar). Then make the bench honest: seed a dead-owner lock (expired heartbeat) before the "warm" samples so `failover_warm_s3_p50_us` measures the steal+touch path. The fix lands in the region #30 flags as untested.

### #16. At-capacity eviction can starve behind busy-but-LRU-cold shards — `Lru.touch` fires only at checkout, so long-lived streams look ancient
**Severity:** Medium | **Category:** Reliability | **Panels:** A
**Likelihood:** High on the product's core workload (persistent WebSocket streams) | **Blast Radius:** Spurious tenant-down 503s at capacity; the soft cap silently degrades into a hard cap

**Problem:** `Lru.touch/1` (`lib/fathom/shards/lru.ex:43-50`) stamps recency **only on checkout**. A tenant on a persistent WebSocket stream (the primary `django-libsql` transport — one checkout, then hours of queries on the held connection) never re-touches, so its shard ages to the front of `lru_order/1` while continuously busy. `evicted_for_room?` (`lib/fathom/shards.ex:433-473`) probes only the **16 coldest** entries (`@max_evict_probes 16`, `:419`); a busy probe returns `{:drain_aborted, …}` → `{:cont, false}`. **Recommended Fix:** Cheapest: have the coordinator re-stamp `Lru.touch(id)` on `checkin`/`:DOWN` release (already in that code path, one ETS insert). Add the mixed busy-front + idle-tail regression test.

### #17. No jitter or node-level concurrency bound on the periodic durability flush — synchronized flush storms after mass adoption
**Severity:** Medium | **Category:** Reliability / Performance | **Panels:** A
**Likelihood:** High after any failover/LB flip that re-homes a burst | **Blast Radius:** Recurring correlated p99 spikes + cold-open starvation on the post-failover survivor node

**Problem:** Each coordinator arms a fixed `:shard_flush_interval_ms` (default 5s) timer with **no jitter** (`lib/fathom/shard.ex:1957-1967`, `schedule_flush/1`), and each dirty shard spawns its own unbounded flush task (VACUUM INTO + full-object PUT) through the one shared Finch pool (`:1102-1141`, `:durability_flush` → per-coordinator `Task.async`). Timers are staggered only by open time — but a failover or LB flip re-homes a *burst* of shards within one interval, phase-aligning their timers. Every 5s thereafter, N concurrent snapshots (disk + CPU) and N PUTs fire together, competing with cold-open pulls for the same pool — exactly when a survivor is absorbing traffic. There is at most one task *per shard* but nothing bounds tasks *per node*.

**Impact:** Recurring correlated p99 latency spikes and cold-open starvation on post-failover nodes; worst at the tightened 5s interval the RPO work just shipped.

**Recommended Fix:** (1) Jitter the interval (`interval ± rand(interval/4)`, or jitter only the first schedule after open). (2) Add a cheap node-level flush token (an `:ets.update_counter` semaphore or `:atomics` counter, checked in `:durability_flush`; over the cap ⇒ reschedule with short backoff, shard stays dirty — the safe direction). Both config-gated, consistent with codebase style. Bench the flush-rate telemetry (`[:fathom, :shard, :flush]`, audit #20) before/after on a mass-adoption scenario.

### #19. `CommandPoller`'s in-flight set leaks permanently if a batch task dies to an exit signal — commands stuck `pending` forever
**Severity:** Medium | **Category:** Reliability | **Panels:** A

### #20. Flip-before-drain makes every handoff a client-visible error window — nothing bridges the target's `{:held}` gap
**Severity:** Medium | **Category:** Reliability | **Panels:** B
**Likelihood:** High whenever autonomous rebalancing is armed | **Blast Radius:** A burst of tenant-visible errors on the *busiest* tenant (the policy moves the hottest shards)

**Problem:** The handoff ordering is right (flip → drain; the lease makes any interleaving safe). But between step 2 (LB flips to target) and step 4 (source releases), every request landing on the target fails `acquire_lease` with `{:held, source}` — and `retry_checkout?` (`lib/fathom/shards.ex:91`) deliberately excludes `:held`, so the error goes straight to the client. **Recommended Fix:** Add `on_mount {FathomWeb.AdminAuth, :require_admin}` to `live_session :admin` re-checking the operator identity (which becomes real once #8 lands), and assert authorization at the top of destructive `handle_event`s. Test that the admin LiveView refuses a mount without admin context.

### #28. Missing capability: no node-level graceful drain lever — deploys and scale-downs rely entirely on supervisor-shutdown ordering
**Severity:** Medium | **Category:** Missing Capability | **Panels:** A
**Likelihood:** High (every deploy is a lifecycle event) | **Blast Radius:** Every deploy exercises the crash-adjacent path — burst flush load, hard-cut live streams, and (per #2) real loss on ephemeral disks

**Problem:** Everything drains *per shard*: `Shards.drain/2`, the rebalancer's `HandoffJob`, the eviction path. There is no `drain_node`/pre-stop operation that, ahead of SIGTERM, walks this node's open coordinators and runs ordered voluntary drains (refuse new checkouts → let streams finish → flush + release lease) with a bounded overall budget (`lib/fathom/shards.ex` has per-shard `drain/2` only; `lib/fathom/application.ex` shutdown ordering is the only mechanism). Consequently every deploy funnels through the shutdown path — including #2's lossy busy-terminate clause — with all coordinators flushing simultaneously inside one 60s window, and the LB keeps routing traffic until the health port dies. The rebalancer already proved the per-shard voluntary-drain direction is safe ("flip-before-drain"; a healthy node can't be stolen from); the node-scope composition is the missing piece.

**Impact:** Deploys — the single most common lifecycle event — exercise the crash-adjacent path rather than the voluntary one: burst flush load, avoidable hard cuts of live streams, and (per #2) real loss on ephemeral disks.

**Recommended Fix:** Add `Fathom.Shards.drain_all(budget_ms)` — snapshot the Registry, issue `request_drain` fan-out with bounded concurrency (reuse `await_coordinator_exit/3`), report `{drained, busy, timed_out}` — plus a health-plug "draining" state so the LB stops routing first. Wire it as a release pre-stop (`bin/fathom rpc`) in the chaos rig's rolling-deploy scenario, and measure the deploy-time loss window with `mix fathom.rpo` to prove it reaches zero for clean shutdowns. This is the structural companion to #2.

### #30. Test gap: the steal-touch takeover revalidation — the subtlest fence logic in the tree — has zero test coverage
**Severity:** Medium | **Category:** Test Gap | **Panels:** B
**Likelihood:** — (latent) | **Blast Radius:** The branchiest, most safety-critical decision tree can only regress in production against real S3

**Problem:** The cluster suite pins the core contract well (steal-on-lapse, epoch bump, self-fence at flush, lapse broadcast, fail-closed checkout, transient-renew tolerance). But the takeover-revalidation lattice — `revalidate_takeover`/`revalidate_touched`/`post_lease_warm_check` (`lib/fathom/shard.ex:395-532`): the `etag == post` fast path, the forged-provenance quarantine, the release-in-gap warm check, the vanished-object branch — is exercised by **no test**. **Recommended Fix:** Add a test storage backend (or extend Local behind a flag) that simulates etag rotation on steal — `acquire_lease` returns `took_over`/`touch_pre_etag`/`touch_post_etag` and rotates the stored etag without changing bytes. ### #31. Read scaling is absent, and the pieces to ship a bounded-staleness read tier already exist
**Severity:** Medium | **Category:** Architecture / Missing Capability | **Panels:** E
**Likelihood:** — (roadmap) | **Blast Radius:** "Single home node serves all reads" is the first architectural objection a prospective adopter raises

**Problem:** A2 (live WAL streaming) is deferred by documented decision (`docs/phase2-scoping.md` §A2) — this is not re-arguing it. The new angle: fathom has built *both* halves of a cheaper read-replica story and left them unconnected. The warm follower (`lib/fathom/shard/warm_follower.ex`, "never serves" by design) already pre-pulls and etag-revalidates near-fresh copies of the hot set every poll; the `ro` token scope (review #24) already exists and rides per-stream. A follower serving **read-only, bounded-staleness** streams from its validated cache (staleness ≤ flush interval + poll interval — the same bound the crash-RPO contract already asks operators to accept) is a read-scaling tier with no WAL shipping, no new replication protocol, and no writer-path changes. Today every read hits the one home node, so a read-heavy tenant's ceiling is one box and the `ro` scope has no scaling payoff.

**Impact:** The comparison class leads with read replicas / embedded replicas; "single home node serves all reads" is the first architectural objection, and the honest answer today is "wait for A2."

**Recommended Fix:** An opt-in `ro`-stream service on warm-follower nodes: `ro`-scoped streams may be routed (LB rule or client-chosen replica hostname) to a follower, which serves from its etag-validated cache and refuses writes (the `FILO_READONLY` path exists). Document the staleness bound explicitly. Gives the deferred A2 a concrete landing slot later (same read tier, tighter bound).

### #32. Live WAL streaming (A2) is now the binding constraint — full-file VACUUM+PUT bounds both RPO and cost
**Severity:** Medium | **Category:** Architecture / Missing Capability | **Panels:** B
**Likelihood:** — (roadmap; the "millions of shards" economics break on the write-active tail first) | **Blast Radius:** RPO floor, S3 cost, and flush latency all set by the same full-file primitive

**Problem:** A2 is deferred *by decision*, so this is an evaluation. With the fence, admission, rebalancing, and lifecycle layers done, the durability primitive is now the limiting term. Every write-active shard pays a **full-database read (VACUUM INTO) + full-object upload every 5s** (`lib/fathom/shard.ex:65`, `snapshot_and_upload` at `:1796`): (a) the RPO floor can't push below a few seconds — the flush is O(file size), measured ~3.5 RTT un-overlapped (AGENTS.md latency-cost run); (b) flush cost scales as `active_writers × shard_size / interval` — at "millions of shards," even 1% write-active of 1 MB shards at 5s is ~2 GB/s of sustained PUT fleet-wide plus per-PUT fees; (c) PITR inside the interval is impossible; (d) #3/#15/#21 all shrink to near-irrelevance with sub-second WAL shipping. The three cheaper mitigations in the project's own reports (overlapping the ~3.5-RTT drain/release path, per-shard adaptive intervals, delta-aware flushes) are tuning, not a fix for the O(file) shape.

**Impact:** RPO, S3 cost, and flush-latency ceilings all set by the same full-file primitive; the "millions of shards" economics break on the write-active tail first.

**Recommended Fix:** Promote A2 from deferred to next major initiative: ship WAL frames (or SQLite session/changeset deltas) to `<shard>@wal-<seq>` objects between full-file checkpoint-flushes, with the existing epoch as the fencing token on segment keys, and compaction folding segments into the base object at idle. Start with the narrowest slice — segment upload + cold-open replay behind a gate — keeping the current full-file path as fallback. Interim: overlap the flush path's serial round-trips (3.5 RTT → ~2).

### #33. `Tombstones`/`Suspensions` restart during a Postgres outage silently drops the deny sets for up to 5 minutes with no fast retry
**Severity:** Low | **Category:** Reliability / Shard Isolation (lifecycle contract) | **Panels:** A
**Likelihood:** Low (a Postgres wobble coincident with a GenServer restart) | **Blast Radius:** Up to a 5-minute per-node window where delete (410) / suspend (403) guarantees don't hold

**Problem:** The ETS deny sets die with their owner GenServers. On restart, `init` calls `load_from_directory/0`, which **rescues any Postgres failure and continues with an empty table** (`lib/fathom/tenants/tombstones.ex:66-75, 112-123`; same shape in `suspensions.ex`), then waits the full `@default_refresh_ms` (5 min) before retrying. During a correlated control-plane wobble (exactly when these processes restart), a deleted tenant's subdomain re-mints an empty shard (breaking the 410 contract) and a suspended tenant serves normally. The boot-load design is sound; the gap is that a *failed* load is treated identically to a successful one.

**Impact:** Up to a 5-minute window per outage-coincident restart where the delete/suspend lifecycle guarantees don't hold on that node. Data exposure is limited (the object was purged), but the re-minted empty shard confuses the directory and the operator.

**Recommended Fix:** On a failed initial load, schedule a short-backoff retry (1s → 5s → 30s, capped) instead of the full refresh interval, and emit `[:fathom, :tenants, :denylist, :degraded]` telemetry while unloaded. Same for `Suspensions`. Test: start the GenServer with the directory raising, assert the retry converges within seconds once it recovers. The S3-tombstone backstop from #6 also hardens this scenario.

### #34. No rate limiting / lockout on admin authentication (and no throttle on the control-plane surface)
**Severity:** Low | **Category:** Security / Reliability | **Panels:** D
**Likelihood:** Medium (online brute force of one shared password) | **Blast Radius:** The one shared admin password is brute-forceable; expensive control-plane ops (list/export/fork) are hammerable

**Problem:** The admin BasicAuth (a single shared password — #8) has no attempt throttling, lockout, or backoff (`lib/fathom_web/router.ex:81-94`), and the `/api/tenants` control plane has no rate limiting of its own (`:56-77`; `NovelLimiter` protects only novel *data-path* minting). **Impact:** The shared admin password is online-brute-forceable with no lockout; an authenticated-but-hostile or buggy client can hammer expensive control-plane operations unbounded.

**Recommended Fix:** Add a per-IP failed-auth throttle (a small `Hammer`/ETS token bucket) in front of `require_admin_auth`, and a modest rate limit on the `/api` scope. Pairs with the audit log (#9) — failed-auth events should be audited.

### #35. `Tenants.provision/1` mints TLS-unreachable ids without a warning — the DNS-safety rule is documented but unenforced at the one enforceable point
**Severity:** Low | **Category:** Reliability (provisioning correctness) | **Panels:** E
**Likelihood:** Medium (any wildcard-TLS deployment provisioning an underscore id) | **Blast Radius:** One tenant handed an un-servable URL, opaque TLS failure days later

**Problem:** The wildcard-TLS caveat (underscore ids can't be served under `*.<zone>` — RFC 6125) is documented in `ShardId` (`lib/fathom/shard_id.ex:15-31`, "naming guideline, not enforced"), and keeping the *validator* permissive is sound. But `provision/1` (and `tenant_controller.ex:20`) is where the deployment's choice is *known* — it composes and returns the `libsql://<id>.<base>` connection URL as the tenant's canonical address. Today it happily hands back a URL for `my_tenant.fathom.example` that no wildcard-TLS deployment can serve, with no warning. The traffic-implied minting path can't check this, but the explicit API can.

**Impact:** A platform customer provisions via the API, receives a URL, and gets an opaque TLS handshake failure in production — a confusing, slow-burn support case for a constraint fathom knew at mint time.

**Recommended Fix:** In `provision/1` (and the fork dst path), when the id contains `_`: reject with a clear error by default when a deployment flag says TLS-wildcard serving, otherwise include a `warnings: ["id not wildcard-TLS-servable"]` field in the API response. Keep `ShardId.valid?` untouched.

### #36. No client-facing error-code reference — the `FILO_*` contract is scattered across internal docs
