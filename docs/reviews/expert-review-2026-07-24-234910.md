### Constraint governing every finding

> "Let's look for performance gains… we can lose no data correctness or reliability."

Every finding below carries an explicit **Correctness/reliability** line. Findings that would trade
durability for speed were either rejected by the panels or are labeled with the exact new failure

### Disjointness from the 2026-07-23 audit

The prior audit (`expert-review-2026-07-23-001259.md`, 31 findings, 24 fixed) covered per-query
Elixir overhead, row encoding, S3 round-trip *counts*, and accounting. This round deliberately
took five untouched angles: SQLite's own configuration, BEAM runtime tuning, socket/listener
configuration, bytes-and-I/O-passes (as opposed to RTT count), and Postgres schema/index fit.
No finding below re-reports a covered item. Panels were given the covered-ground list verbatim.

### TLDR — Top 6

1. **`PRAGMA busy_timeout` silently disables exqlite's cancellable busy handler** — a lock wait becomes an uninterruptible 5 s dirty-scheduler park, and `:query_timeout_ms` cannot cut it short. Cross-tenant starvation through a knob built to prevent it.
2. **The release ships zero BEAM tuning — no `rel/` at all.** `+SDio 10` is a hard node-wide ceiling of 10 concurrent SQLite operations (every exqlite NIF is dirty-IO); `+Q 65536` caps ports below the demonstrated density.
3. **Every `COMMIT` dirties the shard, even when nothing wrote** — a read-only Django tenant under `ATOMIC_REQUESTS` gets a full-file VACUUM + S3 PUT every 5 s. Directly defeats the write-gated flush design.
4. **`wal_autocheckpoint` left at default** — WAL checkpoints are billed inline to a random tenant query while the coordinator, which has no latency SLA, never checkpoints except at drop.
5. **Hrana auth does a Postgres point-read per shard per 30 s, inline on stream-open** — scales with shard count, not revocation events, against a pool of 10.
6. **The Hrana Bandit listener has no transport options at all** — one listen socket, one 1024-deep accept queue, no `reuseport`, for a workload that opens 4096 connections at once.

### #1. `PRAGMA busy_timeout` destroys exqlite's cancellable busy handler; lock waits park dirty-IO threads uninterruptibly for 5 s
**Severity:** High | **Category:** Reliability + Performance | **Panels:** P1
**Likelihood:** High — every connection, default path | **Blast Radius:** node-wide, cross-tenant

**Problem:** `lib/fathom/shard/connection.ex:31` sets `PRAGMA busy_timeout=5000`. That routes to
`sqlite3_busy_timeout()`, which **unconditionally replaces** any installed busy handler
(`deps/exqlite/c_src/sqlite3.c:189046`). exqlite installs its own custom handler at open
(`sqlite3_nif.c:497`) and documents this exact hazard in `Sqlite3.set_busy_timeout/2`:

> "Unlike `PRAGMA busy_timeout` (which internally calls `sqlite3_busy_timeout()` and replaces any
> custom handler), this function only updates the timeout value that the custom busy handler reads.
> This preserves the ability to cancel busy waits via `cancel/1`."

Three consequences, all currently live:
1. SQLite's default handler (`sqlite3.c:188916`) is a bare `sqlite3OsSleep` loop checking neither
   `isInterrupted` nor any cancel flag — so `with_deadline`'s `Sqlite3.interrupt(conn)`
   (`connection.ex:257`) **cannot** cut short a query blocked on the write lock. `:query_timeout_ms`
   bounds VDBE execution only, not lock waits — which are the actual pathology under a convoy.
2. The lost custom handler carried a caller-liveness check (`sqlite3_nif.c:352`,
   `enif_is_process_alive`); a dead Hrana stream's busy wait now sleeps the full 5 s.
3. `multi_step` is `ERL_NIF_DIRTY_JOB_IO_BOUND`, so each blocked query parks a dirty-IO thread
   for up to 5 s, uninterruptibly. With `+SDio 10` (see #2), 10 blocked queries starve the entire
   pool and every co-located tenant stalls behind them.

**Verified:** exqlite exports `set_busy_timeout/2` and `cancel/1` as **non-dirty** NIFs
(`sqlite3_nif.c:2090, 2092` — flag `0`); fathom calls `Sqlite3.interrupt` at `connection.ex:257`.

**Impact:** Bound of 10 blocked queries × 5 s = full dirty-IO pool starvation, node-wide, across all
co-located tenants — the noisy-neighbour blast radius `:max_checkouts_per_shard` and
`:query_timeout_ms` exist to contain, leaking through a knob that does not actually apply. Moves
per-node q/s under contention and `tpcc-fleet` per-txn p99.

**Correctness/reliability:** **Strictly better.** Restores a cancellation path that exists in the dep
and is currently disabled. Zero durability change — same timeout value, different handler.

**Recommended Fix:** In `connection.ex` `open/1`, `Sqlite3.set_busy_timeout(conn, 5000)` in place of
the PRAGMA. In `with_deadline`'s watchdog, `Sqlite3.cancel(conn)` in place of `Sqlite3.interrupt`
— `cancel/1` sets `conn->cancelled` **and** calls `sqlite3_interrupt`, and deliberately avoids
`conn->mutex` (`sqlite3_nif.c:1987-2011`) so it cannot block behind the running query. The
stale-cancel case is already handled upstream: `connection_stash_caller` resets `cancelled = 0` at
the top of every subsequent op (`sqlite3_nif.c:416`). Apply the same swap at `shard.ex:1716`.

**How to measure:** `@tag :bench` regression test — hold a write txn on conn A, issue a conflicting
write on B with `:query_timeout_ms: 200`, assert `FILO_QUERY_TIMEOUT` in ≲300 ms. **Fails pre-fix**
(takes the full 5 s and returns `SQLITE_BUSY`). Fleet: `chaos.sh tpcc-fleet` p99.

### #2. The release ships zero BEAM tuning — there is no `rel/` at all, and `+SDio 10` is a hard ceiling of 10 concurrent SQLite operations node-wide
**Severity:** Critical | **Category:** Performance / capacity wall | **Panels:** P2, P3
**Likelihood:** Certain — every deploy | **Blast Radius:** node-wide

**Problem:** `mix.exs:22-29` defines a release with only `include_executables_for` +
`runtime_tools`. **Verified:** `rel/` does not exist; no `vm.args`, no `ERL_FLAGS`/`ERL_AFLAGS`/
`ELIXIR_ERL_OPTIONS` anywhere in the repo (`config/`, `deploy/`, Dockerfiles — zero hits).

Four separate defaults are therefore load-bearing:

**(a) `+SDio 10` — the big one.** Every exqlite NIF is `ERL_NIF_DIRTY_JOB_IO_BOUND`
(**verified**, `sqlite3_nif.c:2064-2089`: `open`, `prepare`, `step`, `multi_step`, `columns`,
`changes`, `last_insert_rowid`, …). ERTS defaults to ten dirty-IO threads regardless of core count.
So the *entire node's* SQLite work — every tenant, every shard — funnels through 10 OS threads. Two
fathom properties make those threads *block*: `synchronous=FULL` fsyncs inside `multi_step`, and
`busy_timeout` sleeps on the calling thread (#1). A read query costs ≥4 dirty-IO dispatches; at the
measured ~27k q/s that is ~135k dirty-IO jobs/s across 10 threads. The commit ceiling is
`10 / fsync_time` — 10–20k commits/s on cloud block storage. **The "clean CPU plateau" reported in
`tpc-fleet-elixir-driver-2026-07-24.md` has never been tested against this hypothesis, and it costs
one env var to rule in or out.**

**(b) `+P 262144` / `+Q 65536`.** Production materializes 3–4 processes and 1 port per served shard
(Bandit handler, `Filo.Stream`, coordinator, optional watchdog). `chaos.sh served-data` reached
105k shards held (~35k/node) and extrapolates to ~50k/node. `docker-compose.yml:70-73` already
raises `nofile` to 65536 so fds stop binding — but **`+Q` caps ports at 65536 regardless of
`nofile`**, so that headroom is unreachable. Both limits are hard cliffs, not degradation: `+P`
exhaustion makes `spawn` throw `system_limit` (refused checkouts); `+Q` exhaustion makes `accept`
return `{:error, :system_limit}` (listener stops accepting). This silently invalidates the
"fds are a knob, not an architectural wall" conclusion an order of magnitude below the fd limit.

**(c) `+IOt 1` / `+IOp 1`.** One OS thread dispatches socket readiness for every socket on the node
— Hrana connections, health, Phoenix, and every Finch connection to S3. ThousandIsland sockets are
`active: false`, which does not bypass the pollset. Unmeasured, but the knob is at its floor two
orders of magnitude below the documented target working set.

**(d) `+sbwt none` / `+sbwtdcpu none`.** Scheduler busy-wait before sleeping burns CPU on a
co-tenanted VM — the chaos rig is exactly that. Standard lever for I/O-bound BEAM services.

**Impact:** (a) is potentially the fleet's actual throughput ceiling and is currently unattributed.
(b) caps a node at ~65k concurrent connections. Moves `tpc-fleet`/`tpcc-fleet` aggregate tps,
`chaos.sh served`/`served-data` ceilings.

**Correctness/reliability:** **Neutral-or-better on all four.** These are thread-count, table-size,
and spin-policy knobs — no data path, no durability guarantee, no ordering. (a) *improves*
reliability by removing the convoy-starves-the-node mode. Memory cost is trivial: ~1 MB RSS per 32
dirty threads; `+P 1048576` + `+Q 262144` preallocate ~10 MB of pointer tables against the ~6 GB/node
the served-data regime already uses.

**Recommended Fix:** `mix release.init`, then in `rel/vm.args.eex`:
```
+SDio 64          # exqlite runs every SQLite op on dirty-IO; 10 is the ERTS default, not a fit
+P 1048576        # 3-4 processes per served shard at 35k+/node demonstrated
+Q 262144         # ports: nofile is already 65536; +Q was the real cap
+IOt 4
+IOp 2
+sbwt none
+sbwtdcpu none
```
**A/B each lever separately** — landing them as one commit makes none of them attributable. Add a
telemetry gauge on `process_count/process_limit` and `port_count/port_limit` so approach-to-limit is
alertable rather than a cliff. Independently, consider lowering `busy_timeout` from 5000 to a few
hundred ms once #1 lands — a 5 s thread pin is an expensive way to wait.

**How to measure:** `chaos.sh tpc-fleet` with `TPC_NET=container TPC_DRIVER=elixir` at N=1024,
sweeping `+SDio` 10/64/256 via the compose `fathom-env` anchor. Direct proof: sample
`:erlang.system_info(:dirty_io_run_queue)` via `bin/fathom rpc` during the run — a standing non-zero
dirty-IO run queue is the smoking gun. `msacc` attributes poll-thread time for (c).

### #3. Every `COMMIT`/`END` dirties the shard — a read-only transaction triggers a full VACUUM + full-object PUT
**Severity:** High | **Category:** Performance / durability PUT volume | **Panels:** P4
**Likelihood:** High — Django `ATOMIC_REQUESTS` is a default-shaped config | **Blast Radius:** per read-only tenant, fleet-wide

**Problem:** `lib/fathom/shard_executor.ex:165-166`:
```elixir
if wrote?(result, sql) or ends_transaction?(sql),
  do: Fathom.Shard.WriteCounter.bump(shard_id)
```
`ends_transaction?` (`:281-284`, **verified**) matches any `COMMIT`/`END` unconditionally. So a
transaction in which **nothing wrote** still marks the shard dirty. Django with
`ATOMIC_REQUESTS = True`, or any `transaction.atomic()` around a read view, emits
`BEGIN … SELECT … COMMIT` — so a purely read-only tenant is dirty at every flush tick.

**Impact:** Directly defeats the invariant `docs/durability.md` states as the storm fix
("durability PUTs track *writes*, not open-shard count"). Each such shard pays, every 5 s: a full
`VACUUM INTO` (full read + full write + fsync, see #4/#10), a full read for the MD5, and a
**full-object PUT**. At 1,000 read-active open shards × 640 KiB that is ~128 MB per 5 s ≈ 25 MB/s of
pure-waste egress per node, plus 1,000 PUTs per 5 s of request cost.

**Correctness/reliability:** **Neutral.** The unconditional bump exists for a real race, documented
at `shard_executor.ex:155-164`: a periodic flush capturing the watermark *between* the last data
statement and the COMMIT would snapshot without the uncommitted rows. That case has "something wrote
in this transaction" true and must still bump — and will. The only behaviour that changes is
transactions where **no statement wrote at all**, in which there is by construction nothing to lose.

**Recommended Fix:** Track a per-stream "wrote since BEGIN" boolean in the owning process's
dictionary keyed by the conn ref — the exact idiom the statement cache already uses
(`connection.ex:124-147`), race-free because the connection is single-owner for the stream's life.
Set it at **every** existing bump site — including the `exec` script path at
`shard_executor.ex:345`, which bumps unconditionally and would otherwise have no COMMIT re-bump —
clear on BEGIN and on COMMIT/ROLLBACK, gate the `ends_transaction?` bump on it. Do **not** compare
the shared ETS counter across BEGIN/COMMIT: another stream's write to the same shard would
spuriously re-dirty.

**How to measure:** `[:fathom,:s3,:op]` PUT count + bytes (`s3.ex:1798`) under a read-only
`tpc-fleet` load with `ATOMIC_REQUESTS`-shaped framing; `[:fathom,:shard,:flush]` `outcome: :uploaded`
rate.

### #4. `wal_autocheckpoint` at its default bills every WAL checkpoint to a random tenant query; the coordinator never checkpoints except at drop
**Severity:** High | **Category:** Performance (tail latency) | **Panels:** P1
**Likelihood:** High — every write-active shard | **Blast Radius:** per shard, p99

**Problem:** Nothing sets `wal_autocheckpoint`, so every serving connection inherits
`SQLITE_DEFAULT_WAL_AUTOCHECKPOINT 1000` (~4 MB at 4096-byte pages). SQLite runs that checkpoint
**inline, inside the committing statement**, on whichever connection crossed the threshold — and
under `synchronous=FULL` it also fsyncs the main database file.

Meanwhile the coordinator's periodic flush explicitly does *not* checkpoint: `snapshot/2`
(`shard.ex:2084-2086`, **verified**) runs `VACUUM INTO`, which reads the WAL but never truncates it.
`docs/durability.md` already records the other half of the interaction — the VACUUM snapshot "is
also the long-lived reader that holds back the passive WAL checkpoint." So on a write-active shard
the flush task **blocks** the auto-checkpoint a tenant query is trying to run, the WAL grows past
1000 frames, and the next tenant to win the race pays a checkpoint now *larger* than 4 MB.

This is pure work misplacement: the checkpoint must happen, but it is billed to a latency-sensitive
client query instead of to a flush task that already exists, already opens a connection to the same
file, and has no client waiting.

**Impact:** A periodic multi-ms-to-tens-of-ms spike on one arbitrary tenant query per ~4 MB of WAL,
per shard — a p99/p999 tail with no p50 signal, the shape that hides from throughput benchmarks.
Moves `Fathom.ShardLatency` p99 and `tpcc-fleet` per-txn p99. Secondary: an un-checkpointed WAL
inflates local disk and lengthens the pre-drop `wal_checkpoint(TRUNCATE)` inside the 60 s shutdown
budget on every rolling deploy.

**Correctness/reliability:** **None — same guarantees.** WAL frames are already fsynced at commit by
`synchronous=FULL`; a checkpoint only relocates already-durable frames. Keeping a *raised* (not
disabled) autocheckpoint preserves the safety net if the coordinator is wedged.

**Recommended Fix:** (1) `PRAGMA wal_autocheckpoint=4000` on serving connections — a backstop ~4×
the default so the coordinator wins the race in steady state but the WAL can never run away. Do
**not** set `0`. (2) In the flush task, after a successful `snapshot/2`, on the **same connection**
(read txn ended, checkpointer unblocked) run `PRAGMA wal_checkpoint(PASSIVE)` before close. PASSIVE
never blocks writers and never waits on readers, so it cannot add latency to a concurrent tenant;
ignore a `busy=1` result.

**How to measure:** `mix fathom.scale --hotspots --stream-len 64`, comparing p99/max (p50 should be
flat — the win is entirely in the tail). Fleet: `chaos.sh tpcc-fleet` per-txn p99 at N≥256. Direct:
`@tag :bench` asserting `<path>-wal` size stays bounded across a sustained write soak.

### #5. Hrana auth does one Postgres point-read per shard per 30 s, inline on the stream-open path
**Severity:** High | **Category:** Performance / hot-path coupling | **Panels:** P5
**Likelihood:** High whenever `HRANA_AUTH=required` | **Blast Radius:** every stream open

**Problem:** `lib/fathom/hrana_auth/revocations.ex:111-129` — on a TTL miss, `floor_info/1` runs
`Directory.token_floor_info/1` (`directory.ex:588-597`) **in the calling stream process**. TTL is
`:hrana_revocation_ttl_ms`, default **30 s** (`revocations.ex:33`), keyed per shard — so the
read-through rate is `distinct_shards_per_node / 30 s`, scaling with *shard count*, not revocation
events. A push channel already exists (`:fathom_revocations`); the TTL is only a missed-notification
backstop, but it drives the entire cost.

**Impact:** At 10k active shards/node ≈ 333 reads/s; at 100k ≈ 3,300/s — each taking a connection
from a pool of **10** (see #20). At ~0.7 ms per checkout+round-trip that is ~2.3 connections
continuously busy on revocation reads before Oban is considered. This is the same per-checkout
Postgres coupling `Directory.Recorder` and `Migrator.HeadCache` were built to remove; it survived in
the auth path.

**Correctness/reliability:** **Neutral-or-better.** Keeps the monotonic floor, the storage DR union
on cold miss, `read_error_fallback`, and the notifier push. Fewer synchronous Postgres dependencies
on the auth path means fewer paths that degrade when the pool saturates.

**Recommended Fix:** Switch from per-shard read-through to the `Fathom.Tenants.DenyList` pattern
already in the codebase — the revoked set is tiny because `token_version` defaults to 1 and only
revoke/rotate raises it:
```sql
CREATE INDEX CONCURRENTLY shards_revoked_token_version_index
  ON shards (shard_id) INCLUDE (token_version, token_version_bumped_at)
  WHERE token_version > 1;
```
Then one bulk load per refresh instead of N point reads; a shard absent from the set is at floor 1
with no grace, identical to today's `{1, nil}`. Keep per-shard read-through **only** as the cold-miss
path so the storage DR floor union is unchanged. Minimum viable alternative: raise the default TTL
to 300 s (matching Tombstones/Suspensions) — a 10× cut on its own, and the push channel already
delivers revocations in milliseconds.

**How to measure:** Bench that opens N streams across N distinct shards with `hrana_auth: :required`
and counts `[:fathom, :repo, :query]` events; assert reads/stream ≈ 0 after warm-up.

### #6. The Hrana Bandit listener ships with zero transport tuning — one listen socket, one 1024-deep accept queue, no `SO_REUSEPORT`
**Severity:** High | **Category:** Performance / accept path | **Panels:** P3
**Likelihood:** High under connection bursts | **Blast Radius:** node-wide connection establishment

**Problem:** `lib/fathom/application.ex:500` (**verified**) —
`{Bandit, plug: {Filo.Plug, opts}, scheme: :http, port: hrana_port(), ip: hrana_bind_ip()}`. No
`thousand_island_options`, no `http_options`, no `http_1_options`, no `websocket_options`. So:
`num_acceptors: 100`, **`num_listen_sockets: 1`**, `backlog: 1024`, no `reuseport`, no socket buffer
sizing (`thousand_island/server_config.ex:34-41`, `transports/tcp.ex:22-26`). All 100 acceptors
contend on a **single** listen socket with a **single** 1024-slot kernel queue. ThousandIsland
documents `num_listen_sockets` + `reuseport: true` as the supported multi-queue path
(`thousand_island.ex:123-129`); fathom uses neither.

**Impact:** This is the structural version of the `ListenOverflows` the 4096-shed report measured
(0–1,315/run) and correctly dismissed as not the *primary* cause. A 4096-wide connect burst offers
~4096 SYNs to one 1024-slot queue; overflow → SYN drop → client retransmit after 1 s → straight into
the 15 s `Filo.Client` timeout that **is** the shed's cause. With `num_listen_sockets: 4,
reuseport: true, backlog: 4096`, queueable SYNs go 1024 → 16,384 across 4 independent queues.

**Correctness/reliability:** **Strictly positive.** A deeper queue does not hide a failure — it
removes an artificial drop of connections the node has the CPU and fds to serve (max_fd measured
17–21k against a 65,536 limit). The classic SO_REUSEPORT rebalance hazard does not apply: all listen
sockets belong to one BEAM node started together.

**Recommended Fix:**
```elixir
thousand_island_options: [
  num_acceptors: 100,
  num_listen_sockets: 4,
  transport_options: [backlog: 4096, reuseport: true]
]
```
`backlog` above `somaxconn` is silently clamped — document raising `net.core.somaxconn` as a
provisioning step. **Gate `num_listen_sockets`/`reuseport` behind config**: ThousandIsland *fails
startup* if the option is unsupported, so a hardcoded value is a boot-fail hazard on an exotic kernel.

**How to measure:** `chaos.sh tpc-fleet`/`tpcc-fleet` at 2048/4096 with the shed report's harness —
diff `/proc/net/netstat` `ListenOverflows`/`ListenDrops` and read the driver's `err_reasons` timeout
bucket.

### #7. nginx upstream keepalive is undersized by 1–2 orders of magnitude — and the rebalancer pins the *hottest* shards to an even smaller pool
**Severity:** High | **Category:** Performance / connection reuse | **Panels:** P3
**Likelihood:** High under bursty per-tenant traffic | **Blast Radius:** every HTTP request

**Problem (verified):** `deploy/lb/fathom.nginx.conf:60` and `deploy/chaos/nginx.conf:25` —
`keepalive 64`. `lib/fathom/rebalancer/lb_map.ex:74` renders each **pin-upstream** with
`keepalive 16`. `worker_connections 4096` in both.

nginx's `keepalive N` is the **per-worker** idle-connection cache; past N, nginx closes the LRU
connection. With `worker_processes auto` (12 on the rig) that is 12 × 64 = 768 cached connections
against a documented target of 1024–4096 concurrent tenants. Every request arriving after its
tenant's connection was evicted pays a fresh handshake, a fresh trip through #6's accept path, and a
fresh connection-process spawn.

Worse: a shard reaches a pin-upstream *because* `Rebalancer.Policy` found it **hot** — so the moment
a tenant becomes the hottest thing on the fleet, its connection reuse is cut 4×. That inverts the
intent of the B1 handoff.

Also missing: **`keepalive_requests`** (nginx default 1000), so every pooled connection is recycled
every 1000 requests — at ~1,080 tps through a 64-slot pool, roughly every 60 s per connection, each
re-opening the FIN race the 2026-07-23 502 fix closed for the *idle* case. The request-count race is
separate and still open. And each proxied request consumes **two** connections, so
`worker_connections 4096` tops a worker out near 2048 concurrent proxied requests.

**Impact:** An extra RTT + handshake + accept + spawn on every request whose upstream connection was
evicted. The always-busy tpc drivers keep all connections active and therefore *hide* this; real
bursty traffic does not.

**Correctness/reliability:** **Positive.** A larger idle cache and higher `keepalive_requests` mean
*fewer* teardowns, i.e. fewer chances to hit the FIN race that produced the 502 storm. Budget the
raised steady-state socket count against the measured 65,536 `nofile` and 1 fd/held-connection.

**Recommended Fix:** Both nginx configs: `keepalive 512;` (≈ target concurrency ÷ workers) and
`keepalive_requests 100000;` on every upstream block; `worker_connections 16384;`. Raise
`lb_map.ex:74`'s pin-upstream to the same 512 — sizing the hot minority *below* the hash pool is
backwards. Make both values a shared module attribute so the two configs cannot drift.

**Housekeeping (not a finding):** `deploy/chaos/lb-runtime/exceptions.conf` is checked out with
`keepalive 16` and **no** `keepalive_timeout 30s` — a stale generated artifact still carrying the
pre-502-fix idle race. `LbMap` will overwrite it on the next render; regenerate or delete it so the
next rig run does not start from the buggy file.

**How to measure:** `chaos.sh tpc-fleet "256,1024"` with `TPC_NET=container TPC_DRIVER=elixir`; add
`$upstream_connect_time` to the nginx log format (a reused keepalive connection reports `0.000`) and
track the non-zero ratio.

### #8. Prepared-statement cache keys are Jason sub-binaries — each cached SQL pins its entire originating Hrana request body for the life of the stream
**Severity:** High | **Category:** Performance / memory density | **Panels:** P2
**Likelihood:** High — every WebSocket stream (the django-libsql path) | **Blast Radius:** per served shard

**Problem:** `lib/fathom/shard/connection.ex:131-147` stores SQL strings as **map keys in the stream
process dictionary**. The provenance chain, verified end to end:
1. `filo/lib/filo/plug.ex:561-586` reads the whole HTTP body into one flat binary; `socket.ex:84`
   does the same per WebSocket text frame (the long-lived, production case).
2. Jason extracts strings with `binary_part(original, skip, len)`. On a body >64 bytes the source is
   a refc binary, so each extracted string is a **sub-binary holding a ProcBin reference to the
   whole body**.
3. `filo/lib/filo/stmt.ex:29` takes `Map.get(stmt, "sql")` verbatim — no copy.
4. `Filo.Stream.run/4` is a `GenServer.call`; ERTS flattens sub-binaries on copy only *below* 64
   bytes. Django's generated SQL is comfortably over.
5. `Process.put` stashes it until LRU-evicted (cap 64) or the stream dies.

So each of up to 64 cache slots pins one whole request body, freed only on the holder's GC — and
`Filo.Stream` has no `fullsweep_after`/`hibernate_after` either (#22), so the ProcBins sit in the old
heap.

**Impact:** Worst case per stream = `64 × sizeof(the body that introduced each distinct SQL)`. At
modest 4 KiB pipeline bodies that is ~256 KiB pinned per served shard — **the same order as the
entire measured ~220 KiB/shard served cost**, i.e. plausibly doubling it. At 30k served shards, up
to ~7.5 GB/node. It will not show in `process_info(:memory)`; it shows in `:erlang.memory(:binary)`,
which is exactly why the density harness never attributed it.

**Correctness/reliability:** **None.** `:binary.copy/1` returns an equal binary — map lookups, LRU
behaviour, and `Sqlite3.prepare` semantics are byte-identical.

**Recommended Fix:** Copy on the **miss** path only (zero added cost on the hot hit path), and store
the canonical key inside the value so the hit-path re-put cannot reinstate the sub-binary key:
```elixir
%{^sql => {k, stmt, _stamp}} ->
  Process.put(key, {seq + 1, Map.put(cache, k, {k, stmt, seq + 1})})   # re-put under stored key
...
  k = :binary.copy(sql)   # unpin the whole Hrana request body Jason sliced this out of
```
Secondary, same family: `filo/lib/filo/plug.ex:583` builds the body with `read_all(conn, acc <> chunk)`
— O(n²) copying plus a fresh refc allocation per chunk; accumulate an iolist and
`IO.iodata_to_binary/1` once.

**How to measure:** `@tag :bench` — run one query whose SQL is embedded in a 512 KiB Hrana body,
`garbage_collect(stream_pid)`, assert `:erlang.memory(:binary)` does not retain it. Fails pre-fix.
At scale: `chaos.sh served-data` with `bin/fathom rpc ":erlang.memory()"` per node.

### #9. 30k long-lived coordinators run with `fullsweep_after: 65535` and no `hibernate_after` — the one-shot init GC worth +53% `fanout_kb_per_shard` is never repeated
**Severity:** High | **Category:** Performance / memory density | **Panels:** P2
**Likelihood:** Certain | **Blast Radius:** ~800 MB/node at 30k shards

**Problem:** `lib/fathom/shard.ex:124-126` starts coordinators with no `spawn_opt`. The codebase's own
comment at `shard.ex:264-271` is the strongest evidence that retained heap dominates per-shard cost:
dropping the init `:erlang.garbage_collect()` measured **+53% `fanout_kb_per_shard` (16.99 → 26.06
KiB/shard)**. But that shrink is *one-time*. Afterwards the coordinator runs with
`fullsweep_after: 65535` (effectively never) — anything surviving two minor collections is promoted
to the old heap and **stays there for the process's life**: flush-cycle terms, `Task`/monitor
bookkeeping, `%Storage.Lease{}` churn, `:rand` state, Logger metadata. The old heap only grows.

The measured regimes corroborate: `fleet-density-2026-07-10.md:154-158` reports an idle
*data-bearing* coordinator at ~43 KiB RSS versus the ~16 KiB idle floor for one that never served.
That ~27 KiB delta is retained-after-work state no GC will reclaim — **~810 MB/node at 30k shards**.

**Correctness/reliability:** `fullsweep_after: 0` and `hibernate_after` are purely reclamation
policy; `hibernate` preserves GenServer state and the process dictionary. **Explicitly do NOT set
`max_heap_size` on `Fathom.Shard`** — a coordinator killed at the heap limit mid-`terminate/2` skips
the final fence + checkpoint + PUT + lease release. That is a durability regression and can strand a
lease; it is the one knob in this family that violates the hard constraint.

**Recommended Fix:**
```elixir
GenServer.start_link(__MODULE__, shard_id,
  name: via(shard_id),
  spawn_opt: [fullsweep_after: 0],   # live set is a ~30-key map; a full sweep is cheap and is the
                                     # only thing that reclaims old-heap garbage AND returns pages
  hibernate_after: 30_000
)
```
**Sequencing: #10 is a hard precondition.** Today every coordinator receives a `:durability_flush`
every ~5 s, so any `hibernate_after` above 5 s never fires and any value below it causes a
hibernate/wake fullsweep pair per tick. Land #10 first.

Singleton GenServers (`Heartbeat`, `NovelLimiter`, ETS owners, `Reporter`) are noise here — except
`Directory.Recorder`, see #23.

**How to measure:** `mix fathom.scale --ramp --max 30000` + `mix fathom.bench`
(`fanout_kb_per_shard` is already gated at ±20%), then `chaos.sh served-data` followed by the
idle-drop phase — the ~43 KiB/shard idle-with-data figure is the headline target. `@tag :bench`
asserting `process_info(pid, :memory)` after a serve-then-idle cycle pins it.

### #10. Every coordinator wakes on a ~5 s timer even when provably unwritable — 6,000 wakeups/s at 30k shards, and it structurally blocks #9
**Severity:** High | **Category:** Performance / timer churn | **Panels:** P2
**Likelihood:** Certain | **Blast Radius:** node-wide, and gates ~400 MB of #9's win

**Problem:** `shard.ex:2222-2235` re-arms unconditionally; `shard.ex:1212-1224`'s clean branch
re-schedules and returns. A **clean** coordinator with **zero** checked-out connections cannot
become dirty — `WriteCounter.bump/1` is reachable only from `ShardExecutor.run_statement/3` and the
abnormal-stream-death path (**verified**: bump sites at `shard_executor.ex:166`, `:345`,
`shard.ex:1061`, `:1703`), all of which require a live checkout. Yet it re-arms forever, costing per
tick a timer-wheel insert, a `:rand.uniform`, a message send + dispatch, an ETS lookup, and a heap
touch (defeating page-out).

**Impact:** 6,000 no-op wakeups/s and 6,000 standing timer entries at 30k shards — modest CPU
(~1–2% of a core) but it is the **blocker** for #9's hibernation win, and it keeps 30k heaps hot.

**Correctness/reliability:** **Zero RPO change**, and this is the load-bearing argument: the contract
is "at most `:shard_flush_interval_ms` of *acknowledged writes* lost." A shard with
`map_size(conns) == 0` and `unflushed?(state) == false` has no acknowledged unflushed writes and no
way to acquire any before the next `:checkout`, which re-arms. A *dirty* coordinator keeps ticking
unchanged. Writes bypassing the Hrana path (migrator, `mix fathom.shard`) are already invisible to
`WriteCounter` — unchanged. **Re-arm on the `:checkout` grant, not on checkin**, so the timer is live
for the whole window a connection can write.

**Recommended Fix:**
```elixir
# Idle + clean ⇒ provably unwritable until the next checkout. The :checkout grant re-arms.
defp schedule_flush(%{conns: conns} = state) when map_size(conns) == 0 do
  if unflushed?(state), do: do_schedule_flush(state), else: cancel_flush(state)
end
defp schedule_flush(state), do: do_schedule_flush(state)
```
plus `state = if state.flush_timer == nil, do: do_schedule_flush(state), else: state` in
`handle_call({:checkout, op}, …)` (`shard.ex:856`).

**How to measure:** Regression test asserting a clean connectionless coordinator has
`flush_timer == nil` and the next checkout re-arms it; `mix fathom.rpo` sweep to prove the loss
window is unchanged. Scale: `--ramp --max 30000` + scheduler utilization at idle.

### #11. `VACUUM INTO` inherits `synchronous=FULL` — every periodic flush force-fsyncs a full shard-sized throwaway temp
**Severity:** High | **Category:** Performance / wasted device I/O | **Panels:** P4
**Likelihood:** High — every write-active shard, every interval | **Blast Radius:** node device bandwidth

**Problem:** `shard.ex:2084-2086` (**verified**) opens the snapshot connection via
`Connection.open/1`, which unconditionally sets `synchronous=FULL` (`connection.ex:30`). The
destination pager inherits `safety_level` from the source (`deps/exqlite/c_src/sqlite3.c:161539-161556`):
```c
pgflags = db->aDb[iDb].safety_level | (db->flags & PAGER_FLAGS_MASK);
sqlite3BtreeSetPagerFlags(pTemp, pgflags|PAGER_CACHESPILL);
```
So the temp is written with journal + database fsyncs — for a file `snapshot_and_upload/1`'s `after`
block unlinks seconds later (`shard.ex:2037-2039`).

**Impact:** Per write-active open shard, every 5 s, the node forces `shard_bytes` to the device for
nothing. At ~640 KiB/shard × 1,000 write-active shards that is ~128 MB/s of pure-waste synchronous
writes, plus SSD endurance. With `synchronous=OFF` the temp can live entirely in page cache —
written, MD5'd, uploaded, unlinked — and on a healthy box may never reach the device. Moves
`[:fathom,:shard,:flush]` duration and `mix fathom.rpo --cost` p50/p99 (currently ~5–8 ms on Local,
"dominated by the VACUUM INTO snapshot" per `docs/durability.md`).

**Correctness/reliability:** **None.** `VACUUM INTO` takes only a **read** transaction on the source
(`sqlite3BtreeBeginTrans(pMain, 0)`), so the live shard's WAL + per-commit `synchronous=FULL` is
untouched. The temp has *no* durability requirement: it is read back in-process for the Content-MD5
and the PUT; a crash mid-snapshot leaves the shard dirty and re-snapshots next interval. The durable
artifact is the S3 object, still gated by `content-md5` over the same file.

**Recommended Fix:** In `snapshot/2`, after `Connection.open(path)` (so the `journal_mode=WAL`
transition still runs at FULL), `Connection.exec(conn, "PRAGMA synchronous=OFF")` before the
`VACUUM INTO`. **Do not** relax it on the `checkpoint/1` connection — a checkpoint at
`synchronous=OFF` can corrupt the main db on power loss.

**How to measure:** `mix fathom.rpo --cost` (flush µs p50/p99 at 5 s and 30 s);
`chaos.sh latency-cost` drain leg; `iostat` write-bytes on a chaos node during `soak`.

### #12. No index serves any non-`active` status predicate — five control-plane queries seq-scan the whole `shards` table, some every 5 minutes per node
**Severity:** High | **Category:** Performance / index fit | **Panels:** P5
**Likelihood:** Certain | **Blast Radius:** control plane + `dir_resolve` via buffer eviction

**Problem:** The verified index inventory on `shards`: PK, unique `shard_id`,
`(schema_version, last_active_at)` non-partial, and two partials both predicated
`status = 'active'` (`20260702011500_add_status_partial_indexes_to_shards.exs`). There is **no index
on `status` alone and no partial for any other status.**

Postgres's `predicate_implied_by` cannot derive `status = 'active'` from `status = 'deleted'`, so
these all plan as **Seq Scan**: `deleted_shard_ids/0` (`directory.ex:424`), `suspended_shard_ids/0`
(`:452`), `count_failed/0` (`:545`), `failed_shards/0` (`:551`), `count_by_status/0` (`:566`), and
`flush_lag_report/1` (`:186-198`, which adds a Sort because no non-partial index leads with
`last_active_at`). `count_by_status/0`'s own docstring concedes the point ("revisit… if the directory
grows large").

Callers: `Tombstones` (`tombstones.ex:77`, `:217-218`) and `Suspensions` (`suspensions.ex:62`,
`:181-182`) each refresh **every 5 min, per node**.

**Impact:** A `shards` row is ~155 bytes; 1M rows ≈ 155 MB, and this table is updated on every
Recorder flush so real bloat is typically 2–4×. Per node that is 2 full-table scans per 5 min; a
20-node fleet is 8 full scans/minute. At 10M rows each scan is 1.5–5 GB — enough to evict the
Recorder's hot index pages from `shared_buffers` on every pass, which is how this surfaces as a
**`dir_resolve_p50_us` regression with no code change behind it**.

**Correctness/reliability:** **Strictly neutral** — indexes change plans, never result sets. This
*improves* reliability: `Tombstones`/`Suspensions` refresh has a retry-with-backoff path
(`deny_list.ex:23-34`) that a slow scan under load can trip, leaving the 410/403 admission gate stale.

**Recommended Fix:** Three equality-predicate partial indexes (each holds only rows in that state —
a few KB in a healthy fleet):
```sql
CREATE INDEX CONCURRENTLY shards_deleted_index          ON shards (shard_id) WHERE status = 'deleted';
CREATE INDEX CONCURRENTLY shards_suspended_index        ON shards (shard_id) WHERE status = 'suspended';
CREATE INDEX CONCURRENTLY shards_migration_failed_index ON shards (shard_id) WHERE status = 'migration_failed';
```
Equality predicates, not one `WHERE status <> 'active'` — equality-to-equality implication is
unambiguous in `predtest.c`, and three tiny indexes cost less write maintenance. Set
`@disable_ddl_transaction true` + `@disable_migration_lock true` exactly as `20260702011500` does.
`count_by_status/0` needs a call-site fix (see #13). `flush_lag_report/1`: split into the
`status = 'active'` branch (served by the existing partial, ordered LIMIT) ∪ the non-active branch,
merged and top-`n`'d in Elixir — verify `SELECT status, count(*) FROM shards GROUP BY 1` first in
case `retired` is large in your rollout model.

**How to measure:** `mix run scripts/directory_scale.exs 3_100_000`, then
`EXPLAIN (ANALYZE, BUFFERS) SELECT shard_id FROM shards WHERE status = 'deleted'` — expect
`Seq Scan … shared read=19000+` before, `Index Only Scan` after. Add these four calls to the probe
script's sweeps block; today it measures only the *indexed* paths, which is why this gap was unseen.

### #14. Finch's S3 pool never expires idle connections, has no production knob, and the resulting stale-connection race lands on the **flush PUT**, which nothing retries
**Severity:** High | **Category:** Performance + RPO reliability | **Panels:** P3
**Likelihood:** Medium-High (S3 closes idle keep-alives ~20 s) | **Blast Radius:** per flush, extends RPO

**Problem:** `lib/fathom/shard/storage/s3.ex:91-93` — `pools: %{default: [size: …, count: …]}` and
nothing else. Three gaps:
1. **`conn_max_idle_time` unset** → Finch defaults it to `:infinity` (`finch.ex:90-97`) and
   `reusable?` short-circuits to `true` (`http1/conn.ex:85`). A checkout landing ahead of a server
   FIN in the pool's mailbox hands out a dead socket. With a 200-connection pool and a per-shard
   flush cadence in minutes, essentially every S3 connection is past S3's idle-close window.
2. **The failure lands asymmetrically.** `req/0` sets no `:retry`, so `:safe_transient` applies —
   which retries **GET/HEAD only** (`req/steps.ex:2221-2231`). `download/4` opts out deliberately and
   rolls its own 3 attempts. But `flush/3`'s **PUT is retried by nobody**: a raced `:closed` →
   `shard.ex:1493` "flush failed, keeping local copy" → the idle drop aborts, the coordinator keeps
   the local file *and the lease*, and the tenant's RPO window extends by one backoff interval.
3. **No env knob.** `runtime.exs:67-77` sets bucket/region/endpoint/credentials only, so
   `pool_size: 200 / pool_count: 1` — AGENTS.md's own "measured knee on the localhost rig" — is baked
   into every release. The real-S3 tuning `s3.ex:78-88` invites is impossible without a rebuild.

Also: no `:receive_timeout`, no connect timeout override — a hung S3 socket sits for Req's default
15 s, the same 15 s that dominates the 4096 shed.

**Impact:** On flush, a stale-connection hit costs a whole flush interval of RPO and blocks the idle
drop (holding a lease and an open shard against `:max_open_shards`). On the GET/HEAD lease paths
`:safe_transient` *does* fire — but `exp_backoff` starts at **1000 ms** (`req/steps.ex:2398-2410`)
against a `cold_open_s3_p50_us` budget of ~26 ms at 10 ms one-way: one blip is a ~40× p99 spike.

**Correctness/reliability:** **Positive on both.** Expiring an idle connection *before* the server
does is the same discipline as the nginx `keepalive_timeout` fix — the client is always the closing
side. Retry coverage is unchanged: **explicitly do not add Req-level PUT retries** — `flush/3` is
`If-Match`-fenced and a blind retry would re-issue with a stale etag. The coordinator-level backoff
is the correct retry tier.

**Recommended Fix:**
```elixir
default: [size: pool_size(), count: pool_count(),
          conn_max_idle_time: :timer.seconds(15),      # < S3's ~20s idle close
          conn_opts: [transport_opts: [timeout: 3_000]]]
```
plus `S3_POOL_SIZE`/`S3_POOL_COUNT` in `runtime.exs`, and
`retry_delay: fn n -> Enum.at([50, 200, 800], n, 800) end` on the base Req struct — the 1 s floor is
sized for public-internet APIs, not a same-region S3 whose whole budget is ~1 RTT.

**How to measure:** `scripts/benchmark_s3_latency.sh` for `cold_open_s3_p50_us` /
`warm_s3_shards_per_s`; `chaos.sh latency-cost` for flush/drain; attach the already-emitted
`[:finch, :conn_max_idle_time_exceeded]` and `[:finch, :reused_connection]` telemetry to confirm
reuse rate against a real bucket.

### #16. Bandit compresses every Hrana pipeline response by default — a per-response zlib context on the hot path, invisible to every chaos-rig measurement
**Severity:** Medium-High | **Category:** Performance / CPU | **Panels:** P3

**Problem:** No `http_options` on the listener ⇒ `compress: true` (`bandit/compression.ex:23`). Any
client advertising `accept-encoding: gzip` — reqwest (Rust SDK), undici/`fetch` (JS), Python
`requests`/`httpx`, all by default — makes Bandit gzip **every** `/v2|v3/pipeline` response.
`:zlib.gzip/1` is a full open→deflateInit→deflate→deflateEnd→close cycle per response, plus a
`vary: accept-encoding` header on everything. Production images are `erlang-27.3.4` so gzip wins; a
dev machine on OTP 28+ picks zstd — **dev and prod take different code paths here.**

**This cost is absent from every number in the docs.** `Filo.Client` sends only `content-type`
(`filo/lib/filo/client.ex:93`), so neither chaos driver ever advertises an encoding — the entire
`tpc-fleet`/`tpcc-fleet`/`hotspots` corpus measures the **uncompressed** path. Real SDK traffic does
not. (The cursor endpoint is unaffected: `compression.ex:88-89` only matches `streamable == false`.)

**Impact:** A 1–3 KB response at gzip level 6 is roughly 15–30 µs, init-dominated at that size. At
27k q/s that is ~0.4–0.8 of a core — 3–7% of a 12-vCPU node — compressing kilobyte JSON for a
datacenter LAN hop. **Estimate from zlib small-buffer throughput, not a fathom measurement**; the A/B
below settles it.

**Correctness/reliability:** **Neutral.** Moving compression to nginx is wire-transparent, and better
shaped: `gzip_min_length` skips tiny responses, which Bandit has no knob for.

**Recommended Fix:** `http_options: [compress: false]`, then in both nginx configs inside `location /`:
`gzip on; gzip_types application/json; gzip_min_length 1000; gzip_proxied any;`. If you prefer to
keep it in-BEAM, at minimum `proxy_set_header Accept-Encoding "";` on the LB so the node↔LB hop stops
paying while the LB still compresses for the WAN hop.

**How to measure:** `--hotspots` is **not** sufficient (it drives the executor, not HTTP). Use
`chaos.sh tpc-fleet` with the driver patched to send `accept-encoding: gzip`, A/B against
`compress: false`.

### #17. `Sqlite3.columns/2` is re-fetched on every execution of a cached prepared statement
**Severity:** Medium | **Category:** Performance | **Panels:** P1

**Problem:** `connection.ex:98` calls `Sqlite3.columns(conn, stmt)` per execution. The prior audit's
#1 landed an LRU-64 statement cache, so a Django stream re-executes the same compiled statement
thousands of times — but column names are re-derived every time. `exqlite_columns`
(`sqlite3_nif.c:1084-1140`) is `ERL_NIF_DIRTY_JOB_IO_BOUND` despite doing no I/O, and per column does
`sqlite3_column_name()` + `enif_alloc` + a fresh binary copy. For a 20-column Django SELECT: one
dirty dispatch plus 20 heap binaries allocated and immediately garbage, per execution, for a value
that is a property of the *compiled statement*.

This is the other half of the win #1 banked — the cache removed per-execution `prepare_v2`; the
column list was left behind.

**Impact:** One dirty-IO dispatch removed per query (directly relieving #2's 10-thread pool) plus
`O(ncols)` allocation. Widest on wide-SELECT shapes (TPC-C, `SELECT *`). Moves per-node q/s at
`L≥16`; flat at `L=1` where the cache never hits, mirroring #1's measured profile.

**Correctness/reliability:** **None — with one constraint that must be honored.** `prepare_v2`
auto-recompiles on schema change, and a recompiled `SELECT *` can legitimately change its column list
after `ALTER TABLE ADD COLUMN`. Cache columns in the statement-cache entry and purge the whole
per-connection cache when this stream runs DDL, using `ShardExecutor`'s already-computed `ddl?(sql)`
(`shard_executor.ex:644`). Exact for the single-connection case; note fathom already blocks client
DDL on tenant shards via `:block_tenant_ddl`, and the migration engine runs DDL on its own connection.

**Recommended Fix:** Extend the cache entry from `%{sql => {stmt, stamp}}` to
`%{sql => {stmt, cols, stamp}}`, populate at prepare time, drop the per-execution call, purge on DDL.

the new column.

### #18. Every read query pays a `last_insert_rowid` dirty-IO NIF round-trip whose result is then discarded

### #19. No content-identity check before the flush PUT — a byte-identical flush still uploads the whole object
**Severity:** Medium-High | **Category:** Performance / PUT volume | **Panels:** P4

**Problem:** `s3.ex:213-239` + `:592-608` — `stat_and_md5/1` already computes the exact hex digest of
the bytes about to be uploaded and stamps it as `x-amz-meta-fathom-md5`. Nothing compares it against
what is already stored, so a flush whose content is unchanged pays the full body transfer anyway.

**Impact:** The byte-level backstop for every source of no-op dirtiness — #3's read-only COMMITs,
no-op UPDATE/DELETE, rolled-back transactions, `exec` scripts that wrote nothing. Each hit removes an
entire object PUT at **zero added cost**, because the digest pass already happens.

**Correctness/reliability:** **None.** Skipping a PUT of bytes the object already holds is a provable
no-op: the shard is *already durable to the last write*, so the RPO contract is satisfied, and
advancing `Directory.Recorder.record_flush/1` + the `FlushWatermark` is correct. `state.etag` stays
unchanged so the next real flush's `If-Match` still matches. The fence is unaffected — the skip
decision happens strictly **after** `Fence.check` returned `{:ok, _}` (`shard.ex:1537-1549`), and a
peer's steal-touch rotates the object etag so our next actual PUT 412s and self-fences as today.

**Honest caveat:** `VACUUM INTO` output is **not** guaranteed byte-identical run-to-run for an
unchanged database, so the hit rate on the *periodic* path must be measured, not assumed. The **idle
drop-flush** path (`upload_for_drop/1`, `shard.ex:1610-1637`) uploads the actual file, where an
unchanged database is byte-identical and the hit is reliable.

**Recommended Fix:** Extend the fenced-flush return to carry the uploaded body's digest
(`{:ok, etag, md5_hex}` — the S3 backend already has it, and `Local`'s `content_etag/1` *is* a content
hash), store as `state.flushed_md5`, short-circuit the PUT when the fresh digest matches. Ship behind
a `[:fathom,:shard,:flush] outcome: :unchanged` counter and read the hit rate split by
idle-drop vs periodic before claiming the win.

### #22. `Filo.Stream`: idle timeout unreachable from fathom config, cancel/re-arm per request, and no hibernation on an idle-by-construction process **(filo)**
**Severity:** Medium | **Category:** Performance + client-visible reliability | **Panels:** P2, P3 (merged)

**Problem, three parts:**
**(a) Not configurable.** `filo/lib/filo/stream.ex:37` — `@default_idle_timeout 10_000`.
`Filo.Plug` accepts `:idle_timeout` (`plug.ex:43-44`) and `application.ex:488-497` passes none. There

doing `BEGIN; SELECT; …app logic…; UPDATE; COMMIT` under load can plausibly exceed 10 s between
statements. Cost is bounded and explicit (1 checkout + ~3 fds per held stream, with
`:max_checkouts_per_shard` already capping per-tenant exposure). **Do not set `:infinity`.**

**Recommended Fix:** fathom `application.ex:488`: add

`HRANA_STREAM_IDLE_MS` in `runtime.exs`. filo `stream.ex:214-217`: `async: true, info: false`, or
better, the coalesced-deadline pattern (store a monotonic `last_activity`, arm one timer per window,

window instead of two per request. Expose `hibernate_after`/`spawn_opt` through `start_link`'s

**Note on `max_heap_size`:** `Filo.Stream` is the one process where it would be *defensible* (it
holds no durability state), but `Filo.Executor.close/1` → `Shard.checkin` runs in `terminate/2`,
which a heap kill skips — leaking a checkout until the coordinator's monitor fires. Safe-but-messy;
do not enable without measurement.

### #23. `Directory.Recorder.drain/1` materializes the whole buffer with `tab2list`, then re-reads every row with `take` — a multi-MB heap spike every second, never shed

### #24. `Lru.touch/1` performs 4 ETS ops on every checkout at shipped defaults, including a CA-tree delete+insert pair

reachable" — but `enabled?/0` (`:55-58`) only tests *config*, and `config.exs:22` ships

### #25. `Storage.Local` reads whole shard files into BEAM binaries and hashes the full remote object on every etag operation
**Severity:** Medium | **Category:** Performance / memory | **Panels:** P4

**Problem:** `local.ex:53-73` (`flush/3`) does `File.read(local_path)` → `File.read(remote_path)` →
`content_etag(remote_body)` (full SHA-256) → `atomic_write(remote_path, body)`. `SHARD_STORAGE=local`
is a supported production selection (`runtime.exs:57-62`) and local-NVMe is a stated deployment. One
fenced flush = 2 shard-sized binaries resident + 2 full SHA-256 passes + a full write; at N
concurrent flushes, `2·N·shard_bytes` of transient binary heap.

Worst is `pull_if_changed/3` (`:91-112`): it reads and hashes the **entire** object to conclude
nothing changed — so on Local, the warm-follower revalidation loop is O(cached × shard bytes) of disk
read + hash *per poll*, where S3 does a bodiless 304.

**Correctness/reliability:** All three fixes are value-preserving: `content_etag` still returns the

unchanged; `atomic_copy/2` carries the same fsync-before-rename contract as `atomic_write/2`

**Recommended Fix:** (1) Stream the hash via `File.stream! |> :crypto.hash_update`, the shape

etag and produce a false `:unchanged` — exactly how a stale warm copy gets promoted.

**Severity:** Medium | **Category:** Performance / unbounded growth | **Panels:** P2

`&Directory.deleted_shard_ids/0` — **every** deleted shard id, ever, on every node, every 5 minutes.
Two unbounded costs: resident (1M lifetime deletions ≈ ~100 MB per node, permanently, never
reclaimable) and periodic (the full list materialized in one process heap every 5 min, plus a
full-table Postgres read from every node simultaneously — see #12). `Suspensions` has the same shape
but is bounded by *currently* suspended tenants; not a leak.

**Impact:** Turns a per-node footprint that should track the *active* working set — the density
thesis — into one that tracks *cumulative lifetime deletions*. This is the one structure that
violates that thesis.

**Correctness/reliability — the loud part:** **Do not evict tombstones.** Dropping one re-opens
exactly the hole the module closes (`tombstones.ex:6-13`) — a stray request re-mints a deleted tenant
as an empty shard and the 410 contract breaks. A Bloom filter is also unacceptable: false positives
would 410 a *live* tenant.

**Recommended Fix (safe half only):** Make the **refresh incremental** — add
`Directory.deleted_shard_ids_since(timestamp)` (indexed on the deletion stamp) and load only rows
newer than the last successful refresh, keeping the boot load full. Removes the O(all-deleted) heap
spike and Postgres scan per node per 5 min with **zero** change to set contents or guard
completeness. Add a telemetry gauge on `:ets.info(…, :size)`/`:memory` now regardless.
**Needs design, not a patch:** bounding the resident set at all requires an age-tiered guard (recent
deletions in ETS, older resolved through the directory + the durable `tombstones/<id>` marker,
fail-closed on error). Flagging as an initiative.

### #31. `quick_check` is an O(database-size) scan on the shutdown-budget drop path, and the drop opens two SQLite connections back to back
**Severity:** Medium | **Category:** Performance | **Panels:** P1, P4 (merged)

**Problem:** `shard.ex:1610-1637` calls `checkpoint(state.path)` then `verify_integrity(state.path)`,
each doing its own `Connection.open` → work → `Connection.close`. Each open is `File.mkdir_p!` +
`Sqlite3.open` + five pragma NIF round-trips — and because each close of the *last* connection to a
WAL database triggers SQLite's close-time checkpoint and unlinks `-wal`/`-shm`, the second open
**recreates the WAL index files the first close just deleted**. At 10k–30k shards/node cycling idle
that is tens of thousands of avoidable open/close + WAL-index cycles per turnover.

Separately, `verify_integrity/1` (`:1644-1659`) justifies `PRAGMA quick_check` as "Cheap (shards are
small by premise)" — but that premise is enforced only when `:shard_max_page_count` is configured,
and it is **unset by default** (`connection.ex:59-63`). So on a default deployment `quick_check` reads
and validates **every page**, inside the 60 s `:shard_shutdown_ms` budget whose own sizing comment
(`shard.ex:88-95`) already warns is tight on a rolling deploy.

**Correctness/reliability:** The check is **load-bearing and must not be removed** — it is the
2026-07-14 #4 corruption gate and the *only* guard on the checkpoint-then-raw-upload fast path (the
`snapshot_and_upload` fallback runs `VACUUM INTO`, which reads every page anyway). Both fixes preserve
it exactly. Note the folded connection must keep `synchronous=FULL` — #11's relaxation applies only
to the snapshot connection, and quick_check must still run **after** the checkpoint and **before** the
raw upload.

**Recommended Fix:** (1) Fold `quick_check` onto the connection `checkpoint/1` already holds, before
closing it. (2) Bound the scan: either default `:shard_max_page_count` so "small by premise" is
actually true, or gate full `quick_check` behind a size threshold and fall through to
`snapshot_and_upload` above it. `test/fathom/shard_corrupt_flush_test.exs` must stay green — it is the
pinned proof the guard survives.

### #33. No `Oban.Plugins.Lifeline` — a node crash strands jobs in `executing` forever, and `unique` then wedges that shard permanently
**Severity:** Medium | **Category:** Reliability (with performance consequences) | **Panels:** P5

**Problem:** `config.exs:73-87` configures `Pruner` + `Cron` only; Oban 2.23 defaults
`plugins: []`, so that is the complete list. When a node dies mid-job, its `executing` rows stay
`executing` — nothing transitions them back. The Pruner prunes terminal states only. Every per-shard
worker is `unique` over states **including `:executing`**: `ShardMigrationJob` (`:18-21`), `RevertJob`
(`:10-13`), `DeleteJob` (`:18-21`), `HandoffJob` (`:43-47`, with `period: :infinity`). So a stranded
row means that shard can **never** have another migration, revert, delete, or handoff enqueued — the
lazy path, the hourly `ReconcileJob`, and the rollout sweep all dedup against a ghost.

`HandoffJob` is worst: `period: :infinity` makes the block permanent, and
`RebalanceJob.handoff_in_flight?/1` counts `executing`, so the dead-pin reconciler skips that shard
forever, leaving it pinned to a node that is gone. `Directory.reclaim_stale_migrating/1` is a partial
backstop for migrations but does not touch the Oban row; `DeleteJob` and `HandoffJob` have none.

**Impact:** One crash strands up to 21 jobs, each permanently wedging one shard's lifecycle
machinery. The symptom is "this tenant never migrates / can't be deleted / stays pinned" with no
error anywhere.

**Correctness/reliability:** **Strictly better.** Lifeline rescues only jobs whose `attempted_at` is
older than `rescue_after` **and** whose state is `executing`. Every affected worker is documented
idempotent (`DeleteJob`'s moduledoc says so explicitly; `ReconcileJob` relies on `ShardMigrationJob`'s
copy being idempotent). Set `rescue_after` generously (30–60 min) so a genuinely long migration copy
is never rescued out from under itself — the same reasoning as
`@default_migration_stale_seconds 3_600`.

**Recommended Fix:** `{Oban.Plugins.Lifeline, rescue_after: :timer.minutes(60)}`. In the same change,
consider dropping the Pruner's `max_age` for `completed` to 24 h — a 1M-shard rollout leaves millions
of completed rows for a week, inflating #13's group-by and every index scan in #20.

### #35. A redundant non-partial index on the fleet's most-frequently-updated table
**Severity:** Medium | **Category:** Performance / write amplification | **Panels:** P5

**Problem:** `20260628001559` creates `index(:shards, [:schema_version, :last_active_at])`, superseded
by `20260702011500`'s `shards_active_schema_version_last_active_at_index` (same columns,
`where status = 'active'`). All four `schema_version` predicates in `lib/` also filter
`status == "active"` (`directory.ex:769`, `:491`, `:501`, `:522`), so every one can use the partial.
The non-partial index is **unused for reads and pure write overhead** — the exact mistake
`20260708012318` fixed for `shard_load_samples` and `20260710005722` for `shard_warm_locations`.

It sits on the worst possible table: `record_batch/1` updates `last_active_at`, which appears in three

*and* entries in all five indexes.

**Impact:** ~20% fewer index-entry writes and ~20% less index bloat/vacuum on the directory's hottest

**Secondary (note only):** `Recorder.do_flush/0` (`recorder.ex:125-132`) issues `record_batch` and

`record_flush_batch`'s comment at `directory.ex:156` already relies on). **Do not** merge by giving
flush-only entries a synthetic `last_active_at`: that phantom-bumps recency, which is precisely the
bug round-2 #32 fixed for `revoke` and which feeds the revert write-age guard.

**Recommended Fix:** `DROP INDEX CONCURRENTLY IF EXISTS shards_schema_version_last_active_at_index`
with `@disable_ddl_transaction true`. Before dropping, confirm disuse:

### #37. 5 GB is a hard, silent cliff — past it a shard is permanently un-flushable, and the only default brake is on the *flush*, not the *write*
**Severity:** Medium | **Category:** Reliability / RPO | **Panels:** P4

**Problem:** `s3.ex:60` `@max_single_put`, `:592-596` `{:error, {:object_too_large, size}}`; `:1166`
`copy_object` and `:464` `upload_part_copy` carry the same 5 GB limit. `:shard_max_page_count` is
**unset by default** (`runtime.exs:384` sets it only from an env var). So the first defence against a
runaway tenant is a *flush* failure: the shard keeps accepting and **acknowledging** writes, stays
permanently dirty, retries every interval, and its RPO becomes **unbounded** — precisely the failure
`docs/durability.md` names ("this bound holds only while flushes succeed"). `FathomFlushFailing` fires
forever with no operator remedy, and the same ceiling silently disables `snapshot`, `fork_shard`, and
`retain`. The multipart machinery to fix it already exists in the file — wired only to the
etag-rotation touch, not the data PUT.

**Correctness/reliability:** A **write-time** cap cannot lose data: the write is rejected with
`SQLITE_FULL` and never acknowledged, so nothing acknowledged goes unflushed. Strictly safer than
today, where writes *are* acknowledged and then cannot be made durable. A multipart data upload
changes the etag *form* to `…-N`, which every consumer already handles (`multipart_etag_form?/1`, and
`verify_integrity/3`'s `x-amz-meta-fathom-md5` fallback exists precisely because rotation produces
that form); `If-Match` on a multipart-completed object is still enforced.

**Recommended Fix:** Cheapest first — default `:shard_max_page_count` to a value comfortably under the
ceiling (≈1,048,576 pages at 4 KiB ⇒ 4 GB) so the brake bites at write time. Make
`{:object_too_large, _}` a distinct, loud flush outcome in telemetry rather than a generic transient
error. Consider real multipart for the data PUT.

### #38. Compression is absent from the entire storage path — worth building, behind a flag, for the bandwidth-bound paths only
**Severity:** Medium | **Category:** Performance / bytes at rest and on the wire | **Panels:** P4

**Problem:** `grep -rn "zstd\|:zlib\|gzip\|deflate\|content-encoding" lib/ config/` returns only the
web endpoint's static-asset gzip. Every shard object is stored and transferred as a raw SQLite file.

**Impact, both directions honestly:** SQLite files of ORM row data compress ~2.5–3.5× with `:zlib`
(in OTP, no new dep) at level 6, ~3–5× with zstd — 60–75% off every flush PUT, every cold-open GET,
every warm re-pull, and the at-rest bill, at single-digit ms of CPU per operation at 640 KiB.
**Where it does not pay:** cold-open at fathom's shard sizes is RTT-bound, not transfer-bound
(`latency-cost-2026-07-23.md`: 26/70/133 ms at 10/30/60 ms one-way ≈ 1 RTT with the body essentially
free), so ~0 win on `cold_open_s3_p50_us` for small shards on a fat pipe. **Where it does pay:**
`warm_s3_shards_per_s` (mass warming/failover is aggregate-bandwidth-bound — `S3_FAKE_RATE_KBPS` can
prove it), steady-state PUT volume for hot shards, cross-region, storage cost. And the CPU is **not**
free on a saturated box — `tpc-fleet` already shows a CPU plateau — so measure on a *loaded* node.

**Correctness/reliability — the constraints that keep the contracts intact:**
- A compressed object is still **one self-contained object**; a crash-steal taker with only the object
  store pulls and inflates it deterministically. "Pull is authoritative" unchanged.
- Inflate inside the existing streamed-to-disk `download/4` so nothing is materialized whole in the
  BEAM; take the integrity digest over the **uncompressed** bytes so `x-amz-meta-fathom-md5` keeps
  meaning "this database's hash" and `verify_integrity/3` needs no change. `content-md5` covers the
  compressed wire body.
- Carry an explicit format marker (`x-amz-meta-fathom-enc`). A node that cannot decode the marker must
  **fail the pull closed**, never serve raw bytes as a database — that is the one way this becomes a
  correctness incident.
- **Do not** use HTTP `Content-Encoding: gzip` — the etag/`If-Match` fence is over the exact stored
  bytes, and a store or CDN that transforms encodings would move the etag under the fence. Compress in
  the application layer, store opaque bytes.
- Unaffected by construction: the server-side copy paths (`retain`, `restore/2`, `snapshot`,
  `fork_from`, `fork_shard`) are byte-opaque; the sentinel and etag-rotation touch operate on the
  object regardless. `Snapshots.restore`'s `PRAGMA user_version` read must go through an inflating
  `pull_snapshot`.

**Recommended Fix:** Config-gated `:shard_object_encoding`, default `:none`, marker-tagged,
decode-always/encode-optionally so a fleet can roll forward and back.

### #41. Incremental / delta upload — a reasoned **NO** under the current fence
**Severity:** — (decision record) | **Category:** Architecture | **Panels:** P4

Recorded so it is not re-proposed.

**The naive forms are unsafe, specifically.** Uploading only changed pages requires a taker — which by
contract holds *only* the object store — to read a base plus deltas 1..k as one image. S3 gives
per-object atomicity, never cross-object atomicity, so a taker reading while the owner writes delta
k+1 cannot know which deltas form a consistent image. Any scheme letting the taker infer the set (a
LIST, a naming convention, "highest sequence wins") is a torn read waiting to happen.

**The one constructible variant** is immutable never-reused delta objects plus a **manifest written
last and `If-Match`-fenced**, readers reading the manifest first. That is Litestream-shaped and
genuinely correct. **It still loses at fathom's shape:**
1. Object count goes from ~1/shard to O(flushes)/shard, breaking the properties the design leans on at
   millions of shards: a fork is *one* copy, a snapshot is *one* copy, `purge_shard`'s
   exact-delimiter sweep enumerates a bounded key set, `stored_usage` is a LIST. All become O(chain).
2. It trades the metric that matters for the one that doesn't: a taker's cold open becomes `1 + k`
   GETs, so `cold_open_s3_p50_us` and both `failover_*_s3_p50_us` regress by `k × RTT` to buy PUT
   bytes. Failover RTO is the availability metric; PUT bytes are a cost line.
3. The base must be re-uploaded periodically to bound `k`, so the best-case byte saving is `1 − 1/k`
   while tail latency is `k×`.
4. The crash-steal fence does not generalize for free: today a superseded flush is one 412 on one key
   and the steal-time `touch_object/2` rotates exactly one etag. With a chain, a stealer must
   invalidate a *set* of keys a zombie may still be writing into — a substantially larger fence
   surface for the same guarantee.

**Recommendation:** Do not build page-level delta upload. The correct incremental lever is the
already-scoped **A2 WAL streaming**, which has the same manifest problem but at least reuses SQLite's
own frame ordering and per-frame checksums instead of inventing a second consistency protocol. Until
then the levers are #3, #11, #19, #38, and `:shard_flush_interval_ms`.

## Rejected on the hard constraint

Recorded so they are not re-investigated:

- **`mmap_size`** (default 0) would cut read syscalls, but SQLite's documented `SIGBUS`-on-I/O-error
  behavior under mmap is a reliability trade the constraint rules out, and address-space consumption
  at millions of shards makes it the wrong lever regardless. (P1)
- **`max_heap_size` on `Fathom.Shard`** — a coordinator killed at the limit mid-`terminate/2` skips the
  final fence + checkpoint + PUT + lease release: a durability regression that can strand a lease. (P2)
- **Evicting from `Tenants.Tombstones`** — re-opens the re-mint hole; a Bloom filter would 410 live
  tenants. Only the *refresh* is safe to make incremental (#30). (P2)
- **Req-level retries on the flush PUT** — `flush/3` is `If-Match`-fenced; a blind retry would re-issue
  with a stale etag. The coordinator-level backoff is the correct retry tier. (P3)
- **`PRAGMA optimize` at stream close** (SQLite's own recommended pattern) — it *writes* to
  `sqlite_stat1`, which would trip `wrote?`, bump `WriteCounter`, and make **every read-only stream
  close trigger a full-file S3 PUT**. A direct attack on the write-gated flush design. If pursued at
  all, it belongs on the coordinator's drop path, only when the shard is *already dirty*, with
  `analysis_limit=400`, behind a default-off flag — and only after an `EXPLAIN QUERY PLAN` diff on the
  TPC-C statement set proves there is anything to win. (P1)
