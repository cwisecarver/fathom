## What already exceeds expectations

Yes — for a pre-launch demo package, the materials are well above the median, and the gap between them and a fundable story is a day of edits, not a rebuild. The single most impressive artifact is the **engineering-honesty culture that shows up in the docs themselves**: `docs/durability.md` publishes a *measured* RPO table (452 rows p50 / 800 p99 lost at the 5 s default under 200 writes/s), states the cost side, and explicitly refuses zero-loss language; `fleet-density-2026-07-10.md` carries an "Honest limits" section that says the millions figure is arithmetic, not an exhaustive run; `tpc-fleet-2026-07-23.md` publishes a null result against its own metric; `pitr_proof` opens with "Scope (honest)". Diligence engineers grade for exactly this, and it is rare. **Nothing in the top-4 findings below is a product defect — they are all cases where the *pitch* is weaker than the *product*, or where the demo stack's dev-mode defaults outrun its "EVAL ONLY" labels.**

Specific things that hold up under scrutiny:

- **djathom's `DEMO.md` is a genuinely good demo-day script** — 90-second pitch, Do → Say → Proves act structure, three-persona login, and a what-proves-what table. Most seed-stage demos have no script at all.
- **The 564-line number is the pitch.** 564 lines of fathom-specific plumbing (aliases 157, managers 99, router 51, exceptions 29, `__init__` 25, fathom_api 157, routers 46) carry the entire tenancy story against ~2,000 non-test lines; the domain code (models + views = 416 lines) needs zero fathom imports beyond `objects = TenantManager()` and a `shard_id=` queryset kwarg. Panel E verified `router`/`managers`/`exceptions` byte-identical to upstream by diff.
- **Secret hygiene is clean.** `identity.sqlite3` is not committed and never was (walked `git log --all --diff-filter=A`); gitignored *and* dockerignored; contents synthetic (6 demo users, pbkdf2 hashes of their own usernames, no PII). Full secret sweep of both repos clean — every credential is a self-labeling placeholder. Django never holds `secret_key_base`; that's the correct shape and the threat model is documented.
- **The demo does not hide behind auth-off.** The stack runs `HRANA_AUTH: required` with real TLS, and `deploy/README.md` admits the self-signed CA honestly.
- **Fail-closed routing by construction** — `ShardRequired`, no ambient tenant anywhere, `allow_relation` refuses cross-shard FKs, integer cents with a float-drift test, an FK-enforcement test defending the `PRAGMA foreign_keys`/`ATOMIC_REQUESTS` footgun, and a real integration test proving cross-shard isolation.
- **django-fathom-example's `scale_probe`/`churn` numbers are a model of concrete proof** (20,000 tenants × 4 MB against a 1,000-shard cap; open set self-stabilizes ~760; 1,977 verified cold reopens; 0 refusals), and its README leads its "Sharp edges" with limitations.
- **"Physically separate database, not a `tenant_id` column"** is a sharp, VC-legible differentiator, and the warehouse/DuckDB answer preempts the cross-tenant-analytics objection before it's asked.

## Ranked Findings

### #1. Demo stack publishes the control plane on 0.0.0.0 with admin/admin, and DEBUG=True renders that credential on any 500 page
**Severity:** Critical | **Category:** Security | **Panels:** D (D4), E (E8)
**Likelihood:** High (any demo on shared/conference wifi) | **Blast Radius:** Full tenant delete / export / token-mint for every tenant in the stack, to anyone on the same network

**Problem:** Three defaults chain into a live exposure:
- `djathom/deploy/docker-compose.yml:120-121` publishes fathom's admin/control-plane port **4000 on all interfaces**, with credential `admin/admin` (`:35-36`).
- Django runs `manage.py runserver 0.0.0.0:8000` with `DEBUG=True` and `ALLOWED_HOSTS=["*"]` (`settings.py:29-31`, `entrypoint.sh:32`).
- Panel D verified against the vendored Django 5.0.6 that the setting name **`FATHOM_ADMIN_AUTH` matches none of Django's cleanse substrings** (`API|TOKEN|KEY|SECRET|PASS|SIGNATURE|HTTP_COOKIE`), and that `cleanse_setting` recurses tuples with an empty key — so **any** Django 500 page renders `FATHOM_ADMIN_AUTH = ("admin", "admin")` in plaintext.

`settings.py:29-31` also hardcodes `SECRET_KEY`/`DEBUG`/`ALLOWED_HOSTS` with no dev/prod split and no env override — unlike the `FATHOM_*` URLs, which are env-driven (E8). The docstring says "Dev only. Never a real secret," which is honest but not load-bearing.

**Impact:** Demo the product on conference wifi and anyone on the LAN can read the admin credential off a stack trace, then delete, export, fork, or mint tokens for every tenant — including live during the pitch. "EVAL ONLY" banners mitigate this reputationally, not operationally. This is the one finding in the queue with real operational blast radius.

**Recommended Fix:**
1. Bind loopback in `deploy/docker-compose.yml`: `127.0.0.1:4000:4000`, `127.0.0.1:8000:8000`, `127.0.0.1:8443:8443`.
2. Generate a random `ADMIN_PASS` at `up` instead of shipping `admin/admin`.
3. **Rename the setting to `FATHOM_ADMIN_SECRET`** so Django's own `cleanse_setting` filter catches it — a one-word change that removes the credential-print path entirely.
4. Env-drive `DEBUG` with a `False` default (`DEBUG = os.environ.get("DJANGO_DEBUG", "") == "1"`), and narrow `ALLOWED_HOSTS` likewise.

### #5. "TLS end to end / no tenant token crosses the network in plaintext" — the LB→node hop is plaintext
**Severity:** High | **Category:** Claim credibility → Security | **Panels:** C (C4)
**Likelihood:** Medium-High (falsifiable in minutes with tcpdump, by exactly the audience that checks) | **Blast Radius:** A security claim demonstrably false on the demo's own stack

**Problem:** `djathom/DEMO.md` (Set up + Act 4: "**No tenant token crosses the network in plaintext**") does not describe what the deploy config does. The LB **terminates** TLS and proxies **plaintext** to the fathom nodes: `deploy/docker-compose.yml:15`, `docker-compose.chaos.yml:52` `LB_BACKENDS fathomN:8080`, and the `exceptions.conf` upstreams on `:8080`. The per-home token therefore crosses the LB→node hop in the clear. `deploy/README.md` describes this correctly — **only DEMO.md overstates.**

**Impact:** This is the claim a security-minded diligence engineer tests, and it takes one `tcpdump` on the compose bridge to disprove. The honest version — client→LB TLS plus a private backend segment — *is* fathom's documented trust boundary and is a perfectly good answer; overstating it converts a defensible design into an apparent misrepresentation.

**Recommended Fix:** Claim client→LB TLS + a private backend segment (fathom's documented trust boundary), and amend Act 4's *Proves*:

> "no tenant token crosses the **public** network in plaintext — the LB terminates TLS and the LB→node hop rides the private segment, which is fathom's documented trust boundary (see `docs/auth.md`)."

### #6. "Even a full app compromise can mint only what the admin API allows, not a token for any home it likes" — it can mint any home's token
**Severity:** High | **Category:** Claim credibility → Security | **Panels:** C (C5)
**Likelihood:** Medium-High (10 minutes in `router.ex` + the compose file disproves it) | **Blast Radius:** The blast-radius claim itself — the thing a security reviewer grades

**Problem:** `djathom/README.md` claims "even a full app compromise can mint only what the admin API allows, not a token for any home it likes," and `DEMO.md` Act 3 says "A Django compromise can't cross it." fathom's API scopes are **capability-level, not tenant-level**:
- `lib/fathom/api_keys.ex:20` — `read < manage < destroy`; `api_key.ex:9`.
- The mint route is `POST /tenants/:id/token` with **`:id` free** (`router.ex:66`).
- The compose gives djathom the **shared admin BasicAuth credential**, which `router.ex:106` maps to scope **`destroy`** (max).

A compromised djathom can therefore mint **any** home's token and delete/fork/export **any** tenant.

**Impact:** The claim is the strongest security statement in the demo materials and it's the one that fails first. The *real* win is still substantial — no offline forgery, an audited/revocable/rate-limited mint path, per-home revocation — and it survives scrutiny. Claim that instead.

**Recommended Fix:** Rewrite both passages to the backed claim (draft):

> "A compromised app can't *forge* a token offline — every credential comes from an audited, revocable, rate-limited mint path, and any home's access can be revoked individually without touching the others. Tenant-scoped API keys (mint-for-this-home-only) are the next step; today the admin key is capability-scoped, not tenant-scoped."

Soften Act 3's *Proves* to the **connection-scoped** claim — `FILO_READONLY` refusal on a `:ro` connection — which is fully backed by the code and by `docs/auth.md`.

### #12. The runtime alias registry is mutated with no lock, on the routing hot path, under threaded WSGI
**Severity:** High | **Category:** Code quality / Shard-isolation-adjacent | **Panels:** E (E1)
**Likelihood:** Medium (needs concurrency the demo doesn't currently drive) | **Blast Radius:** 500s / over-eviction under load — **not** a cross-tenant leak

**Problem:** `aliases.py:89-142` (**identical in both repos**) mutates the `_registered` OrderedDict LRU **and** `connections.databases` with **no lock**, on the request hot path, under threaded WSGI. The same author correctly used `threading.Lock` in `fathom_api.mint_token` — one file protected, the other not. The eviction loop is a compound check-then-act: concurrent requests can over-evict or hit `popitem` `KeyError` ⇒ 500. Panel E is explicit that this is **not** a misrouting bug — the failure mode is crash or over-eviction, not tenant A reading tenant B — but it *is* the first question a Django veteran asks of the routing seam. The docstring's "Proven by `scale_probe`" is unverified: `scale_probe` is a **sequential for loop** and never exercises concurrency.

**Impact:** Latent today (the demo is single-threaded-ish), real under any production-shaped load, and a credibility hit during code review because it sits in the exact 157 lines you're asking reviewers to read.

**Recommended Fix:**
1. Wrap `_registered` mutations, the `connections.databases` writes, and the eviction loop in a module-level `threading.Lock` (mirror `fathom_api.mint_token`'s pattern).
2. Add a `ThreadPoolExecutor`-driven concurrency test that hammers the registry past the LRU bound and asserts no exception and a bounded registry — then the docstring's "proven" claim is true.
3. Fix in `django-fathom-example` first (it's upstream), then re-vendor into djathom.

### #14. The `FILO_READONLY` proof never checks that fathom actually said `FILO_READONLY`
**Severity:** Medium-High | **Category:** Code quality / Claim credibility | **Panels:** D (D2), E (E4)
**Likelihood:** High (any transient failure renders the false proof) | **Blast Radius:** Act 3's proof is unfalsifiable — and stays green if `:ro` enforcement regresses

**Problem:** `web/views.py:166-171` catches **bare `except Exception`** and unconditionally renders "refused by fathom (FILO_READONLY), not by the app." A dead node, a suspended tenant, a TLS handshake failure, or a malformed row all render the **identical** proof text. `tests/test_ro_scope.py:31` is the same shape (`assertRaises(Exception)`).

**Impact:** Two-sided. On stage, a network hiccup produces a **false positive proof** — you'd claim a security guarantee you didn't demonstrate. In CI, if fathom's `:ro` enforcement silently regressed, both the demo and the test **stay green**. This is the demo seam's most consequential correctness gap because the whole act is an assertion about *who* refused.

**Recommended Fix:** In both places, inspect before labeling:

```python
except Exception as e:
    if "FILO_READONLY" not in str(e):
        raise                      # a real failure — don't dress it as the proof
    messages.error(request, "Write refused by fathom (FILO_READONLY), not by the app.")
```

And in `tests/test_ro_scope.py`, replace `assertRaises(Exception)` with `assertRaisesRegex(Exception, "FILO_READONLY")`. Render a **distinct** message for any other failure so the presenter can tell "the guarantee held" from "the network died."

### #15. The ro/rw scope ContextVar defaults to `rw` and is never reset between requests
**Severity:** Medium | **Category:** Security / Code quality | **Panels:** D (D5), E (E3)
**Likelihood:** Low today, Medium as the app grows | **Blast Radius:** A future view that forgets `set_scope` silently gets write access — or inherits the previous request's scope on a pooled thread

**Problem:** Two defects in one mechanism (`config/…/aliases.py:39-49`, `web/views.py:40-47`):
- **Fails open.** `_scope_for` picks ro/rw and `set_scope` must be called before the first shard query, but the module-level ContextVar **defaults to `"rw"`** (`aliases.py:49`). A view that forgets `set_scope` silently inherits write access.
- **Never reset.** There is no middleware — only per-view calls at `views.py:80` and `:148`. Invisible under `runserver` (fresh thread per request); under **pooled-thread WSGI (gunicorn `gthread`, how Django is actually deployed)** threads are reused, so a stale `rw` can leak into what should be a `:ro` advisor connection.

This also contradicts the codebase's own stated no-ambient-state principle, which is otherwise held rigorously.

Consequently `DEMO.md:78`'s "A bug in our app couldn't let her write" is overstated — the app-layer scope selection is exactly what a bug can skip.

**Impact:** Latent (both call sites are disciplined today), but it's a fail-open default in the one module that decides read-vs-write, and it undercuts a spoken guarantee.

**Recommended Fix:**
1. Default the ContextVar to `"ro"` (or a raising sentinel that forces an explicit choice).
2. Bind scope in **middleware** from the session, and reset it per request (`copy_context().run(...)`, or an explicit reset in a `finally`).
3. Soften `DEMO.md:78` to the backed claim: "a compromised **connection** can't escalate — the `:ro` token is refused by fathom, not by us."
