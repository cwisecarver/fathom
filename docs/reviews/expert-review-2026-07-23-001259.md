# Fathom Expert Panel Review — Performance Audit

**Date:** 2026-07-23
**Panels:** Per-query hot path (P1) · Stream/checkout lifecycle & OTP concurrency (P2) · Cold-open & flush storage path (P3) · Accounting/telemetry overhead (P4) · Filo seam & memory/allocation (P5)
**Methodology:** Panel scoping (performance-focused, per user request: "find inefficiencies in the hot path") → 5 parallel expert reviews → unified ranking

## Project Profile

- **Type:** multi-tenant sharded data platform (SQLite-per-shard, Hrana, S3-bottomless)
- **Expert Domains:** the 5 panels above — all oriented at hot-path cost per fathom's scaling story (per-shard open + fan-out + per-query overhead × fleet)
- **Commit reviewed:** c6f8603
- **Total Findings:** 31 unique after dedup (from 44 raw across panels)
- **Scope note:** filo (`../filo`) is in scope — fathom's per-request cost includes filo's. Findings marked **(filo)** live in that repo.

**TLDR — Top 5:**
1. **No prepared-statement reuse** — every query pays a full SQLite parse+plan; the single largest recoverable per-query cost (est. 1.3–2× point-query throughput).
2. **Full-SQL `String.downcase` in `ends_transaction?`/`control_statement?`** — found by 4 of 5 panels; O(len) binary copy on every SELECT; trivial prefix-slice fix.
3. **OTel checkout-span bridge attached by default** — docs say off-by-default, code defaults on; full recording spans per checkout exported to nothing; one-line fix.
4. **(filo) HTTP path deep-copies the encoded result across the Stream GenServer boundary** — full inter-heap structural copy of every result set.
5. **(filo) Per-cell tagged maps + double walk before Jason** — ~3–5 allocs/cell then a second full traversal; an iodata encoder halves row-encoding CPU on both transports.

## Ranked Findings

### #1. No prepared-statement reuse — every statement re-parsed and re-planned per execution
**Severity:** High | **Category:** Performance | **Panels:** P1
**Likelihood:** High — every query, default-on path | **Blast Radius:** per query

**Problem:** `do_query` (`lib/fathom/shard/connection.ex:91-108`) runs `Sqlite3.prepare` → bind → step → `Sqlite3.release` for every execution; grep confirms no statement cache anywhere. Django (the flagship client) replays identical parameterized SQL on a stream, so each execution pays a full `sqlite3_prepare_v2` parse+plan through the NIF plus statement-resource churn.

**Impact:** Prepare cost is typically 5–50 µs (more for multi-join ORM SQL) — comparable to or larger than step cost for the point reads/writes that dominate. At the measured ~51k q/s/node this is plausibly the single largest recoverable per-query cost; a classic 1.3–2× win on point-query throughput for embedded-SQLite servers.

**Recommended Fix:** exqlite 0.37 has `Sqlite3.reset/1`; the connection is per-stream and single-process-owned, so a cache is race-free. Carry a small LRU statement cache (`sql => stmt`, cap ~32–64) in the executor handle (make the handle's conn a `%Connection{}` struct). Hit: reset + bind + step; miss: prepare + insert (evict oldest). `ShardExecutor.close/1` releases cached statements before `Sqlite3.close`. `prepare_v2` auto-recompiles on schema change — no invalidation logic. Add a `@tag :bench` repeated-statement throughput guard. Synergy: the handle-struct change is the natural carrier for #7's resolved-at-open config.

### #2. `ends_transaction?`/`control_statement?` downcase the entire SQL string — on every read
**Severity:** High | **Category:** Performance | **Panels:** P1, P2, P4, P5 (4 of 5 panels)
**Likelihood:** High — every SELECT, default-on path | **Blast Radius:** per query

**Problem:** Both helpers (`lib/fathom/shard_executor.ex:262-265`, `:247-252`) do `sql |> String.trim_leading() |> String.downcase()` on the full statement. The file's own `dml?`/`ddl?` deliberately slice 6–7 chars first — these two don't. `ends_transaction?` runs on every statement where `wrote?` is false (line 159), i.e. every SELECT.

**Impact:** `String.downcase/1` allocates a full copy: a Django `SELECT ... WHERE id IN (...)` with a routine tens-of-KB IN-list costs an O(len) binary copy + GC pressure per read. At 51k q/s: megabytes/s of avoidable garbage on the hottest processes.

**Recommended Fix:** `ends_transaction?`: slice the first ~7 chars post-trim before downcasing. `control_statement?`: slice ~10 chars (longest prefix `"savepoint"` = 9); fall into the full-string `durable_pragma_write?` scan only when the prefix is `"pragma"`. Synergy with #27: one classification pass can yield dml/ddl/control/commit flags together.

### #3. OTel checkout-span bridge attached by default — recording spans per checkout with no collector
**Severity:** High | **Category:** Performance | **Panels:** P4
**Likelihood:** High — default-on in dev and any prod deploy without a collector | **Blast Radius:** per checkout, node-wide

**Problem:** AGENTS.md says traces are "env-gated on `OTEL_EXPORTER_OTLP_ENDPOINT`, off by default" — but the env var only gates the *exporter* (`config/runtime.exs:40-43`). The bridge attach is gated by `:otel_spans`, which defaults **true** (`lib/fathom/telemetry.ex:388`; only test.exs sets false). All three checkout events run OTel handlers inline in the stream process — span ctx alloc, active-span ETS insert, pdict bookkeeping, `set_attributes`, end — full *recording* spans under `always_on`, exported to nothing.

**Impact:** Few µs + several ETS ops + allocations per checkout producing nothing; at ~20k streams / checkout-per-query workloads, the single biggest hidden per-checkout accounting cost.

**Recommended Fix:** Set `:otel_spans` true inside the existing `if otlp_endpoint` block in runtime.exs and flip the default to false — or gate the attach on `traces_exporter != :none`. One-line semantic change that makes the documented posture true.

### #4. (filo) HTTP path deep-copies the entire encoded result set across the Stream GenServer boundary
**Severity:** High | **Category:** Performance | **Panels:** P5
**Likelihood:** High — every HTTP pipeline request (libsql-experimental/SDK default path) | **Blast Radius:** per request

**Problem:** `Request.handle` encodes rows into Hrana maps inside the `Filo.Stream` GenServer (filo `lib/filo/request.ex:17-19`); `Stream.run` returns them through `GenServer.call` (filo `lib/filo/stream.ex:126-139`) — a full structural copy between heaps in the most expensive term shape (list-of-maps-of-small-maps; only refc binaries >64B cross by reference). The Bandit request process then walks the copy again for `Jason.encode!` (filo `lib/filo/plug.ex:251-257`, `560-564`).

**Impact:** Every HTTP request materializes the result set twice in two heaps simultaneously with a word-by-word copy between — the single largest avoidable per-request allocation on the HTTP path. (django-libsql uses WS, which skips this hop.)

**Recommended Fix:** JSON-encode each result to iodata/binary *inside* the stream process; reply with `Jason.Fragment`-wrapped binaries the plug splices into the envelope. A large refc binary crosses by reference — the copy drops to O(1). Composes directly with #5 (the fragment is the thing the iodata encoder builds) and #9; together they are the fix for #10.

### #5. (filo) Per-cell intermediate tagged maps, then a second full walk by Jason — no iodata fast path for rows
**Severity:** High | **Category:** Performance | **Panels:** P5
**Likelihood:** High — every response row on both transports | **Blast Radius:** per query (per cell)

**Problem:** Every cell becomes a 1–2-key string-keyed map (`%{"type" => "integer", "value" => Integer.to_string(v)}`, filo `lib/filo/value.ex:32-43`, `lib/filo/stmt_result.ex:38`, same in `cursor.ex:36-39`) whose only purpose is immediate consumption by Jason — map alloc + tag binaries + `Integer.to_string` per int cell — then Jason traverses, re-dispatches, re-escapes.

**Impact:** Row encoding is the dominant CPU of a SQL proxy and this doubles it: ~3–5 heap allocations per cell before the encoder starts. 10k rows × 8 cols ⇒ ~240k+ transient allocations per request, on the default JSON encoding of both transports (WS and HTTP).

**Recommended Fix:** Hand-roll the Hrana value/row encoder to emit iodata directly — five value shapes, all trivially concatenable; text needs one `Jason.encode_to_iodata!` for escaping. Wrap rows in `Jason.Fragment`. Composes with #4 (build the fragment in the stream process), gives #8 its natural home (try-text/fallback-blob in the encoder), and multiplies with #9.

### #6. Drain's third RTT is a redundant lock GET — the lock etag is already in the PUT response but discarded
**Severity:** High | **Category:** Performance | **Panels:** P3 (P3's overlap fallback folded in)
**Likelihood:** High — every idle drop, drain, eviction, handoff, deploy shutdown | **Blast Radius:** per flush/drain

**Problem:** `release_lease` (`lib/fathom/shard/storage/s3.ex:1357-1374`) is GET-lock → conditional DELETE (2 RTTs); the GET exists only to learn the lock's etag — but every write of that lock is our own, and both `create_lock` (`:1317-1328`) and `put_lock` (`:1483-1505`) receive the new etag in the PUT response and throw it away. Drain = data PUT + lock GET + lock DELETE = the measured ~3.3–3.5 RTT. **Correction to `docs/reviews/latency-cost-2026-07-11.md`:** the third RTT is this lock GET, not the etag sidecar upload — the sidecar is a local file (`shard.ex:1734`). `renew_lease` (`:1331-1354`) has the identical GET-then-PUT shape. This is the AGENTS.md-named flush-path **tuning target**.

**Impact:** 1 full RTT (~30 ms at 30 ms one-way) on every idle drop, voluntary drain, rebalance handoff, LRU eviction, and rolling-deploy shutdown flush — ×N shards on deploy. Legacy renew/fence pays 2 RTTs where 1 suffices.

**Recommended Fix:** Carry `lock_etag` in the lease map (client-side state; encode/decode unchanged). `release_lease` becomes a single `DELETE If-Match: <cached etag>`; on 412 fall back to read-then-decide. Same for `renew_lease` (single PUT If-Match). Drain 3 → 2 RTTs (~215 → ~150 ms at 30 ms one-way). Fallback if rejected: overlap the read-only lock GET with the data PUT in `flush_then_drop` (`shard.ex:1385-1463`) — the PUT→DELETE ordering itself is irreducible.

### #7. `Application.get_env` sprawl on the hot path — hot gates belong in `:persistent_term` (incl. per-batch `max_rows` read)
**Severity:** Medium | **Category:** Performance | **Panels:** P1, P2, P4
**Likelihood:** High — every query and every stream cycle, default-on | **Blast Radius:** per query + per stream

**Problem:** A single successful statement on default config does 5+ app-env ETS lookups (`timeout_ms` connection.ex:250, `block_tenant_ddl?` shard_executor.ex:604, `template?` :406 via unconditional `capture/3`, `ShardLoad.enabled?` shard_load.ex:58, and `ShardLatency.enabled?` shard_latency.ex:76 — which **re-reads the identical `:shard_load` key**). Per stream cycle: ~13–15 more (`migrate_on_touch_mode` shards.ex:241-250 does a **double read when unset — the default**; `Lru` lru.ex:40-43 does 2 reads × 3 call sites/cycle). Worst instance: `collect/4` (connection.ex:227) re-reads `:query_max_rows` **once per 50-row multi_step batch inside the row-collect loop** — a 200k-row result does ~4,000 redundant get_envs in one query.

**Impact:** >150k config-ETS lookups/s at 51k q/s — a low-single-digit-% tax that grows with every new gated feature (8 gates per checkout+query round trip). The codebase already engineered around this class (`Migrator.HeadCache`, `WriteCounter.generation` use `persistent_term`).

**Recommended Fix:** Mirror stable hot-path gates into `:persistent_term` at boot with an ops/test-facing setter (the `WriteCounter.generation` pattern), or resolve once at `open/2` and ride them in the handle (synergy with #1's handle struct). Immediate one-liners regardless: pass the max-rows cap down as a `collect/5` argument; collapse the double `:shard_load` read; make `migrate_on_touch_mode` a single read; combine Lru's pair.

### #8. (filo) `String.valid?/1` full UTF-8 scan of every text cell — and BLOBs mis-tagged as text on the wire
**Severity:** Medium (perf) / High (correctness component) | **Category:** Performance + Data Correctness | **Panels:** P5
**Likelihood:** High (scan: every text cell, every response); Low-Medium (mis-tag: UTF-8-valid blobs) | **Blast Radius:** per query + wire correctness

**Problem:** (Root cause in exqlite.) exqlite's NIF `make_cell` returns bare binaries for both SQLITE_TEXT and SQLITE_BLOB — the type distinction is erased — so `Value.encode/1` (filo `lib/filo/value.ex:37-43`) must run `String.valid?(v)` on every binary cell (a full byte-walk), and Jason escape-scans the same bytes again. Not removable outright: SQLite TEXT can hold invalid UTF-8, and skipping the check makes Jason raise a 500. **Correctness bug:** a BLOB whose bytes happen to be valid UTF-8 is mis-encoded as `"type":"text"` — the client receives the wrong Hrana type.

**Impact:** O(total text bytes) redundant CPU per response, rivaling the JSON escape cost for text-heavy ORM rows; plus a genuine wire-protocol data-fidelity bug for binary columns.

**Recommended Fix:** Best: tagged-blob support upstream in exqlite (it already accepts `{:blob, bin}` binds — make reads symmetric) — fixes both the perf and the mis-tagging. Interim, inside the #5 hand-rolled encoder: attempt text encoding and fall back to blob on `EncodeError` per result (try/rescue near-free on the happy path).

### #9. (filo) `Jason.encode!` flattens to a contiguous binary where iodata would do; stdlib `:json` available and unused
**Severity:** Medium | **Category:** Performance | **Panels:** P5
**Likelihood:** High — every HTTP response and WS frame | **Blast Radius:** per request

**Problem:** `Jason.encode!` = `encode_to_iodata!` + `IO.iodata_to_binary` — but `send_resp` (filo `lib/filo/plug.ex:560-564`), the cursor lines (`:340`), and the WS frames (filo `lib/filo/socket.ex:357`) all accept iodata, so the final flatten is one more full copy of the whole response; `plug.ex:566-571` flattens protobuf output too. Filo requires Elixir 1.20 (OTP ≥ 27), so stdlib `JSON` (faster, zero-dep) is available and unused.

**Impact:** One avoidable O(response) copy per HTTP response and WS frame; the library switch is a free ~1.3–2× encode/decode CPU win. Multiplies with #4/#5.

**Recommended Fix:** `encode_to_iodata!` at all three send sites (drop the protobuf flatten too); then migrate to stdlib `JSON` and drop the Jason dep (keeping `Fragment`-equivalent splicing per #4/#5).

### #10. Large-result peak memory is ~4–5× the encoded size, and the default path is uncapped
**Severity:** High | **Category:** Reliability (memory) | **Panels:** P5 (systemic composition of #4, #5, #9)
**Likelihood:** Medium — needs large results in flight | **Blast Radius:** node-wide (OOM, cross-tenant)

**Problem:** At response time on HTTP, one query's result exists simultaneously as (a) native rows in the stream process (fathom `connection.ex:221-248`), (b) tagged Hrana maps there (filo `stmt_result.ex:38`), (c) the GenServer-copied maps in the request process (filo `stream.ex:132` → `plug.ex:254`), and (d) JSON iodata + flattened binary (`plug.ex:563`). `:query_max_rows` off by default is a documented decision — but the multiplier is undocumented: whatever cap an operator picks, the node pays ~4–5× wire size per in-flight large result, per stream, across tenants.

**Impact:** A handful of concurrent 100 MB-wire `SELECT *`s ⇒ ~2 GB transient heap — the noisy-neighbor OOM vector `:query_max_rows` exists to prevent, hit at ~4× lower row counts than a wire-size mental model predicts.

**Recommended Fix:** #4, #5, and #9 each remove one resident copy (all three ⇒ ~2×: native rows + iodata). Until they land, document the multiplier in `docs/data-path.md` where `:query_max_rows` sizing guidance lives so operators cap accordingly.

### #11. `Fathom.ShardRegistry` runs on a single Registry partition
**Severity:** High (churn-plane, not lookup-plane) | **Category:** Performance / Scalability | **Panels:** P2
**Likelihood:** Medium — bites during churn events (failover, idle-stop waves, eviction storms) | **Blast Radius:** node-wide

**Problem:** `{Registry, keys: :unique, name: Fathom.ShardRegistry}` (`lib/fathom/application.ex:363`) with no `partitions:` ⇒ one partition process + one ETS table pair serializes every coordinator registration, unregistration, and death-cleanup. Lookups are caller-side ETS and stay fast; the register/cleanup plane is the bottleneck.

**Impact:** Coordinator churn rate capped by one process: mass cold-open after failover (~800 shards/s measured all register through partition 0), idle-stop waves at 10k–30k coordinators/node, eviction storms at the soft cap. Cleanup lag widens the dead-pid window that `retry_checkout?` + `Process.sleep(1)` (shards.ex:104-110, 201-210) papers over.

**Recommended Fix:** Add `partitions: System.schedulers_online()`. One line; `lookup`/`count`/`select` call sites unchanged. Verify with `--ramp` that per-open time at high N improves. Unlocks visibility into #31 (single DynamicSupervisor).

### #12. exqlite `multi_step` runs at the 50-row default chunk — 20× more dirty-NIF round-trips than needed
**Severity:** Medium | **Category:** Performance | **Panels:** P5
**Likelihood:** High for multi-row results, default-on | **Blast Radius:** per query (row-proportional)

**Problem:** `Sqlite3.multi_step(conn, stmt)` (`lib/fathom/shard/connection.ex:222`) uses exqlite's `:default_chunk_size` of 50 (verified `deps/exqlite/lib/exqlite/sqlite3.ex:319-320`); fathom never configures it. Each call is a dirty-scheduler NIF dispatch + result-list handoff: 200k rows = 4,000 dirty round-trips (plus the 4,000 get_envs of #7's collect instance).

**Impact:** Per-batch dispatch overhead is the remaining constant on row collection. `:query_max_rows` granularity is the chunk anyway, so a bigger chunk doesn't materially weaken the cap.

**Recommended Fix:** `config :exqlite, default_chunk_size: 500` or explicit `multi_step(conn, stmt, chunk)` with a module attribute; 500–1000 is the sweet spot. Bench-gate it. Pairs naturally with #16 (count in `collect`).

### #13. Crash-takeover is 6–9 sequential RTTs; mass failover re-GETs the same dead node's heartbeat per stolen shard
**Severity:** High | **Category:** Performance (failover RTO) | **Panels:** P3
**Likelihood:** Low frequency (node death) but certain when it matters | **Blast Radius:** fleet-wide during failover

**Problem:** The steal path (`lib/fathom/shard/storage/s3.ex:1152-1253`, `:269-321`, `:393-410`, `:1260-1302`) serializes create-412 → lock GET → heartbeat GET → lock PUT → object HEAD → touch (multipart form = 3 requests — the common case, since fathom's flushes produce single-form MD5 etags) → confirm HEAD ≈ 9 requests, only the pull overlapped. On node death the survivor steals many shards from the same owner, and `owner_live?` re-reads the identical `heartbeat/<owner>` object per shard.

**Impact:** Failover RTO per shard is takeover-chain-bound (~270+ ms at 30 ms one-way), not pull-bound; a 1000-shard failover issues ~1000 redundant heartbeat GETs + ~9000 sequential requests, contending the 200-conn Finch pool with warm-follower promotions at the worst possible moment.

**Recommended Fix:** (a) Memoize heartbeat reads per owner with a sub-second TTL (persistent_term/ETS in the S3 backend; ≤1 s staleness is inside `steal_margin_ms`) — collapses to one GET per owner per second. (b) Drop the confirm-HEAD on the multipart-touch direction (CompleteMultipartUpload 2xx + `copy_body_ok?` + etag-form rotation already prove it). (c) Capture the post-touch etag from the CompleteMultipartUpload response body instead of a follow-up HEAD.

### #14. At-capacity admission does an O(N log N) full-table LRU scan per checkout
**Severity:** Medium (High when finite `:max_open_shards` + soft cap — the documented steady state for a dense node) | **Category:** Performance | **Panels:** P2
**Likelihood:** Medium — every new-shard open while at the cap | **Blast Radius:** node-wide (CPU/GC spike when saturated)

**Problem:** `lru_order/1` (`lib/fathom/shards/lru.ex:101-109`, called from `shards.ex:639-679`) does `:ets.tab2list |> Enum.sort_by` — every admission at the cap copies the entire recency table (10k–30k tuples) into the calling stream's heap and sorts it, to yield ≤16 candidates. Concurrent at-capacity opens each pay it simultaneously.

**Impact:** At 30k open shards, milliseconds of copy+sort per scan; a burst of novel opens at the cap = a node-wide CPU/GC spike exactly when the node is saturated.

**Recommended Fix:** Two-table LRU: an `:ordered_set` keyed `{monotonic_time, shard_id}` (touch = insert new key; stale keys tolerated) plus the existing `set` with current stamps; probe from the cold end via `:ets.first/:ets.next`, skipping stale entries, stopping after `@max_evict_probes` validated candidates. O(probes) per admission.

### #15. Warm-follower revalidation is O(cached) conditional GETs every 10 s, with per-304 temp-file churn, ignoring the directory's `last_flushed_at`
**Severity:** High (when `:warm_follower` on; gated off by default) | **Category:** Performance / Scalability | **Panels:** P3
**Likelihood:** Medium — gated, but continuous once A1 is enabled | **Blast Radius:** node-wide S3 traffic + freshness degradation

**Problem:** Every poll (`lib/fathom/shard/warm_follower.ex:51`, `:207-239`, `:272-288`) issues one signed conditional GET per cached shard: default 500-cap ⇒ 50 req/s/node forever collecting 304s; 10k cached ⇒ 1000 GET/s, and at schedulers×4 concurrency and 30 ms RTT a 10k sweep takes ~6+ s of the 10 s poll (~20k can't finish). Each 304 also pays a temp-file create/open/close/rm because `do_download` (`s3.ex:635-707`) opens the fd before the status is known. Meanwhile the follower already queries Postgres per poll, and the directory **already persists `last_flushed_at`** (review #28) — exactly the "did the owner flush since my pull" signal.

**Impact:** Warm capacity is supposed to be disk-bound but revalidation makes it request-bound: steady-state S3 request cost (and real-S3 per-request bills) linear in cache size, becoming the node's dominant S3 traffic at exactly the scale A1 targets; freshness silently degrades past ~10–20k cached.

**Recommended Fix:** (a) Return `last_flushed_at` from `active_recent` (or a sibling); skip the conditional GET for any cached shard whose `last_flushed_at` hasn't advanced past the cache stamp — GET count then tracks flushes-since-last-poll, not cache size; keep a slow rolling 1/N full sweep as belt against directory lag. (b) Defer temp-file creation until the first 200 data chunk so 304s touch no disk.

### #16. `rows_read: length(rows)` is a second full O(R) walk — count already computable in `collect`
**Severity:** Low | **Category:** Performance | **Panels:** P1, P2
**Likelihood:** High — every query | **Blast Radius:** per query (row-proportional)

**Problem:** `to_stmt_result` (`lib/fathom/shard_executor.ex:584`) computes `length(rows)` on the materialized list — O(R) on top of the O(R) reverse/concat `collect` (`connection.ex:221-248`) just did. With `:query_max_rows` set, `collect` already computes the count and throws it away.

**Impact:** One extra list traversal per query; a 200k-row result pays another ~1–2 ms.

**Recommended Fix:** Have `collect` count unconditionally and return `{:ok, rows, count}`; thread `row_count` into `to_stmt_result`. Lands naturally with #7's collect-arg change and #12.

### #17. Idle-timer cancel/rearm churn and duplicated LRU writes per stream cycle on the coordinator
**Severity:** Medium | **Category:** Performance | **Panels:** P2
**Likelihood:** High — every short stream on a hot shard | **Blast Radius:** per stream (hottest-shard admission ceiling)

**Problem:** For a shard oscillating 1↔0 connections (the hot pattern for short HTTP streams), each cycle costs the coordinator: monitor + Map.put + `Lru.record_conns` on grant; demonitor + Map.delete + `Lru.record_conns` + `Lru.touch` + `Process.send_after(:idle_timeout)` on release; the next checkout immediately cancels the timer (`lib/fathom/shard.ex:812-833`, `:1331-1347`). The caller *also* does `Lru.touch` per checkout (`shards.ex:86`) — recency stamped twice per cycle from two processes; each `Lru.*` call re-reads two app-env keys.

**Impact:** This is the serialization budget of the hottest shard — the ceiling the L=1 numbers brush against; trimming raises the hottest-shard stream-admission ceiling directly.

**Recommended Fix:** (a) Coalesced-deadline idle timer: keep `last_idle_at` in state, arm one timer only if none pending, compare-and-rearm on fire. (b) Drop the caller-side `Lru.touch` (single writer for recency). (c) Hoist `Lru.enabled?` to persistent_term (part of #7).

### #18. Per-stream connection open pays a redundant `mkdir_p` and 4–5 sequential PRAGMA round-trips
**Severity:** Medium | **Category:** Performance | **Panels:** P1, P2
**Likelihood:** High — every stream open | **Blast Radius:** per stream

**Problem:** `Connection.open` (`lib/fathom/shard/connection.ex:19-34`) runs once per Hrana stream: `File.mkdir_p!` (redundant — the coordinator did it in `handle_continue`, `shard.ex:243`) plus 4–5 sequential `Sqlite3.execute` NIF round-trips — `journal_mode=WAL` (persistent in the database file, unlike busy_timeout/foreign_keys/synchronous — a no-op re-negotiation every stream), `synchronous=FULL`, `busy_timeout`, `foreign_keys` (+get_env), optionally `max_page_count` (+get_env).

**Impact:** Syscalls + tens of µs per stream open, on the stream-open critical path that dominates short-stream workloads (per-stream overhead is what capped the L=1 harness at ~3k q/s vs 51k at L=64).

**Recommended Fix:** Delete the per-open `mkdir_p!` (move to the migrator/capture callers that need it); move `journal_mode=WAL` to the coordinator's file-materialization step; cache the env reads (#7). Larger option (measure first via `hrana_rt_us`): coordinator-owned idle-connection pool, reusing only cleanly-checked-in conns with `Connection.autocommit?/1` true — isolation and orphan-writer safety preserved.

### #19. `drop_clean` skips the lease release when no local file exists — lease leak
**Severity:** Low | **Category:** Reliability / Performance | **Panels:** P3
**Likelihood:** Low — abandon-checkout / failed-first-open exits | **Blast Radius:** per shard, cross-node availability

**Problem:** `drop_clean` (`lib/fathom/shard.ex:1374-1383`) wraps both `drop_local` and `Storage.release_lease` in `if File.exists?(state.path)` — a coordinator stopping clean *without* a local file (abandon-checkout → idle with no connection ever opened; or a brand-new shard whose pull found nothing and whose first checkout timed out) exits with the lock object still present.

**Impact:** Rare, but the next same-owner open silently downgrades from the optimistic 1-RTT create to the 2-RTT reclaim path; a *different* node sees `{:held, us}` while our heartbeat stays fresh — a cross-node availability wart plus leaked stale `.lock` objects.

**Recommended Fix:** Unconditionally `Storage.release_lease` in `drop_clean`; keep the `File.exists?` guard only around `drop_local`. One-line fix; ship with a regression test pinning the invariant (clean stop ⇒ no lock object).

### #20. (filo) Cursor path: full result materialization + one HTTP chunk write per row
**Severity:** Medium | **Category:** Performance / Architecture | **Panels:** P5
**Likelihood:** Medium — cursor-endpoint users, who by definition have large results | **Blast Radius:** per request (memory + syscalls)

**Problem:** The cursor endpoint exists for large results, but `Cursor.entries/1` (filo `lib/filo/cursor.ex:22-48`) builds the complete entry list in memory first, and `stream_lines` (filo `lib/filo/plug.ex:338-343`) issues one `chunk/2` call per entry — a separate transport write with HTTP/1.1 chunk framing around a ~40-byte JSON line. WS holds the full entry list in socket state (`socket.ex:249-252`).

**Impact:** Memory stays O(result) — defeating the cursor's purpose; a 100k-row cursor = 100k chunk calls with framing overhead dominating payload. Clients that pick /v3/cursor *because* the result is big get the worst path.

**Recommended Fix:** Short term: batch entries into fixed-size iodata chunks (256 lines or ~32 KiB per chunk call). Longer term: an optional streaming executor callback (fathom's `collect/4` could yield batches) so cursor memory is O(batch); bound the WS cursor entry list. Encoder work shares parts with #5/#9.

### #21. Shard-id regex validation 3× per stream open + `template?/1` re-cast per statement
**Severity:** Low-Medium | **Category:** Performance | **Panels:** P1, P2
**Likelihood:** High — every stream open (regex ×3) and every successful statement (template cast) | **Blast Radius:** per stream + per query

**Problem:** One stream open runs the `~r/^[a-zA-Z0-9_-]{1,64}$/` match three times on the same already-canonical id, each cast re-downcasing (`shard_executor.ex:44`, `shards.ex:62`, `:538` via `ensure` → `valid?`). Worse: `capture/3` runs on every successful statement and `template?/1` (`shard_executor.ex:376-381`, `:405-410`) does `ShardId.cast(Application.get_env(:fathom, :template_shard_id))` — a fresh regex match + downcase allocation per query to canonicalize a **constant**; `close/1` repeats it per stream.

**Impact:** ~1–3 µs per stream open plus ~1 µs-class per query wherever a template shard is configured (even unset it's an env read + two calls per query).

**Recommended Fix:** Canonicalize the template id once at boot (`check_template_default!` already touches it) into `:persistent_term`, or compute `template? :: boolean` at `open/2` and carry it in the handle (#1/#7 synergy). For the id: either a hand-rolled allocation-free byte-loop guard (~10× faster, keeps all three belt-and-suspenders sites) or an internal `ensure_valid/1` post-validation path keeping `cast` at the two trust boundaries.

### #22. Warm-restart open pays 3 sequential RTTs (two HEADs of the same object + acquire) where cold pays 1
**Severity:** Medium | **Category:** Performance | **Panels:** P3
**Likelihood:** Medium — every node-restart-with-persisted-dir reopen (rolling restarts = whole working set) | **Blast Radius:** per open (restart path)

**Problem:** Warm open runs `quarantined_fork?`'s HEAD sequentially *before* `acquire_lease` (`lib/fathom/shard.ex:292`, `:1768-1800`), then `post_lease_warm_check` (`:552-581`) HEADs the *same object* again after: HEAD → PUT → HEAD = 3 serialized RTTs transferring zero bytes, vs cold's overlapped ~1 RTT. The path that skips the body transfer is 3× slower in RTTs than the one that doesn't.

**Impact:** ~90 ms extra at 30 ms one-way per reopened shard; on a rolling restart that's the entire working set.

**Recommended Fix:** The post-lease check subsumes the pre-lease one: (a) drop the pre-lease HEAD — compute `warm?` from `File.exists?` + readable sidecar, letting the existing `post_lease_warm_check` quarantine+repull branch arbitrate rare divergence; or (b) overlap the HEAD with `acquire_lease` as a Task. Either gets warm restart to ~1–2 RTTs.

### #23. Every flush reads the shard file twice (MD5 pre-pass + body stream); the idle-drop path reads it three times
**Severity:** Medium | **Category:** Performance (I/O/CPU) | **Panels:** P3
**Likelihood:** Medium — every dirty flush; bites on big shards / mass drain | **Blast Radius:** per flush (file-size-proportional I/O)

**Problem:** `Content-MD5` must precede the body, so `stat_and_md5` (`s3.ex:556-572`) does a full chunked read to hash, then `File.stream!`s the file again as the PUT body (`:197`, `:222`). The drop path (`shard.ex:1556-1605`) adds `PRAGMA quick_check` — a full page-level read — for a third traversal.

**Impact:** A 100 MB tail shard costs 200–300 MB of reads to upload 100 MB; multiplied across draining coordinators on deploy or under memory pressure (page cache stops covering it).

**Recommended Fix:** Single-pass upload via trailing checksum: `x-amz-checksum-crc32c` as a trailer with `STREAMING-UNSIGNED-PAYLOAD-TRAILER` keeps torn-upload rejection without the digest up front (note the `x-amz-meta-fathom-md5` header precedes the body — switch download-verify metadata to CRC32C too, or accept the pre-pass only on the fenced path). At minimum skip `quick_check` when the following upload is the `snapshot_and_upload` fallback (VACUUM INTO already reads every page and fails on corruption).

### #24. `Directory.Recorder.record/1` builds a `DateTime` struct per checkout
**Severity:** Low | **Category:** Performance | **Panels:** P2, P4
**Likelihood:** High — every checkout, default-on | **Blast Radius:** per checkout

**Problem:** `record/1` (`lib/fathom/directory/recorder.ex:42-44`; `record_flush/1` at `:59` same) allocates `DateTime.utc_now()` — calendar math + a 9-field struct — per checkout, when the buffer only needs an ordering timestamp.

**Impact:** Small but pure waste on every checkout; also a larger ETS object than needed.

**Recommended Fix:** Buffer `System.system_time(:millisecond)`; convert once per batch at flush (`DateTime.from_unix!` in `Directory.record_batch/1`).

### #25. `req/0` rebuilds the full Req struct (config read, sigv4 opts, response step, `Process.whereis`) on every S3 call
**Severity:** Low | **Category:** Performance | **Panels:** P3
**Likelihood:** Medium — every S3 request; hot during warming bursts/failover/follower polls | **Blast Radius:** per S3 request

**Problem:** Every S3 request (`s3.ex:1610-1626`, `:1682-1684`) calls `config()`, builds `Req.new` with sigv4 options, appends the meter step, and does a `Process.whereis`. Signing is inherently per-request; the base struct is invariant per config.

**Impact:** Allocation/ETS-read overhead at high request rates (warming ~800/s, follower loop, mass failover — compounding #13/#15).

**Recommended Fix:** Cache the base `Req` struct in `:persistent_term` keyed by the config term; fall back to build-per-call in tests where `req_plug` varies.

### #26. Per-query watchdog process spawn when `:query_timeout_ms` is enabled
**Severity:** Low (off by default; real when the recommended co-tenancy knob is on) | **Category:** Performance | **Panels:** P1
**Likelihood:** Low (gated) — but every query once enabled | **Blast Radius:** per query (gated)

**Problem:** With the timeout gate on, `with_deadline` (`lib/fathom/shard/connection.ex:117-155`) spawns a fresh watchdog process per query, sends `{:done, ref}`, and sweeps with `receive after 0` — ~2–5 µs + ~2.7 KB process heap + scheduler churn each.

**Impact:** At 50k q/s with the gate on: ~50k spawns/s ≈ 100–250 ms/s CPU plus GC/scheduler pressure — a tax on exactly the co-tenancy deployments the feature targets.

**Recommended Fix:** One long-lived watchdog per connection/stream, armed/disarmed per query with `:erlang.start_timer`. (Alternative: `Sqlite3.set_progress_handler_steps` avoids the second process but changes interrupt semantics; the persistent watchdog is the low-risk path.)

### #29. `Rebalancer.Reporter` fully materializes the ShardLoad table twice per window and retains one copy in state
**Severity:** Low (gated `:load_reporter`, off by default; interval work) | **Category:** Performance | **Panels:** P4
**Likelihood:** Low — gated, 10 s interval | **Blast Radius:** node-wide GC spikes at high shard counts

**Problem:** Each window (`lib/fathom/rebalancer/reporter.ex:192-194`, `:64`, `:125`, `:131-152`, `:106-111`) builds two full materializations of every resident shard's counters (list of 5-key atom maps, then a keyed map), diffs+sorts all shards for top-50, and keeps `prev` alive in state.

**Impact:** Fine at 10k; at 100k+ (the density target) tens of MB transient + comparable retained per window, O(N log N) where top-N is needed — periodic GC spikes on a control-plane process.

**Recommended Fix:** Keep `prev` as `%{id => {q, rr, co}}` raw tuples; single-reduce the positive-rate rows; bounded top-N selection (or sort only rows above the Policy's q/s floor).

## Fix synergies

- **"Resolve config once at open/2, carry in the handle" family — #1, #7, #21, #24, #27:** #1's handle-struct change (conn → `%Connection{}` with a statement cache) is the natural carrier for #7's resolved gates, #21's precomputed `template?` boolean, and #27's one-pass classification flags; #2's prefix-slice work feeds the same classifier pass. Land as one or two adjacent commits behind the same bench gate.
- **Row-collection family — #7 (collect arg), #12, #16:** all touch `Connection.collect/4` — pass the cap down, raise the chunk, return the count — one small commit.
- **Filo iodata-encoding family — #4, #5, #8, #9 (resolving #10):** the hand-rolled iodata encoder (#5) is where the text/blob fallback (#8 interim) lives, produces the fragment that #4 builds inside the stream process, and #9's `encode_to_iodata!`/stdlib-`JSON` migration finishes the pipeline; together they collapse the ~4–5× memory multiplier (#10) to ~2×. #20's batched cursor chunks reuse the same encoder.
- **S3 lease/etag family — #6, #13(c), #25:** #6 caches the lock etag from PUT responses; #13(c) captures the post-touch etag from the CompleteMultipartUpload body; #25 caches the base Req struct — all "stop re-fetching what a prior response already told us."
- **Stream-open family — #18 + #21:** both trim the per-stream open critical path; land together and verify with a `hrana_rt_us`-style measurement.
- **Churn-plane pair — #11 then #31:** #11 (Registry partitions) first; only re-measure #31 afterward.

## Verified non-issues (recorded so future audits don't re-open them)

- **Periodic flush of a busy shard does NOT block queries** — fence/VACUUM/PUT run in a monitored Task; checkouts stay unblocked (P3).
- **Dirty-gating is complete** — `unflushed?` gates flush; clean shards take `drop_clean` with no upload; `valid_for_write?` is a lock-free ETS read, 0 RTT steady-state (P3).
- **S3 backend streams both directions** — whole-file `File.read` exists only in the dev-only Local backend, by design (P3).
- **Recorder/ShardLoad/ShardLatency/WriteCounter/Lru/WriteFence/Tombstones/Suspensions are lock-free as documented** — caller-side `:ets.insert`/`update_counter` on public write_concurrency tables; Recorder flushes as chunked-1000 `insert_all` upserts (P4).
- **Auth cost is per-stream, not per-request** — `Phoenix.Token.verify` once per HTTP stream open (baton = one HMAC-SHA256) and once per WS hello; revocation floor is an ETS read; only the stateless legacy /v1 path verifies per-request, inherently (P5).
- **NovelLimiter GenServer serialization is deliberate** — one call per *novel* open only; documented backpressure (P4).
