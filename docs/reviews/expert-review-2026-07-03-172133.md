### #1. Warm restart adopts the store's current etag, silently overwriting another node's flushed writes
**Severity:** Critical | **Category:** Data Loss | **Panels:** Distributed (C1)
**Likelihood:** Medium (ordinary crash + failover + node return; no clock skew or partition needed) | **Blast Radius:** Per-shard, unrecoverable loss of another node's durably-flushed acknowledged writes

**Problem:** A warm restart ("present local file is authoritative") fences its first flush with the store's **current** etag, not the etag its local copy derives from. `lib/fathom/shard.ex:156-160` (warm restart skips pull), `lib/fathom/shard.ex:319-324` (`await_pull(nil, ...)` adopts the store's current etag via HEAD), `lib/fathom/shard.ex:664-668` (`init_flushed_through` marks warm ⇒ dirty). Sequence: node A crashes with un-flushed writes (local file left on disk). A's heartbeat expires; node B steals (epoch+1), pulls the last flushed object, serves and flushes new acknowledged writes, then idles and *releases* (lock deleted). A restarts; the LB (consistent hash) maps the shard back to A; the coordinator sees `File.exists?(path)` ⇒ `warm? = true`, skips the pull, `acquire_lease` finds no lock and creates a fresh `{A, epoch: 1}`, and `await_pull(nil, ...)` does `Storage.object_etag/1` — a HEAD returning **B's** etag. A is seeded dirty, so within one flush interval it uploads its forked, stale copy with `If-Match: <B's etag>` — which succeeds. The etag fence (finding #15) is defeated because the expected etag is refreshed to "whatever is there now" instead of being tied to the local copy's provenance; the lock gives no protection because release deleted it and a fresh create restarts at epoch 1, erasing all history.

**Impact:** Permanent, silent loss of another node's acknowledged, durably-flushed writes — the exact clobber the whole lease/epoch/etag machinery exists to prevent — triggered by an ordinary crash + failover + node return.

**Recommended Fix:** Persist the base etag alongside the live shard file (a sidecar written on every pull and every successful flush, like the warm follower's `.db.etag`). On warm restart, compare the sidecar etag to `object_etag/1`: match ⇒ proceed as today; mismatch ⇒ the local copy has forked from the store — do not adopt the current etag; quarantine the local file (or refuse to open with an operator alarm) instead of silently flushing over the newer lineage.

### #2. `checkpoint/1` ignores busy/failure, then flush-and-drop uploads a stale image and deletes the WAL
**Severity:** High | **Category:** Data Loss | **Panels:** OTP (A2), Storage (B1)
**Likelihood:** Medium (fd pressure, brutally-killed streams — exactly the loaded conditions) | **Blast Radius:** Per-shard, silent unbounded loss of committed acknowledged writes

**Problem:** The idle/terminate flush uploads only the main `.db` file (`Storage.flush(state.id, state.path, state.etag)` at `lib/fathom/shard.ex:612`; every backend reads just `local_path` — `lib/fathom/shard/storage.ex:164`), relying on `checkpoint/1` (`lib/fathom/shard.ex:670-682`) to fold the WAL in first. But `checkpoint/1` ignores every failure mode: `Connection.open` failure falls into the `_ -> :ok` clause at line 677, and the result of `Connection.query(conn, "PRAGMA wal_checkpoint(TRUNCATE)", [])` at line 674 is discarded — `wal_checkpoint` does not error when it can't complete; it *returns a row* `(busy, log, checkpointed)` with `busy=1` when frames couldn't be folded. A TRUNCATE checkpoint can legitimately be blocked even with `conns == 0`: a Hrana stream killed brutally leaves its exqlite connection open until NIF-resource GC, and that zombie's read mark blocks truncation (the exact orphan class finding #8 worries about); `Connection.open` itself fails under fd exhaustion (the documented ~82k fd ceiling is exactly when many shards idle-flush). After the silently failed checkpoint, `flush_then_drop` (`shard.ex:603-647`) unconditionally uploads a `.db` image missing the un-checkpointed WAL frames, and on success `drop_local/1` (`shard.ex:684`) deletes the `-wal` file.

**Impact:** Silent, unbounded loss of committed, acknowledged transactions on idle/terminate flush-and-drop — precisely under load/failure conditions (fd pressure, killed streams) — with a "successful" flush in the logs. The stored "durable" object is a stale image and nothing ever retries.

**Recommended Fix:** Make `checkpoint/1` return `{:ok, ...} | {:error, _}`: check the open result and parse the `busy/log/checkpointed` row, treating `busy > 0` or `log != checkpointed` as failure. On failure, either (a) abort the drop — keep the local copy + lease (`:skip` branch semantics), log, and retry later, or (b) fall back to a `VACUUM INTO` snapshot (which captures WAL content regardless) and upload that instead. Never `drop_local` after an incomplete checkpoint. Regression test: hold a second open read connection (un-checkpointable WAL) through idle flush/terminate and assert the WAL-resident rows survive (local copy retained or flushed object contains them).

### #3. Steal never invalidates the data object's etag, so a zombie's in-flight flush beats the new owner
**Severity:** High | **Category:** Data Loss / Data Correctness | **Panels:** Distributed (C3)
**Likelihood:** Medium (any steal racing an in-flight flush; VM pause / S3 slowness widens the window) | **Blast Radius:** Per-shard: stale reads for the new owner's clients, then the new owner discards its own accepted writes

**Problem:** The steal protocol (`lib/fathom/shard/storage/s3.ex:241-254`) never touches the **data object** at acquisition, so an old owner's in-flight fenced flush can land *after* the new owner's pull. Owner A passes `Fence.check` (`lib/fathom/shard/fence.ex:50-57`, checked at `lib/fathom/shard.ex:477-504` *before* a snapshot+upload of unbounded duration), then stalls (whole-VM pause / S3 slowness) inside `snapshot_and_upload`. A's heartbeat expires past `steal_margin`; B steals and pulls the object (etag E, pre-A's-final-PUT bytes). A's PUT with `If-Match: E` then **succeeds** (B hasn't written yet — the steal left the object untouched). B now serves a copy missing A's final acknowledged writes, and B's own first flush gets a 412 → `{:error, :superseded}` → B self-fences (`shard.ex:492-497`) and **drops its local copy including B's acknowledged writes** (`terminate` with `lease_lost: true`, `shard.ex:524-532`). The If-Match fence prevents torn objects but arbitrates in favor of the *zombie*. The overlapped speculative pull (`shard.ex:159-160`) widens the same window at cold-open (`shard.ex:144-190` has no post-lease etag revalidation).

**Impact:** After any steal that races an in-flight flush: clients of the new owner read stale data (acknowledged writes invisible), then the new owner discards *its* accepted writes on the first flush. Both sides lose.

**Recommended Fix:** On acquiring by steal (and on any acquire where a prior lock existed), immediately "touch" the data object — a conditional server-side self-copy (`x-amz-copy-source` onto itself with `If-Match`) that changes the etag — *before* pulling/serving. The zombie's late `If-Match` PUT then deterministically 412s and the zombie correctly self-fences. Additionally, after the lease confirms at cold-open, revalidate the speculatively-pulled etag against `object_etag/1` and re-pull on mismatch.

### #4. Shutdown ordering: heartbeat object is deleted before coordinators flush, making shards stealable mid-deploy
**Severity:** High | **Category:** Data Loss | **Panels:** Storage (B2) — related to but distinct from #7 (C4)
**Likelihood:** High (every rolling deploy with concurrent LB-rerouted traffic) | **Blast Radius:** Every open dirty shard on the stopping node

**Problem:** `data_plane_children/0` (`lib/fathom/application.ex:98-120`) lists `{DynamicSupervisor, ...}` then `++ heartbeat_children()` (line 119); supervisors stop children in reverse start order, so on a clean shutdown `Fathom.Shard.Heartbeat` terminates first and deletes the node's heartbeat object (`lib/fathom/shard/heartbeat.ex:118-121`), and only then do the coordinators run their terminate-flushes. In heartbeat mode coordinators never renew per-shard locks, so `lock.expires_at_ms` is frozen at acquire time; the moment the heartbeat object is gone, `owner_live?` hits the `:not_found` fallback (`lib/fathom/shard/storage/s3.ex:276-290`, `lib/fathom/shard/storage/local.ex:176-188`) and any shard open longer than TTL+margin (~35 s) is judged dead and stealable. A survivor node receiving LB-rerouted traffic (exactly what a deploy produces) steals the lock; the dying coordinator's flush fence (`flush_then_drop` → legacy renew, heartbeat process down) returns `:superseded` and it **drops its local copy without flushing** (`lib/fathom/shard.ex:632-637`) — while the stealer serves the older stored image.

**Impact:** Acknowledged-write loss (up to a full flush interval per shard) during a routine rolling deploy with concurrent failover traffic — the exact scenario the trap_exit/terminate flush machinery (`shard.ex:124-131`) was built to protect.

**Recommended Fix:** Start the Heartbeat *before* the shard Registry/DynamicSupervisor so it stops (and clears its object) only after every coordinator has flushed and released. Alternatively split "stop renewing" from "delete the heartbeat object": clear the object in a final step after the data plane is fully down (e.g. from `Application.prep_stop`). See also #7 (C4) for the crash-path variant of the same fallback.

### #5. Coordinator shutdown budget is the 5000 ms default, brutally killing the terminate flush on deploy
**Severity:** High | **Category:** Data Loss | **Panels:** OTP (A1), Storage (B3)
**Likelihood:** High at scale (every rolling deploy; all coordinators flush concurrently through one Finch pool) | **Blast Radius:** Every shard whose final flush exceeds 5 s; worst on ephemeral-disk replacement (local copy gone too)

**Problem:** The coordinator traps exits specifically so a supervisor `:shutdown` (SIGTERM / rolling deploy) runs `terminate/2`'s final checkpoint + flush + lease release ("Without this ... up to a full flush interval of acknowledged writes is lost on a *clean* shutdown", `lib/fathom/shard.ex:122-141`) — but the child spec is `use GenServer, restart: :temporary` with no `shutdown:` option (`lib/fathom/shard.ex:53`; started via `DynamicSupervisor.start_child` at `lib/fathom/shards.ex:256`), so the worker default of **5000 ms** applies. `terminate/2` → `flush_then_drop/1` (`shard.ex:534-542`, `610-615`) does a fence check (1-2 S3 round-trips), a `wal_checkpoint(TRUNCATE)` (up to the 5 s `busy_timeout`), a `File.read` of the whole shard, a full-body S3 PUT, and a lease release (GET+DELETE). On a rolling deploy the DynamicSupervisor shuts down *all* coordinators concurrently, contending for the 200-conn Finch pool — a multi-MB shard at tens of ms RTT (AGENTS.md puts one round-trip alone at ~60-215 ms cross-region), queued behind hundreds of siblings, easily exceeds 5 s. The supervisor then sends `:kill`, aborting the flush mid-PUT: no upload, no lease release.

**Impact:** The clean-shutdown durability guarantee the code documents is silently defeated at scale: up to a full `:shard_flush_interval_ms` (default 30 s) of acknowledged writes lost per shard on a *planned* deploy, plus delayed failover (lease never released, steal-margin wait). The conditional PUT means no torn object, but the writes are gone — and gone permanently if the deploy replaces the machine (ephemeral disk).

**Recommended Fix:** Give `Fathom.Shard` an explicit shutdown budget sized to the flush path — `use GenServer, restart: :temporary, shutdown: 30_000` (or config-driven, aligned with `@pull_timeout`-class budgets), or `:infinity` bounded by an internal terminate deadline so a hung S3 call can't wedge the deploy. Consider draining terminate flushes with bounded concurrency on shutdown rather than N simultaneous PUTs against one pool.

### #6. Owner identity has no incarnation nonce; same-name reclaim keeps the epoch, so two incarnations pass every fence
**Severity:** High | **Category:** Data Loss / Data Correctness | **Panels:** Distributed (C2)
**Likelihood:** Medium (replaced K8s pod with a lingering S3-reachable predecessor; blue/green overlap) | **Blast Radius:** All shards shared by the two incarnations — dual live coordinators, lost updates

**Problem:** Owner identity is the bare node name (`owner = to_string(node())`, `lib/fathom/shard/heartbeat.ex:44`) with no incarnation/boot nonce. Two concurrent incarnations with the same name (a replaced Kubernetes pod whose predecessor lingers partitioned-but-S3-reachable; blue/green overlap; epmd only prevents duplicates per host) both unconditionally renew the *same* `heartbeat/<owner>` object (`renew_heartbeat` is an unconditional PUT, `lib/fathom/shard/storage/s3.ex:369-377`), so each considers the other's shards "live under my own name." Worse, the reclaim path in `acquire_existing` (`{:ok, %{owner: ^owner, epoch: epoch}, etag} -> put_lock(..., epoch: epoch, ...)`, `s3.ex:234-237`) deliberately does **not** bump the epoch, so the new incarnation holds a lease **byte-identical** to the old incarnation's, and `check_lease/2` (equality on owner+epoch, `s3.ex:354-361`) passes for both zombies simultaneously. The epoch is only a fencing token if every change of writer changes it.

**Impact:** Two live coordinators for one shard, both passing every lease fence; the data-etag fence then arbitrates flushes by luck — whichever flushes second self-fences and discards its acknowledged writes, and interleaved flush/pull orderings produce lost updates.

**Recommended Fix:** Make `owner` incarnation-unique: `node()` + a per-boot nonce (e.g. a UUID generated at application start). A lock found under the same *node name* but a different incarnation must go through the steal path (heartbeat-liveness check, then epoch+1), never silent same-epoch reclaim. Include the incarnation in the heartbeat object so a stale incarnation's renewals can be detected.

### #7. Heartbeat `terminate/2` clears the heartbeat object on crash, opening a fleet-wide steal window on a live node
**Severity:** High | **Category:** Reliability / Data Loss | **Panels:** Distributed (C4) — related to but distinct from #4 (B2)
**Likelihood:** Medium (any Heartbeat crash/restart; also S3 lifecycle rules or operator deletion of the object) | **Blast Radius:** Every long-lived shard on the node becomes instantly stealable while still being served

**Problem:** `Heartbeat.terminate/2` (`lib/fathom/shard/heartbeat.ex:117-123`) deletes the heartbeat object for **any** termination reason, including a crash the supervisor is about to restart (Heartbeat is a permanently-restarted child, `lib/fathom/application.ex:178-182`). In heartbeat mode, shard locks are never renewed (`shard.ex:232` — `schedule_renew` only when `acquire_gen == nil`), so a lock's `expires_at_ms` is frozen at acquire-time + 30 s for the shard's entire (possibly hours-long) life. During the crash-restart gap the heartbeat object is *absent*, so a contender's `owner_live?` hits the `:not_found` fallback (`lib/fathom/shard/storage/s3.ex:287`, `lib/fathom/shard/storage/local.ex:185`), evaluates the long-stale lock TTL, and concludes `:dead` — every long-lived shard on a perfectly healthy node is instantly stealable, with the node still serving them.

**Impact:** A routine Heartbeat process crash (or transient supervisor restart) opens a fleet-wide steal window on a live node → split-brain per #3's (C3) mechanics. The same fallback fires if the heartbeat object is ever removed by an S3 lifecycle rule or operator error. This is the *crash-path* sibling of #4 (B2), which covers the clean-shutdown ordering; the fixes are independent.

**Recommended Fix:** In `terminate/2`, clear the heartbeat only for planned shutdowns (`:normal`, `:shutdown`, `{:shutdown, _}`); on a crash, leave the object in place — the restarted process re-renews it within `renew_ms`. Consider also making the `:not_found` fallback require the *lock* to be expired by well more than one heartbeat interval.

### #8. Heartbeat lapse generation resets to 0 on restart, forging "no lapse since acquire" for pre-restart coordinators
**Severity:** High | **Category:** Data Correctness | **Panels:** Distributed (C5)
**Likelihood:** Medium (any Heartbeat restart, especially crash-loops after failed renewals — exactly the lapse-prone window) | **Blast Radius:** All coordinators acquired at generation 0 of the previous incarnation flush without revalidating ownership

**Problem:** The lapse generation is process-local state that resets to `0` when the Heartbeat GenServer restarts (`generation: 0, lapsed: false` in `init`, `lib/fathom/shard/heartbeat.ex:85-86`). A coordinator that acquired its shard at generation 0 of the *previous* incarnation compares `state.generation != acquire_gen` → `0 != 0` is false → `:ok` (`valid_for_write?`, `heartbeat.ex:102-115`), so its flushes skip revalidation — even though a Heartbeat restart gap (especially a crash-loop with supervisor backoff, or a crash following failed renewals) is precisely a window in which the heartbeat may have lapsed and a steal occurred. The whole point of the generation is "no lapse since acquire ⇒ no steal was possible" (finding #5's invariant), and a restart silently forges that proof. Combined with #7 (C4) — the restart itself deletes the heartbeat, *creating* the steal window — the coordinator then flushes with only the etag fence between it and a clobber, which #3 (C3) shows is race-prone.

**Impact:** After any Heartbeat process restart, coordinators acquired at gen 0 treat a possible steal window as "no lapse ever happened" and write without re-checking ownership.

**Recommended Fix:** Persist the generation across process restarts (e.g. `:persistent_term` / an ETS table owned by the supervisor) and increment it once in `init` — treating every boot of the heartbeat process as a lapse episode — so all pre-restart `acquire_gen` values mismatch and force one cheap `check_lease` revalidation per shard.

### #9. No boot guard requiring auth when `:template_shard_id` is set in prod — anonymous fleet-wide DDL poisoning
**Severity:** High | **Category:** Security / Data Correctness | **Panels:** Security (D1)
**Likelihood:** Low-Medium (requires the documented-forbidden config: template set in prod with auth `:disabled`; nothing enforces the prohibition) | **Blast Radius:** Fleet-wide — arbitrary DDL/DML replayed onto every tenant's database

**Problem:** AGENTS.md states the invariant "never set a prod `:template_shard_id` without auth on that shard … it's a poisoning vector if reachable anonymously," but only `check_template_default!/0` (default ≠ template, finding #17) is enforced at boot (`lib/fathom/application.ex:47-58`, `config/runtime.exs:79-93`). There is **no** guard requiring `:hrana_auth == :required` (or any access control) when `:template_shard_id` is set in prod. Template capture fires purely on `template?(shard_id)` after any successful statement (`lib/fathom/shard_executor.ex:80-83,157-191`), and the template shard is reachable via its ordinary Host subdomain. With auth `:disabled` an anonymous client that reaches the node can send arbitrary DDL inside a transaction that bumps the `django_migrations` row count; `Capture.commit` then records it as a new fleet version (`lib/fathom/migrator/capture.ex:84-110`), which `Migrator.Copy.migrate/4` later **replays verbatim onto every shard in the fleet**.

**Impact:** Unlike an ordinary shard compromise (one tenant), a poisoned template version is replayed fleet-wide — arbitrary DDL/DML executed against every tenant's database. A fleet-scale integrity/data-destruction vector guarded only by network isolation, with a documented-but-unenforced auth requirement. Ranked above the remaining data-loss findings because the blast radius is every tenant at once, though it requires a misconfiguration to be reachable.

**Recommended Fix:** Add a boot guard in `Fathom.Application` (alongside `check_template_default!`) that refuses to start in prod when `:template_shard_id` is set and `:hrana_auth != :required`. Optionally also require a distinct, non-guessable template shard id and log every captured version's source.

### #10. Revert retry after a failed cutover clobbers the vN backup with vN-1 bytes
**Severity:** High | **Category:** Data Loss | **Panels:** Migration (E1)
**Likelihood:** Medium (any Postgres blip between restore and cutover, then Oban's automatic retry) | **Blast Radius:** Per-shard, unrecoverable — the only copy of post-cutover vN writes is destroyed

**Problem:** `revert/4` (`lib/fathom/migrator/shard_migration.ex:62-82` — retain at :75, restore at :76, cutover at :77) runs `Storage.retain(shard_id, current)` → `Storage.restore(shard_id, to_version)` → `Directory.cutover(...)`, where `current` comes from the *directory* (`current_state/1`), not the live file. If `restore` succeeds but `cutover` fails (Postgres blip), `RevertJob` returns `{:error, reason}` (`lib/fathom/migrator/revert_job.ex:52-55`) and Oban retries. On attempt 2 the directory still says `current = vN`, the write-age guard passes identically, and `retain(shard_id, vN)` copies the live object — which now holds **vN-1 bytes** from attempt 1's restore — over `<shard>@vN`, destroying the only copy of the post-cutover vN writes. `retain` is an unconditional overwrite in both backends (`lib/fathom/shard/storage/local.ex:111-119`, `lib/fathom/shard/storage/s3.ex:179-186`).

**Impact:** The recoverability guarantee of the revert backup is silently voided; the "discarded but recoverable at `<shard>@<from>`" log line becomes false, and `schedule_retirement(shard_id, from)` later retires the clobbered object. Tenant writes destroyed unrecoverably.

**Recommended Fix:** Give revert a crash-forward: pull the live file (or its `user_version`) under the lease first; if `user_version == to_version` skip retain/restore and just finish the cutover; only `retain(current)` when the live file's `user_version` actually equals `current`. Alternatively make the revert's retain a no-clobber conditional write (`If-None-Match: *` / `O_EXCL`) keyed to the operation token. Ship with a regression test that fails cutover once and retries.

### #11. `Directory.Recorder.do_flush` drains ETS before writing; a Postgres failure permanently drops the touches the revert guard depends on
**Severity:** High | **Category:** Data Loss (guard-input) / Reliability | **Panels:** Migration (E3) — related: #30 (A5, Recorder terminate never runs)
**Likelihood:** Medium (any Postgres outage — exactly when operators are reverting) | **Blast Radius:** Fleet-wide guard blindness: unforced reverts pass despite real post-cutover writes and discard them

**Problem:** `do_flush` (`lib/fathom/directory/recorder.ex:96-116`) destructively drains the ETS buffer (`:ets.take`) *before* calling `Directory.record_batch/1`; when the batch raises (Postgres outage) the `rescue` logs and returns 0 — the drained rows are gone, never re-buffered (and `record_batch`'s chunked reduce, `lib/fathom/directory.ex:78-118`, means a mid-chunk raise loses all later chunks too). These aren't just metrics: `last_active_at` is the *sole input* to the revert write-age force-guard (`last_active_at > cutover_at`, consumed at `lib/fathom/migrator/shard_migration.ex:93-108`). A checkout whose touch was dropped in a failed flush (or is still sitting in another node's ≤1 s buffer — nothing flushes the Recorder before `current_state/1` reads the directory) is invisible to the guard.

**Impact:** During or shortly after a Postgres outage — exactly when operators are reverting things — an unforced revert passes the guard despite real post-cutover writes and discards them (compounded by #10/E1: the backup may also be clobbered on retry). Warm-follower targeting and laggard ordering also silently degrade.

**Recommended Fix:** On flush failure, merge the drained rows back into ETS keeping the max timestamp per shard; emit a telemetry counter for dropped batches. In `ShardMigration.revert`, call `Recorder.flush()` before reading `current_state` (node-local best-effort) and document the cross-node staleness window in the guard's error details.

### #12. Fleet HEAD never drops after a revert, so ReconcileJob/lazy-migrate re-apply the reverted-from version
**Severity:** High | **Category:** Data Correctness | **Panels:** Migration (E2)
**Likelihood:** High (deterministic — every revert without manual SQL surgery) | **Blast Radius:** Fleet-wide: revert is effectively unusable; the bad version returns within the hour (or seconds under lazy migrate)

**Problem:** `revert/3` flips shards back to `to_version` and marks them `active`, but HEAD never drops: `head/0` (`lib/fathom/migrator.ex:50`) is `max(version)` over `Release` rows, and `HeadCache`'s own moduledoc (`lib/fathom/migrator/head_cache.ex:22-24`) states "a revert flips shard pointers but leaves the `Release` row, so `max(version)` never drops." `laggard_query` (`lib/fathom/directory.ex:245-247`) is simply `schema_version < head AND status == "active"`, so every reverted shard is immediately a laggard. The hourly `ReconcileJob` (`lib/fathom/migrator/reconcile_job.ex:15-31` → `Migrator.rollout()`, `migrator.ex:71-87`) re-enqueues `ShardMigrationJob(target: head)` for all of them — and with `:lazy_migrate` on, `Fathom.Shards.checkout` (`lib/fathom/shards.ex:96-108`) re-runs the migration to the reverted-from version **synchronously on the next checkout**. There is no yank/pause/pin API on `Fathom.Migrator`.

**Impact:** An operator reverting a bad vN watches the fleet re-migrate to that same bad vN within the hour — or within seconds under lazy migrate. Revert is unusable without manually deleting the `shard_migrations` row via SQL.

**Recommended Fix:** Add a release yank: `Migrator.yank(version)` marks the `Release` row yanked and `head/0` excludes yanked versions; have `Migrator.revert/3` yank `from_version` by default. Regression test: revert a fleet, run `ReconcileJob.perform`, assert zero `ShardMigrationJob`s enqueued.

### #13. Host-subdomain routing has no serving-zone anchor: any first label of any ≥2-label Host selects a shard
**Severity:** Medium | **Category:** Shard Isolation / Security | **Panels:** Security (D2)
**Likelihood:** Low-Medium (needs a foreign `Host` to reach a node — misrouted/misconfigured LB, SSRF from a co-tenant app, or direct-to-node access — with auth `:disabled`) | **Blast Radius:** Cross-tenant shard selection — release-blocker class per AGENTS.md

**Problem:** `shard_from_host/1` (`lib/fathom/shard_executor.ex:229-232,257-267,274`) treats the **first label of any host with ≥2 labels** as the shard id, with no check that the remaining labels match fathom's serving zone — no configured base-domain/allowlist anywhere. Finding #4 correctly gated the `?db=`/`x-fathom-shard` override off in prod because it is an unauthenticated tenant-selection primitive — but the subdomain path is the *same* kind of primitive (a client-controlled `Host` header) and, unlike #4, is neither gated nor anchored, even in prod. A request that reaches a node with a spoofed/foreign `Host` selects an arbitrary shard by first label: `Host: victimshard.anything.com` → shard `victimshard`.

**Impact:** When auth is `:disabled` (the documented default outside prod), Host-subdomain routing is the *sole* isolation control, and it trusts an unvalidated header with no domain anchoring. Any path that lets a non-zone `Host` reach a node yields cross-tenant shard selection. Ranked here (below the fence/durability chain) because prod defaults to `HRANA_AUTH=required`, which blocks the leak with per-shard tokens — but isolation is fathom's top-weighted category, so this outranks all remaining data-loss findings.

**Recommended Fix:** Add a configured serving-zone suffix (derive from `PHX_HOST` or a new `:shard_base_domain`). ### #14. WriteCounter restart resets ETS to empty, instantly classifying every dirty shard on the node as clean
**Severity:** Medium | **Category:** Data Loss | **Panels:** OTP (A4)
**Likelihood:** Low (a near-inert process, but one errant `GenServer.call` to it crashes it — no `handle_call` exists) | **Blast Radius:** Node-wide: all in-flight unflushed writes silently dropped via `drop_clean`

**Problem:** The WriteCounter GenServer owns the named ETS table with no `:heir` (`lib/fathom/shard/write_counter.ex:84-99`). If it dies (an errant `GenServer.call(Fathom.Shard.WriteCounter, :anything)` crashes it; a code-upgrade/kill), the supervisor restarts it with a **fresh empty table**, so `count/1` returns 0 for every shard — while every open coordinator retains its old `flushed_through` watermark (`lib/fathom/shard.ex:225`). `unflushed?/1` (`shard.ex:657`) is `count(id) > flushed_through` → `0 > 500` → false: every dirty shard on the node instantly classifies **clean**. The idle path then takes `drop_clean/1` (`shard.ex:592-601`), deleting the local file *without uploading*, and the durability flush skips (`shard.ex:469`).

**Impact:** A single crash of a near-inert process converts all in-flight unflushed writes on the node into silent data loss — the exact invariant (findings #1/#27) the module exists to protect, defeated by its own restart semantics.

**Recommended Fix:** Treat counter regression as dirty: `unflushed?` returns true when `count < flushed_through` (unknown state ⇒ flush; an extra upload is the safe direction, mirroring the `wrote?/2` philosophy in `shard_executor.ex:108-112`). Optionally give the table an `:heir` (a supervisor-stable process) so counts survive an owner restart.

### #15. `PRAGMA user_version =` and other header-writing pragmas classified as reads, silently lost on idle drop
**Severity:** Medium | **Category:** Data Loss | **Panels:** Storage (B6)
**Likelihood:** Medium (external migration tooling stamping `user_version` through the data path is plausible client behavior) | **Blast Radius:** Per-shard: acknowledged durable header writes vanish; version skew after flush-and-drop

**Problem:** `wrote?/2` (`lib/fathom/shard_executor.ex:113-129`) classifies every `PRAGMA` as a control statement (`@control_prefixes` includes `pragma` at line 122). But some pragmas are **durable file mutations**: `PRAGMA user_version = N` and `PRAGMA application_id = N` write the database header and report `num_changes == 0`, `cols == []`. A client issuing them over Hrana never bumps the `WriteCounter`, so the shard stays "clean"; on idle, `drop_clean` (`lib/fathom/shard.ex:589-601`) deletes the local copy without a flush and the change is silently lost. This is pointed: `user_version` is fathom's own O(1) schema-version gate (the stamp lives in three places per AGENTS.md), so external migration tooling stamping it through the data path is exactly the write that vanishes.

**Impact:** Durable header writes (version stamps) silently dropped on idle; a shard can appear un-migrated / version-skewed after a flush-and-drop cycle even though the client's stamp was acknowledged.

**Recommended Fix:** Classify pragma *assignments* as writes: treat `PRAGMA <name> = <value>` (or at minimum a whitelist: `user_version`, `application_id`, `schema_version`) as dirtying. Regression test: set `user_version` via the executor, idle-drop, re-open, assert the stamp survived.

### #16. Nothing verifies the store actually enforces conditional writes — a lax store silently disables the entire fence
**Severity:** Medium | **Category:** Data Correctness / Reliability | **Panels:** Distributed (C7)

### #17. `with_atomic_temp` never fsyncs — power loss can make a torn local file the durable truth
**Severity:** Medium | **Category:** Data Loss (crash-consistency) | **Panels:** Storage (B4)
**Likelihood:** Low (power loss / hard reboot) | **Blast Radius:** Per-shard: corruption can be flushed over the good stored object with a valid `If-Match`

**Problem:** `with_atomic_temp` (`lib/fathom/shard/storage.ex:317-337` — `atomic_write/2`, `atomic_copy/2`) does `File.write`/`File.cp` then `File.rename` with **no `:file.sync` on the temp and no fsync of the directory**. Rename-without-data-fsync is only atomic against process crash, not power loss: after a power cut the name can exist with zero-length/partial content (guaranteed on XFS; heuristic-dependent on ext4). Two consequences: (a) the `Local` backend's "durable" flushed object (`local.ex:36-39,60-63`) can be torn/empty after power loss; (b) worse, a *pulled* live-dir file promoted via the same path can be torn, and on reboot `warm? = File.exists?(path)` (`lib/fathom/shard.ex:159`) adopts it as **authoritative**, `init_flushed_through` (`shard.ex:664-668`) bumps it **dirty**, and the next fenced flush uploads the corrupt bytes over the good stored object with a valid `If-Match` — the corruption becomes the durable truth.

**Impact:** Power loss can silently destroy a shard's stored object via the local-file-authoritative rule; the Local backend's durability guarantee is weaker than its atomic-write comments (#24/#28) claim.

**Recommended Fix:** In `with_atomic_temp`: open the temp, write, `:file.sync/1`, close, rename, then fsync the parent directory. At minimum for (a) `Local.flush` destinations and (b) live-data-dir promotions (`promote_pull`); the warm-follower cache can skip it.

### #18. `promote_pull` doesn't remove stale `-wal`/`-shm` sidecars — SQLite replays a different-generation WAL into a fresh pull
**Severity:** Medium | **Category:** Data Correctness (corruption) | **Panels:** Storage (B5)
**Likelihood:** Low (narrow crash window between `drop_local`'s two `File.rm`s) | **Blast Radius:** Per-shard silent corruption, then flushed back as the durable object

**Problem:** `promote_pull` (`lib/fathom/shard.ex:348-355`) renames the pulled temp onto `path` without first removing any pre-existing `path-wal`/`path-shm`, and `drop_local` (`shard.ex:684`) deletes the main db **first**, then the WAL. A crash between those two `File.rm`s (or any path removing the db but not its WAL — e.g. the `lease_lost` terminate at `shard.ex:524-532` interrupted mid-`drop_local`) leaves an orphan `-wal`. The next cold open sees `warm? = false`, pulls a fresh object, renames it into place — and SQLite, on first open, runs WAL recovery against the **stale, different-generation** `-wal` sitting next to it, replaying old frames into the freshly pulled database. Pairing a db with a WAL from a different database state is a classic silent-corruption vector (resurrected deletes, torn pages, malformed db).

**Impact:** Narrow crash window, corruption-grade outcome: a shard's local working copy silently corrupted after recovery, then flushed back as the durable object.

**Recommended Fix:** In `promote_pull`, `File.rm(path <> "-wal")` and `File.rm(path <> "-shm")` before renaming the temp into place (a pulled object is always a self-contained checkpointed image, so any sidecars are by definition stale). Optionally invert `drop_local`'s order where the WAL is known checkpointed.

### #19. Template capture is fire-and-forget: one Postgres blip permanently forks template schema from fleet schema

### #20. Every S3 transfer buffers the whole shard in BEAM memory — correlated flush bursts can OOM the node mid-deploy
**Severity:** Medium | **Category:** Performance / Reliability (cascading) | **Panels:** Storage (B7)
**Likelihood:** Medium at scale (shutdown = N concurrent flushes; warming/failover bursts) | **Blast Radius:** Node OOM during the durability-critical path — the crash then loses the data being persisted

**Problem:** Every transfer materializes the entire shard object in BEAM memory: `flush` does `File.read(local_path)` and PUTs one binary (`lib/fathom/shard/storage/s3.ex:109-134`); `pull` (`s3.ex:86-106`) and `pull_if_changed` (`s3.ex:151-174`) receive the whole body before `atomic_write`; `Local` has the same pattern (`local.ex:16-33,42-68`). No streaming in either direction, no size guard. The moments this bites are the correlated ones: node shutdown (N coordinators flushing at once — N × shard-size resident), warm-follower refresh/startup warming (up to `warm_cache_max`/pool-size concurrent pulls), the failover burst.

**Impact:** Memory spikes proportional to (concurrent transfers × shard size); worst-case OOM during shutdown/failover — turning a durability flush into the crash that loses the data it was persisting. Also silently caps practical shard size below S3's 5 GB single-PUT limit.

**Recommended Fix:** Stream both directions: `Req` supports `body: File.stream!(path, chunk)` for PUT and `into:` for GET writing straight to the temp file. Bound concurrent whole-file transfers (semaphore) as a stopgap, and reject/multipart objects above the single-PUT ceiling.

### #21. Heartbeat lapse detection uses the wall clock — a backward clock step converts "lapse → revalidate" into "still valid → write"
**Severity:** Medium | **Category:** Data Correctness | **Panels:** Distributed (C6)
**Likelihood:** Low (NTP step / VM live-migration coinciding with a renewal outage) | **Blast Radius:** Per-node: flushes skip revalidation against a real concurrent stealer

**Problem:** The heartbeat's *local* self-assessment — `valid_for_write?` (`lib/fathom/shard/heartbeat.ex:103-114`, uses `Storage.now_ms()` = `System.system_time`, `lib/fathom/shard/storage.ex:288`) and the lapse edge-detect `now > state.expires_at_ms` (`heartbeat.ex:126-132`) — uses the wall clock, but both are purely local elapsed-time questions. A backward clock step after a renewal inflates perceived remaining validity and can keep `now > expires_at_ms` false past real expiry — so a genuine lapse (during which a peer with a correct clock legitimately stole shards) is never edge-detected: the generation doesn't bump, `valid_for_write?` keeps returning `:ok`, flushes skip revalidation. **Impact:** A clock step coinciding with a renewal outage leaves only the etag fence (#3/C3's race) against a concurrent stealer.

**Recommended Fix:** Record a monotonic deadline at each successful renew (`System.monotonic_time(:millisecond) + ttl_ms`) and drive `valid_for_write?`'s margin check and `do_renew`'s lapse edge-detection off the monotonic clock; keep the wall-clock `expires_at_ms` only for the object other nodes read.

### #31. Hrana tokens: global salt + shared `secret_key_base` + `max_age :infinity` means no per-shard revocation
**Severity:** Medium | **Category:** Security | **Panels:** Security (D4)
**Likelihood:** Medium (any single token leak) | **Blast Radius:** Revoking one tenant's token requires a fleet-wide credential reset that also breaks all web sessions

**Problem:** A Hrana credential is `Phoenix.Token.sign(secret_key_base, @salt, shard_id)` with a single global salt (`lib/fathom/hrana_auth.ex:31`) and a payload of only the shard id — and `max_age` defaults to `:infinity` (`hrana_auth.ex:128`). The signing key is the endpoint's `secret_key_base` (`:122-126`), the **same** secret used for cookie/session signing on the web/dashboard endpoint. The docstring's revocation story is "revoke by rotating `SECRET_KEY_BASE`" (`:25-27`) — but with no per-shard or per-token component, that is the *only* revocation mechanism, and it invalidates **every** shard's token fleet-wide and simultaneously breaks all web sessions/CSRF tokens.

**Impact:** Effectively no per-shard revocation; in practice a compromised long-lived token stays valid.

**Recommended Fix:** Incorporate a per-shard rotatable component into the signing material (e.g. a per-shard secret/version from the directory folded into the salt or verified as a claim), enabling single-shard revocation. At minimum, sign with a dedicated secret separate from the web `secret_key_base`, and document that expiry (`:hrana_token_max_age`) is the only bounded-exposure control.

### #32. Host-subdomain routing — the primary production tenant-selection path — has one happy-path test and no adversarial cases
**Severity:** Medium | **Category:** Test Gap (Shard Isolation) | **Panels:** Security (D3)
**Likelihood:** N/A (latent) | **Blast Radius:** A future `shard_from_host` change could regress cross-tenant selection with no failing test

**Problem:** AGENTS.md's shard-isolation gate requires any routing change to ship a test proving shard A never resolves to shard B. The suite pins the `?db=`/override path and case-normalization (`test/fathom/shard_executor_test.exs:99-168`) and path-traversal ids (`test/fathom/cluster/isolation_test.exs:64-75`) — but there is **no** test for Host-subdomain edge cases: nested/multi-label subdomains (`victim.attacker.fathom.example` → `victim`), hosts outside the serving zone, trailing-dot FQDNs, `Host` with an embedded port, or IPv6 literal hosts. `shard_from_host` has only the single happy 3-label assertion (`shard_executor_test.exs:101`).

**Impact:** The routing surface most exposed to attacker-controlled input is the least tested.

**Recommended Fix:** Add isolation tests asserting that a nested/foreign `Host` resolves to `nil` (or the intended label) and cannot select another tenant's shard, plus trailing-dot, port, and IPv6-literal cases, wired to the same `shard_from_conn` boundary the production listener uses. Natural companion to fixing #13 (D2) and #35 (D6).

### #33. Checkout during drain surfaces as a 500 with no retry semantics instead of a 503
**Severity:** Low | **Category:** Reliability / Test Gap | **Panels:** OTP (A10)
**Likelihood:** High during every blue/green migration window | **Blast Radius:** Client-visible errors during every planned drain

**Problem:** A checkout hitting a draining coordinator returns `{:error, :draining}` (`lib/fathom/shard.ex:372-374`). `retry_checkout?/1` (`lib/fathom/shards.ex:75`) retries only `[:unavailable, :normal]`, so `:draining` surfaces immediately, and `ShardExecutor.open_error/1` (`lib/fathom/shard_executor.ex:214-215`) has no clause for it — it falls to the generic message with **no status**, i.e. the transport-default 500, unlike the deliberate 503/429 mappings for `:node_at_capacity`/`:novel_shard_rate_limited`. A drain is a routine short-lived state ("the caller should retry later", `shards.ex:137-146`), and no test pins the checkout-during-drain HTTP semantics.

**Impact:** During every migration window, clients of the draining shard get 500s instead of a retryable 503; SDKs treat 500 as failure, not back-off — a planned drain becomes visible errors.

**Recommended Fix:** Add `defp open_error(:draining), do: %Error{message: "shard draining", code: "FILO_DRAINING", status: 503}` and a test asserting the status; optionally a single bounded retry for `:draining` in `do_checkout/2` covering the drain-then-stop race.

### #34. `broadcast_lapse` has no subscriber — the documented proactive revalidation doesn't exist
**Severity:** Low | **Category:** Architecture / Documentation | **Panels:** Distributed (C8)
**Likelihood:** N/A (behavior gap) | **Blast Radius:** Longer acknowledged-write-discard windows after a lapse than the design describes

**Problem:** The Heartbeat moduledoc claims a lapse "broadcasts so coordinators can revalidate proactively instead of waiting for their next flush" (`lib/fathom/shard/heartbeat.ex:26-29,46-47,165,172-178`), but no process subscribes to `"fathom:heartbeat"` — neither `Fathom.Shard` nor anything else handles `{:heartbeat_lapsed, gen}`. The lapse→steal window is covered only lazily at the next flush's generation compare — up to `:shard_flush_interval_ms`, or unboundedly if the durability flush is disabled with interval `0`.

**Impact:** A superseded coordinator keeps accepting writes it will later discard for longer than designed; misleading documentation on the most safety-critical path.

**Recommended Fix:** Either subscribe coordinators to the topic (on `{:heartbeat_lapsed, gen}` with `gen != acquire_gen`, run `Fence.check` immediately and self-fence/stop accepting writes on `:superseded`), or delete the broadcast and correct the moduledoc.

### #35. Trailing-dot hosts promote bare hostnames to shards
**Severity:** Low | **Category:** Shard Isolation | **Panels:** Security (D6) — combine with #13 (D2)
**Likelihood:** Low (trailing-dot FQDNs from some clients/resolvers/proxies) | **Blast Radius:** Same logical host routes to different shards with vs. without the dot

**Problem:** `shard_from_host/1` (`lib/fathom/shard_executor.ex:257-267`) splits on `"."` and matches `[sub, _ | _]`, so a **trailing-dot** host promotes an otherwise-bare hostname to a shard: `localhost.` → `["localhost", ""]` → shard `localhost`; `bareword.` → shard `bareword`. Trailing-dot FQDNs are legal, so a host the operator expects to fall through to `default_shard` instead resolves to a first-label shard.

**Impact:** Inconsistent routing that can silently split or misdirect a tenant, and widens the set of `Host` values that select a shard without zone anchoring.

**Recommended Fix:** Strip a single trailing dot before splitting (`String.trim_trailing(host, ".")`) and require ≥2 **non-empty** labels before treating the first as a shard. Best combined with the base-domain anchor in #13 (D2).

### #36. `?db[]=` / `?db[k]=v` hands a list/map to `normalize_resolved/1`, crashing shard resolution
**Severity:** Low | **Category:** Reliability | **Panels:** Security (D5)
**Likelihood:** Low (dev/test-scoped today; a remote crash oracle if override is ever enabled in prod) | **Blast Radius:** Request abort / 500 on the resolve path

**Problem:** `normalize_resolved/1` (`lib/fathom/shard_executor.ex:242-243`) only has `nil` and `is_binary` heads, but with `:allow_shard_override` on, `shard_from_params/1` (`:269-272`) returns `conn.query_params["db"]` unchecked. Plug parses `?db[]=a&db[]=b` into a **list** and `?db[k]=v` into a **map**, raising `FunctionClauseError` on the resolve path (`shard_from_conn/1` is Filo's `open_arg` with no rescue).

**Impact:** A crafted query param crashes shard resolution — dev/test-scoped today, a trivial remote crash oracle if an operator enables override in prod.

**Recommended Fix:** In `shard_from_params/1`, coerce/reject non-binaries (`is_binary` guard → `nil`), and/or add a catch-all `normalize_resolved(_)` head returning `nil` so non-binary trust-boundary values fail closed.

### #37. No integrity checksum on flush PUTs or pull verification — pre-socket corruption becomes durable truth
**Severity:** Low | **Category:** Data Correctness | **Panels:** Storage (B8)
**Likelihood:** Low (bad disk, proxy, or S3-compatible store bug) | **Blast Radius:** Per-shard: silent persistent corruption, discovered only at next cold open after the good local copy is gone

**Problem:** Flushes PUT the shard bytes with no `Content-MD5` / `x-amz-checksum-*` (`lib/fathom/shard/storage/s3.ex:109-134`), and pulls never verify the received body against the object's etag (`s3.ex:86-106`). TLS/TCP catch most wire corruption, but nothing catches corruption introduced before the socket. A corrupted upload is accepted as the durable object, and because the fence etag chain (`state.etag`) advances from the response, every subsequent conditional operation treats the corrupt object as truth.

**Impact:** Silent, persistent corruption of the durable object with no detection point.

**Recommended Fix:** Compute MD5 (or CRC32C via `x-amz-checksum-crc32c`) of the local file and send it on the PUT so the store rejects a torn upload; on pull, verify the body against the returned etag when it's an MD5-shaped single-part etag.

### #38. Local backend lacks CAS fidelity on the lock/heartbeat paths — the default test suite can't catch fence regressions
**Severity:** Low | **Category:** Test Gap | **Panels:** Distributed (C9)
**Likelihood:** N/A (latent) | **Blast Radius:** Interleaving bugs in the conditional protocol are structurally invisible to Local-driven tests

**Problem:** The Local backend — explicitly positioned as "a faithful test double for the S3 fence semantics" (`lib/fathom/shard/storage/local.ex:130-137`) — implements steal/reclaim/renew/release as non-atomic read-modify-write with no CAS equivalent of S3's `If-Match` (`local.ex:241-258` renew, `261-268` release, `292-300` `write_lock`); release lacks S3's conditional delete (the finding #22 fix exists only in `s3.ex:341-345`).

**Impact:** The default suite cannot catch regressions in exactly the contention paths the fence exists for; the `Req.Test`-stubbed S3 tests assert request shape, not multi-writer interleavings.

**Recommended Fix:** Give Local real CAS fidelity: route lock mutations through an etag-checked compare-and-swap, mirror S3's conditional release, then add an interleaved two-stealer test at the Storage behaviour level that both backends must pass.

### #39. Local heartbeat written with bare `File.write` — readers can observe a truncated file and fail closed
**Severity:** Low | **Category:** Reliability | **Panels:** Storage (B9)
**Likelihood:** Low (concurrent reader on the same machine / shared filesystem) | **Blast Radius:** Intermittent shard-open failures / flaky lease tests on the Local backend

**Problem:** `Local.renew_heartbeat` (`lib/fathom/shard/storage/local.ex:203-212`) writes the heartbeat object with a bare `File.write` (open-truncate-write), unlike the lease and data objects which go through `atomic_write` (`storage.ex:317-337`). A concurrent `read_heartbeat` (from another shard's `acquire_lease`/`owner_live?`) can observe the empty/partial file between truncate and write, getting `{:error, :corrupt_heartbeat}` — which `owner_live?` correctly fails closed on, turning it into `{:error, {:transient_lookup, ...}}` acquire failures.

**Impact:** Intermittent shard-open failures and divergence between the test double and S3 semantics on the heartbeat path.

**Recommended Fix:** Use `Storage.atomic_write(heartbeat_path(owner), Storage.encode_heartbeat(hb))` in `Local.renew_heartbeat`, matching the lease/data objects.

### #40. Control-plane sweeps use touching `Directory.resolve/1`, phantom-bumping `last_active_at` fleet-wide
**Severity:** Low | **Category:** Data Correctness | **Panels:** Migration (E9)
**Likelihood:** High (every rollout/reconcile sweep) | **Blast Radius:** Degraded recency signals; noisy revert-guard refusals that train operators toward `force: true`

**Problem:** `ShardMigration.run/3` (`lib/fathom/migrator/shard_migration.ex:40-46`) uses `Directory.resolve/1` (`lib/fathom/directory.ex:44-60`) — which upserts `last_active_at = now` and registers unknown ids — as its version read. Every rollout/reconcile sweep attempt phantom-bumps `last_active_at` on shards no client touched (including attempts that merely snooze), and a mistyped `shard_id` in `enqueue_migration/2` mints a bogus `active` directory row at version 0. The bumps corrupt recency signals: warm-follower `active_recent/1` pre-pulls cold shards, `laggards` "hottest first" ordering degrades, and the revert write-age guard over-refuses (safe direction, but noisy).

**Impact:** Recency-driven machinery increasingly reflects control-plane churn instead of tenant traffic; guard refusals become noisy during any rollout-then-revert sequence.

**Recommended Fix:** Use `Directory.get/1` in `run/3` (registering genuinely-new shards is the checkout path's job), or add a non-touching `resolve` variant for control-plane reads.

### #41. `Shards.drain/2` safety-net exit strands `{:drain_aborted, pid}` messages in long-lived callers' mailboxes
**Severity:** Low | **Category:** Reliability | **Panels:** OTP (A8)
**Likelihood:** Low | **Blast Radius:** Slow unbounded mailbox leak in migration job runners / admin processes; hazard for future bare `receive`s

**Problem:** When `drain/2` (`lib/fathom/shards.ex:147-170`) exits via the `after drain_timeout + 30_000` safety net (:166-168), it demonitors with `[:flush]` but a `{:drain_aborted, pid}` message the coordinator sends afterwards stays in the caller's mailbox forever — the pin `{:drain_aborted, ^pid}` on any later call names a different coordinator pid. Symmetrically, matching the `:DOWN` first can leave the abort message behind.

**Impact:** Mailbox garbage in long-lived callers; a slow unbounded leak for a process that drains many shards.

**Recommended Fix:** After resolving either branch, drain the counterpart with a zero-timeout receive: `receive do {:drain_aborted, ^pid} -> :ok after 0 -> :ok end` (the `[:flush]` demonitor already covers the DOWN side).
