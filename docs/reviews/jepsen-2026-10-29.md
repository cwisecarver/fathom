## The bugs this gate's runs found and that are now fixed

- **Bug 10, `f0b72d46` + `12fc3a9d`.** A follower whose reply was lost stayed "busy" forever, so a
  shard with two of them refused writes with all three followers up. The fix bounds "busy" at
  `2 * timeout()`, not `timeout()`: at exactly `timeout()` a slow straggler's waiter is still live
  (`test/fathom/shard/replication/session_free_followers_test.exs`).
- **Bug 11, `87136f97`.** After a heartbeat lapse, a coordinator armed one ownership re-check per
  episode. If that re-check failed (a renew error from the isolate that caused the lapse), nothing
  retried it on a clean shard, which then refused writes with `:ownership_unconfirmed` for the
  rest of the run (hard mix 3 on `12fc3a9d`, shard 4, 601 refusals). The coordinator now re-arms
  while the heartbeat still reads `:revalidate`
  (`test/fathom/cluster/heartbeat_fence_test.exs`, "a failed lapse revalidation is retried").

Neither bug lost data. Both were found by the liveness checker, which fails a shard that takes no
ok write after the faults heal; Elle alone judges only completed operations and passed them.

## Totals to date

Jepsen has found 11 bugs in fathom: 9 that could lose or corrupt acked data and 2 that could
leave a shard unable to take writes. All 11 are fixed. Earlier reports:
[`jepsen-2026-10-24.md`](jepsen-2026-10-24.md), [`jepsen-2026-10-27.md`](jepsen-2026-10-27.md).

This is fathom's own Jepsen test, not an official Jepsen analysis. The rig is five containers on
one VM: no real clock skew between nodes, no partition that splits the fleet in half, no disk
corruption, no real AWS S3.
