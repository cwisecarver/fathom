## Product Opportunity — snapshots, PITR, and forking

Fathom's one-file-per-shard + S3-bottomless model makes version history, point-in-time recovery, and per-tenant database forking almost embarrassingly cheap compared to every competitor's architecture: a snapshot is one immutable S3 object, a fork is a server-side copy of one object under a new shard id, and a restore is the existing fenced `restore/3` pattern pointed at an older version — no WAL replay engine, no copy-on-write page server, no branching storage layer required. The competition treats exactly this as their flagship: Neon built an entire copy-on-write pageserver to sell branching + PITR, PlanetScale's database branching is its core workflow product, and Turso ships point-in-time restore and database forks on the same SQLite-file substrate fathom already has — "everyone and their brother is doing database forking now," and fathom can do it with a fraction of their machinery. Beyond disaster recovery, the same primitive yields preview environments, per-tenant staging, test-database forking (fork a tenant, run the test suite, drop it), and safe pre-migration snapshots. The stepping stones in the ranked list are: **#12** (version history / PITR — bucket versioning is the zero-code start), **#13** (hardened-bucket reference config that turns versioning on by default), **#14** (`mix fathom.shard pull|inspect|restore|fork` operator tooling — fork-to-new-shard-id is the fork feature's kernel), **#15** (tenant export — a fork handed to the customer), and **#10** (fork-from-template for new-tenant birth — the identical copy-one-object primitive, so building it once serves both onboarding and forking). Shipping these turns fathom's durability floor into its most marketable feature.

## Ranked Findings

### #1. RunPython data migrations are captured as template-literal DML and replayed verbatim — silent tenant data corruption fleet-wide
**Severity:** High | **Category:** Data Correctness | **Panels:** Django migrations (#4)
**Likelihood:** High (data migrations are the most common Django pattern after DDL) | **Blast Radius:** Fleet-wide — every tenant shard on rollout

**Problem:** `lib/fathom/migrator/capture.ex:73-78` (`append`) buffers every statement with no DML inspection; the limitation is documented at `docs/migration-engine-plan.md:195-198`, but the doc says RunPython "never reaches fathom as replayable SQL" — the opposite is the danger: RunPython's ORM calls *do* cross the wire inside the migration transaction and *are* captured. A backfill (`for u in User.objects.all(): u.slug = slugify(u.name); u.save()`) captures `UPDATE ... WHERE id=<template-row-id>` with template values, then replays those literal statements onto every tenant: tenants whose rows share ids get template data written over theirs; an empty template emits no DML, so tenants are silently never backfilled while the version stamp says they were. Either way, all three stamps agree the migration "applied."

**Impact:** The single most common Django migration pattern after DDL (data migrations) either corrupts or silently skips tenant data fleet-wide. This is a known-documented gap, but the failure mode is silent corruption rather than a clean refusal — that distinction is unguarded.

**Recommended Fix:** Lint the captured buffer at `commit`: any INSERT/UPDATE/DELETE touching a table other than `django_migrations` should at minimum flag the release (`requires_review: true`, blocking `rollout` until confirmed) or refuse capture with an operator error. Long term: a documented per-shard data-migration hook (run a statement template per shard, not template-literal SQL). *Status: known-documented limitation — but the silent-corruption mode is unguarded.*

### #2. Foreign-key enforcement is off by default and connection-scoped pragma state is silently lost on transparent stream re-creation
**Severity:** High | **Category:** Data Correctness | **Panels:** Django integration (#3)
**Likelihood:** High (every Django app relies on FK enforcement; stream churn is constant) | **Blast Radius:** Per-tenant data integrity, nondeterministic

**Problem:** `lib/fathom/shard/connection.ex:15-31` sets no `PRAGMA foreign_keys`; `../filo/lib/filo/stream.ex:37` — streams expire and a client reconnect gets a brand-new server connection. SQLite defaults `foreign_keys=OFF`; Django ≥2.2 assumes ON (its backend executes `PRAGMA foreign_keys = ON` in `get_new_connection`, and toggles it OFF/ON around migrations). Whether that pragma reaches fathom depends entirely on django-libsql replaying Django's connection-init on its remote connection — and even when it does, the pragma is scoped to the *current* Hrana stream's server-side SQLite connection. HTTP streams expire (Filo default 10 s idle) and clients transparently mint a new stream; the replacement connection comes up with `foreign_keys=OFF` and no one replays the pragma. Fathom correctly classifies `PRAGMA busy_timeout`-style assignments as clean control (`lib/fathom/shard_executor.ex:148-159`), but provides no server-side default for FK enforcement.

**Impact:** `on_delete=CASCADE`/`PROTECT` and FK integrity silently stop being enforced — either always (if the client never sends the pragma) or intermittently after stream churn (worse: nondeterministic). Orphaned rows accumulate with no error; Django users discover it via data corruption, not exceptions.

**Recommended Fix:** Add a per-shard/global config `:foreign_keys` (default ON for a Django-facing platform) applied in `Connection.open/1` alongside the existing pragmas, so enforcement doesn't depend on client init replay. Document that migrations needing `foreign_keys=OFF` still work (the client's per-stream pragma overrides for that stream). Ship a regression test: FK violation errors on a fresh stream with no client pragma.

### #3. Every SQL failure is flattened to code `"SQLITE_ERROR"` — Django can't distinguish IntegrityError from OperationalError, breaking `get_or_create` and busy-retry logic
**Severity:** High | **Category:** Data Correctness | **Panels:** Django integration (#2)
**Likelihood:** High (every adopter hits constraint/contention errors) | **Blast Radius:** All Django exception-driven control flow

**Problem:** `lib/fathom/shard_executor.ex:66,70,122` hardcode `code: "SQLITE_ERROR"`; `:411-412` (`reason_to_string`) turns an atom into `inspect/1` output; `lib/fathom/shard/connection.ex:83` maps busy-timeout expiry to `{:error, :busy}`. Hrana carries a SQLite error `code` string (Filo's `Error` docs even cite `"SQLITE_CONSTRAINT"`), and libSQL client exception mapping keys off it: constraint violations must surface as `SQLITE_CONSTRAINT*` (→ Python `IntegrityError`), lock contention as `SQLITE_BUSY` (→ `OperationalError` "database is locked"). Fathom sends `"SQLITE_ERROR"` for everything; worse, a busy timeout reaches the Django user as the literal message `":busy"` (the `inspect`ed atom) since `reason_to_string(:busy)` falls into the inspect clause.

**Impact:** Django's `get_or_create`/`update_or_create` race handling (`try: create; except IntegrityError: get`) doesn't fire — a concurrent create surfaces as a generic `DatabaseError` and the request 500s. Application-level "database is locked" retry patterns, `unique_together` violation handling, and `IntegrityError`-driven form validation all misclassify. The `":busy"` message is also indefensible DX for the platform's most common contention error.

**Recommended Fix:** Map exqlite's error reasons to real Hrana code strings: parse/propagate the extended result code from `Exqlite.Sqlite3` (e.g. `SQLITE_CONSTRAINT_UNIQUE`, `SQLITE_CONSTRAINT_FOREIGNKEY`, `SQLITE_BUSY`, `SQLITE_FULL`, `SQLITE_READONLY`) into `Filo.Error.code`, with a human-readable message (never `inspect` of an atom). Add regression tests: a UNIQUE violation must arrive with code `SQLITE_CONSTRAINT_UNIQUE`; two-writer contention must arrive as `SQLITE_BUSY`.

### #4. SQLite page-level integrity is never checked before flush — a corrupted local file clobbers the last good S3 copy
**Severity:** High | **Category:** Data Correctness | **Panels:** Durability (#2)
**Likelihood:** Low-Medium (disk/fs/memory fault, exqlite/OS bug) | **Blast Radius:** Total, permanent loss of the affected tenant (compounded by #12: no version history)

**Problem:** `lib/fathom/shard.ex:1288-1300` (`upload_for_drop`) and `lib/fathom/shard.ex:1494-1515` (`snapshot_and_upload`) verify integrity at the **transport** layer only (Content-MD5 on PUT, checksum-verified downloads — `s3.ex:529-591`, good). SQLite **page-level** integrity is never checked — no `PRAGMA integrity_check`/`quick_check` anywhere in `lib/` (only one test at `test/fathom/shard_durability_test.exs:770`). The idle-flush fast path checkpoints and uploads the raw file bytes as-is, so a db corrupted locally is uploaded with a perfectly valid If-Match by the legitimate owner — the fence can't help, it's not a steal. The `VACUUM INTO` path incidentally catches some page corruption (it reads every page); the checkpoint-then-raw-upload path catches none.

**Impact:** A corrupted flush **clobbers the last good copy**, and with no version history (#12) the corruption becomes the permanent, only truth for that tenant. Silent, unrecoverable, and discovered only when the tenant's queries start failing after the next cold open.

**Recommended Fix:** Run `PRAGMA quick_check` (cheap — shards are small by premise) before the pre-drop upload, and periodically for hot shards (e.g. every Nth durability flush). On failure: refuse the flush, quarantine the local copy, raise telemetry/alarm — the last good S3 object stays authoritative. Pair with bucket versioning (#12/#13) as the fallback for anything that slips through.

### #5. Self-fence deletes the local copy outright — acked-but-unflushed writes are destroyed when a rename would preserve them
**Severity:** High | **Category:** Data Loss | **Panels:** Durability (#3)
**Likelihood:** Low-Medium (GC-pause/partition steal) | **Blast Radius:** Per-tenant acked-write window, plus zero forensics

**Problem:** `lib/fathom/shard.ex:1079-1091` (`terminate` with `lease_lost: true` → `drop_local`) and `lib/fathom/shard.ex:1229` (`:superseded` pre-flush → `drop_local`): on self-fence (the crash-steal zombie direction), the coordinator **deletes** its local copy — including acked-but-unflushed committed writes. This is asymmetric with the fork path, which carefully preserves `.forked.<ts>` recovery copies (`quarantine_fork!`, `shard.ex:1444`) precisely because "a quarantine's sole purpose is preserving acknowledged writes." The self-fenced copy holds exactly the same class of data (acked writes the store never got) and is destroyed when a rename would preserve it. The loss itself is within the documented RPO contract (`docs/single-writer.md:85`) — the finding is the needless destruction plus zero after-the-fact accounting: nothing records *which* writes vanished beyond a log line and a `lease.superseded` counter.

**Impact:** After a GC-pause/partition steal, a tenant's acked writes silently vanish. The operator cannot answer "what did tenant X lose?" even when the zombie node's disk is perfectly healthy and the data was sitting right there. Customer-facing data loss with no forensics and no recovery path — one the system itself foreclosed.

**Recommended Fix:** In the `lease_lost` terminate paths, quarantine (rename to `.fenced.<ts>`, same pattern as `quarantine_fork!`) instead of `drop_local` when the shard is dirty (`unflushed?`); emit a structured event (shard, epoch lost at, watermark delta) so the lost window is enumerable. A follow-up tool can diff the quarantined copy against the stolen lineage.

### #6. Backwards and non-atomic Django migrations are invisible to capture — silent template/fleet fork discovered only as fleet-wide replay failure
**Severity:** High | **Category:** Reliability / Data Correctness | **Panels:** Django migrations (#5)
**Likelihood:** High (backwards migrate and `atomic = False` are routine Django operations) | **Blast Radius:** Every future rollout — mass quarantine

**Problem:** `lib/fathom/migrator/capture.ex:84-110` (`commit` records only when `count > before`), `capture.ex:14-16` (autocommit ignored); the atomic-only limitation is documented at `docs/migration-engine-plan.md:199-201` — the backwards case is not documented anywhere. Boundary detection is "row count rose inside a tracked transaction." Two routine Django operations fail that test: (a) `manage.py migrate <app> <prev>` (backwards) — Django *deletes* from `django_migrations`, count falls, capture returns `:noop`; (b) `atomic = False` migrations (Django's standard escape hatch for big-table operations, and required patterns on SQLite for some rebuilds) run autocommit and are ignored. In both cases the template schema moves and the fleet never hears about it; the *next* captured version assumes DDL state the fleet doesn't have, so every shard's replay fails (clean per-transaction rollback, then retry-exhaust → mass quarantine). There is no detection — e.g., no check that `count_at_begin` matches the count implied by prior captures.

**Impact:** A Django dev doing a completely ordinary backwards migrate or non-atomic migration on the template poisons all future rollouts, with the blast radius appearing hours-to-days later.

**Recommended Fix:** Track the expected `django_migrations` count (or row set) from prior captures; on any observed decrease or unexplained gap at `begin`/`commit`, raise a loud alarm and freeze `rollout` until an operator reconciles. Document that fleet undo is fathom's revert, never Django's backwards migrate.

### #7. No guard against `manage.py migrate` run directly on a tenant shard — stamps diverge silently, then the sweep quarantines the shard
**Severity:** High | **Category:** Data Correctness | **Panels:** Django migrations (#2)
**Likelihood:** High (the natural Django multi-DB pattern — and today the only tenant-bootstrap path, per #10) | **Blast Radius:** Per-tenant quarantine, frozen out of all future rollouts

**Problem:** Missing — no code. Divergence path: `lib/fathom/migrator/shard_migration.ex:325-364` (`do_run` trusts `PRAGMA user_version` only), `lib/fathom/directory.ex:356-358` (`laggard_query`). Django tracks applied migrations in `django_migrations`; fathom tracks its stamp in `user_version` + `_fathom_migrations` + `shards.schema_version`. If a Django team migrates a live tenant shard directly, the shard's schema advances but all three fathom stamps stay 0. The shard then looks like a laggard; `ShardMigrationJob` replays the whole captured chain onto the already-migrated file, fails deterministically on the first `CREATE TABLE ... already exists`, retries, and lands the tenant in `migration_failed` quarantine. Nothing anywhere compares `django_migrations` contents against the fleet's released versions to detect the divergence.

**Impact:** Every tenant a team migrates "the Django way" ends up quarantined and frozen out of all future rollouts, with no signal at migrate time — the failure surfaces hours later in the reconcile sweep.

**Recommended Fix:** Detect out-of-band migration before replay: in `do_run`, when `user_version < target` but the copy's `django_migrations` row set already contains the target chain's migration names, adopt-and-stamp (repair the three stamps) instead of replaying; and/or refuse non-template DDL at the executor (a config-gated "DDL only via the engine" mode) so direct migrate fails loudly at the client.

### #8. The template shard is itself swept as a laggard: the reconcile job drains and quarantines the capture source — and can silently lose a fleet version
**Severity:** High | **Category:** Reliability | **Panels:** Django migrations (#3)
**Likelihood:** High (deterministic after the first capture) | **Blast Radius:** The capture pipeline itself; potentially a permanently forked template/fleet schema

**Problem:** `lib/fathom/directory.ex:356-358` (`laggard_query` — no template exclusion), `lib/fathom/migrator/reconcile_job.ex`, `lib/fathom/shard_executor.ex:210` (`Capture.forget` on close). The template is registered in the directory at `schema_version: 0` like any shard, but Django migrates it directly, so its `user_version` and directory stamp never advance. After the first capture raises HEAD, the template is the *most recently active* laggard (`laggards/2` orders by `last_active_at desc`), so the hourly `ReconcileJob` targets it first: drains it, replays its own captured DDL onto itself, hits "already exists", retries, and quarantines it `migration_failed`. Worse, a drain racing an in-flight `manage.py migrate` refuses/tears down the migrate stream — and a dropped connection discards the Capture buffer (`Capture.forget`) for a transaction that already committed on the template, permanently forking template schema from fleet schema (the exact failure Capture's expert-review-#19 retry path exists to prevent, reintroduced via the engine's own sweep).

**Impact:** The capture pipeline attacks itself: quarantined template status pollutes the quarantine gauge, and a mid-migrate drain can silently lose a fleet version.

**Recommended Fix:** Exclude `:template_shard_id` from `laggard_query`/`rollout`/`shards_at_version` (or stamp the template's directory row to HEAD on each successful capture). Ship a regression test: capture a version, run `ReconcileJob`, assert no job targets the template.

### #10. New-tenant bootstrap is broken end-to-end: a novel shard is born empty and can never reach HEAD by replay
**Severity:** Critical | **Category:** Product Gap | **Panels:** Django migrations (#1)
**Likelihood:** Certain (every new tenant) | **Blast Radius:** Tenant onboarding — the product's headline motion

**Problem:** Missing — no code. `docs/migration-engine-plan.md:177-179` ("*Deferred:* fork-new-shard-from-template (new shards born at HEAD)"); `lib/fathom/shards.ex:121-122,141` — comments claim "a brand-new shard is born at HEAD via fork-from-template," but that mechanism does not exist anywhere in `lib/`; `test/django_validation/README.md:30-31`. Fork-from-template is deferred, so a novel shard minted on first request is an empty SQLite file at v0. The fallback the code comments assume — lazy migrate / laggard replay from v0 — cannot work for Django schemas: Django's `CREATE TABLE django_migrations` bootstrap (MigrationRecorder.ensure_schema) runs autocommit and is deliberately not captured (the "14 vs 15" result in the validation README proves it), so replaying captured version 1 (which ends with `INSERT INTO django_migrations ...`) onto an empty file fails with "no such table". `lazy_migrate`'s `behind?/2` also returns `false` for a shard not yet in the directory (`lib/fathom/shards.ex:138-143`), so nothing even tries.

**Impact:** The headline use case — a Django tenant's shard appearing on first request with the current schema — does not work. A new tenant's first ORM query hits "no such table". The only workaround (run `manage.py migrate` per tenant) triggers finding #7's quarantine. For a platform pitched at easily-shardable Django apps, tenant onboarding is the product.

**Recommended Fix:** Build fork-from-template: on novel-shard admission, copy the template's live object (or a retained `template@HEAD` snapshot), stamp `user_version = HEAD`, and register the directory row at HEAD. Alternatively, capture must record the recorder-bootstrap DDL (special-case the autocommit `CREATE TABLE django_migrations` as a version-0 preamble) so replay-from-empty works. Note this copy-one-object primitive is the same kernel as the user-upweighted database-fork feature (#12/#14) — build it once. *Status: known-planned gap (deferred), but the in-code comments asserting it exists should be corrected regardless.*

### #11. Django's SQLite backend depends on ~30 connection-registered Python UDFs that cannot exist server-side — large parts of the ORM throw "no such function"
**Severity:** Critical | **Category:** Product Gap | **Panels:** Django integration (#1)
**Likelihood:** Certain (date/regex lookups are core ORM surface) | **Blast Radius:** The "unchanged Django app" promise itself

**Problem:** Missing — no code (`lib/fathom/shard/connection.ex:15-31` opens with only `journal_mode`/`synchronous`/`busy_timeout`; `deps/exqlite/lib/exqlite/sqlite3.ex` exposes no `create_function` API — verified by grep). Django's sqlite3 backend registers user-defined functions on every DB-API connection (`django/db/backends/sqlite3/_functions.py`): `django_datetime_extract`, `django_datetime_trunc`, `django_datetime_cast_date/_time`, `django_date_extract/trunc`, `django_time_*`, `django_format_dtdelta`, `django_timestamp_diff`, `regexp`, plus `LPAD`/`RPAD`/`MD5`/`SHA*`/`SIGN`/`REPEAT`/math functions and the `STDDEV`/`VARIANCE` aggregates. These implement `__year`/`__month`/`__date`/`__time` lookups, `__trunc`, `USE_TZ` datetime casting, `__regex`/`__iregex`, `DurationField` arithmetic, and several ORM `Func`/aggregate classes. Over a network protocol the client cannot register Python functions in the server's SQLite process, and fathom's exqlite connection registers no equivalents. Nothing in fathom's SQL path shims them.

**Impact:** An unchanged Django app hits runtime `OperationalError: no such function: django_datetime_extract` the first time it runs `Model.objects.filter(created__year=2026)`, any `__date`/`__trunc` lookup, `timesince`-style duration math, or `__regex` — extremely common ORM surface. This silently narrows "unchanged Django app" to "Django apps that avoid date/regex lookups," which guts the pitch.

**Recommended Fix:** Ship a server-side Django-compat function pack registered at `Connection.open/1` — either a small C/Rust extension loaded via `Sqlite3.enable_load_extension` (a strong first job for the planned `fathom_native` NIF) reimplementing Django's `_functions.py` semantics, or upstream `create_function` support to exqlite and implement them in Elixir. Gate with a CI compat suite that runs Django's own `queries`/`db_functions`/`expressions` backend tests through django-libsql → fathom, and publish a supported-ORM-surface matrix until it's green.

### #12. No time-based snapshot history or PITR of any kind — every flush destructively overwrites the shard's single S3 object [USER-UPWEIGHTED]
**Severity:** High (upweighted to flagship product gap per user steer; owner +1 on PITR specifically) | **Category:** Product Gap / Data Loss | **Panels:** Durability (#1), Production readiness (#3)
**Likelihood:** Certain (the canonical customer incident: bad deploy, mass UPDATE, accidental delete) | **Blast Radius:** Every tenant's ability to recover from logical corruption; also the platform's biggest missed differentiator

**Problem:** `lib/fathom/shard/storage/s3.ex:210` (fenced `flush/3` PUTs to the live key), `lib/fathom/shard/storage.ex:155-175` (`retain`/`restore` take only migration schema versions). Every flush **overwrites the shard's single S3 object**. The only versioned copies that exist are migration-scoped (`<shard>@<schema_version>`, created around blue/green cutovers). There is no time-based snapshot history, no S3 object-versioning integration, no PITR — and A2 (live WAL streaming, the thing that would give true PITR) is a documented known-planned gap (AGENTS.md "Phase 2 remainder", `docs/durability.md:35`). Nothing in the docs even tells an operator to turn on bucket versioning. There is no snapshot schedule, no `mix fathom.restore <shard> <timestamp>` tooling, and no restore runbook — on-call has literally no page to open. The migration engine can revert *schema* versions, but a tenant whose data is corrupted by an app bug, a bad bulk update, or an accidental delete has no undo.

**Impact:** The canonical customer incident — "our bad deploy ran a mass UPDATE / the app deleted tenant X's rows; restore to yesterday 14:00" — is **unanswerable**. The mistake propagates to the only durable copy within one flush interval (default 30 s, `lib/fathom/shard.ex:62`), and the previous state is gone forever. ### #18. Multi-worker write contention semantics are unspecified and untested: deferred `BEGIN` upgrades fail fast regardless of the hardcoded 5 s busy_timeout
**Severity:** High | **Category:** Reliability | **Panels:** Django integration (#5)
**Likelihood:** High (2 gunicorn workers on one tenant is enough) | **Blast Radius:** Every read-modify-write transaction under concurrency

**Problem:** `lib/fathom/shard/connection.ex:28` (`busy_timeout=5000`, not configurable); no contention test in `test/fathom/shard_executor_test.exs` (26 tests, none exercise two concurrent writers). **Impact:** Under modest concurrency on a single tenant, read-modify-write transactions fail non-retryably with "database is locked"-class errors. This is *the* SQLite-behind-a-web-framework footgun and the platform neither mitigates nor documents it.

**Recommended Fix:** (a) Make `busy_timeout` configurable; (b) add an opt-in server-side `BEGIN` → `BEGIN IMMEDIATE` rewrite gate (or at minimum document Django 5.1 `transaction_mode: "IMMEDIATE"` / an init-command equivalent through django-libsql); (c) add a regression test with two streams doing read-then-write in overlapping transactions pinning the exact error code surfaced (ties into #3's `SQLITE_BUSY`).

### #26. No query timeout, statement interrupt, or result-size cap — one tenant's bad query pins memory and makes its shard un-drainable
**Severity:** High | **Category:** Reliability / Performance | **Panels:** Tenant lifecycle (#5)
