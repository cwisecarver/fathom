# The node-loss RPO window, measured — and the 5s-default change it justified

**2026-07-18, Apple M5 Max, macOS 27.0.** In-process, dev build, one-host-relative (the loss
window scales with write rate and flush interval, not with the host). This is the first reader of
the `Fathom.Rpo` harness (`mix fathom.rpo`), the in-process complement to the multi-node
`deploy/chaos/chaos.sh soak`.

## What it measures

Two deaths, two numbers (see [durability.md](../durability.md)):

- **Node / disk loss** — a survivor cold-opens the **last flushed object**, so it loses every write
  committed since that flush = the RPO window. The harness drives a steady write stream and, at
  points spread across the flush sawtooth, compares the acked max-seq against what the stored object
  holds. The stored object *is* the survivor's view (a failover cold-opens exactly it), so the loss
  is measured directly, without killing a node.
- **Process crash, disk intact** — write N with the flush disabled, hard-kill the coordinator,
  re-open on the same disk, count survivors. `synchronous=FULL` ⇒ zero loss.

The harness sets each swept interval **explicitly**, so the per-interval rows are independent of the
`@default_flush_interval_ms` constant — what the default sets is only *which row you get with no
config*.

## Results — 200 writes/s, 24 samples/interval

Two runs, before and after the default change, reproduce within noise (`lost rows` / `lost window`,
p50 / p99):

| `:shard_flush_interval_ms` | run 1 rows | run 2 rows | run 1 window | run 2 window |
|---|---|---|---|---|
| 1 000 | 97 / 160 | 99 / 160 | 0.59 / 0.97 s | 0.61 / 0.97 s |
| 5 000 **(default since 269a22c)** | 452 / 800 | 448 / 800 | 2.72 / 4.81 s | 2.70 / 4.81 s |
| 30 000 (was default) | 2 647 / 4 800 | 2 719 / 4 800 | 15.9 / 28.9 s | 16.3 / 28.8 s |
| 0 (idle-only) | 2 600 / 4 800 | 2 600 / 4 800 | 16.2 / 29.5 s | 15.8 / 29.0 s |
| **process crash (disk intact)** | **0** (200/200) | **0** (200/200) | — | — |

## Findings

1. **p99 lost window ≈ the interval** (0.97 / 4.81 / 28.8 s at 1 / 5 / 30 s). A node that dies just
   before a flush loses the full interval; the p50 is ~half, mid-sawtooth. This confirms the
   `RPO ≈ interval` formula empirically.
2. **Lost rows ≈ rate × interval**, so the window is a knob you set by the interval — it shrinks
   linearly as you tighten `:shard_flush_interval_ms` (5 s → ~0.5 k rows, 1 s → ~0.15 k).
3. **Idle-only (`0`) loses the whole busy session** — only the ~24 s run length bounded it here; a
   never-idle shard's window is unbounded. This is why the periodic flush exists.
4. **Process crash loses nothing** — `synchronous=FULL` fsyncs every commit to the local WAL, and a
   present local file is authoritative on wake, so a same-node restart re-adopts it. The RPO window
   is strictly about losing the node's disk, not about a process/BEAM crash.

## What it justified

The default was **30 000 ms**, giving a busy shard a ~16 s p50 / ~29 s p99 node-loss window out of
the box. Finding 1 says the knob is linear and cheap to tighten, so the default dropped to **5 000
ms** (`lib/fathom/shard.ex:62`, commit 269a22c) — ~2.7 s p50 / ~4.8 s p99, a ~6× tighter window for
~6× more flush PUTs on *write-active* shards (write-gated, so clean/idle tenants still skip the
upload). Operators override per-node with `SHARD_FLUSH_INTERVAL_MS` (`30000` for the old behavior,
`0` for idle-only). Sub-second RPO would need A2 (WAL streaming); the knob covers everything down to
~1 s.

Pinned as deterministic invariants in `test/fathom/rpo_test.exs`; the multi-node / real-disk
complement is `deploy/chaos/chaos.sh soak`.
