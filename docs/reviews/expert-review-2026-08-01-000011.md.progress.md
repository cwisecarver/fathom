**Bug 1 — #12 was fixed in S3 and MISSED in `Local`.** `owner_live?/3`'s stale-heartbeat branch
returned `:dead` without consulting the lock TTL — backwards from its own `:not_found` branch, so
a stale-but-present heartbeat was strictly *worse* than an absent one. `SHARD_STORAGE=local` is a
supported production selection, so this was live: one Heartbeat crash (which deliberately leaves
its object behind) made that node's entire keyspace slice instantly stealable while it kept
serving. **Three existing tests had pinned the defect**, which is how it survived; each is updated
in place and says so.

**Bug 2 — the S3 double could not produce a 304.** `S3EtagStore` had no `If-None-Match` handling,
so `pull_if_changed/3` — the warm-standby freshness check, the entire reason a failover can
promote a warm copy instead of re-transferring the body — could never take its 304 path against
the double. Its only S3 coverage was behind `@tag :s3` (MinIO), which the default suite
**excludes**. Found by the contract suite on its first run. Also added `ListObjectsV2` so
`purge_shard/1`'s cross-tenant delimiter rule is testable on both backends at all.

**Deliberately NOT done, with reasons recorded in the code** so silence is not read as coverage:
steal sentinels stay S3-only (`local.ex:447` documents why — content-hash etags cannot rotate
without the bytes changing, and the backend is single-node; a deliberate constraint is not a gap),
and #44's source-vs-destination etag divergence stays invisible (`file_etag/1` and
`content_etag/1` are the same sha256, so a quiescent source makes them agree — catching it needs a
mutate-mid-flush seam neither live backend has).

**Bug 3 — the crash-hold predicted a steal the lock TTL forbade. FIXED `8e49c2e`.**
`Shards.holder_stealable_soon?/2` read **only** the heartbeat, while post-#12 `acquire_lease`
required **both** signals lapsed — so a checkout held and retried its whole
`crash_failover_hold_ms` budget waiting for a steal that could not happen, then returned the same
error it would have returned immediately. Live in S3 from the moment #12 shipped there.

**The fix is not "teach the predicate about locks".** Copying the rule into a second place is what
produced the bug; doing it again with one more term leaves the same trap for whoever changes the
rule next. Both backends now derive `owner_live?/3` **and** a new `lease_stealable_at/1` from one
function returning the instant the hold becomes stealable — `owner_live?` is "is now past it", the
callback is "how long until it". S3 normalises onto the caller's clock before returning, so the
store-Date comparison (#13) is not leaked into the caller's arithmetic. The contract suite pins
the invariant for both backends: **`lease_holder` is `{:held, _}` iff `lease_stealable_at` puts
the steal in the future.**
