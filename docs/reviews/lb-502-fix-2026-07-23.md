# LB 502-storm root cause + fix — 2026-07-23

The chaos rig's "documented 502 storms" (`tpc-fleet-2026-07-11.md`: "transient nginx↔node
upstream 502s rise with concurrency"; re-observed 2026-07-23) are fixed. They were an LB
config bug — present in the **prod** config too — not a fathom/filo behavior.

## Root cause (verified by error-log signature)

A 24-tenant burst reproduced 21× `upstream prematurely closed connection while reading
response header from upstream` + 3× `recv() failed (104: Connection reset by peer)` — the
classic upstream-keepalive FIN race. Two config defects compounded:

1. **`map $http_upgrade $connection_upgrade { default upgrade; '' close; }`** — the
   WebSocket-upgrade idiom sent **`Connection: close` upstream on every plain HTTP
   request**, so Bandit closed each connection after one response. The `keepalive 64`
   pool (comment: "helps the per-stream HTTP path") was therefore defeated on every
   request: constant connection recycling, and under load nginx grabs a pooled conn at
   the instant the backend's FIN from the *previous* response arrives → 502. Explains
   "rises with concurrency" exactly.
2. **No `keepalive_timeout` in the upstream blocks** — nginx's default (60s) ties
   Bandit's 60s idle close, leaving the idle-expiry race even once the pool works.

## Fix (both the prod `deploy/lb/fathom.nginx.conf` and the rig config, plus the
`Fathom.Rebalancer.LbMap` pin-upstream template + rendered `exceptions.conf`)

- `'' ""` in the map: an empty Connection header is **removed** — nginx's documented
  requirement for upstream keepalive; upgrade requests still get `Connection: upgrade`.
- `keepalive_timeout 30s` in every upstream block: nginx always closes an idle pooled
  conn before Bandit's 60s idle close can race it.

| 12 | 56.1 | **1,065.8** | 10.99 | 22 → **0** |

## Addendum — 64 tenants, the previously-impossible concurrency

`tpc-fleet-2026-07-11.md` documented 64 tenants as the rig's hard ceiling ("enters a 502 +
reconnect storm") and framed the harness as "moderate concurrency by design." Post-fix:

| tenants | txns | txn/s | p50 ms | p95 ms | p99 ms | errs | LB upstream failures |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 64 | 9,600 | 1,075.3 | 57.35 | 79.79 | 90.18 | **0** | **0** |
| 128 | 19,200 | 1,082.1 | 113.75 | 163.16 | 186.09 | **0** | **0** |

At 128 tenants (2× the old collapse point): p50 within 4% of the fair-queueing prediction
(128 ÷ 1,082 ≈ 118.3 ms vs 113.75 measured), and the consistent-hash spread IMPROVES to
1.27× (44/37/47 shards) as the key count grows — both curves exactly as theory says.

The same ~1,080-tps CPU plateau as 24 tenants, with p50 within ~4% of the fair-queueing
prediction (64 ÷ 1,075 ≈ 59.5 ms vs 57.35 measured) — linear latency growth on a flat
plateau, i.e. textbook saturation with no convoy and no collapse. Spread 2.08× over 3
nodes (13/27/24 shards — normal consistent-hash unevenness at N=64). The "moderate
concurrency by design" caveat is retired along with the storm.

## Prod note

The same `'' close` idiom shipped in `deploy/lb/fathom.nginx.conf`, so any real deployment
was paying the same per-request upstream connection churn and 502/retry rate on the HTTP
SDK path (WebSocket streams were unaffected — they hold one upgraded connection). The
`proxy_next_upstream http_502` retry also sent those raced requests to a *different* node
than the shard's hash-home (a churn amplifier, though single-writer safety was never at
risk — the lease fence holds regardless). Roll this config change out with the next LB
reload.
