# TPC remote-client rig run — 2026-07-10

**Phase 4 of `docs/tpc-benchmark-plan.md`: the realism layer.** A real libSQL/Hrana **remote
client** (`deploy/chaos/tpc_driver.py`, dep-free Python stdlib) drove the TPC-B and TPC-C
workloads over the network through the LB on the chaos rig — the true client path the in-process
loopback WS gate (`mix fathom.wire_bench` / `mix fathom.tpcc`) cannot reach. Driven by
`chaos.sh tpcb` / `chaos.sh tpcc`.

**What this is / is not.** The rig is single-host (macOS 27.0, arm64; 3 prod-release fathom nodes
behind nginx + MinIO + Postgres via colima). So the **client→LB hop is loopback** — these are
**not** a WAN RTT. The realism vs the in-process gate is the full real stack every request now
crosses: the **nginx LB hop** (subdomain → node consistent-hash, as prod), a **prod-release node**
(Bandit + Filo Hrana over HTTP `/v2/pipeline`), and **S3(MinIO)-backed storage** — none of which
the loopback WS client touches. Every transaction is sent **statement-by-statement on a held
stream** (chatty, non-batching — the real django-libsql shape), so per-txn latency includes each
statement's network round-trip. Recorded-only: never a gate.

Rebalancer quieted for the latency runs (`Application.put_env(:fathom, :rebalancer_enabled,
false)` per node) so shard handoffs don't move a shard mid-measurement.

---

## Headline — the cross-LB round-trip

| Probe | in-process loopback WS (Phase 1) | **remote client through the LB (this run)** |
|---|---|---|
| warm `SELECT 1` RTT, p50 | ~130 µs | **559 µs** (p95 656, p99 756) |

A warm read round-trip costs **~4× more** through the real LB + HTTP + prod-release node than the
in-process WS client. That constant is the floor every statement of every transaction pays, and it
is what makes a *chatty* transaction expensive over the wire (below).

## TPC-B — the write-path tax over the real client wire

Single tenant (one client, one shard, **0 errors** — the clean latency):

| metric | value |
|---|---|
| per-txn p50 | **4.05 ms** |
| per-txn p95 | 5.05 ms |
| per-txn p99 | 5.76 ms |
| per-txn max | 7.02 ms |

The pgbench bank txn is 7 statements; **7 × ~0.56 ms RTT + server ≈ 4 ms**, and the number lands
there — so the per-txn cost is dominated by the round-trip count, exactly the "chatty client" model
the loopback `tpcb_wire_overhead_us` measured, now over the real LB.

Multi-tenant (8 tenant shards, **one writer each** — fathom's real model): per-txn **p50 6.1 ms,
p95 10.2 ms, p99 11.5 ms** with a tight tail (68/4000 transient LB errors, auto-recovered). No
intra-shard contention because each tenant is its own single-writer file — the point of the
architecture.

## TPC-C — W = 1..5 sweep, per-transaction-type latency

4 threads on one shard per W (the spec's multi-terminal-per-warehouse model), scale 0.02.
**p50 is the clean signal and is stable across W** (per-txn cost is warehouse-independent — W
scales data size, not the statement count per txn):

| txn type | p50 (µs), W=1..5 | shape |
|---|---|---|
| **New-Order** | 27453 / 27847 / 28468 / 27684 / 27398 | ~30–60 chatty round-trips (per-line item+stock reads → writes) |
| **Payment** | 5674 / 5650 / 5703 / 5620 / 5732 | ~9 statements incl. the by-last-name multi-row select |
| **Order-Status** | 3053 / 2889 / 3002 / 3041 / 2961 | read-only: latest order + its lines |
| **Delivery** | 41185 / 40685 / 41333 / 40985 / 40855 | batch over 10 districts (~7 statements each) |
| **Stock-Level** | 2392 / 2387 / 2504 / 2442 / 2408 | read-only low-stock distinct-item join |

`tpmC` came in noisy (489–1610 across W) and the **p99 tails blow out to 1–2 s** — both explained
by the finding below, not by per-txn cost (the p50s are rock-stable).

## The finding — chatty writes convoy on a single shard

A New-Order holds the **`BEGIN IMMEDIATE` write lock for its whole ~27 ms** — because that 27 ms is
~30–60 **network** round-trips (read an item, read its stock, update stock, insert the line, ×
5–15 lines), and SQLite is single-writer. So with multiple threads on **one** shard, every other
writer waits behind the lock for tens of ms per txn, and the p99 tails to seconds while `tpmC` is
lock-bound (≈ 1 / lock-hold-time), independent of W.

This is not a fathom defect — it is the **argument for fathom's architecture**. The contrast is
right in the data:

- **Many threads on one shard** (TPC-C single-tenant): lock convoy, p99 → 1–2 s.
- **One writer per shard across many tenants** (multi-tenant TPC-B, 8 shards): tight p99 (11.5 ms),
  no convoy.

fathom scales by **millions of small single-writer shards** (one tenant = one file = one writer),
*not* by concurrency within a shard. TPC-C's within-tenant concurrency is exactly the workload that
does **not** fit that model, and the sweep shows why. A single tenant's OLTP concurrency over a
chatty remote protocol is bounded by the write-lock-hold, which the round-trip count dominates.

## Rig artifacts (honest noise, not fathom)

- **~1–2% transient 502s** (nginx↔node upstream keepalive races), present with the rebalancer
  **off**. A real client reconnects and retries; the driver does the same (`Stream.reconnect`), so
  they cost a skipped txn, not a dead worker. Reported per run (`errors`).
- **tpmC + max are polluted** by the convoy tails + these stalls; the **p50 percentiles are the
  trustworthy signal**. Throughput is not a rig-meaningful number here (single host, loopback
  client→LB) — the loopback `mix fathom.tpcc` sweep is the reproducible throughput trend; this run
  is the *latency-shape + real-stack* headline.

## Reproduce

```bash
cd deploy/chaos && ./chaos.sh up
./chaos.sh tpcb [shards txns accounts]        # RTT probe + N tenant-shard TPC-B through the LB
./chaos.sh tpcc [max_w threads txns scale]    # W=1..max_w TPC-C sweep through the LB
# each prints a human summary (stderr) + one JSON result per run (stdout)
```

Raw JSON captured this run: single-tenant TPC-B p50 4052 µs (0 errs); the W-sweep rows above.
Numbers are **relative** (one host, loopback client→LB) — a trend + latency-shape characterization,
not an absolute or peer-certifiable TPC result.
