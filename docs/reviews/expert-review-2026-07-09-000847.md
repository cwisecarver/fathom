## What is CONFIRMED SAFE (do not "fix")

- **Affinity preserves read isolation.** `best_target` only reorders *among viable, load-improving
  backends*; a wrong/lying warm advertisement at worst makes the target cold-open (200 not 304) — it
  still re-derives the shard from `Host`, acquires the `{owner,epoch}` lease for *that* shard, and
  serves its own S3 object. Affinity cannot mis-associate shard→node or read another tenant's data.
- **Telemetry cardinality is clean.** Every rebalancer metric tags only `:outcome`/`:command`;
  shard_id/from/to ride in event **metadata** only (the "never shard_id in a tag" rule holds). Event
  names match emits exactly; every declared tag is present in the emitted metadata (no nil-grouping).
- **Policy stays pure** — no `:telemetry.execute` in `policy.ex`; affinity hit/miss is derived in
  `RebalanceJob.warm_target?/2`, consistent with how `plan_moves` reads the same map.
- **The bench lock is race-free.** `File.open(O_EXCL)` atomic claim + `try/after File.rm` release
  (on success and on raise) + `:eexist` `Mix.raise`s without removing a lock it didn't create. No TOCTOU.
- **`Stats.percentile/2`** correct at n=1 / pct 0 / 100 / empty; **`fleet_p99` division guard**
  (`total > 0`), all-nil handling, and idle-node exclusion are correct; **`lb_apply` `:noop`-per-tick**
  is intentional and low-volume. `async_stream_nolink` genuinely isolates a crashing command; the
  `TaskSupervisor` is unconditional so tests never miss it; `#13`'s `try/rescue/catch :exit` correctly
  wraps all the new Reporter Postgres calls.

### #1. The dead-node reconciler keys off the reporter beat, which diverges from S3 data-plane liveness — a live-but-not-beating node has its hot pins yanked and re-homed to a node that can't acquire the still-held lease
**Severity:** High | **Category:** Distributed / Availability | **Panels:** 1
**Likelihood:** Medium-High (a Reporter crash / a non-reporting handoff target / a NODE_KEY↔lb_backends drift) | **Blast radius:** the hottest pinned shards

**Problem:** `RebalanceJob.reconcile_dead_pins` (`rebalance_job.ex:100-120`) unpins any override whose
`pinned_node ∉ Nodes.alive(60s)`. But `alive` is the `rebalancer_nodes` beat, which only fires inside
the `:load_reporter`-gated `Reporter.do_report` tick — `NodeBeat`'s own moduledoc says it is *"distinct
from the S3 heartbeat"* (the real data-plane liveness the lease respects). They diverge:
- A node whose **Reporter crashes / is toggled off** while its data plane keeps serving stops beating
  but keeps its S3 heartbeat fresh and keeps holding leases. Within ~1 tick the reconciler declares it
  dead and `unpin`s all its hot shards → they fall back to the hash pool → the hash-home node calls
  `acquire_lease`, sees the original owner's S3 heartbeat still fresh → `{:held}` → **cannot serve**.
  The hottest shards go down until the original node truly dies or its Reporter recovers.
- A **non-reporting node contributes no LoadSamples**, so `Policy.best_target` reads its load as `0.0`
  (`policy.ex:165`) and picks it as the *preferred (idle-looking) target*; the `HandoffJob` pins the
  shard there → the very next reconciler tick `unpin`s that fresh pin.
- Latent config coupling: the reconciler compares `pinned_node` (`:lb_backends` key) to `alive`
  (`node_key`s). If `NODE_KEY` ≠ the `:lb_backends` key for any node, *no* `pinned_node` is in `alive`
  and the reconciler unpins **every** pin **every** tick — a silent total defeat with only per-shard logs.

**Impact:** The reconciler added to *restore* failover introduces a higher-probability outage: a single
Reporter crash (or a non-reporting target, or a key mismatch) yanks live nodes' hottest pins and routes
them to nodes that can't acquire the lease. This is the strongest reason not to enable B1 as-is.

**Recommended fix:** Base the dead-node decision on the liveness the lease actually respects.
(a) Consult the S3 heartbeat (`Fathom.Shard.Heartbeat`) for `pinned_node`'s freshness before unpinning
(map `node_key`→owner), or require **both** signals stale. (b) Never unpin a shard with an in-flight
`HandoffJob` (grace window on the override's age). (c) Exclude non-reporting `:lb_backends` nodes from
target selection (treat "no samples" as *unknown*, not idle). (d) Boot-guard that every `:lb_backends`
key has a matching `NODE_KEY`, and emit a tripwire counter when a tick would unpin an unusually large
fraction of pins.

### #2. The fleet-wide LB-map advisory lock holds a pooled connection across an unbounded `System.shell` reload — a wedged reload freezes every node's `apply!` and crash-loops the leader tick
**Severity:** High | **Category:** Concurrency / Reliability | **Panels:** 1, 2 (both)
**Likelihood:** Medium (a hung/slow `nginx -t` / `-s reload` / sidecar HUP) | **Blast radius:** the whole fleet's LB-map updates

**Problem:** `with_lock/1` (`lb_apply.ex:93-103`) does `Repo.checkout(fn -> pg_advisory_lock; promote(); unlock end)`,
and `promote → write_test_promote` runs **two** `System.shell` calls — `:lb_test_cmd` then `:lb_reload_cmd`
(`lb_apply.ex:168,188`) — with **no timeout**. So the checked-out DB connection and the **fleet-wide
session** advisory lock are held for the full duration of two external shell commands. A session advisory
lock releases only when the connection ends; a hung shell never ends it. Every other node's `apply!` then
blocks in `pg_advisory_lock` (each inside its own `Repo.checkout`, pinning a connection); waiters
eventually hit Postgrex's 15s query timeout, which **raises** out of `Repo.query!`, crashing the leader's
`RebalanceJob` tick (`max_attempts: 1` → dropped).

**Impact:** One hung reload on one node freezes every LB-map update fleet-wide (pin, unpin, #1b reconcile,
#10 drift-heal, #11 failed-reload heal all go dark) and crash-loops the leader tick, while stacking blocked
waiters against the 10-connection pool (starving Directory.Recorder / Oban / the reporter). Even a merely
slow reload holds a connection + the fleet lock for its full duration on every real change.

**Recommended fix:** Do the render + config-test + atomic rename inside the lock, but run the actual
**reload after** `pg_advisory_unlock` / outside the checkout (nginx picks up the renamed file on its own
trigger). Give every `System.shell` a hard timeout (`Task.async` + `Task.yield`/`shutdown`, or a killable
Port with a deadline) → `{:error, {:reload_timeout, _}}`. Use `pg_try_advisory_lock` + bounded backoff (or
set `lock_timeout`) so a waiter degrades to "skip this tick" instead of raising and crashing the leader.

### #3. The affinity load-band is anchored to the source's load, so on a hot source it admits warm targets far above the least-loaded — the move can relocate the hotspot onto the warm node
**Severity:** Medium | **Category:** Data Correctness / control-loop stability | **Panels:** 5
**Likelihood:** High (fires on exactly the hottest sources — the common affinity path) | **Blast radius:** balance quality of every affinity-driven move

**Problem:** In `best_target/5` (`policy.ex:166,174-181`), the improvement guard requires only
`t_load + q_per_s < from_load` (target-post below source-**pre**), and the affinity ceiling is
`least + band × (from_load − least)` — both anchored to `from_load`, not the least-loaded node. On a
heavily-overloaded source the ceiling is a large absolute value, so a warm target far more loaded than the
least node is "within band" and preferred. Concrete (defaults `band=0.5`, `floor=300`): n1 = hot_1(350) +
filler(550) = 900; n2 warm-for-hot_1 @ 300; n3 cold @ 10. `least=10`, `ceiling = 10 + 0.5×890 = 455`; n2
(300 ≤ 455, warm) beats the far-colder n3. **Post-move: n2 = 650, n1 = 550** — the warm target is now the
fleet max, hotter than the source became. Strict least-loaded would have picked n3 (→360), max 550. The
moduledoc's "the band means affinity never picks a materially-more-loaded target" is inaccurate.

**Impact:** The hottest sources (the intended targets) are exactly where the band is loosest, so this is the
*common* affinity path. The move under-improves balance and can install a fresh hotspot on the warm node —
the "just relocates the hotspot" outcome the improvement guard claims to prevent — weakening the
rebalancer's core value whenever affinity fires on a hot source.

**Recommended fix:** Anchor the band to the **least-loaded post-move** load, not `from_load`: accept a warm
target only if its post-move load `l + q_per_s ≤ least_post + band × (from_load − q_per_s − least_post)`
where `least_post = least + q_per_s`; at minimum reject any warm target that would end hotter than the
source's post-move load (`l + q_per_s ≥ from_load − q_per_s`). Correct the moduledoc claim. Add a test with
a hot source + a within-old-band-but-more-loaded warm target asserting the cold least-loaded wins.

### #4. `fleet_p99` (count-weighted mean of per-node p99s) is not a sound fleet-relative bar — a busy-but-balanced node inflates it and masks hotspots on quiet nodes, and it silently reverts to the head-only percentile below the sample floor
**Severity:** Medium | **Category:** Data Correctness (hot detection) | **Panels:** 1, 5 (both)
**Likelihood:** High (any mixed busy/quiet fleet, the documented p99 default) | **Blast radius:** the headline p99-relative detection mode

**Problem:** `Nodes.fleet_p99/2` (`nodes.ex:63-76`) weights each node's p99 by `sample_count` = **active-shard
count** (`reporter.ex:100`), not query volume, and `min_p99_samples` gates on the sum of those counts. Two
consequences:
1. **Wrong direction of bias.** The 2026-07-08 refinement fixed idle nodes dragging the bar to 0, but the
   *opposite* is unaddressed and worse: a uniformly-busy node (many active shards, moderate p99) **inflates**
   the bar and hides a genuine hotspot on a quieter node. Concrete: node A (60 shards ≈ 200 q/s → p99≈200,
   count 60) + node B (99 idle + one 400-q/s hotspot → p99≈6, count 100) → `fleet_p99 ≈ 78.7`, bar (×20)
   ≈ **1574**; B's real 400-q/s hotspot never clears it. Remove A → bar ≈ 120 and it flags. The bar tracks
   the busiest node's p99, not the fleet's. A mean of per-node p99s is not the pooled-distribution percentile.
2. **Fallback below the floor is the exact bias #2 removed.** With < `min_p99_samples` (50) active shards,
   `fleet_p99` returns `nil` and `Policy.hot_threshold` falls through to `mult × percentile(samples, 99)`
   (`policy.ex:200`) over the published **top-N head** (cold tail truncated) — the head-only p99 that prior
   review #2 set out to eliminate.

**Impact:** The p99-relative default is under-flagging (or mis-calibrated) for any fleet that isn't both
large (≥50 active shards) and tail-heavy — the same failure class #2 aimed to close, now masked. Fail-safe
(no wrong move) but the headline detection mode is unreliable outside the absolute-floor path.

**Recommended fix:** Weight by a **load proxy** (Σ `q_per_s`) not active-shard count, and gate
`min_p99_samples` on that same quantity — or use a robust unweighted combiner (median of live nodes' p99s),
or, faithfully, publish a small per-node q/s histogram and merge to a true pooled p99. Do **not** silently
fall back to the head-only percentile below the floor (return no p99 threshold instead). Add a mixed
busy/quiet fleet test (not hand-set `sample_count`) asserting the quiet node's hotspot flags.

### #5. `Nodes.beat/1` (liveness-only) silently NULLs a node's published `q_p99`/`sample_count`
**Severity:** Medium | **Category:** Data Correctness | **Panels:** 3, 5 (both)
**Likelihood:** Low today (only the Reporter beats, always with stats) | **Blast radius:** the fleet-p99 hot bar

**Problem:** `beat/2` (`nodes.ex:21-33`) reads `q_p99 = opts[:q_p99]` / `sample_count = opts[:sample_count]`
(nil when absent) and **unconditionally** writes them in `on_conflict: [set: [last_seen_at, q_p99,
sample_count]]`. So a plain `Nodes.beat(node_key)` issues `SET q_p99 = NULL, sample_count = NULL`, clobbering
the node's last-published distribution; `fleet_p99` then filters that node out (`not is_nil(q_p99) and
sample_count > 0`). The module's own moduledoc advertises the wiping arity as the primary per-tick call, and
the tests (`nodes_test`, `rebalance_job_test`, `telemetry_test`) all call bare `beat("n1")`.

**Impact:** Latent — production only beats via the Reporter (always with stats). But it's a live footgun in
the exact data path feeding the hot bar: the moment any second path adds a lightweight liveness beat (a
`CommandPoller`/`HandoffJob` keeping a node alive during a long handoff — exactly what the moduledoc invites),
it zeros that node's p99 for a window, shifting or collapsing the bar. Untested ("stats beat, then plain beat").

**Recommended fix:** Build the `on_conflict` `set:` dynamically — include `:q_p99`/`:sample_count` only when
supplied — so a liveness-only beat refreshes `last_seen_at` without erasing the distribution. Regression test:
`beat(n, q_p99: 5.0, sample_count: 100)` then `beat(n)`, assert `fleet_p99` still sees 5.0.

### #6. A NEW shard_id boundary (warm-locations + drain/warm commands) lacks the `Fathom.ShardId` gate; a `warm` command builds a file path from the id, giving a write/delete traversal primitive
**Severity:** Medium | **Category:** Shard Isolation (defense-in-depth / isolation doctrine) | **Panels:** 4
**Likelihood:** Low today (live ids are pre-validated upstream) | **Blast radius:** arbitrary-path write/rm outside the warm-cache dir if bypassed

**Problem:** Finding #14 established that any *new* place a shard_id enters routing must enforce `Fathom.ShardId`
and closed it for the `Override` boundary. This session added three parallel boundaries that did **not** get
the gate: `shard_warm_locations` is written via a bare `Repo.insert_all` against a changeset-less schema
(`warm_locations.ex:35`); `Command.changeset` validates `:command`/`:status` but never the shard_id format
(`command.ex:30-36`); and a `"warm"` command flows `CommandPoller.execute → WarmFollower.warm_now →
cache_path(shard_id) = Path.join(cache_dir, "#{shard_id}.db")` where `pull_if_changed` **writes bytes** and
`drop/1` does `File.rm`. An id like `../../x` escapes the cache dir — a write/delete traversal primitive, not
just a read. `Reporter.publish_warm_locations` similarly feeds unvalidated ids into `WarmFollower.cached?`
→ `File.exists?(cache_path(id))`. No live leak today (every id originates from the pre-validated checkout
path), but the doctrine #14 was raised to enforce is left un-closed on the sibling paths.

**Impact:** No exploitable cross-tenant leak today, but a future caller / an ops-or-manual insert into
`shard_warm_locations` or `rebalance_commands` / an upstream regression could put a traversal id into the warm
path, turning `warm_now` into an arbitrary-path write + `File.rm`.

**Recommended fix:** Add `Fathom.ShardId.valid?/1` at each boundary: a `Command.changeset`
`validate_change(:shard_id, ...)` mirroring `Override`; validate before `WarmLocations.publish`'s
`insert_all`; and a guard in `WarmFollower.cache_path/1` (or its callers) that refuses an id failing
`ShardId.valid?/1`, so the file-path builder itself never accepts an unvalidated id.

### #7. A retry issues a fresh `drain` without cancelling the prior attempt's still-pending drain; the poller then runs same-shard drains concurrently → the coordinator's busy-guard marks the *current* attempt `failed`, causing a spurious revert of a handoff that actually drained
**Severity:** Medium | **Category:** Concurrency | **Panels:** 2
**Likelihood:** Medium (poller pickup lag under a hotspot storm) | **Blast radius:** spurious revert/thrash + cold-reopen of a good move

**Problem:** Each `HandoffJob` attempt's `drain/2` unconditionally `Commands.issue(shard, from, "drain")`
(`handoff_job.ex:120-128`); `cancel_pending_drains` is called only on the *final revert*, not between
attempts. If an attempt's `await` times out with the command still `pending`, the retry issues a **second**
pending drain for the same shard. Both land in one `pending_for` batch and `async_stream_nolink` runs them
**concurrently** (`command_poller.ex`); two `Shards.drain(same_id)` hit the coordinator — the second hits the
`%{draining: true}` busy-guard (`shard.ex:748`) → `{:error, :busy}`. If that's the command the current attempt
awaits, it's marked `failed (busy)` even though the shard drained via the stale command.

**Impact:** A handoff that genuinely succeeded (source flushed + released its lease) is reported failed → the
last attempt **reverts** (marks the pin failed, re-renders the LB to send traffic back to a source that
already dropped the shard). The lease prevents any double-write, so it's not a correctness leak — but it's a
spurious revert/thrash + an extra drain+cold-reopen on exactly the hot shards the rebalancer targets.

**Recommended fix:** Make drain single-in-flight per shard: `Commands.cancel_pending_drains(shard)` at the
**start** of `drain/2` (before issuing), and/or have the poller skip a `drain` whose shard already has an
in-flight drain. A partial unique index `(shard_id, command) WHERE status='pending'` on `rebalance_commands`
enforces it at the DB.

### #8. `CommandPoller.complete/3` emits telemetry *before* the durable `Commands.complete` — a raising handler aborts the completion and wedges the command in a re-execution loop
**Severity:** Medium | **Category:** Reliability / observability-correctness | **Panels:** 2
**Likelihood:** Low (needs a raising/exiting handler) | **Blast radius:** one command loops until stale-expiry (~15 min)

**Problem:** `complete/3` (`command_poller.ex:142-149`) calls `:telemetry.execute(...)` **first**, then
`Commands.complete`. `:telemetry.execute` runs every attached handler **synchronously in the calling process**
(the async_stream task). A handler that raises/exits propagates out, so `Commands.complete` never runs and the
command stays `pending`; the task death is absorbed by `async_stream_nolink` (logged) but the command is
re-picked next poll and re-executes (`Shards.drain`/`warm_now`) → same crash. The ordering is backwards: the
observability emit should never be able to prevent the state transition it observes. The other emit sites
(RebalanceJob/HandoffJob/LbApply) correctly emit *after* their durable action — this one is the outlier.

**Impact:** One buggy handler turns a warm/drain command into a per-second loop (re-`Shards.drain`, a log line
each tick) until `expire_stale_pending` (default 15 min) marks it `failed`. For a drain, the handoff's `await`
keeps seeing `pending` → premature retry/revert (feeds #7).

**Recommended fix:** Complete the command **first**, then emit; or isolate the emit in `try/rescue` so a handler
crash can't abort the DB write.

### #9. Dead-node unpin compares cross-node wall-clock `last_seen_at` to the leader's clock — NTP skew drives a *destructive* (delete) unpin, or an un-reconcilable zombie pin
**Severity:** Medium | **Category:** Distributed / Data Correctness | **Panels:** 1
**Likelihood:** Low-Medium (NTP hiccup, VM migration, container clock drift) | **Blast radius:** a skewed node's hot pins

**Problem:** `beat/1` stamps `last_seen_at` with the *beating node's* wall clock (`nodes.ex:22`); `alive/1`
compares it to the *leader's* `utc_now() - within_ms` (`nodes.ex:38`); `fleet_p99` uses the same window. This
is the skew class already flagged for `load_samples` (#15) — but here it drives a **destructive** decision, not
a mis-attribution: a node whose clock lags the leader past the residual of `node_stale_ms` is judged dead and
has all its hot pins **deleted** (→ the #1 outage); a fast-clock node writes a future `last_seen_at` and looks
alive forever, so a genuinely-dead fast-clock node's pins are never reconciled. `rebalancer_nodes` is a new
table not covered by the #15 note.

**Impact:** A clock-skewed node either loses its hottest shards to an unnecessary re-home or becomes an
un-reconcilable zombie — on a signal that should be monotonic within one authority.

**Recommended fix:** Stamp + compare `last_seen_at` with a **single authority — the Postgres server clock**:
set it server-side in the upsert (`fragment("now()")` / a column default) and compare against `now()`
in-query, so liveness never depends on cross-node clock agreement. (Pairs with #1's fix and also fixes the
`fleet_p99` freshness window.)

### #11. The `CommandPoller` blocks on the whole batch, so #8's "poll liveness decouples from drain duration" holds only *within* a batch; `on_timeout: :kill_task` is dead config
**Severity:** Low | **Category:** Concurrency / Performance | **Panels:** 2
**Likelihood:** Medium under a storm | **Blast radius:** delayed warm pickup (best-effort), test-only `poll_now`

**Problem:** `do_poll` forces the `async_stream_nolink` to completion via `Enum.reduce`, so the poller can't start
a new batch until the current batch's slowest `drain` (~40s) returns; a `warm` arriving just after a drain batch
begins waits up to ~40s, but the handoff awaits only `handoff_warm_timeout_ms` (30s) — a target loses the warm/
affinity optimization it was picked for. `on_timeout: :kill_task` is meaningless alongside `timeout: :infinity`;
`poll_now`'s 120s call can be exceeded when `⌈N/concurrency⌉ × per-drain > 120s`.

**Impact:** Bounded (warm is best-effort; `poll_now` is test-only), but the decoupling the moduledoc claims
isn't achieved — drain duration still gates warm pickup, eroding the thin margin that feeds #7.

**Recommended fix:** Fire the batch without blocking the poll loop (reschedule immediately; track in-flight
command ids so a running command isn't re-selected), keeping the synchronous consume only for the test
`poll_now`. Drop the dead `on_timeout: :kill_task` or give tasks a real `timeout`.

### #12. `Reporter` does N `File.exists?` + several Postgres round-trips inline; `report_now`'s default 5s call timeout can be exceeded
**Severity:** Low | **Category:** Performance / Reliability | **Panels:** 2
**Likelihood:** Low | **Blast radius:** test flake today; latent tick-time growth

**Problem:** `do_report` now runs, inline in the GenServer, `beat` + `publish` + `prune` + `publish_warm_locations`
(which does `recent_shard_ids` → **one `File.exists?` per recent-hot shard** → `WarmLocations.publish` +

**Impact:** Latent test flake today (`report_now` has no prod callers); the N-`File.exists?`-in-the-GenServer

**Recommended fix:** Give `report_now` an explicit generous timeout (or make it a cast + confirmation); move the
`WarmFollower.cached?` fan-out off the reporter (batch-stat, or have the follower maintain its cached set in ETS
for O(1) reads).

### #13. `shard_warm_locations` indexes the wrong column — `[:shard_id]` is never queried while the real filter (`updated_at`) is unindexed
**Severity:** Low | **Category:** Performance | **Panels:** 3
**Likelihood:** High (every tick) | **Blast radius:** write amplification + unindexed scans on a hot-write table

**Problem:** The migration adds `index(:shard_warm_locations, [:shard_id])` "the policy's read," but no query
filters by `shard_id`: `warm_nodes/1` reads `where updated_at >= ^cutoff` and groups in Elixir; `prune` filters
`updated_at`. So `[:shard_id]` is pure write overhead (the exact "unused index" mistake #18 just fixed for
`shard_load_samples`), while `updated_at` — read every rebalance tick and every reporter tick — is a full scan.
(The unique `[:node_key, :shard_id]` correctly serves the upsert + node-scoped deletes.)

**Impact:** Small (the table is bounded to hot warm-cached shards) but a real index/query mismatch on a
hot-write path, with an index documenting a query the code doesn't implement.

**Recommended fix:** Drop `[:shard_id]`, add `index(:shard_warm_locations, [:updated_at])` (serves `warm_nodes` +
`prune`) — or, if a per-shard read is intended, change `warm_nodes` to `where shard_id in ^hot_ids and updated_at
>= ^cutoff`. Pick one.

### #14. `WarmLocations.publish/2` uses `shard_id not in ^shard_ids`, an unbounded bind-parameter list that can exceed Postgres's 65535 limit at fleet scale
**Severity:** Low | **Category:** Reliability | **Panels:** 3
**Likelihood:** Low (only at very large scale) | **Blast radius:** the affinity signal silently degrades on the busiest fleets

**Problem:** The non-empty `publish` clause deletes stale rows with `where node_key == ^node_key and shard_id
not in ^shard_ids` — one bind parameter per element. `shard_ids` is `recent_shard_ids` (distinct hot shards
across all nodes, up to `load_report_top_n × num_nodes`) ∩ this node's warm cache (`warm_cache_max`). Past 65535
params the `delete_all` raises; the reporter's `try/rescue` swallows it and drops **every** such window, so the
node can never retract stale warm advertisements (they only age out via `prune`). (The empty-list case is
correctly handled by the separate `publish(node_key, [])` clause.)

**Impact:** Bounded and large-scale-only, but when hit it silently degrades the affinity signal on exactly the
busiest fleets (fail-safe: warmth is advisory).

**Recommended fix:** Replace the retract-delete with an **age-based sweep after the upsert** — since `publish`
stamps a fresh `updated_at = now` on every kept/inserted row, `delete_all(where node_key == ^node_key and
updated_at < ^now)` retracts exactly the rows this publish didn't refresh, with a constant 2-parameter query.
(Pairs with #13's `[:updated_at]` index.)

### #15. `Override.changeset` validates the shard_id with `ShardId.valid?` but never canonicalizes (no `cast`), so a mixed-case pin dead-routes
**Severity:** Low | **Category:** Shard Isolation (canonicalization, #19) | **Panels:** 4
**Likelihood:** Low (needs a mixed-case id at the pin boundary) | **Blast radius:** a silent dead pin

**Problem:** `validate_shard_id` (`override.ex:41-45`) calls `ShardId.valid?/1`, which admits uppercase; only
`ShardId.cast/1` downcases to the one canonical value (#19: `ACME` and `acme` are the same shard). A pin written
with `"Acme"` passes validation and `LbMap` renders map key `Acme.fathom.test`; nginx lowercases `$host`, so the
incoming `acme.fathom.test` never matches → the pin silently falls through to the hash pool. Fail-safe (correct
hash-home routing, no misroute) but two routing boundaries disagree on the shard_id rule.

**Impact:** Not a leak — a mixed-case pin is a silent no-op (the hot shard never moves; a reconcile can't find
it), an operability footgun.

**Recommended fix:** Canonicalize at the boundary — `Fathom.ShardId.cast/1` + `put_change(:shard_id, canonical)`
in `Override.changeset` (matching the request path), or reject any non-canonical id so it fails loudly.
