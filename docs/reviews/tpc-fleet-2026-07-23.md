# tpc-fleet re-run — 2026-07-23 (throughput scaling check after the perf iteration)

**Rig:** `deploy/chaos/chaos.sh tpc-fleet "6,12,24" 150 1000` — the exact 2026-07-11
configuration. Extra rigor because the filo wire changes (row fragments, iodata sends) are
ON this path: a same-night image A/B was built from the pre-iteration trees (fathom
`c6f8603` + filo `df685a9`) and run back-to-back with the current image on the same VM.

## What held (the claims the test exists for)

- **The partition carries the throughput**: 42 tenant shards spread across all 3 nodes
  (spread 1.80×), queries recorded per node in proportion — the LB-keyspace-partition
  contract intact on the new code.
- **Low-concurrency per-txn latency matches July**: p50 at 6 tenants was 4.74 ms (current)
  / 4.81 ms (baseline image) vs July's 4.67 ms — the per-request wire path did not regress.
- **End-to-end correctness under a real client**: thousands of TPC-B transactions through
  the LB over the fragment-encoded JSON path, error rates in the same band as the
  documented runs (46/59/247 vs July's 22/56/332 — the known 502/reconnect rig artifact),
  zero node-side exceptions in the logs.

## What did NOT hold — and why it isn't a code signal

Absolute tps tonight was far below July on BOTH images, with huge run-to-run scatter:

| tenants | July 11 | current #1 | baseline | current #2 |
|---:|---:|---:|---:|---:|
| 6 | 17.8 | 14.0 | 17.2 | 746.7 (!) |
| 12 | 39.1 | 26.1 | 24.2 | 12.9 (223 errs) |
| 24 | 40.4 | 27.3 | 33.6 | 39.7 |

- The 746.7 outlier is self-consistent with its own p50 (6 clients ÷ 7.8 ms ≈ 770 tps),
  which exposes what `tpcb_tps` really is: an error-recovery-sensitive composite (driver
  reconnect/backoff dominates whenever the rig throws its documented 502 storms), not a
  clean txn-latency-derived rate. July's own numbers sit ~70× below their p50-implied
  ceiling for the same reason.
- Same-night baseline-vs-current: overlapping p50 bands (4.7–8.7 ms both), interleaved tps
  ranks, comparable error counts — **no code-attributable difference**; the scatter is the
  measurement.
- Both images sitting below July's tps says the VM/host is in a different state tonight
  (this box ran builds, 30k-shard seeds, and benches all day) — a cross-day rig-state
  effect, not a fathom/filo change.

## Addendum — rerun after a colima restart (same night)

The fresh-VM rerun confirms the rig-state hypothesis and restores July-class numbers:

| tenants | txn/s | p50 ms | p95 ms | p99 ms | errs |
|---:|---:|---:|---:|---:|---:|
| 6 | 17.0 | **4.20** | 7.73 | 15.54 | 37 |
| 12 | **56.1** | 6.24 | 7.59 | 10.41 | 22 |
| 24 | 32.1 | 6.38 | 10.23 | 15.72 | 106 |

Spread 1.64× over 3 nodes (42 shards, proportional query split). The 12-tenant step
*exceeds* July's 39.1 tps, and the 6-tenant p50 (4.20 ms) is the best recorded — the
current code is at worst at parity and plausibly ahead, but the harness stays
non-monotonic (12 > 24 in tps) and error-bearing even on a fresh VM, so no fine-grained
claim is made from single runs. The 502-storm investigation (nginx↔Bandit keepalive race,
driver session churn, direct-port isolation) **landed 2026-07-23** — see
`lb-502-fix-2026-07-23.md`, which supersedes the caveat below. At the time of this run it was
still open, so `tpcb_tps` here is a smoke-level signal only.

## Verdict

Throughput-scaling contract intact (partition + flat low-concurrency p50); absolute tps
from this harness is not comparable across days and too noisy tonight for regression
inference — the same-night A/B is flat. If an absolute tps record is wanted, re-run on a
freshly restarted colima with a quiet host; better, prefer the hotspots A/B
(`hotspots-ab-2026-07-23.md`, +13–16% held-stream throughput) as the iteration's
throughput evidence — it has ~50× the sample volume and none of the driver's
error-recovery noise.
