# Jepsen, 2026-10-27: acked writes lost after a three-node kill, on a follower ring

Two 30-minute runs of the bar command from `docs/reviews/jepsen-2026-10-24.md`
(`./run.sh --time-limit 1800 --hard --target mixed --max-concurrent-faults 3 --faults all --shards 16
--rate 120`) on the three-follower ring rig (each node ships to the next three of five, quorum 2,
`SHARD_FLUSH_INTERVAL_MS` 300 s, rebalancer on). **Both were invalid:**

| run | layout | invalid shards |
|---|---|---|
| 1 | replicas on a second block device | 1 of 16 (shard 3) |
| 2 | replicas on the container's root disk (the layout the 2026-10-24 green run used) | 3 of 16 (shards 10, 13, 15) |

So the replica disk is not the cause: the root-disk layout fails too. The 60 s no-fault smoke run
was valid.

## Run 1, shard 3: the mechanism

Elle reported `G2-item-realtime`. The evidence under it is a lost acked write: on key 702, appends
15-18 were acked at 03:05:32-03:05:51Z by fathom5 and read back at 03:05:5xZ; the final read at
03:15:32Z returned `[1 2 3 4 9 10 11 12 13]`.

1. fathom5 acked 15-18, so two of its three followers (fathom1, 2, 3) held them. The flush interval
   is 300 s, so the S3 object did not.
2. At 03:07:49Z the nemesis killed fathom3, fathom1 and fathom5 at once (`kill-majority`), reviving
   them at 03:08:08Z.
3. fathom3 took the shard over at 03:08:24Z (`local copy FORKED from the stored lineage`, then a
   re-pull of the stale object). Its log has **no** `pulled a replica`, no `PROMOTED` and no
   under-quorum refusal for the shard.
4. At 03:09:14Z fathom5 restarted, was "FORKED" in turn (its local copy, which held the writes, went
   to `.db.forked.*`) and promoted a one-frame replica from fathom3's new ownership over the stored
   object.

Why fathom3 saw nothing: `Recovery.peers/0` asks the opening node's OWN follower list. fathom3's is
fathom4, fathom5, fathom1. Recovery's responder floor is `N - Q + 1` over that list, so 3 - 2 + 1 = 2.
fathom5 was the dead owner (its answer is excluded), fathom1 was still booting (silent), fathom4 said
"I hold nothing". With fathom3's own empty answer that is two definite answers: the floor is met,
`choose` returns `:none`, the open proceeds from the stale object. The acked tail sat on fathom5's
followers (fathom1, 2, 3), and fathom2, which held it, was never asked.

The floor only guarantees that a holder is read when N is the dead owner's follower set. The code
documents that as "the symmetric-fleet assumption" (every node follows every other). A ring breaks
it, and a node cannot tell from its own config whether it is in one. The ring was adopted on the rig
on 2026-10-27 (`1c58c4cb`) for a 19% p99 gain; its `rpo` and one Jepsen run passed, which did not
exercise a three-node kill landing on the owner and two of its followers.

Status: the mechanism is established from the node logs, the code, and two regression tests that
fail on the unfixed code and pass on the fix. Run 2's three invalid shards (10, 13, 15) were traced
only partly (their losses cluster at 03:22Z, after a kill / isolate / S3-fault window, with
`FORKED` then `PROMOTED` events), so they are not shown to be this mechanism. What was shown is the
outcome: with the fix, the same command was **valid on both layouts**.

| run | code | replicas on | result |
|---|---|---|---|
| 1 | unfixed | second disk | invalid (1 of 16 shards) |
| 2 | unfixed | root disk | invalid (3 of 16 shards) |
| 3 | `5f9566df` | root disk | **valid**, exit 0, 16 of 16 |
| 4 | `5f9566df` | second disk | **valid**, exit 0, 16 of 16 |

`rpo` (`./chaos.sh rpo`, 5 s flush, second-disk layout, unfixed code) passed. Two valid runs against
two invalid ones is evidence, not proof: the nemesis is random. Runs 3 and 4 had 11 and 10 expected
`clock lags the store` lines (the run steps the clock on purpose).

## The fix

`REPLICATION_RECOVERY_PEERS` (`:replication_recovery_peers`): the nodes a takeover asks. Unset keeps
the old behaviour (own followers), which is correct for a full mesh or `REPLICATION_MEMBERSHIP=roster`.
Set it to every other node whenever `REPLICATION_FOLLOWERS` is a subset. The rig now sets it on every
node. Tests: `replication_recovery_test.exs` ("a holder that is not one of this node's followers is
asked and pulled") and `recovery_underquorum_test.exs` ("the floor is counted over the recovery
peers"). Both fail without the change.

## The guard

A node cannot tell from its own config whether its follower list is every other node, so unset
recovery peers on a ring is a silent hazard. In prod (`:replication_recovery_guard`, on by default
there, off in dev/test) a node that ships, listens, and runs promote-on-open with peer recovery
REFUSES TO BOOT unless one of these is set: `REPLICATION_RECOVERY_PEERS` (every other node),
`REPLICATION_RECOVERY_SYMMETRIC=true` (an operator's claim that the follower list already is every
other node), `REPLICATION_MEMBERSHIP=roster`, or peer recovery / promote-on-open is switched off
(`Fleet.recovery_peers_problem/0`, `replication_recovery_guard_test.exs`). Existing prod deployments
with a full mesh must add `REPLICATION_RECOVERY_SYMMETRIC=true` on upgrade. Roster membership is
exempt although it falls back to the static list when the roster is too small; that gap is not
closed here.
