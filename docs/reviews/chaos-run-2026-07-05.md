# Chaos run — 2026-07-05

First end-to-end run of the Docker chaos rig (`deploy/chaos/`): the "failover
time + loss window" layer of `docs/deploy-cluster.md` § Chaos testing that the
in-process cluster suite (`test/fathom/cluster/`) can't measure. Three prod-release
fathom nodes behind nginx (`hash $host consistent`), one MinIO bucket (lease store
+ bottomless backend) reached through per-node toxiproxy proxies, one Postgres.

**Reading these numbers:** all timings are **relative** — one host, loopback MinIO,
shared CPU/disk. **30 ms each-way S3 latency was injected** (`./chaos.sh latency 30`)
so failover reflects a plausible S3 RTT rather than loopback. Rig knobs shorten the
clocks for fast iteration: `SHARD_LEASE_TTL_MS=10000`, `steal_margin_ms=5000` (default,
the clock-skew guard), `SHARD_FLUSH_INTERVAL_MS=5000`, `SHARD_IDLE_MS=20000`.

## Result summary

| Scenario | Outcome | Key invariant |
|---|---|---|
| Smoke (5 tenants via LB) | PASS | every tenant `foreign=0` — no cross-shard leak |
| Kill-failover (held shard) | 15.0 s to first acked write on a survivor | TTL + steal margin bounded; flushed data survived |
| Failover (idle-released shard) | 2.1 s | no held lease to wait out — LB reroute + open only |
| Pause-fence (frozen zombie) | PASS | zombie self-fenced; no split-brain |
| Node↔S3 partition | PASS | fail-closed (flushes refused); recovered on heal |
| Soak (100 s, 4 node kills) | 584 acked / 584 stored / **0 lost**, 0 leaks | no acked write lost, isolation held through churn |
| Warm-standby promotion | `result=hit` | survivor opened warm (304, no body transfer) |

## What each scenario showed

### Kill-failover — TTL-bounded, no data loss
Silent node death (network-disconnect **then** kill, so peers see a hang, not a clean
socket RST). Wrote a row, waited one flush interval (durable in S3), killed the owner
(fathom3), drove writes through the LB until a survivor served one.

- **15,012 ms** to first acked write on the survivor (fathom1). This decomposes as
  TTL (10 s) + `steal_margin_ms` (5 s) + cold-open (tens of ms): a survivor may not
  steal until the dead owner's heartbeat age exceeds TTL **plus** the clock-skew steal
  margin. That is the failover-stall ceiling, and it behaved exactly to spec.
- `rows pre=1 → post=2`: the pre-kill **flushed** row survived and the new write landed.
  No loss beyond RPO (committed-but-unflushed).
- Contrast: a shard whose owner had already gone idle (past `SHARD_IDLE_MS`) and
  **cleanly released** its lease failed over in **2,124 ms** — no held lease to wait
  out, just the LB reroute + open. So RTO is TTL-bounded only when the owner dies
  *while holding* the shard.

### Pause-fence — the frozen-not-dead zombie self-fences
`docker pause` the owner (fathom2) with a **dirty, unflushed** write (seq=300) in its
local copy, waited past TTL + margin, forced a survivor (fathom1) to steal by writing
seq=400 to its direct port (passive LB health can't see a frozen-but-listening node —
the documented OSS-nginx limitation; the direct write stands in for active health
checks / operator action). Then unpaused the zombie.

The zombie's own logs on unpause:

```
heartbeat lapsed for fathom@…#… (generation 1); coordinators will revalidate
shard pf3: durability flush skipped, ownership unconfirmed
shard pf3: ownership unconfirmed before flush; keeping local copy
```

- Survivor's post-steal write (seq=400) **present = 1**.
- Zombie's dirty write (seq=300) resurrected = **0**.

The zombie detected its heartbeat had lapsed (frozen longer than TTL) and, before its
next durability flush, re-checked ownership, found itself superseded, and **kept its
local copy without uploading** — the self-fence. Single-writer held across the zombie's
flush; no split-brain.

### Node↔S3 partition — fail-closed, then recovers
Disabled fathom2's toxiproxy S3 proxy for 25 s. Its heartbeat renews failed
(`econnrefused`) and every open coordinator refused its durability flush:

```
heartbeat renew failed …: %Req.TransportError{reason: :econnrefused}
shard partsh: durability flush skipped, ownership unconfirmed
shard echo1: ownership unconfirmed before flush; keeping local copy
```

A node that can't renew its heartbeat stops writing, so a remapped/stolen shard can
never be double-written. After the proxy was restored the node resumed serving — a
post-heal write + read returned the correct row count.

### Soak — zero loss, zero leaks through churn
100 s of round-robin writes across 6 tenants through the LB, killing a random node
every ~25 s (4 kills total: fathom2 ×3, fathom3 ×1), then a settle + audit.

- **584 acked, 584 stored, 0 lost.** During each steal window (~15 s) writes to the
  affected tenants failed and so were never acked; every write that *was* acked
  survived. The committed-but-unflushed RPO window caught nothing at this workload's
  cadence.
- **0 foreign rows** in every tenant — isolation held through all four kills.

### Warm-standby promotion — the A1 path under real failover
All nodes ran `WARM_FOLLOWER=true`. Confirmed the warm caches populate: every node
held `<shard>.db` + `<shard>.db.etag` sidecars for the recently-active set. Attached a
one-shot telemetry→log handler (`[:fathom,:shard,:warm,:promoted]`, which is telemetry
with no default log line) and opened an idle-dropped, warm-cached shard on a
non-owner:

```
RIG-WARM-PROMOTED shard=wq result=hit
```

`result=hit` = the follower cache was storage-current and was promoted via the
conditional 304 GET, **no full body transfer** — the warm-standby win, now observed
live (it was previously only in the `failover_rto` bench, ~2.3× at 1 MB / 30 ms).

## Findings

1. **Boot fence probe rejected MinIO's ETag escaping** (fixed this run, commit before
   the rig lands). The `CopyPartResult` ETag parser accepted `&quot;` (AWS) or a literal
   quote but not MinIO's numeric entity `&#34;`, so the round-2 #4 fail-closed guard
   fired on a false negative and the node refused to boot against a store whose
   conditional writes are fine. Widened the alternation + regression test
   (`copy_part_etag/1`). This is exactly the kind of real-store gap the in-process
   `FaultyStorage` double can't surface — the value of running against MinIO.

2. **The warm follower re-warms shards this node is home for** (fixed in a follow-up
   commit same day). The live exclusion (`owned_shards`) skips a shard only while a
   coordinator holds it; on idle-drop the lease is released, so the home node re-warmed
   its own just-dropped shards — pure waste, since a shard only fails over *away* from
   its home. (The *other* two nodes caching it is correct standby behavior.) Fix: the
   follower now also excludes shards it owned within `:warm_home_retention_ms` (default
   60 s), so a routine idle→reopen never re-warms the home set while a genuine LB remap
   still lets the shard become a warmable failover target. Not a correctness issue —
   an efficiency one against the `:warm_cache_max` budget.

## No hot-spot evidence yet
The soak load was synthetic round-robin, so it produced no organic hot-spot signal for
the dynamic-rebalancing (B) detection policy. `Fathom.ShardLoad` mechanics could be
exercised here, but a load pattern we invented can't substitute for real-traffic
evidence. B stays gated on that.

## Reproduce

```bash
cd deploy/chaos
./chaos.sh build && ./chaos.sh up
./chaos.sh latency 30
./chaos.sh smoke
./chaos.sh failover fo1
./chaos.sh pause-fence pf1
./chaos.sh partition fathom2 25
./chaos.sh soak 100
./chaos.sh down
```
