### #1 — FIXED

`PRAGMA busy_timeout` routes to `sqlite3_busy_timeout()`, which **replaces** exqlite's custom busy
handler (installed unconditionally at `sqlite3_nif.c:497`) with SQLite's default `sqlite3OsSleep`
loop — which polls neither the interrupt flag nor exqlite's cancel flag. Verified in the dep source;
exqlite's own `set_busy_timeout/2` docstring warns about exactly this.

Fix, three parts:
- `connection.ex` `open/1`: `Sqlite3.set_busy_timeout(conn, 5000)` in place of the pragma.
- `connection.ex` watchdog: `Sqlite3.cancel/1` in place of `Sqlite3.interrupt/1`. `cancel` is a
  superset — sets the flag the busy handler polls *and* calls `sqlite3_interrupt` — and is a
  **non-dirty** NIF that avoids the connection mutex, so it can't block behind the running query.
- `shard.ex` `checkpoint/1`: same pragma→function swap on the drop path.

**Timing is unchanged by construction**: exqlite's handler walks the same delay ladder
(`{1,2,5,10,15,20,25,25,25,50,50}` then 50 ms) as SQLite's default. It additionally aborts when the
caller process is dead — a dead Hrana stream's wait used to sleep the full 5 s.

Regression test (`test/fathom/query_bounds_test.exs`): one stream holds `BEGIN IMMEDIATE` + a write,
a second stream writes under `:query_timeout_ms: 200`.
- **Pre-fix: 5451 ms** (the full busy timeout), assertion failed.
- **Post-fix: sub-200 ms**; the whole file went 5.6 s → 0.4 s.

The pre-fix run is the sharpest evidence for the finding: the timeout was *reported*
(`FILO_QUERY_TIMEOUT` came back) but never *enforced* — so the existing error-code coverage could
not have caught this.

Correctness/reliability: strictly better. Same timeout value, same wait ladder, restores a
cancellation path that shipped in the dep but was disabled. No durability surface touched.

Deliberately **not** included: lowering the 5000 ms value (the review lists it as a separate
consideration, gated behind this fix landing first).

### #3 — FIXED (scope widened twice on Fable rulings; **found 2 latent data-loss bugs**)

The finding: `if wrote?(result, sql) or ends_transaction?(sql), do: bump(shard_id)` dirtied the shard
on **any** COMMIT, so Django's `ATOMIC_REQUESTS` read views paid a full VACUUM INTO + full-object PUT
every 5 s.

Implemented a per-connection "wrote since BEGIN" flag (process dictionary keyed by conn ref — the
same single-owner idiom as the statement cache and the deadline watchdog) and gated the boundary
bump on it. Then hit two problems that widened the scope. **Both were escalated to a Fable agent per
the run directive, and both rulings were followed as given.**

**Ruling 1 — widen to reorder `wrote?/2`.** My first cut only helped connections that had never
written: `sqlite3_changes()` is not reset by SELECT/BEGIN/COMMIT/ROLLBACK, so on a persistent
connection a COMMIT inherited `changes>0` and classified as a write *before* the flag was consulted.
Since Django's recommended `CONN_MAX_AGE` keeps connections alive across requests, that is the
primary production topology and the finding's value lived there. Fable ruled **A: reorder**, as a
three-part package, and in doing so **found a data-loss bug I had just introduced**:

- **Hole 2 (mine, caught before it shipped):** `rolls_back?/1` matched any `rollback` prefix, so
  `ROLLBACK TO <savepoint>` — which does *not* end the transaction — deleted the flag. Sequence
  `BEGIN; INSERT; SAVEPOINT s; <0-row UPDATE>; ROLLBACK TO s; <flush>; COMMIT` then skipped the
  boundary re-bump and lost the INSERT on idle drop. That is Django's nested-`atomic()`-raises,
  outer-block-commits shape. Fixed: only a rollback *without* ` to ` clears the flag.
- **Hole 1 (pre-existing, latent):** `RELEASE` is a control statement but not `ends_transaction?`, so
  a savepoint-only client (`SAVEPOINT a; INSERT; <0-row UPDATE>; RELEASE a`) never re-dirtied at its
  commit boundary — a straddling flush advanced the watermark past the uncommitted rows and the idle
  drop deleted them. Fixed: `commit_boundary?/1` = `ends_transaction?` **or** `releases_savepoint?`,
  and RELEASE deliberately does **not** clear the flag (an inner release commits nothing, so the
  outer COMMIT must still be able to re-bump).

**Ruling 2 — the read-verb whitelist.** After the reorder, a plain `SELECT` on a written-on
connection *still* inherited `changes>0` and re-dirtied (and poisoned the flag, so the COMMIT
re-bumped too). I proposed the inverse predicate — "returns columns and is not `dml?` ⇒ read".
**Fable disqualified it as a data-loss bug**, correctly: `dml?/1` is leading-keyword only and its own
comment documents that it does not detect a CTE-prefixed write, so
`WITH x AS (...) INSERT INTO t ... RETURNING id` would have classified as a read, left the shard
clean, and had its committed rows deleted by `drop_clean`. Ruled **C in whitelist form**: ignore the
inherited counter only for verbs *provably* incapable of mutating the file — `select`, `values`,
`explain`. Anything unrecognized falls through to the conservative path, so the failure direction is
always an extra flush, never a lost write. **`with` must never be added**; there is now a test whose
stated job is to fail if anyone converts the whitelist back to a blacklist.

Final `wrote?/2` order: `control_statement?` → `cols != [] and read_verb?` → `changes > 0` →
`cols != []` → write. The RETURNING fix is preserved untouched (`INSERT … RETURNING` is neither
control- nor read-verb-prefixed, so it still reaches `changes > 0`), as are durable PRAGMA
assignments (`user_version` is deliberately not `control_statement?`).

Tests added (all 5 fail pre-fix on the behaviour they pin): read-only txn on a fresh connection;
read-only txn on a **persistent** connection that already wrote (the finding's real acceptance
test); savepoint released across a flush survives drop; `ROLLBACK TO` savepoint does not discard the
outer write; CTE-prefixed `INSERT … RETURNING` dirties and survives drop; whitelisted verbs stay
clean on a written-on connection. Suite 904 → **910**.

### #20 — FIXED

Four hand-written queries filter Oban jobs by the shard id inside `args`, and none could use an
index. Oban's own GIN index on `args` is `jsonb_ops`, which serves containment (`@>`) but **not** the
`->>` extraction these use — which is exactly why Oban's *own* uniqueness check (`args @> $1`) is
fast while these were not — and there was no index on `worker` either.

Migration `20260725064847`: `CREATE INDEX CONCURRENTLY … ON oban_jobs (worker, (args->>'shard_id'))
WHERE state IN (…)`. `(args->>'shard_id')` is immutable so it is index-legal, and the partial
predicate keeps the index the size of the **live** job set rather than the Pruner's 7-day retention.
The state list is the union of `Migrator.@unique_states`, `RebalanceJob.@handoff_live_states`, and
the tighter list in `Tenants` — all subsets, so all four call sites are served.

Verified against the **real** query shape (worker + state ANY + shard-id ANY, as
`enqueue_unique_chunk/1` emits it), with `enable_seqscan = off` to force the planner to reveal
whether it *can* use the index on a small table:

    Index Scan using oban_jobs_worker_shard_id_live_index
      Index Cond: ((worker = …) AND ((args ->> 'shard_id') = ANY (…)))

Both predicates land in the Index Cond, not as a post-filter — which is the property that matters.

### #18 — FIXED

`Sqlite3.last_insert_rowid/1` is `ERL_NIF_DIRTY_JOB_IO_BOUND` — a full dirty-scheduler dispatch —
and ran on **every** statement, while `to_stmt_result/2` discarded it for every read-only one. On a
plain `SELECT` that was roughly a quarter of the query's dirty-IO dispatches spent on a value nobody
reads, against the `+SDio` pool #2 resized.

Now gated on `dml? or columns == []`, which is **exactly** `to_stmt_result`'s own `not read_only?`
(`read_only? = cols != [] and not dml?`) — so what a client sees is byte-identical. `dml?` was
already computed in `do_execute`, and `columns` is now available before stepping thanks to #17, so
the predicate costs nothing new.

`num_changes` stays **unconditional**, deliberately: `wrote?/2` checks `changes > 0` first and the
durability classifier's over-dirtying depends on it. Narrowing that too would be a durability change,
not a perf one.

Tests pin the client-visible contract rather than the internal call: an `INSERT` still reports its
rowid, `INSERT … RETURNING` (columns *and* a mutation) still does, and a read on a connection whose
`sqlite3_last_insert_rowid` still holds a prior write's value reports `nil`.

### #17 — FIXED

`Sqlite3.columns/2` ran on every execution of a cached prepared statement. It is
`ERL_NIF_DIRTY_JOB_IO_BOUND` despite doing no I/O, and allocates a fresh binary per column — so a
20-column Django `SELECT` paid one dirty-scheduler dispatch plus 20 immediately-garbage binaries per
execution, for a value that is a property of the *compiled statement*, not the execution. The
2026-07-23 audit's statement cache removed the per-execution `prepare_v2`; this is the half it left
behind, and it directly relieves the `+SDio` pool from #2.

Columns are now read once at prepare and carried in the cache entry
(`{canonical_sql, stmt, cols, stamp}`).

**The invalidation is the load-bearing part.** `prepare_v2` transparently recompiles a cached
statement on a schema change, so the *statement* stays valid — but the cached column list does not.
Without a purge, `SELECT *` after `ALTER TABLE … ADD COLUMN` would report pre-ALTER columns while
returning post-ALTER rows: a silently wrong result shape, strictly worse than the cost being saved.
`Connection.purge_statements/1` is called on DDL in the query path (using the `ddl?` classification
`do_execute` already computes, so no new per-query work) and unconditionally after any `exec` script,
which is opaque and may contain DDL.

Verified the purge is load-bearing rather than defensive: disabling it makes the new test fail with
a stale column list.

### #16 — FIXED

Bandit defaults `compress: true`, so any client advertising `accept-encoding: gzip` — reqwest (the
Rust libSQL SDK), undici/`fetch` (JS), Python `requests`/`httpx`, all by default — made **every**
`/v2|v3/pipeline` response pay a full open→deflateInit→deflate→deflateEnd→close cycle, which is
init-dominated at kilobyte JSON sizes, for a hop that is usually a datacenter LAN.

**Every measurement in this repo was blind to it.** `Filo.Client` sends only `content-type`, so
neither chaos driver ever advertised an encoding — the whole `tpc-fleet` / `tpcc-fleet` / `hotspots`
corpus measured the *uncompressed* path. Real SDK traffic did not. The test therefore asks for gzip
explicitly, which is the only way the cost is observable at all; verified discriminating by flipping
the flag back to `true`.

Moved to nginx (`gzip on; gzip_types application/json; gzip_min_length 1000;` in both configs),
where it happens once and can be size-gated — Bandit has no `gzip_min_length` equivalent, so it was
compressing replies too small to benefit. Wire-transparent: the client still receives
`content-encoding: gzip`.

Worth noting for future readers: production images are `erlang-27.3.4`, so `:zstd` is unavailable
and gzip was selected; a dev machine on OTP 28+ would have picked zstd instead. **Dev and prod were
taking different code paths here.**

### #15 — FIXED

`Reconcile.run/1` did `Directory.all() |> apply_limit(...)` — `Repo.all(Shard)` with no LIMIT and no
stream, then `Enum.take` in Elixir. So `mix fathom.directory --limit 100` still pulled every row, and
a `Directory.Shard` struct carries 16 fields (7 `utc_datetime_usec`) plus Ecto meta: ~400–600 MB as
structs at 1M rows, ~1.5–2 GB at the 3.1M the probe script uses. **An OOM in the BEAM, not a slow
query** — and this is the documented DR-completion step ("run it with `--fix` after a Postgres
restore, before reopening traffic"), so it failed exactly when the fleet was already down.

Added `Directory.all_paged/1`, a keyset `Stream.resource` over `where: shard_id > cursor, order_by:
asc, limit: page` — served by the existing unique index, peak memory `O(page)` instead of `O(fleet)`
— and `:limit` is now `Stream.take`, so it genuinely bounds the work.

One deliberate behaviour change: the `deleted` set for the tombstone check now comes from
`Directory.deleted_shard_ids/0` rather than from the walked rows. The stream is consumed once
(rebuilding the set would mean a second full walk), and this is also **more correct under `:limit`** —
previously only deleted rows *inside the limit window* counted, so a storage tombstone whose
directory row fell outside it was reported as missing. That query selects ids only (binaries, not
structs) and is index-served thanks to #12.

Tests cover the boundary that breaks hand-rolled cursor loops — a final page that is exactly full,
where the walk must issue one more query and get an empty result rather than stopping early or
looping — plus ordering, no-duplicates, and laziness.

### #14 — FIXED

Finch defaulted `conn_max_idle_time` to `:infinity`, so a pooled connection was never proactively
retired and **S3 became the closing side** — a checkout landing ahead of the server's FIN hands out
a dead socket.

The failure is asymmetric, which is what made it matter: `:safe_transient` retries GET/HEAD only,
`download/4` deliberately rolls its own retries, and **the flush PUT is retried by nobody**. A raced
`:closed` aborts the idle drop, the coordinator keeps the local file *and* the lease, and the
tenant's RPO window extends by a whole backoff interval.

- `conn_max_idle_time: 15s` — under S3's ~20s idle close, so fathom is always the closing side. Same
  discipline as the LB's `keepalive_timeout` vs Bandit's idle close.
- `conn_opts: [transport_opts: [timeout: 3000]]` — a hung connect otherwise sat for the library
  default.
- `S3_POOL_SIZE` / `S3_POOL_COUNT` / `S3_CONN_MAX_IDLE_MS` in `runtime.exs`. The shipped 200/1 is
  the measured knee on the **localhost MinIO rig**; real S3 differs, and there was previously no way
  to tune a deployment without a rebuild. Verified both ways: set → parsed, unset → `nil` so the
  module default applies.
- `retry_delay` 1000 ms → 50/200/800. Req's `exp_backoff` is sized for public-internet APIs; against
  a same-region S3 whose whole cold-open budget is ~1 RTT (~26 ms at 10 ms one-way), one transient
  blip on a retried GET was a ~40× p99 spike.

**Deliberately NOT done:** adding Req-level retries to the flush PUT. It is `If-Match`-fenced, so a
blind re-issue would replay a conditional write with a stale etag. The coordinator's own backoff is
the correct retry tier — this only reshapes the delay for retries Req already performs.

### #11 — FIXED

SQLite's `sqlite3RunVacuum` gives the destination pager the source connection's `safety_level`, so
`VACUUM INTO` at `synchronous=FULL` force-fsynced a full shard-sized temp that
`snapshot_and_upload/1` unlinks seconds later. At ~640 KiB/shard × 1,000 write-active shards that is
~128 MB per interval of pure-waste synchronous device writes.

`PRAGMA synchronous=OFF` on the **snapshot connection only**. The temp has no durability
requirement — it is read back in-process for the Content-MD5 and the PUT, and a crash mid-snapshot
just leaves the shard dirty to re-snapshot next interval; the durable artifact is the S3 object,
still gated by `content-md5` over the same bytes. `VACUUM INTO` takes only a **read** transaction on
the source, so the live shard's WAL + per-commit `synchronous=FULL` is untouched.

**Emphatically not** applied to `checkpoint/1` — a checkpoint at `synchronous=OFF` can corrupt the
main database on power loss. The new test pins the blast radius rather than the speedup: a serving
connection must still report `synchronous = 2` (FULL) both before and after a flush, and so must a
freshly-opened one. That is what fails if anyone later "simplifies" this by hoisting the pragma into
`Connection.open/1` or onto the checkpoint connection.

### #7 — FIXED

`keepalive` is nginx's **per-worker** idle-connection cache; past it, nginx closes the LRU
connection. At 64 with `worker_processes auto` (12) that is 768 cached connections against a
1024–4096 concurrent-tenant target, so a request arriving after its tenant's connection was evicted
paid a fresh handshake plus a fresh trip through the node's accept path.

- Both configs: `keepalive` 64 → **512**, plus `keepalive_requests 100000`. nginx's default of 1000
  recycles a pooled connection roughly once a minute at measured rates, re-opening the FIN race the
  2026-07-23 502 fix closed only for the *idle* case. Two different races; only one was fixed.
- `worker_connections` 4096 → **16384**. Each proxied request consumes **two** connections
  (downstream + upstream), so 4096 capped a worker near 2048 concurrent proxied requests.
- **The inversion:** `LbMap`'s pin-upstream template rendered `keepalive 16` — a quarter of the
  general pool. A shard reaches a pin *because* `Policy` found it the hottest thing on the fleet, so
  becoming hot cut that tenant's connection reuse 4×. Now 512, from a shared module attribute, with
  a test that fails if the pin is ever sized below the pool again.

Also regenerated `deploy/chaos/lb-runtime/exceptions.conf`, which was checked in carrying the
pre-502-fix `keepalive 16` with no `keepalive_timeout` — the review flagged it as a stale generated
artifact the next rig run would have started from.

### #6 — FIXED (config landed and proven to boot; shed A/B is **NEEDS-RIG**)

`hrana_listener/0` passed no `thousand_island_options` at all, so all 100 acceptors contended on
**one** listen socket with **one** 1024-slot kernel accept queue. Now 4 listen sockets with
`reuseport: true` and `backlog: 4096` — ThousandIsland's documented multi-queue path, safe here
because every socket belongs to one BEAM node started together (the SO_REUSEPORT rebalance hazard
needs *separate* processes).

**Config-gated deliberately.** ThousandIsland *fails startup* if `reuseport` is unsupported, so a
hardcoded value is a boot-loop hazard on an exotic kernel; `:hrana_listen_sockets = 1` falls back to
a single socket with no `reuseport`, and a test pins that the fallback really does drop the option.

The test boots a **real Bandit listener** with exactly these options and connects to it, rather than
asserting on a keyword list — the failure mode being guarded against is "the platform refuses this
option at startup", which only a real bind can catch. Confirmed working on this platform.

Documented, not silently assumed: a backlog above the OS `somaxconn` is **silently clamped**, so
raising `net.core.somaxconn` is a node-provisioning step this cannot do for you.

**NEEDS-RIG:** the payoff claim — that deeper, spread accept queues remove the SYN-drop →
1 s-retransmit → 15 s-client-timeout chain behind the 4096-tenant shed — needs
`chaos.sh tpcc-fleet` at 2048/4096 with `/proc/net/netstat` ListenOverflows diffed before/after.

### #4 — FIXED

Nothing truncated the WAL in steady state except SQLite's autocheckpoint, which runs **inline
inside a committing tenant statement** — a p99/p999 spike billed to an arbitrary client query, with
a main-database fsync under `synchronous=FULL`. And the durability snapshot's `VACUUM INTO` is a
long-lived reader that *holds that checkpoint back*, so the WAL kept growing past the threshold and
whichever tenant eventually won the race paid a larger checkpoint than the default implies.

- The coordinator now runs `PRAGMA wal_checkpoint(PASSIVE)` on the snapshot connection after a
  successful `VACUUM INTO` — where no client is waiting, and after the read transaction that was
  blocking the checkpointer has ended. PASSIVE never blocks writers and never waits on readers, so
  it cannot add latency to a concurrent tenant; a `busy` result is ignored and the next interval
  retries.
- `wal_autocheckpoint` raised 1000 → 4000 on serving connections, so the coordinator wins the race
  in steady state. **Raised, not disabled** — at 0 a wedged coordinator would let the WAL grow
  unbounded; this keeps a backstop.

Measuring this took two corrections worth recording. First observable was "the WAL shrinks" —
**wrong**: a PASSIVE checkpoint resets the write position and reuses the space, it does not truncate,
so the file size is unchanged and the test failed against working code. The real observable is that
the WAL **stops growing**: the next batch of writes overwrites from the start. Verified
discriminating — with the checkpoint disabled the WAL goes **2022952 → 4033512 bytes** across one
flush cycle; with it, flat.

Second: my first attempt to verify that discrimination silently no-opped, because `mix format` had
split the line I was pattern-matching on, so the "removal" matched nothing and the restore appended a
duplicate. The test appeared to pass without the fix. Re-done properly.

### #5 — FIXED (Fable ruled **Option C**; the review's own proposal was rejected as an auth bypass)

Escalated per the run directive because this is a security path. **The review's recommended fix was
unsafe and Fable rejected it.** Its proposal was to bulk-load the revoked set and answer from it;
but absence from that set proves only what the *directory* says, and a Postgres PITR can lower
`token_version` — so a genuinely-revoked shard reads as unrevoked there. Only the durable per-shard
storage floor catches that, and only the cold-miss `read_through` consults it. Answering a miss from
bulk completeness would accept a revoked token. The review's fallback (raise the TTL 30 s → 300 s)
was also rejected: it doesn't change the scaling, and it *widens* the missed-notification window 10×.

**Option C, implemented:** a periodic bulk refresh (`Directory.revoked_floors/0`, one bounded query,
served by a new partial index `WHERE token_version > 1`) applies every revoked floor through the
existing monotonic `put_max/3`, then writes a freshness marker **last** so it can never vouch for
unapplied data. A lapsed entry is served while that marker is fresh — **but the marker extends
freshness for entries that already exist, never for an absent one.** A miss always takes the full
`read_through`, storage-floor union included, byte-identical to before.

Steady state goes from `distinct_shards_per_node / TTL` reads (~3,300/s at 100k shards/node) to one
query per node per interval, plus one cold-miss read per shard per node *lifetime*. Independent of
shard count. Every safety path — monotonic guard, storage DR union, stale-serve fallback,
`:hrana_revocation_on_error` posture — is untouched; a failed bulk query just doesn't advance the
marker and the module degrades to exactly its previous behaviour.

Five tests, led by the **bypass regression**: with a fresh marker, no cache entry, directory
`token_version = 1` and storage floor 5, the floor must still resolve to 5. **Verified
discriminating** — simulating the unsafe design (letting a fresh marker answer a miss) fails it,
along with the pre-existing PITR test. That pair is the guard on this whole decision.

### #10 — FIXED

`schedule_flush/1` re-armed unconditionally, so a coordinator with zero connections and nothing
unflushed woke every ~5 s forever: a timer-wheel insert, a `:rand` call, a message send + dispatch,
an ETS lookup, and a heap touch that defeats page-out. ~6,000 wakeups/s at 30k coordinators/node,
and — the bigger cost — it made `hibernate_after` (#9) unusable at *any* value, since a message
always arrived within one interval.

Such a coordinator is **provably unwritable**: `WriteCounter.bump/1` is reachable only from
`ShardExecutor.run_statement/3` and the abnormal-stream-death path, both of which require a
checked-out connection. Verified by grepping every bump site.

- `schedule_flush/1` gains a `map_size(conns) == 0` clause: re-arm only if `unflushed?`, else cancel.
- The `:checkout` **grant** re-arms if the timer is nil. Deliberately the grant, not the checkin, so
  the timer is live for the entire window in which a connection can write.

Self-quiescing rather than instant: the already-armed timer fires once, observes idle+clean, and
declines to re-arm. So the cost of going idle is at most one extra wakeup, not one per interval
forever. RPO is unchanged — the contract bounds loss of *acknowledged* writes, and this state has
none and can acquire none; a dirty coordinator keeps ticking exactly as before.

Tests: idle+clean carries no timer and the checkout grant re-arms it; idle-but-**dirty** keeps
ticking (the guard against over-applying the optimization). The pre-existing jitter test was
updated to hold a connection — it had been asserting on coordinators that are now correctly
timer-less, and holding a stream is both the realistic case jitter exists for and coverage of the
re-arm path. Suite 910 → **912**.
