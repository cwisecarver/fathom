## Open observations

- **The intermittent suite failure — NAMED AND DIAGNOSED (2026-07-25).**
  `Fathom.Migrator.ShardMigrationTest` — *"the write-age guard sees touches still sitting in the
  Recorder buffer"* (`test/fathom/migrator/shard_migration_test.exs:395`). Seen 3 times across ~35
  full-suite runs; passes 6/6 in isolation at different seeds.

  **Root cause (test isolation, not a product bug).** The test buffers a touch with
  `Directory.Recorder.record/1` and asserts the revert write-age guard sees it. `Recorder` is an
  app-global singleton with a ~1s flush timer, shared by the whole suite. Its `drain/1`
  (`recorder.ex:182-186`) **removes** entries from ETS via `:ets.take`, and `restore/1`
  (`:171-177`) only puts them back **on failure** — so between the take and the Postgres commit
  there is a window in which the buffered touch is in neither ETS nor Postgres. If the periodic
  flush lands in that window, the guard sees no buffered touch and no persisted row, permits the
  revert, and the assertion fails.

  That accounts for every observed property: order-dependent, ~1-in-12, invisible in isolation
  (nothing else is driving the Recorder), and seed-insensitive within the file.

  **Not fixed here, deliberately.** It is a pre-existing test-isolation flaw against a global
  singleton, unrelated to this performance audit, and the fix is a test-harness change (isolate the
  Recorder per test, or have the test drive `flush/0` deterministically rather than racing the
  timer). Explicitly NOT papered over with a sleep, retry, or timeout bump.

  Earlier chase, before it was named: ~25 clean runs across 3 seeds, 6 `precommit` runs, 6 targeted
  `command_poller_test` runs, 4 seeded `shard_durability_test` runs, and an 8-iteration loop.
  Note for whoever picks it up: `precommit` does not tee its output, which is why the first two
  sightings were lost; and zsh `noclobber` silently blocks a repeated `>` redirect in a retry loop,
  so use `>|`.

- **The bench gate's single-sample baselines produce false blocks on `fanout_kb_per_shard`.**
  Twice this run the gate blocked on a >20% "regression" measured against a parent baseline that was
  itself a single-run outlier — #4 (`dir_resolve` +27.8% vs a 144 µs low) and #30

### #1 — FIXED

`PRAGMA busy_timeout` routes to `sqlite3_busy_timeout()`, which **replaces** exqlite's custom busy
handler (installed unconditionally at `sqlite3_nif.c:497`) with SQLite's default `sqlite3OsSleep`
loop — which polls neither the interrupt flag nor exqlite's cancel flag. Verified in the dep source;
exqlite's own `set_busy_timeout/2` docstring warns about exactly this.

Fix, three parts:
- `connection.ex` `open/1`: `Sqlite3.set_busy_timeout(conn, 5000)` in place of the pragma.
- `connection.ex` watchdog: `Sqlite3.cancel/1` in place of `Sqlite3.interrupt/1`. `cancel` is a
  superset — sets the flag the busy handler polls *and* calls `sqlite3_interrupt` — and is a
  **non-dirty** NIF that avoids the connection mutex, so it can't block behind the running query.
- `shard.ex` `checkpoint/1`: same pragma→function swap on the drop path.

**Timing is unchanged by construction**: exqlite's handler walks the same delay ladder
(`{1,2,5,10,15,20,25,25,25,50,50}` then 50 ms) as SQLite's default. It additionally aborts when the
caller process is dead — a dead Hrana stream's wait used to sleep the full 5 s.

Regression test (`test/fathom/query_bounds_test.exs`): one stream holds `BEGIN IMMEDIATE` + a write,
a second stream writes under `:query_timeout_ms: 200`.
- **Pre-fix: 5451 ms** (the full busy timeout), assertion failed.
- **Post-fix: sub-200 ms**; the whole file went 5.6 s → 0.4 s.

The pre-fix run is the sharpest evidence for the finding: the timeout was *reported*
(`FILO_QUERY_TIMEOUT` came back) but never *enforced* — so the existing error-code coverage could
not have caught this.

Correctness/reliability: strictly better. Same timeout value, same wait ladder, restores a
cancellation path that shipped in the dep but was disabled. No durability surface touched.

Deliberately **not** included: lowering the 5000 ms value (the review lists it as a separate
consideration, gated behind this fix landing first).

### #3 — FIXED (scope widened twice on Fable rulings; **found 2 latent data-loss bugs**)

The finding: `if wrote?(result, sql) or ends_transaction?(sql), do: bump(shard_id)` dirtied the shard
on **any** COMMIT, so Django's `ATOMIC_REQUESTS` read views paid a full VACUUM INTO + full-object PUT
every 5 s.

Implemented a per-connection "wrote since BEGIN" flag (process dictionary keyed by conn ref — the
same single-owner idiom as the statement cache and the deadline watchdog) and gated the boundary
bump on it. Then hit two problems that widened the scope. **Both were escalated to a Fable agent per
the run directive, and both rulings were followed as given.**

**Ruling 1 — widen to reorder `wrote?/2`.** My first cut only helped connections that had never
written: `sqlite3_changes()` is not reset by SELECT/BEGIN/COMMIT/ROLLBACK, so on a persistent
connection a COMMIT inherited `changes>0` and classified as a write *before* the flag was consulted.
Since Django's recommended `CONN_MAX_AGE` keeps connections alive across requests, that is the
primary production topology and the finding's value lived there. Fable ruled **A: reorder**, as a
three-part package, and in doing so **found a data-loss bug I had just introduced**:

- **Hole 2 (mine, caught before it shipped):** `rolls_back?/1` matched any `rollback` prefix, so
  `ROLLBACK TO <savepoint>` — which does *not* end the transaction — deleted the flag. Sequence
  `BEGIN; INSERT; SAVEPOINT s; <0-row UPDATE>; ROLLBACK TO s; <flush>; COMMIT` then skipped the
  boundary re-bump and lost the INSERT on idle drop. That is Django's nested-`atomic()`-raises,
  outer-block-commits shape. Fixed: only a rollback *without* ` to ` clears the flag.
- **Hole 1 (pre-existing, latent):** `RELEASE` is a control statement but not `ends_transaction?`, so
  a savepoint-only client (`SAVEPOINT a; INSERT; <0-row UPDATE>; RELEASE a`) never re-dirtied at its
  commit boundary — a straddling flush advanced the watermark past the uncommitted rows and the idle
  drop deleted them. Fixed: `commit_boundary?/1` = `ends_transaction?` **or** `releases_savepoint?`,
  and RELEASE deliberately does **not** clear the flag (an inner release commits nothing, so the
  outer COMMIT must still be able to re-bump).

**Ruling 2 — the read-verb whitelist.** After the reorder, a plain `SELECT` on a written-on
connection *still* inherited `changes>0` and re-dirtied (and poisoned the flag, so the COMMIT
re-bumped too). I proposed the inverse predicate — "returns columns and is not `dml?` ⇒ read".
**Fable disqualified it as a data-loss bug**, correctly: `dml?/1` is leading-keyword only and its own
comment documents that it does not detect a CTE-prefixed write, so
`WITH x AS (...) INSERT INTO t ... RETURNING id` would have classified as a read, left the shard
clean, and had its committed rows deleted by `drop_clean`. Ruled **C in whitelist form**: ignore the
inherited counter only for verbs *provably* incapable of mutating the file — `select`, `values`,
`explain`. Anything unrecognized falls through to the conservative path, so the failure direction is
always an extra flush, never a lost write. **`with` must never be added**; there is now a test whose
stated job is to fail if anyone converts the whitelist back to a blacklist.

Final `wrote?/2` order: `control_statement?` → `cols != [] and read_verb?` → `changes > 0` →
`cols != []` → write. The RETURNING fix is preserved untouched (`INSERT … RETURNING` is neither
control- nor read-verb-prefixed, so it still reaches `changes > 0`), as are durable PRAGMA
assignments (`user_version` is deliberately not `control_statement?`).

Tests added (all 5 fail pre-fix on the behaviour they pin): read-only txn on a fresh connection;
read-only txn on a **persistent** connection that already wrote (the finding's real acceptance
test); savepoint released across a flush survives drop; `ROLLBACK TO` savepoint does not discard the
outer write; CTE-prefixed `INSERT … RETURNING` dirties and survives drop; whitelisted verbs stay
clean on a written-on connection. Suite 904 → **910**.

### #19 — DEFERRED (Fable ruled **C**; the review's hit-rate analysis does not hold)

Escalated because it changes the `Storage` behaviour's `flush/3` contract in the durability path.
Fable ruled **defer entirely**, and the reasoning is worth keeping — it is not a scope objection, it
is that **the proposed mechanism cannot produce the hit it promises**:

1. **The first-order win already shipped.** Both flush paths already skip completely when the shard
   is clean (`shard.ex:1249-1254` periodic, `drop_clean` at `:1450-1456`). A digest-skip only fires
   for a shard that is *dirty by write-counter yet byte-identical to the stored object*.
2. **The two upload sites upload different byte layouts.** The periodic path uploads a `VACUUM INTO`
   temp; the drop path uploads the raw checkpointed file. VACUUM rewrites and compacts pages, so a
   vacuum-temp digest will essentially never equal a raw-file digest — the remembered digest is not
   comparable across paths.
3. **The path the review calls "reliable" has nothing to compare against.** Within one coordinator
   lifetime the drop flush runs *once*, at end of life; every earlier upload was a vacuum temp.
   Across lifetimes it cannot help either, because a completed drop deletes the local file, so no
   lineage ever produces two comparable raw-file digests. The review's safety argument is sound
   (the skip is correctly ordered after `Fence.check`); its **hit-rate argument is wrong on both
   paths**, not just the periodic one it flagged.
4. The one variant that would cover the real case couples the coordinator to a backend etag *form*
   (S3 single-PUT etag == body MD5), and the `Local` test double's etag is **sha256** — so the skip
   branch would never fire under the standard test backend, breaking the faithful-double discipline
   `Local` exists for, on a brand-new durability branch.
5. Option A's behaviour-contract change was unnecessary regardless: the coordinator already holds
   the path of the file it uploads and could hash it itself.

**The real root cause it identified:** the recurring waste is the *warm-restart conservative bump*
(`init_flushed_through`) marking a genuinely clean shard dirty. The right fix is at **open** time —
prove cleanliness at warm open (no `-wal` present, provenance sidecar matches the object etag the
warm path already HEADs) and skip the bump — which removes the redundant upload *and* the redundant
fence and vacuum, with no new "believed durable without a PUT" state. That belongs as its own
reviewed finding.

Recorded here specifically so #19 is not re-proposed from the review text.

### #31 — FIXED (the connection fold; the scan-bounding half belongs with #37)

`checkpoint/1` and `verify_integrity/1` ran as two `Connection.open → work → close` cycles back to
back on the drop path. Each open costs a `File.mkdir_p!`, an `sqlite3_open`, and several pragma
round-trips — and, the part that makes it more than double cost: in WAL mode, closing the **last**
connection triggers SQLite's close-time checkpoint and unlinks `-wal`/`-shm`, so the second open
immediately **recreated the WAL index files the first close had just deleted**. Pure churn, on the
path every idle drop and every rolling-deploy teardown traverses — tens of thousands of cycles per
full turnover at 10k–30k shards/node.

Folded into `checkpoint_and_verify/1`, one connection. `verify_integrity/1` stays public and
unchanged — it has three other callers (`RestoreDrillJob`, `Tenants.export`).

The subtlety worth recording: the two failures need **opposite** handling, so the fold has to report
*which stage* failed. A quick_check failure must refuse the flush and quarantine (the 2026-07-14 #4
corruption gate); a merely-busy checkpoint must fall through to `snapshot_and_upload`. Ordering is
preserved exactly — quick_check still runs after the checkpoint and before the raw upload, and is
still *not* run on the busy branch, matching pre-fold behaviour. The connection keeps
`synchronous=FULL` (#11's relaxation is scoped to the snapshot connection; a checkpoint at
`synchronous=OFF` can corrupt the main db on power loss). The now-dead `checkpoint/1` was removed
rather than left as an unused duplicate.

`shard_corrupt_flush_test` — the pinned proof the corruption guard survives — stays green.

**Second half deferred to #37, not dropped:** bounding the `quick_check` scan means either
defaulting `:shard_max_page_count` or size-gating the check. Defaulting that cap is a *behavioural*
change (writes past it fail `SQLITE_FULL`) and is precisely what #37 is about, so it belongs there
as one decision rather than split across two commits.

### #30 — FIXED (the safe half; the rest is flagged as design work, deliberately)

The periodic refresh called `deleted_shard_ids/0` — **every id ever deleted** — on every node every
5 minutes, so both the Postgres read and the receiving process's heap scaled with cumulative
*lifetime* deletions rather than with anything current. At a million lifetime deletions that is a
full-table read plus a million-element list materialized per node per refresh.

The refresh is now incremental (`deleted_shard_ids_since/1`, backed by a new partial index on
`updated_at WHERE status = 'deleted'` with the id INCLUDEd). Safe as an incremental key because
`tombstone/1` always stamps `updated_at`, so a newly-deleted row can never be missed; and because
the set is append-only with idempotent inserts, a row returned twice costs nothing. Two belts on top
of that: a 60 s overlap so a transaction that began earlier but committed later cannot slip below the
cursor, and a **full reload every 12th refresh** to bound any drift. The boot load stays FULL, and
the cursor is seeded from it so the first periodic refresh is already incremental.

**What I deliberately did NOT do:** bound the resident ETS set. The review is right that it grows
forever, but every obvious fix re-opens the hole the module exists to close — evicting a tombstone
lets a stray request re-mint a deleted tenant as an empty shard (breaking the 410 contract), and a
Bloom filter would 410 *live* tenants on a false positive. The only defensible route is an age-tiered
guard (recent deletions in ETS, older ones resolved through the directory plus the durable
`tombstones/<id>` marker, failing **closed** on error), which trades an admission-path Postgres read
for memory and is its own reviewed initiative. Recorded rather than half-built.

Tests pin the two properties that make the incremental path safe, both of which re-open the re-mint
hole if broken: the boot load is FULL (a booting node must see every tombstone, not just recent
ones), and a failed refresh leaves the existing set intact rather than emptying the guard.

### #29 — FIXED

The per-connection page cache was the one resource with **no declared ceiling**. SQLite defaults to
`-2000` — up to ~2 MiB *per connection* — and fathom holds one connection per Hrana stream for the
stream's life. Every other resource here has an explicit cap for exactly this reason
(`:max_open_shards`, `:max_checkouts_per_shard`, `:query_max_rows`, `:shard_max_page_count`,
`:query_timeout_ms`); this one was missed, so one tenant scanning on 50 held streams could silently
claim 100 MB with nothing observing or bounding it.

The sharper point, which is about the *numbers* rather than the memory: the measured density regimes
(~16 KiB idle, ~220 KiB served, ~640 KiB served-with-data) are all workloads whose touched page set
is small, so **none of them ever approached that ceiling**. Those figures are a sample of a
distribution whose tail is 2 MiB per held stream — ~60 GB at 30k — not a bound.

`:shard_cache_size_kb` **defaults to 2000, exactly SQLite's effective default**, verified as
rendering `-2000`. So it ships as a genuine no-op and moves no measurement. It is a declared ceiling
and an operator knob, deliberately **not** a reduction — lowering it trades RAM for page re-reads on
scan-heavy tenants, which is a deployment-shaped decision rather than one to make blind. The sign is
forced in code (negative = KiB in SQLite's convention), so a value can never be misread as a page
count.

### #28 — DEFERRED (implemented, verified against the dep source, then **reverted**)

The finding is real and I confirmed its premise directly in the NIF source: `exqlite_multi_step`
calls `sqlite3_reset` on **every** terminal path — `SQLITE_BUSY`, `SQLITE_DONE`, and the error
default (`sqlite3_nif.c:987-1010`) — so on the dominant path the blanket `after Sqlite3.reset(stmt)`
was a second reset of an already-reset statement, a dirty-CPU dispatch doing nothing (~55k/s at the
measured L=64 ceiling). The only exit leaving a statement mid-execution is a chunk filling without
`SQLITE_DONE`, which in `collect/5` escapes solely via the row-cap abort.

I implemented it (explicit resets on the row-cap abort and the bind-raise path), and the suite
passed. **Then I reverted it, because I could not build a test that discriminates the failure.**

Probes tried and rejected, each for a concrete reason:
- **A peer taking the write lock** — invalid: in WAL mode a held *read* transaction does not block a
  writer. That is WAL's entire point. Passed with and without the reset.
- **`Sqlite3.transaction_status/1`** (the review's own suggestion) — invalid: it reports autocommit
  state, not whether a statement is mid-step. Returned `{:ok, :idle}` both with and without.
- **A peer running `PRAGMA wal_checkpoint(TRUNCATE)`** — the real consequence, but it reported
  `busy=0` both ways in the harness I could construct.

Why that is disqualifying rather than merely inconvenient: this optimization leans on an **internal**
detail of a pinned dep, not its public contract, and the failure mode is silent — a leaked
read-transaction hold blocks WAL checkpointing, which **#4 just made load-bearing** for bounded WAL
growth. So its blast radius is strictly larger now than when the review was written. The review
conditioned it on a pinned regression test precisely so an exqlite bump would fail loudly; shipping
it with a test that *looks* protective but provably does not discriminate is worse than not shipping
it, because it manufactures false confidence.

Worth having anyway: the NIF-source verification above is recorded, so whoever picks this up starts
from a confirmed premise and needs only the missing piece — a harness that reliably exhibits a
blocked checkpoint.

### #27 — FIXED

Both rebalancer observation tables were pruned **fleet-wide from every node every window** (10 s),
so an N-node fleet issued N deletes of the same expired rows per window: one useful, N−1 acquiring
row locks, blocking, re-checking and deleting zero — each after a full index range scan. The waste
grew **linearly with node count**, the opposite of the horizontal additivity the density work
established.

Now node-scoped (disjoint per node ⇒ no cross-node contention), plus a rare fleet-wide sweep with a
3× older cutoff. The sweep is not optional: scoping alone would strand a **departed** node's rows
forever, and the older cutoff means it can never race a live node's fresh rows.

Migration `20260725072541` adds `(node_key, sampled_at)` and `(node_key, updated_at)`. The second
also fixes a pre-existing mismatch the review noted: `WarmLocations.publish/2`'s retract sweep
filters `node_key == … AND updated_at < now`, which matches essentially every row of that node, so
the `[:updated_at]`-only index was a poor fit.

Safe by the nature of the data — both tables are observational (a rolling window the rebalancer
reads with its own anti-flap and confirm windows), so *which* node deletes an expired row is
unobservable. No lifecycle state, tombstone, suspension, or `last_flushed_at` record is involved.

Added `:rebalancer_fleet_sweep_odds` as a testability seam so the sweep can be forced rather than
tested by retrying a coin flip. The rewritten tests pin **both** halves, including the one that is
easy to get wrong: with the sweep off, a node's prune must **not** touch another node's rows — that
disjointness is precisely what removes the contention.

### #25 — FIXED

`SHARD_STORAGE=local` is a supported production selection and local-NVMe is a stated deployment, but
the backend read whole shard files into binaries: a fenced flush held **two** shard-sized binaries at
once (local body + remote body) plus two full in-memory hash passes, i.e. `2 × N × shard_bytes` of
transient binary heap at N concurrent flushes. Worse, `pull_if_changed/3` read and hashed the
**entire** object just to conclude nothing had changed — so on Local the warm-follower revalidation
loop was `O(cached × shard bytes)` of disk read and hashing per poll, where the S3 backend does a
bodiless 304.

Three changes, all value-preserving:
- `file_etag/1` streams the SHA-256 in 256 KiB chunks (the shape `S3.stat_and_md5/1` already uses).
- The fenced flush hashes the remote by streaming and uses `Storage.atomic_copy/2` instead of
  read-then-write. `atomic_copy` carries the same fsync-before-rename crash contract as
  `atomic_write`, so the durability shape is unchanged — it just never materializes the shard.
- `pull_if_changed/3` streams the digest and copies rather than reading the body.

The etag **is** the emulated `If-Match` fence, so the streamed digest must equal the whole-body one
or every fence comparison silently breaks. The new test pins exactly that, across a body larger than
the hash chunk. The pre-existing fence suite — which drives this backend hard precisely because it
is the S3 fence's test double — also stays green.

Deliberately **not** done: caching the digest keyed on `{mtime, size}`. `File.stat` mtime has
1-second granularity, so a same-second same-size rewrite would return a stale etag and produce a

### #5 — FIXED (Fable ruled **Option C**; the review's own proposal was rejected as an auth bypass)

Escalated per the run directive because this is a security path. **The review's recommended fix was
unsafe and Fable rejected it.** Its proposal was to bulk-load the revoked set and answer from it;
but absence from that set proves only what the *directory* says, and a Postgres PITR can lower

storage floor catches that, and only the cold-miss `read_through` consults it. Answering a miss from
bulk completeness would accept a revoked token. The review's fallback (raise the TTL 30 s → 300 s)

freshness for entries that already exist, never for an absent one.** A miss always takes the full
`read_through`, storage-floor union included, byte-identical to before.

Steady state goes from `distinct_shards_per_node / TTL` reads (~3,300/s at 100k shards/node) to one
query per node per interval, plus one cold-miss read per shard per node *lifetime*. Independent of
shard count. Every safety path — monotonic guard, storage DR union, stale-serve fallback,
`:hrana_revocation_on_error` posture — is untouched; a failed bulk query just doesn't advance the
marker and the module degrades to exactly its previous behaviour.

`token_version = 1` and storage floor 5, the floor must still resolve to 5. **Verified
discriminating** — simulating the unsafe design (letting a fresh marker answer a miss) fails it,

### #9 — FIXED (landed after #10, which was its precondition)

Coordinators started with ERTS defaults, so after `init`'s one-shot `:erlang.garbage_collect()` the
old heap only ever grew (`fullsweep_after: 65535` ≈ never). Now
`spawn_opt: [fullsweep_after: 0], hibernate_after: 30_000`.

`max_heap_size` is deliberately **absent** — a coordinator killed at a heap limit mid-`terminate/2`
skips the final fence + checkpoint + PUT + lease release, which is a durability regression that can
also strand a lease. The new guard asserts it stays unset.

**policy** (`fullsweep_after == 0`, `max_heap_size` unset) — deterministic, and it fails pre-fix.

### #10 — FIXED

`schedule_flush/1` re-armed unconditionally, so a coordinator with zero connections and nothing
unflushed woke every ~5 s forever: a timer-wheel insert, a `:rand` call, a message send + dispatch,
an ETS lookup, and a heap touch that defeats page-out. ~6,000 wakeups/s at 30k coordinators/node,
and — the bigger cost — it made `hibernate_after` (#9) unusable at *any* value, since a message
always arrived within one interval.

Such a coordinator is **provably unwritable**: `WriteCounter.bump/1` is reachable only from
`ShardExecutor.run_statement/3` and the abnormal-stream-death path, both of which require a
checked-out connection. Verified by grepping every bump site.

- `schedule_flush/1` gains a `map_size(conns) == 0` clause: re-arm only if `unflushed?`, else cancel.
- The `:checkout` **grant** re-arms if the timer is nil. Deliberately the grant, not the checkin, so
  the timer is live for the entire window in which a connection can write.

Self-quiescing rather than instant: the already-armed timer fires once, observes idle+clean, and
declines to re-arm. So the cost of going idle is at most one extra wakeup, not one per interval
forever. RPO is unchanged — the contract bounds loss of *acknowledged* writes, and this state has
none and can acquire none; a dirty coordinator keeps ticking exactly as before.

Tests: idle+clean carries no timer and the checkout grant re-arms it; idle-but-**dirty** keeps
ticking (the guard against over-applying the optimization). The pre-existing jitter test was
updated to hold a connection — it had been asserting on coordinators that are now correctly
timer-less, and holding a stream is both the realistic case jitter exists for and coverage of the
re-arm path. Suite 910 → **912**.
