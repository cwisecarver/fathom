## Detail

### #1 — FIXED

`PRAGMA busy_timeout` routes to `sqlite3_busy_timeout()`, which **replaces** exqlite's custom busy
handler (installed unconditionally at `sqlite3_nif.c:497`) with SQLite's default `sqlite3OsSleep`
loop — which polls neither the interrupt flag nor exqlite's cancel flag. Verified in the dep source;
exqlite's own `set_busy_timeout/2` docstring warns about exactly this.

Fix, three parts:
- `connection.ex` `open/1`: `Sqlite3.set_busy_timeout(conn, 5000)` in place of the pragma.
- `connection.ex` watchdog: `Sqlite3.cancel/1` in place of `Sqlite3.interrupt/1`. `cancel` is a
  superset — sets the flag the busy handler polls *and* calls `sqlite3_interrupt` — and is a
  **non-dirty** NIF that avoids the connection mutex, so it can't block behind the running query.
- `shard.ex` `checkpoint/1`: same pragma→function swap on the drop path.

**Timing is unchanged by construction**: exqlite's handler walks the same delay ladder
(`{1,2,5,10,15,20,25,25,25,50,50}` then 50 ms) as SQLite's default. It additionally aborts when the
caller process is dead — a dead Hrana stream's wait used to sleep the full 5 s.

Regression test (`test/fathom/query_bounds_test.exs`): one stream holds `BEGIN IMMEDIATE` + a write,
a second stream writes under `:query_timeout_ms: 200`.
- **Pre-fix: 5451 ms** (the full busy timeout), assertion failed.
- **Post-fix: sub-200 ms**; the whole file went 5.6 s → 0.4 s.

The pre-fix run is the sharpest evidence for the finding: the timeout was *reported*
(`FILO_QUERY_TIMEOUT` came back) but never *enforced* — so the existing error-code coverage could
not have caught this.

Correctness/reliability: strictly better. Same timeout value, same wait ladder, restores a
cancellation path that shipped in the dep but was disabled. No durability surface touched.

Deliberately **not** included: lowering the 5000 ms value (the review lists it as a separate
consideration, gated behind this fix landing first).

### #3 — FIXED (scope widened twice on Fable rulings; **found 2 latent data-loss bugs**)

The finding: `if wrote?(result, sql) or ends_transaction?(sql), do: bump(shard_id)` dirtied the shard
on **any** COMMIT, so Django's `ATOMIC_REQUESTS` read views paid a full VACUUM INTO + full-object PUT
every 5 s.

Implemented a per-connection "wrote since BEGIN" flag (process dictionary keyed by conn ref — the
same single-owner idiom as the statement cache and the deadline watchdog) and gated the boundary
bump on it. Then hit two problems that widened the scope. **Both were escalated to a Fable agent per
the run directive, and both rulings were followed as given.**

**Ruling 1 — widen to reorder `wrote?/2`.** My first cut only helped connections that had never
written: `sqlite3_changes()` is not reset by SELECT/BEGIN/COMMIT/ROLLBACK, so on a persistent
connection a COMMIT inherited `changes>0` and classified as a write *before* the flag was consulted.
Since Django's recommended `CONN_MAX_AGE` keeps connections alive across requests, that is the
primary production topology and the finding's value lived there. Fable ruled **A: reorder**, as a
three-part package, and in doing so **found a data-loss bug I had just introduced**:

- **Hole 2 (mine, caught before it shipped):** `rolls_back?/1` matched any `rollback` prefix, so
  `ROLLBACK TO <savepoint>` — which does *not* end the transaction — deleted the flag. Sequence
  `BEGIN; INSERT; SAVEPOINT s; <0-row UPDATE>; ROLLBACK TO s; <flush>; COMMIT` then skipped the
  boundary re-bump and lost the INSERT on idle drop. That is Django's nested-`atomic()`-raises,
  outer-block-commits shape. Fixed: only a rollback *without* ` to ` clears the flag.
- **Hole 1 (pre-existing, latent):** `RELEASE` is a control statement but not `ends_transaction?`, so
  a savepoint-only client (`SAVEPOINT a; INSERT; <0-row UPDATE>; RELEASE a`) never re-dirtied at its
  commit boundary — a straddling flush advanced the watermark past the uncommitted rows and the idle
  drop deleted them. Fixed: `commit_boundary?/1` = `ends_transaction?` **or** `releases_savepoint?`,
  and RELEASE deliberately does **not** clear the flag (an inner release commits nothing, so the
  outer COMMIT must still be able to re-bump).

**Ruling 2 — the read-verb whitelist.** After the reorder, a plain `SELECT` on a written-on
connection *still* inherited `changes>0` and re-dirtied (and poisoned the flag, so the COMMIT
re-bumped too). I proposed the inverse predicate — "returns columns and is not `dml?` ⇒ read".
**Fable disqualified it as a data-loss bug**, correctly: `dml?/1` is leading-keyword only and its own
comment documents that it does not detect a CTE-prefixed write, so
`WITH x AS (...) INSERT INTO t ... RETURNING id` would have classified as a read, left the shard
clean, and had its committed rows deleted by `drop_clean`. Ruled **C in whitelist form**: ignore the
inherited counter only for verbs *provably* incapable of mutating the file — `select`, `values`,
`explain`. Anything unrecognized falls through to the conservative path, so the failure direction is
always an extra flush, never a lost write. **`with` must never be added**; there is now a test whose
stated job is to fail if anyone converts the whitelist back to a blacklist.

Final `wrote?/2` order: `control_statement?` → `cols != [] and read_verb?` → `changes > 0` →
`cols != []` → write. The RETURNING fix is preserved untouched (`INSERT … RETURNING` is neither
control- nor read-verb-prefixed, so it still reaches `changes > 0`), as are durable PRAGMA
assignments (`user_version` is deliberately not `control_statement?`).

Tests added (all 5 fail pre-fix on the behaviour they pin): read-only txn on a fresh connection;
read-only txn on a **persistent** connection that already wrote (the finding's real acceptance
test); savepoint released across a flush survives drop; `ROLLBACK TO` savepoint does not discard the
outer write; CTE-prefixed `INSERT … RETURNING` dirties and survives drop; whitelisted verbs stay
clean on a written-on connection. Suite 904 → **910**.

**Follow-up filed (not a blocker):** the root fix is *measure, don't parse* — a
`sqlite3_total_changes` delta per statement is airtight against every text edge (CTEs, leading
comments, future verbs) and would let `read_verb?` be deleted wholesale. exqlite exposes only
`changes/1`, so this needs an upstream/vendored NIF. Until then the whitelist is correct because its
only failure direction is an extra flush.
