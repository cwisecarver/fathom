## Summary

Four themes recur across panels that did not see each other's output. **First, the A2 replication receive path is the codebase's one unvalidated trust boundary** — three panels independently found defects on the same unauthenticated listener: an unvalidated `shard_id` becomes a filesystem path (`../` escapes to the live tenant data dir, which is a literal sibling directory by default), a forged seed becomes durable tenant data with no peer check and no boot guard, and an 8-byte frame forces a multi-gigabyte allocation. Every other path in the tree — `WarmFollower`, `Snapshots`, `Recovery` — validates identifiers correctly, which is what makes this a gap rather than a matter of taste. **Second, the durability flush's checkpoint is a lineage-changing event that three subsystems read around without accounting for it**: the post-checkpoint object is stamped `{epoch, 0, 0}` — the *most overridable* position — so on the ordinary idle-drop/drain/rebalance path a lagging replica outranks the most complete copy of the shard that will ever exist (found by two panels, and the test suite deliberately routes around the one path where the stamp is wrong). **Third, the OTP release discipline AGENTS.md already documents for the lease reappears verbatim on four other node-global resources** — `WriteFence`, `FlushGate`, `Lru`, `ShardLoad` are acquired by a coordinator and released only from `terminate/2`, which is not guaranteed to run; the `WriteFence` case produces a silent, permanent, per-tenant write outage recoverable only by restarting the node. **Fourth, the ordering primitives A2 rests on are not what their typedocs claim**: the lease epoch is a lock generation that resets to 1 on every clean release, and the replicable extent is the WAL *file size*, which is a high-water mark, not the committed prefix (verified by running SQLite 3.54.0 — an 82 MB rolled-back transaction leaves the file unshortened, and the *next* real commit is then reported quorum-durable while shipping zero bytes to anyone).

**What an operator should do first, in order:** (1) confirm `REPLICATION_BIND_IP` is set on every node running `REPLICATION_LISTEN` — findings #1, #3, #20 and #21 are all remote and pre-authentication, and the network boundary is currently the only control; (2) treat #2 as the highest always-live risk — a transient `EMFILE` or `:busy` during `quick_check` on the periodic flush path destroys a tenant's live database *and* its durable object within one flush interval, with no feature flag involved; (3) do not enable `REPLICATION_PROMOTE_ON_OPEN` or `REPLICATION_RECOVER_FROM_PEERS` in production until #4 is fixed — on those gates the ordinary idle-drop lifecycle silently rolls a tenant back to a lagging replica; (4) verify `SNAPSHOT_RETENTION` is not set to an empty string anywhere in the deploy chain (#13).

Three findings were verified by *execution* rather than by reading (#5 against real SQLite 3.54.0; #18 and #19 against the project's own exqlite build via `mix run --no-start`), and one dedup (#4) was confirmed against source during ranking. Six findings are behind default-off feature flags; each says so explicitly under **Gate** — the project documents prod-enable paths for all of them, so default-off is a mitigation, not a dismissal.

## Ranked Findings

### #1. Unvalidated `shard_id` from a network frame becomes a filesystem path in the replication follower — path traversal, unauthenticated

**Severity:** Critical | **Category:** Shard Isolation | **Panels:** D (Security & Isolation)
**Likelihood:** High (requires only TCP reach to the replication port) | **Blast Radius:** Any file the BEAM user can write — including another tenant's live database and `~/.ssh/authorized_keys` | **Gate:** `REPLICATION_LISTEN` (default off — but `config/runtime.exs:679-690` instructs enabling it FLEET-WIDE FIRST, before any node ships, so on any A2 fleet it is live everywhere)

**Problem:** The follower builds every filesystem path from the `shard_id` field of a frame decoded straight off the network, with no validation:

```elixir
def wal_path(name \\ __MODULE__, shard_id), do: Path.join(dir(name), shard_id <> ".db-wal")
```

(`lib/fathom/shard/replication/follower.ex:167`, and the `db_path` twin at `:170`). `serve/3` (`:271-332`) decodes a frame and dispatches on it; `Protocol.decode/1` (`protocol.ex:326-340`) extracts `shard_id` as an arbitrary `slen`-byte binary — any bytes at all, including `/`, `..` and NUL. `begin_seed/3` (`:486-494`) then opens write handles at `seeding_path(db_path(name, b.shard_id))` and `install/3` (`:623-635`) publishes them with `File.rename/2`. `Path.join/2` neutralizes a leading `/` but does **not** neutralize `..` (verified: `Path.join("/var/lib/fathom/repl", "../data/victim.db")` → `/var/lib/fathom/repl/../data/victim.db`, which the OS resolves).

This is the rule the codebase already enforces everywhere else **and documents as an isolation gate**: `warm_follower.ex:108-117` — *"shard_id becomes a file name here, so a `..`/`/` id would escape cache_dir. Enforce ShardId's one rule."* (and its input is an operator-issued rebalance command, not a network frame); `snapshots.ex:48`, `:238-246` — `@snapshot_id_pattern ~r/^[a-zA-Z0-9_-]{1,128}$/`; `recovery.ex:403-420` — the PULL direction pins `^shard_id` in every frame clause. The LISTEN direction — the only one whose input is fully attacker-controlled — is the one that skipped it.

**Impact:** Anyone who can open a TCP connection to `:9100` sends `seed_begin(shard_id: "../fathom_shards/victim", ...)` + `seed_chunk(:db, 0, <a SQLite file of the attacker's choosing>)` + `seed_end`, and `install/3` renames the attacker's file over `/tmp/fathom_shards/victim.db`. Under the **default** configuration this is not a stretch: `Follower.default_dir/0` (`:151-154`) is `System.tmp_dir!()/fathom_replication` and `Shard.data_dir/0` (`shard.ex:3223-3227`) is `System.tmp_dir!()/fathom_shards` — literal siblings, so a single `../` reaches the live tenant database. With non-default dirs it reaches anything the BEAM user can write. `forget/2` (`:100-107`) gives the same primitive for `File.rm/1`; `apply_write/4` (`:844-863`) gives arbitrary APPEND to any path once a row exists. `decode(nil, _push) → {:reject, :unknown_shard, 0}` (`follower_log.ex:65`) blocks the PUSH path from bootstrapping a new id — but the seed path has no such precondition. AGENTS.md's shard-isolation gate calls a cross-tenant leak a release blocker, not a finding.

**Recommended Fix:** Reject at the frame boundary: in `serve/3`, immediately after `Protocol.decode/1`, drop any frame whose `shard_id` fails `Fathom.ShardId.valid?/1` (close the connection, as the `{:error, reason}` branch already does). Add the same `valid?` assertion inside `wal_path/2` / `db_path/2` as a fail-closed backstop, matching `warm_follower.ex:113-114`. Do **not** rely on `Path.expand` + prefix comparison — the project already has one allowlist validator and a second mechanism will drift. Regression test per #37.

### #2. The periodic flush's integrity gate renames the LIVE shard file and deletes its WAL out from under active streams, then keeps serving — the next checkout gets a brand-new empty database, and the next flush uploads it over the good stored object with a valid `If-Match`

**Severity:** Critical | **Category:** Data Loss | **Panels:** E (Storage & Durability)
**Likelihood:** Medium — trigger is a transient `EMFILE`, `:busy` or `:query_timeout`, on a node whose density is the design premise | **Blast Radius:** One tenant's live database and durable object, destroyed and effectively unrecoverable | **Gate:** ALWAYS LIVE — no feature flag

**Problem:** `snapshot_and_upload/1` gates on `verify_snapshot/2` (`lib/fathom/shard.ex:3019-3032`), which on **any** error calls `quarantine_corrupt!/2` (`:2062-2065`):

```elixir
dest = "#{state.path}.corrupt.#{System.system_time(:second)}"
_ = File.rename(state.path, dest)
Enum.each(["-wal", "-shm"], &File.rm(state.path <> &1))
```

That is correct on the DROP path (`upload_for_drop/1`, `:1997-1999`), where the coordinator is terminating and releases the lease. It is **not** correct on the PERIODIC path, which runs while the shard is being served: `apply_flush_verdict(state, {:error, _})` (`:3132-3133`) returns `{:noreply, schedule_flush(...)}` — the coordinator stays alive — and `handle_call({:checkout, …})` still returns `state.path` unconditionally (`:1130`).

Three consequences, in order:

1. **Split view, immediately.** Streams already checked out keep writing to the renamed inode through fds SQLite still holds, but their `-shm` has been unlinked, so a *new* connection opening `state.path` creates a fresh `-wal`/`-shm` and a **brand-new empty database**. Two sets of connections to one tenant, one seeing data, one seeing nothing.
2. **The good object is then destroyed.** `state.etag` is unchanged (the flush failed), the shard is still dirty, and the next `:durability_flush` finds `File.exists?(state.path)` true — the new empty file. `verify_snapshot` passes on it, `VACUUM INTO` succeeds, and `Storage.flush(id, temp, state.etag, …)` If-Matches **successfully**, replacing the durable object with an empty database. Recoverable only from the `.corrupt.<ts>` file, whose `-wal` was just deleted.
3. **The trigger need not be corruption at all.** `verify_integrity/1` (`:2042-2057`) returns `{:error, _}` for three distinct situations `verify_snapshot` treats identically: `{:quick_check, rows}` (real corruption), `{:quick_check_failed, reason}` (which includes `collect/4`'s `{:error, :busy}` and, when `:query_timeout_ms` is configured, `:query_timeout` on a large `quick_check`), and `{:quick_check_open_failed, _}` (an `Sqlite3.open` failure under fd pressure — EMFILE on exactly the node whose density is the design premise). "I could not check it" is being answered with the most destructive action available.

**Impact:** A transient fd exhaustion or lock contention on one node destroys a tenant's live database and, within one flush interval, its durable object. Unlike every other flush failure, this one is not retried into safety — it is executed once and cannot be undone. This is the highest-ranked always-live data-destruction path in the review.

**Recommended Fix:** (a) On the periodic path, **do not touch the live file**: log, emit `[:fathom, :shard, :flush, :failed]`, stay dirty, and stop the coordinator with `{:shutdown, :corrupt_local}` so no stream can open a recreated empty file at that path. Quarantining is only safe once the shard is provably not being served. (b) Separate "cannot check" from "is corrupt" in `verify_integrity/1` — only `{:quick_check, rows}` (SQLite ANSWERED, and answered not-"ok") should be treated as corruption; an open failure, `:busy`, or `:query_timeout` is a transient flush error. **Test gap:** `test/fathom/shard_corrupt_flush_test.exs:78-105` exercises only the drain path (`Shards.drain/2`), so the serving path has never been driven.

### #3. No peer authentication, no peer allowlist, and no boot guard on the replication port — while the strictly LESS dangerous Hrana port gets one

**Severity:** Critical | **Category:** Security / Shard Isolation | **Panels:** D (Security & Isolation)
**Likelihood:** Medium-High (TCP reach + the promote gate) | **Blast Radius:** Total, durable replacement of any tenant's data on the node, uploaded to S3 as the tenant's authoritative object | **Gate:** `REPLICATION_LISTEN` for the install; the promotion chain additionally needs `:replication_promote_on_open` or `:replication_recover_from_peers` (both default off)

**Problem:** Two halves, only dangerous together.

**(a) No peer auth.** `accept_loop/2` (`lib/fathom/shard/replication/follower.ex:249-265`) accepts every connection and hands it to a `Task` that will serve `push`, `seed_*`, `position_query` and `replica_request` for any shard. Nothing compares the peer address against `:replication_followers` or the roster. The protocol carries no credential — by design, per `runtime.exs:699-707`, where the network is declared to be the boundary.

**(b) Nothing at boot enforces that boundary.** `Fathom.Application.start/2` runs ten config guards (`application.ex:22-31`), including `check_hrana_exposure!/0` (`:289-304`), which WARNS in prod when the Hrana port is enabled, unauthenticated and wildcard-bound. The replication port is *unconditionally* unauthenticated and has **no guard at all** — not a raise, not a warning. `Fleet.follower_children/0` (`replication/fleet.ex:322-337`) simply omits `:ip` when `:replication_bind_ip` is unset, so `:gen_tcp.listen` binds every interface. The only signal is a `Logger.info` at `follower.ex:213`.

**Impact:** Distinct from #1 and **not fixed by validating the id**. A replica installed by any reachable party becomes servable tenant data. The attacker chooses `epoch` and `wal_gen` in `SeedBegin`; `install/3:633-636` writes them into ETS via `FollowerLog.seeded/4`, which sets `torn: false`. On the next cold open of that shard on this node, `Shard.maybe_promote_replica/4` → `try_promote_local/4` (`shard.ex:2277-2285`) evaluates `Promote.fresher?(%{epoch: e1, ...}, %{epoch: e2, ...})` = `{e1,g1,o1} > {e2,g2,o2}`. With `epoch: 2^63` the comparison is always true. `Promote.install_and_publish/3` (`promote.ex:181-209`) then renames the attacker's database onto `Shard.db_path(shard_id)` **and** calls `Storage.flush/2`, so the forged content is uploaded to S3 as the tenant's durable object. `quick_check` passes — the attacker supplied a valid SQLite file. The code is aware and stops one step short: `shard.ex:2291-2294` says `fresher?` is re-asserted because *"the alternative is trusting a promise made by a different module about bytes that arrived over an unauthenticated socket"* — but the re-assertion checks freshness, which is the attacker's input.

**Recommended Fix:** In order of cost: (1) Add `check_replication_exposure!/0` beside `check_hrana_exposure!/0`: **RAISE** in prod when `:replication_listen` is on and `:replication_bind_ip` is unset or wildcard. This port has no auth mode to fall back on, so it warrants a refusal where the Hrana port only warrants a warning. (2) Restrict accepts to the known fleet: on accept, compare `:inet.peername/1` against the resolved `Fleet` membership / `:replication_followers` addresses and close otherwise. (3) Authenticate the peer — a shared HMAC on the frame header keyed off the same `HRANA_TOKEN_SECRET` material. Until then, `docs/a2-quorum-replication.md` should state that a reachable replication port is equivalent to write access to every shard on the node.

### #4. The post-checkpoint flush stamps the durable object at the LOWEST possible position `{epoch, 0, 0}`, so a lagging replica outranks the most complete copy of the shard and is promoted over it

**Severity:** Critical | **Category:** Data Loss | **Panels:** C (Fencing) + E (Storage & Durability) — **found independently by two panels**
**Likelihood:** High — the trigger is the ordinary lifecycle, not a failure | **Blast Radius:** Per tenant; fires most reliably on the rebalance handoff and on every idle drop | **Gate:** the wrong stamp is written ALWAYS; the consumers that act on it are `:replication_promote_on_open` and `:replication_recover_from_peers` (both default off, both with documented prod-enable paths at `runtime.exs:631,653`)

**Problem:** `flush_position/1` (`lib/fathom/shard.ex:2900-2910`) derives the object's position stamp from the **live WAL file**:

```elixir
{:ok, %{ckpt_seq: gen, size: size}} -> %{epoch: epoch, wal_gen: gen, offset: size}
{:ok, :empty} -> %{epoch: epoch, wal_gen: 0, offset: 0}     # shard.ex:2905
```

`Wal.read/1` returns `{:ok, :empty}` both for `:enoent` (`replication/wal.ex:60-61`) **and** for a file shorter than a 32-byte header (`:57-58`) — i.e. for a TRUNCATED OR DELETED WAL, not only a never-written one. The `{:ok, :empty}` comment ("No WAL yet: nothing has been written through one") is true only for a brand-new shard. But `flush_position/1` is read **after** a checkpoint that empties the WAL, on two paths:

- **DROP PATH (deterministic).** `upload_for_drop/1` (`:1982-1990`) runs `checkpoint_and_verify/1` → `PRAGMA wal_checkpoint(TRUNCATE)` (`:2157`) → `Connection.close/1` (`:2165`, which on the last connection also unlinks `-wal`/`-shm`) → **then** `Storage.flush(state.id, state.path, state.etag, flush_position(state))` (`:1990`). Every clean idle-drop, every graceful drain, every rebalance handoff stamps `{epoch, 0, 0}`. `retry_drop_upload/1` (`:1954-1964`) inherits it.
- **PERIODIC PATH (intermittent).** `snapshot/2` closes its connection at `:3203`; the source comment at `:3177-3179` notes this is *"frequently the last connection: the periodic flush fires on any dirty shard, which is routinely one with zero checked-out streams."* Same result.

So **the most complete copy of the shard that will ever exist is stamped the minimum for its epoch.** The stamp is not `nil` (which `Promote.fresher?/2` treats as un-overridable, `promote.ex:90`) — it is a stamp that *claims the object holds nothing*. `fresher?` is a bare lexicographic compare (`promote.ex:106-114`) and `Recovery.rank/1` (`recovery.ex:145`) is the same tuple with no epoch filtering, so any replica at the same epoch with a non-zero position beats a complete object — including one behind by every push a follower rejected as `:already_in_flight`, `:overloaded` or `:stale_wal_gen`, which AGENTS.md measures at ~10k per node per run.

The in-code comment ("the WAL has just been folded into the database, so the position describes bytes that are genuinely here") is the exact inverse of the truth. The reasoning it borrows from `snapshot_and_upload/1` holds *there* because `VACUUM INTO` + `wal_checkpoint(PASSIVE)` leave the WAL header and size intact, so the read **over**-claims. A TRUNCATE checkpoint does not advance the position, it **resets** it — and the code's own comment at `:2886-2896` names under-claiming as the direction that "loses writes": *"Reading BEFORE the snapshot would under-claim, and a replica sitting between the claim and the truth would be judged fresher and promoted — silently dropping exactly the writes that landed during the snapshot."* The checkpoint under-claims by more than any read-ordering mistake could.

Both consumers fire: `try_promote_local/4` (`:2277-2285`) and `try_promote_from_fleet/4` (`:2303-2314`) → `Recovery.best_replica/3`, which pulls a **peer's** replica across the network and installs it.

**Unexercised by design, which is why it survived.** `test/fathom/shard/flush_position_test.exs:199-213` pins the read order ONLY inside `snapshot_and_upload/1` (it string-splits `shard.ex` on that function name). Every test in that file's "the stamp on a real flush" block holds a stream open for its whole duration (`:116`), so `snapshot/2` is never the last connection and the empty-WAL branch is structurally unreachable; there is no test of the drop path's stamp at all. And `test/fathom/shard/promote_on_open_test.exs:134-138` says outright: *"NODE LOSS, not a shutdown. `Shards.stop/1` is a graceful drain and its drop-flush uploads everything on the way out — which would leave the stored object holding all the rows and make every test here vacuous. (It did: the first version used it and three tests failed …)"*. The suite deliberately routes around the one path where the stamp is wrong. Written against a graceful stop, `a_lagging_replica_is_never_promoted` (`promote_on_open_test.exs:196`) fails.

**Impact:** A shard idles past `:shard_idle_ms` (60 s default), `flush_and_drop` uploads everything and stamps `{epoch,0,0}`, the lease is released. On the next open a replica that legitimately lagged the primary's final commits is judged "fresher", and `promote_replica/6` (`:2399-2448`) publishes it over the durable object with a valid `If-Match` and renames it onto the live path. Acknowledged, quorum-committed writes silently discarded, with a `Logger.warning` asserting the opposite. Partial mitigation: `snapshot_before_promotion/1` (`:2453`) takes a `pre-promotion` snapshot first, so this is recoverable rather than permanent — *provided snapshots are enabled* (see #13, #14).

**Recommended Fix:** A checkpointed WAL means "the object holds EVERYTHING", the opposite of `{epoch, 0, 0}`. Capture the WAL header **before** the checkpoint and stamp the post-checkpoint object at the **next** generation: `pre = Wal.read(state.path <> "-wal")` before `checkpoint_and_verify`, with `post_checkpoint_position` returning `%{epoch: e, wal_gen: gen + 1, offset: 0}` for `{:ok, %{ckpt_seq: gen}}` and `nil` on `{:error, _}` (unknown ⇒ never overridable). `{e, gen+1, 0}` is strictly greater than every replica at `{e, gen, ≤N}` and preserves the over-claim direction. Apply to **both** `upload_for_drop/1` and `snapshot/2`. Alternatively make `Wal.read/1` distinguish `:absent` / `:truncated` from `:never_written`. Extend the structural read-order guard in `flush_position_test.exs:199-213` to `upload_for_drop/1`, and add a behavioural test that graceful-stops a shard with a lagging installed replica and asserts it is NOT promoted (see #38).

### #5. The replicable extent is the WAL FILE SIZE, which is a high-water mark, not the committed prefix — a commit after any rollback is reported quorum-durable while shipping zero bytes

**Severity:** Critical | **Category:** Data Loss | **Panels:** B (A2 Replication & Quorum) — **verified by RUNNING real SQLite 3.54.0, not by reading**
**Likelihood:** High — any rolled-back transaction whose dirty set exceeds the 2 MB page cache; a Django `atomic()` block wrapping a bulk import that raises is exactly this shape | **Blast Radius:** Per tenant, permanent divergence between primary and every follower | **Gate:** `REPLICATION_ENABLED` (default off)

**Problem:** `Wal.read/1` reports `size` from `File.stat` (`lib/fathom/shard/replication/wal.ex:52-66`, returned at `:75`). `Primary.plan/3` treats that number as "everything the follower needs" (`primary.ex:98`: `when size > offset`), and `Primary.advance/2` records `offset + len` as the follower's new position (`:129`). **SQLite's WAL file length is not the committed extent.** On `ROLLBACK` (or `ROLLBACK TO SAVEPOINT`), SQLite rewinds `mxFrame` in the wal-index but does **not** shorten the file; the next transaction overwrites those frame slots in place.

Measured on SQLite 3.54.0, WAL mode, `wal_autocheckpoint=0`:

```
baseline committed WAL size:  12,392
peak during a large txn:      82,812,032   <- spilled frames
after ROLLBACK:               82,812,032   <- file NOT shortened
after the NEXT COMMIT:        82,812,032   <- unchanged
committed rows:               2
```

The consequences chain:

1. The first commit after the rollback plans `{:append, 12_392, 82_799_640}` — ships 82 MB of rolled-back garbage to every follower, in ~80 rounds of `REPLICATION_MAX_PUSH_BYTES`, against a 5 s deadline and the 1 GiB node budget.
2. `Primary.advance/2` records `offset: 82_812_032`.
3. The **next real commit** leaves the file size unchanged, so `Primary.plan/3` falls through to `:109` → `:nothing` for **every** follower. `ship_planned/4` hits `plans == []` at `session.ex:514` → `:nothing`; `ship/5` returns `:nothing` at `:426`; `handle_call` replies `{:reply, :ok, state}` (`:229-230`). **The tenant is told the write is quorum-durable and not one byte of it was shipped, to anyone.** `Session.deliver/5:575` makes this worse: a follower planned `:nothing` is COUNTED toward the quorum (`:509`, `:575-581`).
4. Even the shipped bytes are poison: the follower's WAL holds rolled-back frames whose checksum chain diverges. On promotion, `Promote.checkpoint_and_verify/1` recovers only up to the last checksum-valid frame and `quick_check` returns ok — a database silently missing every transaction committed after the rollback point.

Distinct from the flush-interval finding AGENTS.md records: that one is "a reset re-ships a legitimate WAL"; this is "the number we ship to and record is not the committed extent at all". The 5 s→30 s tuning does not touch it, and `PRAGMA wal_checkpoint(PASSIVE)` at `shard.ex:3201` does not truncate.

**Impact:** Acknowledged writes that no follower holds, reported to the client as `:ok` — the exact guarantee A2 exists to provide, silently void. Followers holding a WAL that diverges from the primary's at a byte offset both sides believe they agree on. Plus a per-rollback burst of tens of MB through the byte budget.

**Recommended Fix:** Ship to the **last committed frame**, never the file length. The number is already computed and thrown away: `native/fathom_udf/src/wal.rs:75` receives `pages` (SQLite's `mxFrame`) on every commit and stores it in a process-global `LAST_PAGES` (`:49`) that nothing consumes — the module's own comment (`:26-31`) says A2 *"will carry shard identity through its own channel"*. Make the hook publish `{shard, mxFrame}`, have `Session` compute `extent = 32 + mxFrame * (24 + page_size)` and pass it to `Primary.plan/3` in place of `header.size`. Failing that, have `Wal.read/1` walk frame headers and return the offset past the last checksum-valid frame with non-zero `nTruncate` (the litestream/litefs approach; `Wal` already parses the salts and page size). Regression test: `BEGIN; <spill-sized writes>; ROLLBACK;` then a commit, assert the follower received it.

### #6. A published `WriteFence` row outlives its coordinator and can never be cleared — permanent 503 on every write to that tenant, recoverable only by restarting the node

**Severity:** Critical | **Category:** Reliability (data-plane availability) | **Panels:** A (OTP & Concurrency)
**Likelihood:** Medium-High — the state is reached precisely when the object store is unreachable, which is the case most likely to exhaust the shutdown budget | **Blast Radius:** One tenant, permanently, across coordinator restarts and across the partition healing | **Gate:** ALWAYS LIVE (heartbeat mode — production and the chaos rig)

**Problem:** `note_not_valid/1` publishes a shard id into the node-global `Fathom.Shard.WriteFence` ETS table (`lib/fathom/shard.ex:2773`) when its heartbeat has been not-valid past `stealable_after_ms`. The row is removed by exactly two things: `clear_write_fence/1` (`:2791-2794`) and `WriteFence.forget/1` — and **all four `forget/1` call sites are inside `Fathom.Shard.terminate/2`** (`:1554`, `:1575`, `:1610`, `:1630`). Two independent failures compose:

1. **`terminate/2` is not guaranteed.** The clause that would run here (`:1603`, `conns > 0`) does a fence + checkpoint + full-object PUT against the object store — and this state is reached precisely when the object store is unreachable, i.e. the case most likely to exhaust the 60 s `:shard_shutdown_ms` budget and be brutal-killed. `Fathom.Shards.stop/1` (`shards.ex:539`) has the same shape.
2. **A fresh coordinator can never clear it.** New state starts `not_valid_since: nil` (`:589`), and `clear_write_fence(%{not_valid_since: nil} = state), do: state` (`:2791`) returns without touching ETS. So the successor coordinator — which just acquired a valid lease and is by definition not stealable — never calls `unfence/1`.

**Impact:** `ShardExecutor.do_execute/2` reads the flag lock-free on every write (`shard_executor.ex:132`) and returns `503 FILO_STALE_LEASE`. The tenant **reads fine and every write fails forever**, across coordinator restarts, across the partition healing, with no log line and no telemetry after the single initial `[:fathom, :shard, :write_fenced]` event. The only recovery is restarting the node. A silent, permanent, per-tenant write outage produced by the circuit breaker that exists to *bound* loss.

**Recommended Fix:** Make the fence **owned** rather than merely published. Cheapest correct version: call `Fathom.Shard.WriteFence.unfence(state.id)` unconditionally once in `open_with_lease/8`, beside the existing `FlushWatermark.record(...)` (`shard.ex:643`) — a coordinator that just confirmed a lease is provably not stealable, so clearing is always correct and idempotent. Stronger: have the `WriteFence` GenServer `Process.monitor/1` the fencing coordinator and drop the row on `:DOWN`. Regression test: `Process.exit(coordinator, :kill)` a fenced coordinator, assert a re-opened shard accepts writes — `heartbeat_fence_test.exs:217-239` only exercises the same-coordinator fence→unfence cycle and cannot see this (see #39).

### #7. `FollowerLog.decide/2` rejects a BACKWARDS WAL generation before it ever checks `salt1`, permanently deadlocking replication for that tenant

**Severity:** Critical | **Category:** Reliability / Data Loss | **Panels:** E (Storage & Durability)
**Likelihood:** High — the producing sequence is the ordinary one; a strong candidate for the unexplained `:stale_wal_gen` (14,149) volume AGENTS.md records at 512 tenants | **Blast Radius:** Per tenant, permanent until the `Follower` process restarts; every follower enters the state simultaneously | **Gate:** `REPLICATION_ENABLED` + `REPLICATION_LISTEN` (default off)

**Problem:** Clause order in `decide/2` (`lib/fathom/shard/replication/follower_log.ex`) is `:67` stale epoch → `:75` new epoch → `:81` `pushed < gen` ⇒ `{:reject, :stale_wal_gen, 0}` → `:87` `pushed > gen` → `:106` `salt1 != salt` ⇒ `decide_fresh`. The salt clause is therefore reachable **only** when `pushed == gen`. The comment immediately above it (`:94-98`) states the hazard precisely — *"`ckpt_seq` … restarts at 0 when SQLite deletes and recreates the file … The generation then goes BACKWARDS or stays equal"* — but the clause sits **below** the backwards reject, so only "stays equal" is handled. **The code and its own comment disagree.**

The sequence producing a backwards generation is the ordinary one: (1) `Fathom.Shard.snapshot/2` runs `PRAGMA wal_checkpoint(PASSIVE)` (`shard.ex:3200-3201`) every `:shard_flush_interval_ms`. (2) The next tenant write restarts the log; `ckpt_seq` becomes ≥ 1 and `salt1` increments. (3) The last Hrana stream closes; SQLite unlinks `-wal`/`-shm`. (4) The next write recreates the WAL at `ckpt_seq = 0` with a fresh random `salt1` — generation 1 → 0.

`Primary.plan/3` (`primary.ex:92-96`) is direction-agnostic (`when seq != gen or s != salt`) and correctly emits `{:reset, 0, size}`. The follower rejects it as `:stale_wal_gen`. `:stale_wal_gen` is in `@settled_rejects` (`session.ex:62`), so `reconcile/2` (`:657-658`) deletes only the `inflight` entry and **never corrects** `state.followers[key]` — so the next plan re-derives the same `{:reset, 0, size}`, forever.

**Impact:** Every follower is in the same state simultaneously (they all see the same push), so the tenant gets `FILO_NO_QUORUM` on **every write** until the `Follower` process restarts. Per-tenant, permanent, and survives coordinator liveness (the `Session` monitors the coordinator, which stays up across stream close). Near-silent diagnostically: follower-originated rejects never reach `[:fathom, :replication, :reject]` (only `:overloaded`/`:already_in_flight` are counted, at `shipper.ex:109, 250, 257`) — the sole trace is a per-reject `Logger.warning`. **Cross-reference #8**, a different bug with the same symptom.

**Recommended Fix:** Move the `salt1 != salt` clause **above** both `wal_gen` comparisons. A different salt means a different WAL file regardless of which way the counter moved; `salt1` is the identity, `ckpt_seq` is only an ordinal within one file. Separately, `@settled_rejects` should not include a reason that leaves the primary's per-follower record stale. Tests miss this because `replication_test.exs:241` only covers equal generations and `replication_seed_test.exs:313` closes connections WITHOUT checkpointing first, so `before.ckpt_seq` is 0 and the transition never goes backwards.

### #8. The lease epoch is NOT monotonic — a clean release resets it to 1, breaking both the A2 position order and the follower's `:stale_epoch` fence

**Severity:** High | **Category:** Data Correctness / Reliability | **Panels:** C (Fencing)
**Likelihood:** High — steps 2–3 are the documented normal failover-then-idle sequence | **Blast Radius:** Per tenant, permanent write outage; plus wrong-lineage selection fleet-wide | **Gate:** the epoch reset is ALWAYS LIVE; the two consumers need `REPLICATION_ENABLED` and the promote gates

**Problem:** `release_lease` deletes the lock object (`lib/fathom/shard/storage/s3.ex:1853-1862`, `storage/local.ex:551-552`). `acquire_lease` then takes the optimistic `create_lock` path, which hardcodes `epoch: 1` (`s3.ex:1567`, `:1666-1672`). So the epoch climbs only on crash-steals and **falls back to 1** on the next clean idle-drop, drain or rebalance handoff.

`Storage.position`'s typedoc (`storage.ex:84-101`) asserts the opposite as the basis for the whole ordering: *"the lease `epoch` increases monotonically per shard (it is already the fencing token)"*. It is a **lock generation**, valid only while the lock exists. Two consumers use it as a shard-history counter across time: `Promote.fresher?/2` ranks `{epoch, wal_gen, offset}` lexicographically across lineages that may span a release; `FollowerLog.decide/2` (`follower_log.ex:67-73`) rejects `pushed < epoch` as `:stale_epoch` — permanently, since `:stale_epoch` is in `@settled_rejects` (`session.ex:62`) and `start_seeds/3` seeds only on `:unknown_shard` (`:891-895`).

**Impact (sharper half).** With A2 on: (1) Shard S homed on A at epoch 1; followers B/C/D record epoch 1. (2) A crashes; a survivor steals → epoch 2; followers record epoch 2. (3) S idles out and drops cleanly → `release_lease` → the lock object is gone. (4) Next traffic re-opens S → `create_lock` → **epoch 1**. (5) Every push ships at epoch 1. B/C/D all answer `:stale_epoch` and are never re-seeded. Quorum is unreachable, so `Session.commit` fails and `ShardExecutor` returns 503 `FILO_NO_QUORUM` on **every write** to that tenant, **permanently** — until a follower restarts (`recover_shard/3` re-seeds at epoch 0) or another crash-steal climbs back over 2.

**Impact (second half).** Combined with #4: a replica stranded at a *higher* epoch from a previous ownership generation can outrank an object flushed under a *lower*, post-reset epoch, so `fresher?` picks the older lineage.

Note also that `Follower.recover_shard/3` (`follower.ex:744-752`) re-inserts `FollowerLog.seeded(0, gen, salt, size)` with `torn: false` for a pair whose torn state was in-memory only — safe today **only** because epoch 0 loses every `fresher?` comparison, which is load-bearing and undocumented (see #11).

**Recommended Fix:** Make the epoch durable and monotonic per shard. Cheapest change preserving the 1-RTT optimistic create: on release, don't DELETE — conditionally PUT a tombstone lock `{owner: nil, epoch: E, released: true}`, and have `acquire_existing` treat `released: true` as free-but-numbered, acquiring at `E + 1` (the `:not_found` create at epoch 1 then only applies to a genuinely never-leased shard). Alternatively seed the epoch in `Fathom.Shard.init` as `max(lock_epoch, object_head.position.epoch) + 1`. **Correct `Storage.position`'s typedoc.** Test: acquire → steal → release → re-acquire, assert the epoch never decreases (see #38).

**Severity:** High | **Category:** Data Loss | **Panels:** A (OTP & Concurrency)
**Likelihood:** Medium — a `DataPlane`/`ShardSupervisor` restart, or a single coordinator crashing while streams are held | **Blast Radius:** Every acked write landing during the terminate window on that shard, silently | **Gate:** ALWAYS LIVE

**Problem:** The `lease_lost: true` terminate clause reasons explicitly about live streams and therefore **renames**: *"`quarantine_fenced!`'s `File.rename` is safe while streams hold the file open (Unix keeps the fd on the renamed inode); the streams tear down when their monitor on this dying coordinator fires."* (`lib/fathom/shard.ex:1542-1544`). The sibling clause added later for the same `conns > 0` situation (`:1603-1617`) instead calls `flush_and_drop/1` (`:1613`), whose success path ends in `drop_local(state.path)` (`:1745`) — `File.rm` on `.db`, `-wal`, `-shm` (`:2190`).

So for the whole duration of terminate's `checkpoint_and_verify` → `VACUUM INTO` → full-object PUT (budgeted up to 60 s; seconds at real S3 latency), live streams keep committing writes that are (a) not in the uploaded snapshot and (b) then unlinked. **Those writes were acked to the client.**

**Recommended Fix:** Do not unlink under live connections. In `flush_and_drop/1`, gate the drop on `map_size(state.conns) == 0`: with connections still checked out, upload and **keep** the local copy (the next open adopts it warm and the provenance sidecar arbitrates), or quarantine by rename as the `lease_lost` clause does. Secondarily, publish `WriteFence.fence(state.id)` at the top of the `conns > 0` clause so remaining in-flight statements are refused (503) rather than acked-then-discarded — pairing with #6's unconditional clear at open.

### #10. `incarnation_dead?` makes a predecessor's locks stealable IMMEDIATELY, bypassing the lock-TTL fallback that protects a node serving in legacy mode

**Severity:** High | **Category:** Shard Isolation / Data Loss | **Panels:** C (Fencing)
**Likelihood:** Medium — needs a `Heartbeat` GenServer death on a node that keeps serving, plus a shared/persisted `:shard_data_dir` | **Blast Radius:** An entire node's keyspace slice at once — fleet-wide split-brain | **Gate:** ALWAYS LIVE (core lease machinery)

**Problem:** `stealable_at/3`'s `:not_found` branch (`lib/fathom/shard/storage/s3.ex:1748-1751`, mirrored at `storage/local.ex:599-606`):

```elixir
if Storage.incarnation_dead?(other),
  do: {:ok, 0, s3_now || now},
  else: {:ok, lock_expires_at_ms + margin, s3_now || now}
```

The `else` is finding #11's protection, and `s3.ex:1724-1730` explains who it protects: *"when the Heartbeat GenServer dies abnormally it deliberately LEAVES its object behind, and coordinators degrade to the legacy per-shard renew fence — a node that is healthy, serving, and renewing every lock it holds. Under the old logic a single process failure … made that node's ENTIRE keyspace slice instantly stealable."* The `incarnation_dead?` fast path (round-2 #34) discards that protection for one owner — and the proof of death that gates it, `judge_previous/1` + the `{:clear_previous_incarnation, ...}` recheck (`heartbeat.ex:296-301`), proves only that **the heartbeat object stopped being renewed**, not that the node stopped.

A node whose `Heartbeat` GenServer is dead is *precisely* the case the `else` exists for: `Fence.heartbeat_valid/2` catches the `:exit`, returns `:legacy` (`fence.ex:72-77`), and the coordinators keep serving and keep renewing their per-shard locks. The successor then clears the heartbeat, calls `Storage.mark_incarnation_dead/1`, and every lock the predecessor is **actively renewing** reads as stealable at 0.

**Impact:** On a shared/persisted `:shard_data_dir` — the exact deployment `judge_previous/1`'s own comment says the design "actively encourages" (hostPath / PV / NFS, or a pod still in its termination grace) — a still-serving predecessor loses its whole keyspace slice to the successor with no waiting period. Every one of those shards then self-fences at its next flush and quarantines its acked-but-unflushed writes to `.fenced.<ts>`. This is the fleet-wide split-brain that `heartbeat.ex:426-437` says the two-read protocol exists to prevent; **the protocol catches a live RENEWER and misses a live NODE.**

**Recommended Fix:** Keep the fast path but respect the signal the predecessor is still producing:

```elixir
if Storage.incarnation_dead?(other) and lock_expires_at_ms <= (s3_now || now),
  do: {:ok, 0, ...},
  else: {:ok, lock_expires_at_ms + margin, ...}
```

A genuinely dead predecessor's locks are frozen and already past TTL, so #34's win is fully preserved; a predecessor still renewing keeps its normal protection. Mirror in `local.ex:604-606`. Test with a lock whose `expires_at_ms` is in the FUTURE under a `mark_incarnation_dead` owner, asserting `:live`.

### #11. The `torn` quarantine flag is defeated two ways — cleared without evidence, and not durable across a restart

**Severity:** High | **Category:** Data Correctness | **Panels:** B (A2 Replication & Quorum) — two independent mechanisms, merged
**Likelihood:** High — "being behind" is the documented norm under load (`:already_in_flight` ~10k/node at 512, `:overloaded` 8,419/9,294 at 1024); node restarts are documented as routine | **Blast Radius:** A replica genuinely missing committed pages becomes promotable and offerable **fleet-wide** | **Gate:** `REPLICATION_LISTEN` + `:replication_promote_on_open` / `:replication_recover_from_peers`

**Problem — mechanism (a): `absorb_before_reset/3` clears `torn` without any evidence the local WAL was complete.** `FollowerLog.decide_fresh/2` correctly sets `torn: true` on every generation change (`lib/fathom/shard/replication/follower_log.ex:139`). `absorb_before_reset/3` (`follower.ex:792-814`) clears it in two places, neither establishing the property `torn` encodes:

- `:801` clears it whenever `checkpoint_into_db/1` returns `:ok` — but `:ok` only means "SQLite folded whatever frames we happened to hold". If this follower was BEHIND in the old generation, the frames it never received are gone: `Primary.plan/3:92-96` answers a generation change with `{:reset, 0, size}` and the old generation's un-shipped range is never re-sent. Our `.db` absorbed a PREFIX; the primary's absorbed the whole thing.
- `:812` clears it when there is nothing to absorb (`.db` absent, or a zero-byte WAL). A follower that missed the entire generation has a zero-byte WAL, so *"we hold nothing to fold in"* is indistinguishable from *"there was nothing to fold in"*.

`Session.ship/5:441-442` abandons a catch-up when the deadline passes, and `native/fathom_udf/src/wal.rs:79-83` PASSIVE-checkpoints at 4000 pages independently of replication progress — the file's own comment (`:26-31`) says the A2 rule ought to be *"checkpoint only what the write quorum has already acked"* and it is not implemented.

**Problem — mechanism (b): `torn` is not durable, and `recover/3` resurrects a torn replica as promotable.** `:ets.insert(tab, {shard_id, FollowerLog.seeded(0, gen, salt, size)})` (`follower.ex:744-752`, esp. `:747`, via `follower_log.ex:153-157`). `torn` lives only in ETS, which dies with the `Follower` GenServer. `recover/3` (`:727-742`) deliberately rebuilds state from files on boot — a good fix for the re-seed storm it documents — but `torn` **cannot be derived from the files** (nothing on disk records that the `.db` and `-wal` are a generation apart; the `-shm` that would hint at it is deleted at `:836`). So `FollowerLog.seeded/4` stamps `torn: false` for every recovered shard, and a replica correctly quarantined before the restart is fully promotable after it. The moduledoc at `:15-20` reasons that losing ETS is safe because *"the next push is refused with `:unknown_shard`"* — `recover/3` removed exactly that safety and `torn` was not carried across.

**Impact:** A replica genuinely missing committed pages advertises `torn: false`, so `Promote.fresher?/2:106` lets it through, `Follower.offerable/2:128` offers it to peers, and `Recovery.choose/3` can pull it fleet-wide. It passes `quick_check` (`promote.ex:257`) because a database missing pages is structurally valid. A node restart (deploy, crash, OOM-kill — all documented as routine on this rig) launders every torn replica on that node into a promotable one. This is the 2026-08-12 failure class (`docs/reviews/a2-checkpoint-torn-replica-2026-08-12.md`) with the guard defeated, twice.

**Recommended Fix:**
- **(a)** The follower cannot detect this alone. Fix on the primary: `Session` holds each follower's position, so when `Primary.plan/3` decides `{:reset, ...}` and that follower's recorded `offset` is short of the last extent shipped in the outgoing generation, send a **SEED** instead of a reset (route through the existing `:unknown_shard`/`start_seeds/3` path). Belt and braces on the follower: only clear `torn` at `:801`/`:812` when the push is at offset 0 **and** the local `next_offset` equals a `prev_extent` field carried in the push (additive at `@version 2`, per the precedent at `protocol.ex:56-69`).
- **(b)** Make `torn` durable: write a zero-byte `<dir>/<shard>.db.torn` marker whenever `decide_fresh/2`'s result is installed with `torn: true`, remove it in `install/3` (`:633`) and on a successful absorb (`:801`). `recover_shard/3` reads `File.exists?` for the marker instead of assuming false. Test that a restarted `Follower` still refuses to promote a replica torn before the restart; verify the test fails without the marker.

### #12. `Snapshots.restore/3` PROBES the lease but never HOLDS it — the restore is silently undone within one flush interval

**Severity:** High | **Category:** Data Loss / Reliability | **Panels:** E (Storage & Durability)
**Likelihood:** Medium-High — worst on a fleet where the LB is still routing traffic for that subdomain, i.e. every real incident | **Blast Radius:** One tenant, at maximum operator pressure | **Gate:** ALWAYS LIVE (snapshots feature)

**Problem:** The first-order clobber is fenced — the `If-Match` on `restore_snapshot/3` means a flush landing between the etag read and the copy-back aborts the restore with `{:error, :superseded}` (the comment at `lib/fathom/snapshots.ex:107-110` describes this). The second-order case is not:

1. `drain(id)` succeeds; `Storage.lease_holder(id)` (`:105`) returns `:free`; `Storage.object_etag(id)` (`:111`) returns `E`.
2. A request arrives on another node. It cold-opens the shard, acquires the lease, pulls the object at `E`, and starts serving. It has not flushed, so its `state.etag` is `E`.
3. The restore's `If-Match: E` succeeds (`:113`). The object is now `E'` — the snapshot's bytes.
4. That node's next durability flush PUTs `If-Match: E` → 412 → `reconcile_superseded/1` (`shard.ex:1926-1940`) re-checks the LOCK, finds it still its own, and returns `{:reconciled, E'}`. `apply_flush_verdict/2` (`:3118-3121`) resyncs the fence to `E'` and keeps the shard dirty.
5. The next interval PUTs the node's **pre-restore** bytes with `If-Match: E'` — which succeeds. The restore is silently undone.

Every step is a path the code implements deliberately and correctly in isolation; the gap is that nothing prevents a new owner appearing between the probe and the copy.

**Impact:** An operator restoring a tenant to a known-good point-in-time — a maximum-pressure, low-frequency operation — sees `:ok` and gets the corrupt state back within one flush interval.

**Recommended Fix:** Acquire and **hold** the lease across the whole restore, as `Fathom.Tenants.fork_into_leased_dst/2` already does for the fork path — the correct pattern is in the codebase. Release only after the copy-back and the directory reconcile have landed.
