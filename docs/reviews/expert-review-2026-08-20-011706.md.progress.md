## Notes

### #2 — FIXED (`65f29e6`)

The reviewer's prescribed fix was wrong in two places, and both are recorded in the code so they
are not "simplified" back:

1. **Classify on the reason, not the tuple tag.** The finding said only `{:quick_check, rows}` is
   corruption. Running it showed SQLite reports bad bytes through *two* channels — a badly damaged
   page makes `quick_check` ERROR, arriving as `{:quick_check_failed, "database disk image is
   malformed"}`, the same shape a transient `:busy` produces. The prescribed narrowing would have
   stopped quarantining genuinely malformed files on the drop path.
2. **Did not stop the coordinator.** Not renaming already breaks the data-loss chain at step one,
   and `object_too_large` already establishes this codebase's policy for "this flush can never
   succeed" (alarm loudly, keep serving). A second policy would add a restart-loop failure mode.

An existing test (`shard_snapshot_integrity_test.exs`) asserted the opposite and was updated — it
pinned the rename *mechanism* rather than the invariant, and never caught the bug because it closes
its connection before corrupting.

**Left open, deliberately:** a corrupt shard now serves indefinitely with an unbounded RPO and a
loud first-occurrence alarm. That matches `object_too_large`'s behaviour. If the project decides
"serving a corrupt db is worse than being down", the coordinator-stop is a separate, deliberate
policy change — not a bug fix.
