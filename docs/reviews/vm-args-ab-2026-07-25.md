## 0. The packaging bug — none of #2 was ever running

Reading the limits back out of a booted rig node gave `dirty_io: 10`, i.e. the ERTS default, on an
image built from a tree that contains `rel/vm.args.eex` with `+SDio 64`. The rendered
`/app/releases/*/vm.args` inside the container had **no non-comment lines at all**.

Cause: neither `deploy/chaos/Dockerfile` nor `deploy/compose/Dockerfile` copied `fathom/rel`, and
both per-Dockerfile `.dockerignore` whitelists excluded it. `mix release` does not fail when the
template is missing — it **generates a default `vm.args`**. The build succeeds, the release boots,
and every flag silently vanishes.

`deploy/compose/Dockerfile` is described in its own header as "the canonical deployable image", so
this shipped ERTS defaults to every container deployment while the release was believed to be tuned.

The 2026-07-24 write-up's verification (`MIX_ENV=prod mix release` locally, then read the limits
back) was correct *and* passed — a local release built from the repo root does pick `rel/` up. The
gap is only in the container build context.

Fixed in both Dockerfiles + both `.dockerignore`s, with a guard
(`test/fathom/release_packaging_test.exs`) that pins the packaging rather than the values: any image
running `mix release` must `COPY fathom/rel rel` before it, and any deny-all `.dockerignore` in
front of such an image must whitelist it. The guard fails on the pre-fix tree (2/4) and passes after.

**Lesson, and it is the same one as #9's first test:** a config value must be read back out of the
*running system*. A test that asserts the template renders correctly passes either way.

## 1. #2 — `+SDio` (dirty-IO schedulers): the hypothesis is refuted

Method: same image, same workload, only `ERL_ZFLAGS="+SDio N"` differs (ERTS applies `ERL_ZFLAGS`
after `vm.args`, so it wins). `tpc-fleet` at 256/512/1024 tenants, 50 txns each, 100 accounts.
**Two passes, the second in reverse order**, so host drift cannot masquerade as an effect.

The run-queue probe the review asked for needed fixing first:
`:erlang.statistics(:dirty_io_run_queue)` **is not a valid stat item** and raises. The dirty-IO
queue is the **last element** of `:erlang.statistics(:run_queue_lengths_all)` (normal schedulers,
then dirty-CPU, then dirty-IO). Sampled in-node at 10 ms.

### Throughput (txn/s)

| `+SDio` | pass | 256 | 512 | 1024 |
|---|---|---|---|---|
| **10** | A | **3903.4** | **3794.6** | **3659.6** |
| **10** | B | **4083.1** | **3815.7** | **3679.4** |
| 64 | A | 3725.4 | 3438.2 | 3328.5 |
| 64 | B | 3650.5 | 3273.9 | 3389.1 |
| 256 | A | 3678.6 | 3416.8 | 3355.2 |
| 256 | B | 3610.4 | 3337.8 | 3331.7 |

### Dirty-IO run queue (the direct proof)

| `+SDio` | pass | samples | max | mean | non-zero |
|---|---|---|---|---|---|
| 10 | A | 7730 | 39 | 1.151 | 34.1% |
| 10 | B | 7707 | 43 | 1.680 | 35.3% |
| 64 | A | 8287 | 13 | 0.384 | 23.8% |
| 64 | B | 8386 | 8 | 0.375 | 23.9% |
| 256 | A | 8336 | 8 | 0.374 | 23.3% |
| 256 | B | 8430 | 8 | 0.373 | 23.6% |

**The mechanism is exactly as the review described, and the conclusion is backwards.** At the
default of 10 there IS a standing dirty-IO queue (mean 1.2–1.7, max ~40, non-zero a third of the
time). Raising to 64 drains it — mean falls 4×, max falls 3–5×. 64 → 256 changes nothing further
(mean 0.373 vs 0.374), so the drain saturates.

Draining it **costs ~9% throughput at every tenant count, in both passes, in both orders.** The
bottleneck is CPU, not dirty-IO thread count: this box runs three nodes + the LB + the driver on 12
vCPUs, so more runnable OS threads buy context switching, and the queue at 10 is useful
backpressure rather than a stall.

Reverted to `+SDio 10` (the ERTS default), written explicitly so the number stays attached to its
measurement.

**Not settled for every deployment.** The review's mechanism — threads *block* on fsync under
`synchronous=FULL` — scales with fsync latency, and this rig's fsync is a local VM disk. Cloud block
storage at ~0.5–1 ms could invert the result. Re-run before raising it:

```
cd deploy/chaos && ERL_ZFLAGS="+SDio N" ./chaos.sh up && ./chaos.sh tpc-fleet 1024
```

### `+P` / `+Q` / `+IOt` / `+IOp`

Live defaults read back from a booted node on this OTP: **`+P 1048576`, `+Q 65536`** — not the
`+P 262144` the review took from the docs. So `+P 1048576` is a **no-op** that documents the value
we depend on, and `+Q 262144` is the only real change of the pair. `+Q` is a hard availability
cliff, not a perf knob, so it stays without a throughput claim.

`+IOt 4 / +IOp 2` vs the ERTS default `1 / 1`, same two-pass method:

| config | pass | 256 | 512 | 1024 |
|---|---|---|---|---|
| `+IOt 4 +IOp 2` | A | 3823.8 | 3701.6 | 3649.2 |
| `+IOt 4 +IOp 2` | B | 4089.8 | 3693.3 | 3591.7 |
| default `1 / 1` | A | 3989.9 | 3728.2 | 3650.2 |
| default `1 / 1` | B | 3991.1 | 3735.4 | 3608.0 |

**Neutral** — the spread within one config exceeds the gap between configs. Kept (5 extra OS threads
is free), now labelled measured-neutral rather than unmeasured. The regime it was argued for — 30k+
held sockets per node — is not what a 1024-tenant `tpc-fleet` exercises, so it remains open there.

## 2. #6 — accept queue: the premise does not reproduce

Method: `tpcc-fleet` at 2048 and 4096 tenants, in-network driver, diffing the kernel's own
`TcpExt.ListenOverflows` / `ListenDrops` from `/proc/net/netstat` across the run on all three nodes
**and** the LB (each container has its own netns).

- **pre-fix**: `num_listen_sockets: 1`, `backlog: 1024` (ThousandIsland's default shape)
- **post-fix**: `num_listen_sockets: 4`, `backlog: 4096`, `reuseport: true`

Both read back live from `Fathom.Application.hrana_transport_options/0` on the running node.
Container `somaxconn` is **4096**, so the 4096 backlog was **not** clamped — the A/B is valid.

| side | tenants | tpmC | txn/s | p99 ms | errors | ListenOverflows Δ |
|---|---|---|---|---|---|---|
| pre-fix | 2048 | 20309.9 | 742.8 | 1120.39 | **0** | **0** (all 3 nodes + LB) |
| pre-fix | 4096 | 18027.2 | 666.4 | 1171.33 | **0** | **0** |
| post-fix | 2048 | 19869.8 | 728.8 | 1064.56 | **0** | **0** |
| post-fix | 4096 | 17777.1 | 657.0 | 1162.46 | **0** | **0** |

**Zero accept-queue overflows on either side, including the pre-fix single 1024-slot queue at 4096
tenants — and zero driver errors.** The shed the fix was aimed at does not occur on this rig today,
so there is nothing for the fix to remove. Throughput is neutral (post-fix ~2% lower, inside the
run-to-run spread seen in §1).

This does **not** mean the accept path was never the problem — it means the 4096-tenant shed is not
reproducing here, and when it does not reproduce, the accept queue is demonstrably not the thing
that is full. A separate root-cause investigation of that shed exists
(`docs/reviews/` 2026-07-24 tpcc-4096 work); this result is evidence *against* the accept-queue
explanation for it.

The fix is kept: it is free, it is correct, and `somaxconn` on a real node may differ from 4096. But
**#6's payoff claim is withdrawn, not proven.** The knobs are now reachable on a release
(`HRANA_LISTEN_SOCKETS`, `HRANA_BACKLOG`) — previously `1` was documented as the escape hatch for a
node that boot-loops on `reuseport`, while being settable only at compile time, i.e. unreachable on
the release that would be boot-looping.

## 3. #9 — coordinator GC policy: real, and ~4× smaller than claimed

**`chaos.sh density` cannot measure this.** Its sampler runs
`Enum.each(Process.list(), &:erlang.garbage_collect/1)` before reading memory, and
`:erlang.garbage_collect/1` defaults to a **major** collection — precisely what `fullsweep_after: 0`
automates. Both sides converge by construction, and indeed both report "~7 KiB/shard". This is the
same trap that made #9's first guard pass against broken code.

Method instead: mint 30 000 shards through the LB (10k/node), **settle 40 s** past
`hibernate_after: 30_000` (half the policy — measuring straight after the mint burst only exercises
the fullsweep half), then measure the summed coordinator heap **with no forced GC**, then force a
major GC on the coordinators only and re-measure. The delta is retained-but-reclaimable heap: what
the policy is supposed to prevent accumulating. `fullsweep_after` was read back off live coordinator
processes on both sides (0 and 65535) before trusting either run.

| | retained heap | KiB/shard | still reclaimable | density fleet RSS Δ |
|---|---|---|---|---|
| pre-fix (`65535`, no hibernate) | 88.4 MiB | 3.02 | 7.0 MiB (7.9%) | 625 MB |
| post-fix (`0` + `hibernate_after`) | **58.8 MiB** | **2.01** | **0.0 MiB (0.0%)** | **414 MB** |

**The policy works.** Retained coordinator heap drops **33%** (−29.6 MiB fleet-wide, ~10 MiB/node),
and post-fix a forced major GC finds **nothing left to reclaim** — the steady state is fully
collected. The density harness's own fleet RSS delta drops 625 → 414 MB (**−211 MB fleet, ~70
MB/node**).

**The ~810 MB/node claim is not supported.** That number assumed 30k coordinators *per node*; at the
10k/node this run actually holds, the pro-rated claim is ~270 MB/node against a measured ~70 MB/node
of RSS (or ~10 MiB/node of coordinator heap). The 16 KiB → 43 KiB gap between a never-served and a
served coordinator was attributed entirely to reclaimable GC residue; only a fraction of it is.

**Mechanistically, hibernation is doing most of the work, not `fullsweep_after`.** A calibration run
at 6 000 shards measured *without* settling still showed 28.7% reclaimable on the post-fix build;
after settling past `hibernate_after` it is 0.0%. `fullsweep_after: 0` only forces a full sweep when
a collection happens at all, and an idle coordinator that stopped allocating (which #10's removal of
the idle tick made possible) never triggers one.

Kept as-is. `max_heap_size` remains correctly absent.

## Reproducing

Scripts used are throwaway harnesses, not committed; each is ~40 lines around `chaos.sh`. The four
things worth carrying forward:

1. `ERL_ZFLAGS` and `HRANA_LISTEN_SOCKETS` / `HRANA_BACKLOG` are now passed through
   `deploy/chaos/docker-compose.yml`, so a VM-flag or accept-path A/B is a restart, not a rebuild.
2. The dirty-IO run queue is `List.last(:erlang.statistics(:run_queue_lengths_all))`.
3. Any memory A/B must avoid `chaos.sh density`'s forced GC and must settle past `hibernate_after`.
4. Read every configured value back off the running node before trusting a side of an A/B. Three of
   the four findings here turned on that step: `rel/` missing from the image, `HRANA_BACKLOG` not yet
   in the baked-in `runtime.exs`, and `fullsweep_after` on live coordinator processes.
