## Shard data path

**Shard data path.** One **connection per Hrana stream** (`Fathom.Shard.Connection`, an `exqlite` connection to the shard file, WAL + busy_timeout), opened at stream start and closed at stream end, so transactions are isolated. A stream also **monitors its coordinator** (Filo's `Executor.owner/1` seam) and tears down if it dies — an orphan writer's WAL frames would be lost by a successor's flush-and-drop (finding #8). `Fathom.Shard` is the per-shard **coordinator** (one GenServer per active shard) owning the file lifecycle: on cold start it **pulls** the file from `Fathom.Shard.Storage`; it tracks checked-out connections (monitoring the stream processes); when idle with zero connections it **checkpoints + flushes** the file back to storage, drops the local copy, and stops — so a flush never races a write, and the local copy is bottomless-backed. All flushes are **write-gated by a `dirty` flag** (set by `ShardExecutor` on a write): a clean read-only/idle shard skips the upload, so durability PUTs track writes, not open-shard count. `Fathom.Shards` is the find-or-start router (`Fathom.ShardRegistry` + `Fathom.ShardSupervisor`); `Fathom.Shards.checkout/1` resolves a `shard_id` to its coordinator, starting it on demand, and returns `{:ok, pid, ref, path}`. **The shard engine is exqlite** (SQLite via `Exqlite.Sqlite3`, wrapped by `Fathom.Shard.Connection`) — decided 2026-07-06: the `Ecto`/`ecto_libsql` path was evaluated and **removed** (the data plane is a SQL proxy over opaque client SQL, which gains nothing from Ecto's schema layer and pays per-query overhead + a Rust NIF for it). `Fathom.Shard.Connection` is the single swap-point if a client ever needs the libSQL *engine* for compatibility. Rationale in `docs/cluster-architecture.md`. **Per-query resource bounds (review #26, all config-gated, off by default)** protect co-located tenants from one runaway query: `:query_timeout_ms` (a watchdog `Sqlite3.interrupt`s the connection at the deadline → 503 `FILO_QUERY_TIMEOUT`), `:query_max_rows` (`Connection.collect/2` errors past the cap instead of materializing an unbounded result → 400 `FILO_RESULT_TOO_LARGE`), and `:max_checkouts_per_shard` (the coordinator refuses a checkout past the cap → 503 `FILO_SHARD_BUSY`, so one tenant can't monopolize a node's streams or wedge the shard un-drainable). **Prod defaults since expert review 2026-10-08 #8:** `MAX_CHECKOUTS_PER_SHARD=256` (a Django worker/thread holds one stream, and all of a tenant's workers land on its one node; 64 was tried first and the bench gate refused it — its same-shard metric runs 72 workers on one shard), and a node-wide SQLite `soft_heap_limit` of 8 GiB (`SHARD_SOFT_HEAP_LIMIT_BYTES`) applied once at boot by `Connection.apply_soft_heap_limit/0` from a trusted `:memory:` connection — process-global in SQLite (probed: a value set on one connection reads back on already-open and new ones), and SOFT, so past it the page cache recycles instead of growing and no statement fails (probe: 4 × 200 MB-cache scans grew memory ~505 MiB unbounded vs ~61 MiB at 64 MiB). It closes the gap `:shard_cache_size_kb` leaves: that ceiling is per connection, so total cache was held streams × 2 MiB. Never `hard_heap_limit` (fails allocations with `SQLITE_NOMEM`). Both are prod-gated; dev/test are unchanged. **How it works end to end** — the request→stream→connection→coordinator lifecycle, the orphan-writer monitor, and the idle/dirty flush — is `docs/data-path.md`; the durability/RPO contract (WAL + `synchronous=FULL` + the write-gated periodic flush) is `docs/durability.md`. **Coordinator decomposition (2026-09-13/14).** `Fathom.Shard` had grown to **5,032 lines** owning a dozen concerns. It was reduced to **~3,849** by extracting six **behavior-preserving** modules (each its own commit, precommit-green + bench-gated), in dependency order: `Fathom.Shard.Position` (WAL-ordinal / object-position stamping — a **pure** module owned by *neither* flush nor promote because both stamp the object), `Provenance` (the `<path>.etag` sidecar I/O; `Fathom.Shard.stamp_local_provenance/1` stays as a thin public seam and delegates), `Integrity` (`quick_check` + `quarantine_corrupt!`; `verify_integrity/1` stays as a public wrapper), `Fork` (warm-restart fork detection — `evidence/2` observe-only + `resolve/4` post-lease verdict + `quarantine!/3`), `Materializer` (the S3-pull / warm-promotion open path — the one concern that **blocks on the network**, the same reason `Session` was split out), and `PromoteOnOpen` (A2 failover promote). **The seam principle, and the trap:** the extractions were chosen for LOW state-coupling; what deliberately **stays** in `Fathom.Shard` is the cross-cutting **fence envelope** — lease validity ↔ flush fence ↔ `dirty`/`flushed_through` ↔ drop/terminate ↔ heartbeat-lapse — which share one consistency envelope over `lease`, `etag`, `acquire_gen`, `lease_lost`, `flushed_through`, `not_valid_since`. **Do not "finish the job" by splitting that core**: a naive feature-split there reintroduces exactly the split-brain the lease fence exists to prevent. Two functions were left behind on purpose despite looking extractable — `quarantine_fenced!/1` (coupled to `drop_local/1` + the write-counter watermark) and the pull-region's `subscribe_lapse/lapse_subscribe_failed` (heartbeat concern, not materialization). Traps the move surfaced: extracting `flush_position` made its no-lease clause *reachable* (a `pattern_match_cov` dialyzer filter became unnecessary and was dropped), and a long-standing `pattern_match` filter *misattributed* to `shard.ex:1` as a "GenServer child_spec macro" turned out to be `PromoteOnOpen.elem_reason/1`'s defensive `else` — it relocated with the code and the comment was corrected. `@pull_timeout` is intentionally duplicated in `Fathom.Shard` (needs it as a compile-time constant for the open/checkout budget) and `Materializer`.
## Shard storage

**Shard storage.** `Fathom.Shard.Storage` is a `pull/2` + `flush/2` behaviour, backend chosen by `config :fathom, :shard_storage` — `Fathom.Shard.Storage.Local` (a filesystem object store, the default for dev/test) or `Fathom.Shard.Storage.S3` (Req + `aws_sigv4`, no AWS dep; works with S3 / R2 / Tigris / MinIO). A present local file is authoritative on wake (pull only on cold start), so an un-flushed shard is never clobbered.
## Shard storage: the flat 60 s pull timeout is deliberate **Env-config footguns refuse rather than weaken** (expert review 2026-11-07 #81): `env_bool` in `config/runtime.exs` raises on anything but true/false/1/0 (case-insensitive; empty = unset — compose passes `X: "${X:-}"`), which reverses the 2026-11-06 #8 "identical behavior" decision for booleans (that sweep was about integers); `MAX_OPEN_SHARDS` ≤ 0 raises (0 refused every new open; there is no env spelling of unlimited, and raising beats guessing which 0 was meant); `SHARD_LEASE_TTL_MS` is bounded to [5 s, 10 min] (the write-validity margin is ttl/3); `SHARD_FLUSH_INTERVAL_MS` ≤ 0 warns in prod but boots (idle-only durability is a documented mode); `LB_BACKENDS` keys that collide after `LbMap.upstream_name/1`'s sanitising are refused at parse time. The obvious-looking fix for the collision — an injective upstream-name encoding — was rejected: it renames the upstream of every existing key containing `_`, `-` or `.` (the chaos LB's checked-in `exceptions.conf`) to cure a collision only near-identical keys can have.

`Fathom.Shard.Materializer` bounds a `pull/2` with a flat `Task.yield(task, 60_000)` that covers the
retries too, and a partial download is not resumed. Expert review 2026-10-10 #28 proposed a
progress-based deadline that resets on each byte received. **Decision (2026-10-10): keep the flat
timeout (WONTFIX).** Reasons:

- The design targets small shards. A shard is capped at 4 GiB, so a full pull inside 60 s is the
  normal case. A pull that runs past it signals a slow store or a wedged transfer, and an operator
  should see that rather than wait it out.
- The checkout budget is derived from this value (`pull + 15 s`, see `Fathom.Shard`). A
  progress-based deadline would make the checkout bound open-ended as well.

Revisit if the size cap rises, or if a real tenant starts hitting the timeout in production.

## Network protocol

**Network protocol.** `Fathom.ShardExecutor` (a `Filo.Executor`) binds each Hrana stream to a shard. The **Filo** library (separate repo, `{:filo, path: "../filo"}`) speaks the libSQL Hrana wire protocol — HTTP v1/v2/v3 (+ cursor) and WebSocket hrana1/2/3 — on its own Bandit listener (`:hrana_port`, default 8080; gated by `:hrana_server`, off in test), separate from the web/dashboard endpoint on 4000. `django-libsql` (WebSocket) and `libsql-experimental`/SDKs (HTTP) both work end to end.
## Shard selection + admission

**Shard selection + admission.** The shard comes from the request's **Host subdomain** (`acme.fathom.example` → `acme`; case-normalized via `Fathom.ShardId.cast` so `ACME`/`acme` are one shard — finding #19). `?db=` / `x-fathom-shard` are **dev-only** fallbacks gated by `:allow_shard_override` (off in prod — finding #4). When nothing resolves, the fallback is `:default_shard` — **unset in prod ⇒ fail closed with a 400**, not commingling into a shared shard (finding #26); dev/test set it to `"demo"`. **Novel-shard admission is double-gated** (finding #14): `:max_open_shards` caps how many shards a node holds open, and `Fathom.Shards.NovelLimiter` (`:novel_shard_rate`, off by default; `NOVEL_SHARD_RATE` in prod) rate-limits how fast *unseen* ids can mint new shards (429 over budget; existing shards — directory row, local file, or running coordinator — are never limited, and the directory check fails open on a Postgres outage). The cap is a **soft cap by default**: at the limit, a new open **evicts the least-recently-used *idle* shard** (flush + drop + release lease — `Fathom.Shards.Lru` + `drain/2`, `[:fathom,:shards,:evicted]` telemetry) rather than 503ing, since a shard's LB home is one node so a refused open means that tenant is down, while an idle shard is bottomless-backed and just cold-re-opens. A **busy** shard (checked-out connections) is never evicted; if the LRU-coldest handful are all busy the node is genuinely saturated and returns 503 (`[:fathom,:shards,:at_capacity]`). Set `:evict_idle_at_capacity` false for a hard cap (503 at the limit). Either way the open count stays bounded by the cap (the fd-cliff protection). **Template capture** (`:template_shard_id`, off in prod by default) records a shard's SQL for fleet-wide replay, so it's a poisoning vector if reachable anonymously: never set a prod template shard without auth on it, and never make `:default_shard` equal it — `Fathom.Application.check_template_default!` refuses that config at prod boot (finding #17). **How it works end to end** — the fail-closed Host routing, the double gate (soft `:max_open_shards` cap + LRU idle-eviction, the novel-shard limiter), and the template-poisoning boot guards — is `docs/admission.md`.
## Auth

**Auth.** `Fathom.HranaAuth`, gated by `:hrana_auth` (`:disabled` default in dev/test; prod refuses to boot unless `HRANA_AUTH` is set explicitly to `required` or `disabled` (`config/runtime.exs`); an unknown `HRANA_AUTH` value raises at boot; a boot guard refuses `:required` without a usable secret). A per-shard `Phoenix.Token` (signed with `secret_key_base`, minted via `mix fathom.token <shard>`) is presented as libSQL's `authToken` — an `Authorization: Bearer` header over HTTP, the Hrana `hello`'s `jwt` field over WebSocket (ws clients send no upgrade header, which is why this is Filo's `:authorize` callback seam, not a pre-plug). With auth `:disabled` the trust boundary is the network — the port must be reachable only via the LB (firewall/SG/private subnet; pin the interface with `HRANA_BIND_IP`). See `docs/deploy-cluster.md`; **how it works end to end** — the two modes, the per-shard token on Filo's `:authorize` seam, the no-oracle posture, and the network trust boundary — is `docs/auth.md`. **Token lifecycle (review #24)**: **zero-downtime rotation** — `HranaAuth.rotate/1` raises the shard's `token_version` (stamping `token_version_bumped_at`) and mints a new token while `verify` keeps accepting the previous version for `:hrana_rotation_grace_ms` (default 1h); `revoke/1` (bumped_at cleared) stays immediate. **Read-only scope** — `token_for(id, scope: :ro)` embeds an `"sc"` claim; `authorize/2` stashes the scope and `Fathom.ShardExecutor` rides it in the connection handle, refusing any write on a `ro` token with **403 `FILO_READONLY`** (no Filo change — the scope is carried per-stream). A **boot warning** fires when `:required` runs with an infinite `max_age`. Mint/rotate/revoke are on the `/api/tenants/:id/token` control-plane API (#21). **Issuance ledger + fleet-wide revocation (review #37):** `hrana_token_issuances` records one row per mint (shard, `token_version`, scope, actor, `minted_at`) via `Fathom.HranaAuth.Ledger` — **claims only, never the secret**, since a Hrana token is verified by signature rather than lookup. Append-only: a revoke moves the floor, so `outstanding/1` reinterprets history against it while `history/1` keeps the audit trail. Recording is best-effort and **never fails a mint** (`mix fathom.token` has no Repo), so the ledger under-reports rather than over-reports — the safe direction for `HranaAuth.revoke_issued_before(cutoff, opts)`, the time-scoped bulk revoke that bumps the floor on every shard with an outstanding pre-cutoff token, paced per-shard through Oban's `:tokens` queue (`RevokeJob`) and **idempotent** so a re-run is a no-op rather than a second round of disconnects. Before this the only fleet-wide lever was rotating `secret_key_base` — an outage, not a revocation. Also: `:hrana_token_max_age` unset under `:required` now **REFUSES to boot in prod** (was a warning) — rotation is zero-downtime, so immortal tokens no longer buy anything.

**Auth — the cold-miss storage-floor read is one bounded attempt (expert review 2026-10-29 #20).** `HranaAuth.Revocations.read_through/2` reads the directory floor and the S3 `tokenfloors/<id>` object concurrently on a cold miss, on the `hello` path before checkout. It was `Task.await(…, :infinity)` over the shared `build_req/1` GET (Req's `:safe_transient` retries + 15 s receive / 5 s pool per attempt), and the fail-open fallback repeated it, so a stalled store held a hello ~60 s and the second read doubled it. Fixed with PER-CALL options on that one GET (`Storage.read_token_floor/2`, `budget_ms:` → `retry: false`, `receive_timeout`, `finch: [pool_timeout]`) — **`build_req/1` is shared with lease/flush/heartbeat and must not be changed for this** (that would make it Jepsen-gated) — plus `Task.yield(task, remaining) || Task.shutdown`, a per-shard `:ets.insert_new` single-flight (claimant + monitored followers, crash hand-over), and `HRANA_STORAGE_FLOOR_BUDGET_MS` (default 3 s, from the heartbeat's `renew_ms/3` per-attempt pattern). A storage read that cannot finish maps to the existing `:hrana_revocation_on_error` posture: `:fail_closed` → `:unavailable`, `:fail_open` → the directory floor, **not cached** (caching it would let a directory-only answer stand in for the PITR backstop for a TTL). **Uncached alone was a trap** (review of 9a97ec71, 2026-10-31): every later hello for that cold shard went back to storage and paid the whole budget, so an S3 outage added 3 s to every connection open. A failed read now starts a per-shard cool-down (`:hrana_storage_floor_backoff_ms`, default 30 s, in its own ETS table, NOT the floor cache) in which the shard's cold hellos take the posture at once. Per shard, not node-wide, so one bad object cannot switch off the backstop fleet-wide. The floor is still unioned on every success path — the storage floor is the PITR backstop, and answering a miss from bulk completeness is an auth bypass. Two traps: `Req.merge` replaces `:finch` wholesale, so the per-call `finch:` must re-state the pool name (`finch_opts/1`); and a stalled store surfaces as a transport error as often as a `Task.yield` timeout, so a fast storage error must be classed with the timeout, not read as floor 0. Not done: the LIST-in-bulk-reload route (it needs a deliberate completeness marker because of PITR) and starting the floor GET concurrently with checkout.
## Postgres — `Fathom.Repo`

**Postgres — `Fathom.Repo`.** The orchestration store and web UI backend, in the supervision tree (Phoenix dashboard on port 4000). It also backs the shard **directory / control plane** below; migrations live in `priv/repo/migrations/` (`shards` directory, `shard_migrations`, Oban jobs).
## Directory / control plane

**Directory / control plane.** `Fathom.Directory` (+ the `Fathom.Directory.Shard` Ecto schema) is the Postgres record of each shard's `schema_version`, lifecycle `status` (`active`/`migrating`/`retired`/`migration_failed`/`deleted`/`suspended`), `last_active_at`, and `retain_until`. It's the source of truth the rollout/migration machinery reads and flips (`resolve`, `cutover`, `retire`, `laggards`). It's decoupled from the data path: per-checkout accesses are **buffered + batch-flushed off the hot path** by `Fathom.Directory.Recorder` (a coalescing ETS buffer; a Postgres outage drops a flush, never a checkout). It also persists **`last_flushed_at`** (review #28) via a parallel Recorder buffer hooked at each successful upload, so a post-node-loss report survives the node: `Fathom.Directory.flush_lag_report/1` (and `mix fathom.shard loss-report`) list the shards active-since-their-last-flush with per-tenant loss windows (the node-local `FlushWatermark` ETS dies with the node). **How it works end to end** — the recorder's lock-free ETS coalesce + batch-flush + outage-safe re-buffer, and what the directory holds for the migration/rebalancing/warm-standby readers — is `docs/directory.md`.
## Migration engine

**Migration engine.** `Fathom.Migrator` runs blue/green per-shard schema migration: `Migrator.Capture` records template migrations into fleet versions, `Migrator.Copy` + `Migrator.ShardMigration` do the copy+transform and stamp `user_version`, `Migrator.Release` releases a fleet HEAD, and Oban jobs drive it — `ShardMigrationJob` (unique per shard), `ReconcileJob` (hourly cron sweep so the cold tail converges), `RetirementJob` (drop expired retained versions), `RevertJob` (fleet pointer-flip back; a revert backs up the live version first, and a **write-age force-guard** refuses a shard the directory shows active since its `cutover_at` — the job cancels, deterministically — unless `force: true` confirms discarding the post-cutover writes). There is **no `Fathom.ShardExec` or `Fathom.Retirement` module** — that work lives in `Migrator.Copy`/`ShardMigration` and `Migrator.RetirementJob`; don't grep for the old names. **Capture strips Django's own introspection before recording (2026-08-14, `Capture.pure_read?/1`).** Its schema editor interleaves `SELECT … sqlite_master`, `SELECT QUOTE(?)…` and `PRAGMA foreign_key_check` with the DDL, so a captured version carried "what Django looked at" alongside "what the migration does", and **every tenant re-ran the lot, once per version in the chain**. `foreign_key_check` scans every FK'd table — free on the empty template, not on a tenant: replaying `0002_budget` measured **6 → 13 → 29 → 109 ms at 4 / 19 / 40 / 160 MB with the reads vs 4 → 7 → 17 → 57 ms without**, i.e. the reads are ~33–48% of the step and the gap grows with tenant size, to produce a result `Copy.replay_each/2` discards (so a violation it found was already being ignored). Proven inert before being acted on: replaying the real `django_migrate_capture.json` fixture with them removed yields a byte-identical `sqlite_master`, `user_version` and `django_migrations`. **The allowlist is the safety property, and it fails closed** — `SELECT` is dropped unconditionally (nothing in SQLite mutates through one), PRAGMAs only if the NAME is in `@read_only_pragmas` *and* there is no assignment, so `foreign_keys = OFF`, `legacy_alter_table = ON`, `optimize` and anything unrecognized all survive; `WITH` is deliberately not matched because `WITH … INSERT` is valid SQLite. Two traps worth keeping: the filter runs on the `{sql, args}` **pairs**, never the two parallel lists separately — filtering statements alone would shift the bookkeeping INSERT onto a dropped read's args, silently reviving the NULL-binding class of bug `beff929` fixed; and the assignment check was **dead code in the first draft** (it tested the whole body for `=` before extracting the name, so the allowlist had already rejected `"foreign_keys = OFF"` as a string) — found only because breaking it deliberately changed no test, which is the same "prove it discriminates in BOTH directions" habit the rest of this file records. **How it works end to end** — the three-place version stamp, the copy-then-flip, cold-tail convergence, the guarded revert, and cross-version tolerance during a mixed vN-1/vN rollout — is `docs/migration.md`.

**`mix fathom.check_migrations` matches the spellings people write (expert review 2026-11-07 #65).** `@atomic_false` required nothing after `False` but whitespace, so `atomic = False  # CREATE INDEX CONCURRENTLY` (the idiom is nearly always explained in a comment), `atomic = False;` and `atomic: bool = False` all scanned clean: CI went green, `manage.py migrate` ran in autocommit on the template, and capture — which can only see a tracked transaction — never heard of it until the NEXT capture's `migration_gap`. The pattern now accepts an optional `: bool` annotation, `;` and a trailing comment, and is anchored to the start of the LINE (`[ \t]`, not `\s`, so it cannot slide over a newline), so a `# atomic = False` comment line and `Falsey` still do not match; a docstring line that is exactly `atomic = False` stays a documented false positive. `RunPython`/`RunSQL` are also recognised in their import form (`from django.db.migrations import RunPython`, then a bare `RunPython(...)`), which the dotted pattern could not see. Test: `check_migrations_test.exs` (pre-fix: 6 of the 16 fail).
## Tenant lifecycle — delete + export (`Fathom.Tenants`, review #15)

**Tenant lifecycle — delete + export (`Fathom.Tenants`, review #15).** The whole-shard operations the migration engine left out of scope: GDPR-erasure/offboarding **delete** and portability **export** (a tenant *is* one SQLite file). `Tenants.delete/1` tombstones the directory row (`deleted` status) and broadcasts the tombstone fleet-wide **synchronously**, then enqueues `Fathom.Tenants.DeleteJob` (queue `:tenants`, unique per shard) for the durable erase: cancel pending per-shard Oban jobs → **force-stop** the home coordinator (`Fathom.Shards.stop/1` terminates it *while its lease is valid* so shutdown flushes/releases cleanly and never self-fences — the fix for a real leak where a graceful drain couldn't stop a busy coordinator, which then quarantined the erased data to a `.fenced.<ts>` file) → `Storage.purge_shard/1` deletes **every** stored object (live `.db`, `.lock`, all `@<version>`, all `@snap-<id>`; exact id-delimiter match so purging `acme` never touches `acme2`) → sweep local files. Purging is safe even if another live node still holds the lease: every coordinator flush is fenced (`If-Match`), so the deleted live object makes that node self-fence on its next flush instead of resurrecting it. The **re-mint guard** is `Fathom.Tenants.Tombstones` — a public ETS set of deleted ids checked O(1) in admission (`start_if_capacity` first branch ⇒ `{:error, :shard_tombstoned}`, off the Postgres hot path), loaded from the directory at boot, pushed on delete over Oban's notifier, and periodically refreshed — so a stray request for a deleted subdomain is refused, never re-minted as an empty shard. **Export** is `Tenants.export/1` (pull the durable object to a temp file) served by `GET /admin/tenants/:id/export` (BasicAuth `send_download`, temp deleted after — never a public URL); `AdminDirectoryLive` gets per-row Delete (with confirm) + Export actions, and `deleted` is excluded from hand-editable statuses. **No feature flag** — inert until an operator invokes it. Cross-node drain of a *busy* remote shard via the `rebalance_commands`/`command_poller` path is a follow-up (single-home + the fenced-flush self-fence cover correctness today). **Provisioning (review #21)** completes the control plane: `Tenants.provision/1` (explicit directory insert + fork-from-template birth when `:fork_from_template` is on + token mint, returning the `libsql://<id>.<base>` URL + `auth_token`) and `FathomWeb.Api.TenantController` — a JSON create/list/get/delete API under `/api`, behind the same admin BasicAuth on `:4000` (separate from the Hrana port), so a platform customer creates/lists/deletes tenants instead of relying on traffic-implied minting. **Suspend/resume (review #20)** is the administrative-offline lever short of deletion: a `suspended` status + `Fathom.Tenants.Suspensions` (the Tombstones ETS gate but reversible — add/remove notification + periodic reconcile). `Tenants.suspend/1` flips the directory, broadcasts so every node denies new streams, and graceful-drains the home coordinator; `resume/1` reverses it. **Both lifecycle denies live in `Fathom.Shards.ensure/1`** (checked on every checkout, O(1) ETS) so a deleted/suspended tenant is refused even with a running coordinator; a suspended open is a distinct **403 `FILO_TENANT_SUSPENDED`** and a deleted one a **410 `FILO_TENANT_DELETED`**. `POST /api/tenants/:id/{suspend,resume}` + admin Suspend/Resume buttons. **Fork + operator tooling (review #14)**: `mix fathom.shard pull|inspect|fork` (`inspect` = a per-shard restore drill: pull + `quick_check` + row counts) and **database forking** — `Storage.fork_shard/2` (one object copy) + `Tenants.fork/2` (clones a live tenant to a new id, registering the dst at the *source* schema version so the laggard sweep won't re-migrate the fork; non-disruptive to src) + `POST /api/tenants/:id/fork`. **How it works end to end** is `docs/tenant-lifecycle.md`.

**Delete revokes tokens; the token-floor mirror is monotonic and backfilled; a reused id is seeded (expert review 2026-11-07 #1, #30, #35).** `Tenants.delete/1` used to end a tenant's data but not its credentials: every token stayed valid, and once the id was freed (hard-delete the row, drop the `tombstones/<id>` marker, restart) `provision/1` inserted a fresh row at `token_version` 1 against a `tokenfloors/<id>` that was never raised, so the old holder's v1 tokens verified against the new tenant's database — and the "obvious" fix of revoking alone strands the new tenant (its v1 token is *below* the durable floor). Both halves ship together: `delete/1` calls `HranaAuth.revoke/1` after the tombstone upsert (a failure is returned as `{:error, {:revoke_failed, _}}` only after the tombstone, broadcast and job are in place — `delete/1` is idempotent, re-run it), `purge/1` re-drives `HranaAuth.mirror_floor/1` under the DeleteJob's retries, and `provision/2` / `register_fork/1` seed a new row at `max(1, Storage.read_token_floor + 1)` (the `+ 1` covers a final mirror write that never landed; an unreadable store REFUSES the birth). **Do NOT purge `tokenfloors/<id>` instead** — it is the Postgres-PITR backstop, and the seed must read the MAX because each delete re-run bumps once more. The old `tenant-lifecycle.md` reuse step ("hard-delete the row and let the tombstone set refresh") never worked: the storage marker is unioned back at boot and the in-memory set is append-only; the recipe now lives in `docs/tenant-lifecycle.md` and the DR runbook. The mirror itself (`Storage.put_token_floor/2`) was one blind PUT, so two bumps arriving out of order (a revoke racing a `RevokeJob`) LOWERED the durable floor; it is now `max(stored, version)` — S3 GET + conditional PUT (`If-Match` / `If-None-Match: *`, re-read on 412/404/409, 4 attempts), Local under the node-local mutex — and the comment promising "the reconcile sweep backfills it" was false (reconcile only read storage → directory), so `Directory.Reconcile` now also writes directory → storage (`:token_backfill`, deleted rows included). `token_for/2` no longer rescues a directory read failure to version 1 (a token dead on arrival that the API returned as 200): it returns `{:error, :version_unavailable}` (API 503; `provision`/`fork` → `{:token_mint_failed, _}`), and `rotate/2` mints at the version its bump returned. A row born at version 1 by a stray request is repaired by `mix fathom.directory reconcile --fix` (raises to the floor, without the `+ 1`).

**The tombstone gate's boot window: the marker check on the open path (shipped) and the admission gate (PARKED for a maintainer decision) (expert review 2026-11-07 #14).** `Tombstones.init/1` returns before it loads (the 2026-10-13 #20 fix, on purpose), so DataPlane/Edge accept traffic while the ETS set is empty and `DenyList.status/0` reads `:ok` until a load has failed once. A node that missed a delete (down during it, or holding a clean-retained copy) still has the erased tenant's residue; a stray request opened the lease, found NO object, and took the "un-flushed brand-new shard" stance — serve the local copy, fence with nil, re-create the object and its `.lock` on the next flush. **Shipped:** the open path's two absent-object branches (`Shard.revalidate_against/5` `{:ok, nil}` and `Shard.post_lease_warm_check/4`, both through `Shard.object_gone/3`; the pre-lease `Fork.resolve(:absent)` verdict is always followed by `post_lease_warm_check`, so it needs no branch of its own) ask the durable `tombstones/<id>` marker (`Storage.tombstone_present?/1`: one HEAD / stat, PG-independent, ONLY on that rare branch, never on a normal open). Present ⇒ the local copy is ERASED (no quarantine — erasure outranks forensics, as in `erase_fenced!/1`) and the open is refused `:shard_tombstoned`; unreadable ⇒ the open is refused retryably (`{:tombstone_check_failed, _}`) and the copy is KEPT (serving blind is the resurrection, deleting blind may destroy a live tenant's un-flushed writes); a claimed clean-retained copy with no marker ⇒ discarded and pulled (it holds nothing the store lacks); anything else keeps the old stance (a live tenant's brand-new shard or an operator-deleted object still serves warm and re-creates — pinned by `test/fathom/shard/erased_open_gate_test.exs`). The `{:ok, nil}` clause of `post_lease_warm_check` moved ABOVE `{:ok, ^etag}` so a copy born here against no object (sidecar "no object", `etag` nil) is also checked. **Parked — decision for the maintainer:** make admission wait for the DIRECTORY half of the gate (a synchronous load with a deadline in `init/1`, as `Suspensions.init/1` does, or `/health` 503 until `loaded: true`). It would close the remaining residual — a node with NO local residue, booting while the directory is unreachable, whose request for an erased id meets an absent object opens a fresh EMPTY shard (the "empty shard re-mint" variant; no erased data is exposed, but the 410 contract is broken and the empty shard's flush creates objects the `ErasureSweepJob` then has to re-drive) — and it reverses review 2026-10-13 #20's stance that a node must serve while Postgres is down at boot. Options: (a) keep as shipped (accepted residual: empty shard, no data, swept); (b) sync directory load with a short deadline (e.g. 2 s) then proceed degraded (bounds the window without making Postgres a hard boot dependency; the existing `DenyList.degraded` signal already marks the rest); (c) hard-gate admission + `/health` 503 until loaded (closes it fully; a Postgres outage at fleet boot becomes a fleet-wide outage); (d) also check the storage marker on every cold-absent open (closes it without Postgres, costs one HEAD per novel shard — hot path, would need the bench gate and a measured number first). (b) and (d) are the options that keep the node serving through a Postgres outage; neither has been measured.

**Scratch forks are identified by provenance, not by name (expert review 2026-11-07 #15).** `ErasureSweepJob.sweep_scratch_forks/0` purged — objects, snapshots AND the directory row — every row older than 24 h whose id matched `^restoredrill[0-9]+$`, with no status filter and no activity check, and the rollout/drill sweeps excluded the same shape. The shape is only a *reservation* (`Tenants.provision/2` and `fork/3` refuse it; a Host subdomain, the token mint and `bump_token_version/1`'s register-if-unknown do not), so a LIVE tenant with such an id was destroyed a day after it was created. Chosen over "enforce the reservation in `Directory` for every writer" because that would have touched every birth path including the Recorder's insert and the checkout admission path, and the drill itself opens scratch ids: the drill's own fork now writes `shards.scratch = true` at birth (`Directory.resolve/2` `scratch: true`, via `Tenants.register_fork/2`; only the INSERT carries it, a re-resolve never marks or unmarks), `stale_scratch_ids/2` selects `scratch AND status <> 'deleted'`, and `exclude_scratch/1` keys on the column — so an organic `restoredrill42` is migrated and drilled like any tenant. The migration (`add_scratch_to_shards`) has NO backfill on purpose: a leaked drill row from before it cannot be told from an organic tenant of the same shape, and marking the latter re-creates the bug; such a row (a drill killed before this release) is a normal row from here on and is removed by hand (`Directory.hard_delete/1` + `Storage.purge_shard/1`).

**A fork re-checks both tombstones after the copy (expert review 2026-11-07 #16).** `Tenants.fork/3` read the source row and tombstone set once, before the optional source flush and the dst lease, so a `delete/1` landing in that window left the object (erase is async) and the atomic copy put the erased tenant's bytes under a new id with an `active` row and an `rw` token. `Snapshots.create/restore` already re-checked after their copy; fork now re-checks `Tombstones`/the directory row for BOTH ids after `Storage.fork_shard/2` with the dst lease held, and again before `register_fork/2`: erased ⇒ `Storage.purge_shard(dst)` and `{:error, :tombstoned}`, no row, no token. It deliberately does NOT call `delete(dst)` (that would tombstone the destination id permanently); a purge failure is returned and logged with the manual remedy. A delete on another node is seen once its NOTIFY lands; the source's hourly `ErasureSweepJob` re-drive is the backstop for that sliver.

**`erase_local_batch/1` attributes a timed-out stop by position, so the stream is ordered (expert review 2026-11-07 #66).** It zipped an `ordered: false` `Task.async_stream` with the input list; a timed-out stop carries no id, so with results in completion order a hung stop in the middle was blamed on the last id — the hung shard had no entry (`{id, nil}`), an unrelated one was recorded as failed with its own `:ok` overwritten, and `LocalEraser.erase_now/1` could return `nil`. It is `ordered: true` now (head-of-line affects delivery, not execution), with `:erase_local_stop` / `:erase_local_stop_timeout_ms` test seams.

**The full restore drill never overwrites a stored failure; an absent object on a long-active row is reported (expert review 2026-11-07 #67).** The full drill's `restore_one` recorded its verdict over the read drill's: its `ok` is the weaker one (`count(*)` can be answered from the smallest index b-tree without reading a table data page, and it never looks at snapshots), so a corrupt tenant read `ok` in the durable column the DR audit query reads. `Directory.record_verification/3 keep_failure: true` makes the full drill's `ok` never replace a stored failure (its own failures always land); running `Integrity.verify_full` on the scratch too was NOT added — it would double an O(rows) scan per sample for a verdict the read drill already owns. The absent-object half stays `:absent` by design (D5: a dropped flush stamp must not raise a false `:lost`) but is now visible: `[:fathom, :restore_drill, :absent_active]` (`fathom.restore_drill.absent_active.count`) fires for an object-less row with no `last_flushed_at` that was active more than a flush interval after it was created.

## Per-shard load counters (`Fathom.ShardLoad`) — the Phase-2 rebalancing (B) prerequisite

**Per-shard load counters (`Fathom.ShardLoad`) — the Phase-2 rebalancing (B) prerequisite.** A public ETS table of per-shard cumulative counters (checkouts, queries, `rows_read`/`rows_written` = query cost), bumped **lock-free from the executing process** (`:ets.update_counter`, `write_concurrency` — the `Directory.Recorder` pattern, no per-query GenServer hop) on `Fathom.Shards.checkout` and `Fathom.ShardExecutor.execute`; a stopped coordinator's row is dropped in `terminate` (`forget/1`). A control plane reads `top(n, by)` / `snapshot/0` to find hot shards (rates = diff two snapshots, churn-safe); the **first reader is `mix fathom.scale --hotspots`** (the §B evidence harness — see Benchmarking). Deliberately **not** a per-shard `Telemetry.Metrics` (a per-shard tag at millions of shards is cardinality death) — the read API is the interface. Gated by `:shard_load`, **on by default in prod** (2026-10-15; the admin dashboard reads it) and **off in dev/test** (the module default, so the hot path there doesn't pay for an unread counter); `SHARD_LOAD=false` turns it off in prod.
## Dynamic rebalancing — Phase 2 B1 (`Fathom.Rebalancer.*`, built 2026-07-06)

**Dynamic rebalancing — Phase 2 B1 (`Fathom.Rebalancer.*`, built 2026-07-06).** Moves a persistently-hot shard off an overloaded node by layering a per-subdomain **exception table** on the LB's consistent hash. Since there's no BEAM cluster (LB-partition coordinates via S3 for data, Postgres for orchestration), each node **reports**: `Rebalancer.Reporter` (gated `:load_reporter`) diffs two `ShardLoad` snapshots into rates and writes its hot set to `shard_load_samples` (Postgres), tagged with a stable `Rebalancer.node_key/0`. The Oban cron `RebalanceJob` (fleet singleton via Oban's Postgres peer leadership; gated `:rebalancer_enabled`) reads the merged fleet view and runs `Rebalancer.Policy` — hot = **absolute q/s floor or `K×p99`, never `K×median`** (the `--hotspots` finding), with 2-window anti-flap, cooldown, an improvement guard (never relocate a lone hotspot), and least-loaded target — then enqueues a unique-per-shard `HandoffJob`. The handoff is **warm the target → pin the `shard_overrides` row + render the nginx map (`LbMap`) + reload (`LbApply`) → drain the source (release the lease) → target acquires**; a **flip-before-drain** ordering (the `{owner,epoch}` lease blocks any double-write regardless — a healthy node can't be *stolen* from, so the move is a voluntary drain, not the crash-path self-fence). Warm/drain reach a node the orchestrator can't RPC via a `rebalance_commands` Postgres channel + per-node `CommandPoller` (gated `:command_poller`). **Proven live on the chaos rig** (`chaos.sh rebalance`: `acme` @ 143.9 q/s moved fathom1→fathom2, isolation intact). All gates **off by default**; the enable-path runbook (staged gate-by-gate, with an observe-before-arming dry run + rollback) is `docs/runbooks/rebalancer.md`. Hardened per the 2026-07-07 expert-panel pass (report kept locally, not in the repo) and re-proven live in `docs/reviews/chaos-run-2026-07-08.md`. See `docs/phase2-scoping.md` §B1 for scoping; **how it works end to end** — detect (per-node reporting) → decide (the p99/floor hotness bar + guards) → execute (the flip-before-drain handoff) — is `docs/rebalancing.md`.
## Cross-node single-writer (lease + epoch fence + node heartbeat)

**Cross-node single-writer (lease + epoch fence + node heartbeat).** `Fathom.Shard.Storage` carries a per-shard **lock** (`{owner, epoch}`, where `epoch` is the fencing token — a **lock generation**, NOT a shard-history counter: `release_lease` deletes the lock and the next `acquire_lease` restarts at 1, so `epoch` is only ordered *within one ownership generation*. A separate monotonic `lineage` counter — `Fathom.Shard.lineage/1`, seeded by `Storage.next_lineage/1`, carried on `flush/5` and every A2 push — is the cross-generation history number, and `FollowerLog.decide/2` / `Promote.fresher?/2` rank on it. The `position` typedoc in `storage.ex` was corrected 2026-09-12 from "Not yet fixed" to "worked around by the lineage counter"; do NOT route any new consumer at `epoch` for history) and a per-node **heartbeat** (`Fathom.Shard.Heartbeat` renews one `heartbeat/<node>` object every `ttl/3` — liveness is O(nodes), not O(shards), which is the F1 fix). A shard's owner is live iff its heartbeat is fresh, so `acquire_lease` consults the owner's heartbeat to decide held-vs-steal (and fails closed on a heartbeat read error). Coordinators do **no per-shard renewal**; before a flush they fence via `Heartbeat.valid_for_write?/1` (heartbeat valid-with-margin + no lapse since acquire ⇒ write with no per-shard I/O; on a lapse, re-check the lock via `Storage.check_lease/2` and **self-fence** if superseded so a remapped shard never double-writes). If the heartbeat process is down, coordinators degrade to the legacy per-shard renew fence. This is the only cross-node coordination — via S3, not BEAM. **How it works end to end** — the storage behaviour, the lease/epoch/heartbeat primitives, cold-open acquire+pull, the steady-state fence, the crash-steal vs voluntary-drain directions, and the loss contract — is `docs/single-writer.md`. **Local is not a fleet store** (expert review 2026-11-07 #8): `Storage.Local`'s lease is `:global.trans` scoped to `[node()]`, so it is node-local. `Application.check_local_storage_fleet!/0` therefore refuses a prod node on Local (explicit or by DEFAULT — an unset `SHARD_STORAGE` is `nil` in app env, and the 2026-07-14 guard compared that against Local without the default `Storage.backend/0` applies, so the unsafe default was the one case it could not see) when `:lb_backends` is set, `:replication_followers` is set, or replication is on. `ALLOW_LOCAL_STORAGE=true` acks only the replication signal, never `:lb_backends`. A single-node prod Local deploy sets `REPLICATION_ENABLED=false`.
## Cluster layer (LB-keyspace-partition)

**Cluster layer (LB-keyspace-partition).** The L7 load balancer consistent-hashes the `Host` subdomain to one backend node; each node is an independent single-node fathom, and the S3 lease above handles remap safety. `Fathom.HealthPlug` serves `GET /health` (per-node LB probe, `:health_port` default 8081, gated by `:health_server`). `Fathom.Telemetry` runs Telemetry.Metrics over the shard/lease/checkout events + an active-shard poller + a checkout→OpenTelemetry span bridge (traces env-gated on `OTEL_EXPORTER_OTLP_ENDPOINT`, off by default). LB config in `deploy/lb/`; `docs/deploy-cluster.md` + runbook in `docs/runbooks/cluster.md`. The **chaos rig** (`deploy/chaos/` — 3 prod-release nodes behind nginx + MinIO + per-node toxiproxy, driven by `chaos.sh`: `failover`/`pause-fence`/`partition`/`soak`/`warm-home`/`hotspots`/`rebalance`/`density`/`served`/`served-data`/`latency-cost`/`tpc-fleet`/`rollout`/`replication`/`rpo`/`quorum-loss`) is the failover-time-and-loss-window layer the in-process cluster suite (`test/fathom/cluster/`) can't measure — and (`hotspots`, gated by `SHARD_LOAD=true`) the real-traffic hot-spot layer the in-process `--hotspots` harness can't: it drives Zipf-skewed real Hrana traffic through the LB and reads `Fathom.ShardLoad.top` per node via `bin/fathom rpc` (2026-07-06 run: 17.5k requests, top-20 Zipf-head recall 0.95, hot set spread across all 3 nodes — the per-node-read/merge model confirmed). **`rebalance`** demonstrates the full **B1 handoff live**: drive load on a shard, show the reporter detected it, then pin it + drain the source + prove it moved to the target — the **`lb-reloader` sidecar** (shares nginx's PID namespace, HUPs its master on a map change) applies the flip with no host bridge. Runs: a manual pin (2026-07-06, `acme` fathom1→fathom2) and a fully **autonomous** one (2026-07-07: `Policy.propose` chose `green: fathom2→fathom1` off an engineered imbalance, `RebalanceJob`/`HandoffJob` executed it), both isolation-intact. **`density`** is the fleet counterpart to the single-node `--ramp` ceiling: it mints N novel shards through the LB and reads per node the coordinators held (the keyspace partition) + BEAM/RSS per shard (the cost) — 2026-07-10 run, N=30000 over 3 nodes (~10k/node), spread evenly (1.22×) at ~16 KiB/shard RSS on every node (marginal cost *falls* with scale as fixed overhead amortizes), so capacity is horizontally additive and only the active working set is resident — this is the warm-resident floor (idle, empty shards). **`served`** measures the complementary **fd-bound** ceiling — shards held under a *live connection*: 30k across the fleet (10k/node) at ~220 KiB/shard and **1 fd each**, so served density is a `nofile` knob (compose raises the nodes' soft limit to 65536; the default 1024 caps ~940/node) not a memory or architectural wall. **`served-data`** adds real data per shard (30k shards seeded 256 KiB each, held + scanned): ~640 KiB/shard and **3 fds** (WAL-active `-wal`/`-shm`), and the key result — an *idle* data-bearing shard drops back to ~43 KiB/0 fds (the 256 KiB lives on disk, not RSS), so a *stored* tenant costs disk and only an *active* one costs the connection + page cache. All four regimes (idle floor ~16 KiB, served ~220 KiB, served+data ~640 KiB, idle+data ~43 KiB) measured at 30k across the fleet; served-data was stress-pushed to **105k held / ~150k RAM-bound** (nofile maxed) — the open-rate decay past ~30k/node is a one-process test artifact (production holds one process per stream), not a fathom limit (`docs/reviews/fleet-density-2026-07-10.md`). **`latency-cost`** MEASURES what `latency <ms>` INJECTS — it times the two S3-round-trip-bound paths (cold-open pull, flush upload) per node, baseline vs an injected one-way RTT (2026-07-23 sweep, 10/30/60 ms: cold-open ~26/70/133 ms ≈ **~1 RTT**, matching the in-process `benchmark_s3_sweep.sh` — the `Fathom.Shard.init` lease+pull overlap working on the fleet; flush/drain ~53/143/270 ms ≈ **~2.3× RTT**, down from ~3.5× in the 2026-07-11 sweep after perf review 2026-07-23 #6 removed the drain's redundant lock GET — the lease carries the lock etag from our own PUT responses, so release is one conditional DELETE. The remaining data-PUT→lock-DELETE ordering is irreducible (releasing before the flush lands would let a peer pull stale bytes), so drain now sits within ~0.3 RTT of the design floor — `docs/reviews/latency-cost-2026-07-23.md`; history in `latency-cost-2026-07-11.md`, whose sidecar-upload attribution of the third RTT was wrong — the sidecar is a local file). **`tpc-fleet`** is the throughput analog of `density`: it drives many tenant shards — one single-writer file each — through the LB so they partition across the nodes, then reads back the aggregate txn/s + the per-node load split (2026-07-23 runs, post the LB-502 fix, 6→1024-tenant sweep: **query load follows the shard partition** across all 3 nodes, **zero errors at every step** — 128 tenants (2× the concurrency that used to collapse the rig in a 502 storm) ran 19,200 txns with 0 driver errors and 0 LB upstream failures, and the consistent-hash spread *improves* with key count (1.27× at N=128, 1.06× at N=256) — aggregate **~890 → ~1,066 → ~1,083 → ~1,075 → ~1,082 → ~1,026 txn/s**, a clean CPU plateau on the one rig VM (sagging only ~5% under 256 concurrent held connections — no second ceiling in sight), within ~5% of the p50-implied fair-queueing ceiling at every step, with per-txn p50 6.6 → 11.0 → 20.9 → 57.4 → 113.8 → 239.8 ms growing linearly with concurrency at saturation across independent writers; at N=256 the consistent-hash spread is **1.06×** (85/83/88 — the ring evening out with key count); **1024 concurrent tenants = ~2,661 tps aggregate** (uniform-methodology sweep 2026-07-24: in-network driver containers, 4×256 clients; 153,008 txns, 0.4% transient client reconnects, zero server-side failures) — and aggregate RISES with driver count (~1,140 → 1,625 → 2,661 at 1/2/4 procs), so every single-driver 'plateau' was the DRIVER's ceiling, not the fleet's; the fleet ceiling on this VM is ≥2.7k tps and unfound. High-concurrency driving rules (colima's host forwarder dies ~1k conns — drive in-network; ≤128 clients per driver process — a solo 256-client in-network proc reproducibly collapses, unattributed, see the addendum): `docs/reviews/tpc-fleet-highconc-2026-07-23.md` — but those driving rules are the *Python* driver's, not fathom's: the **Elixir/Filo.Client driver** (`deploy/chaos/tpc_driver.exs` — one lightweight BEAM process per client, no GIL), run as an **in-network container** (`chaos.sh build-driver`; then `TPC_NET=container TPC_DRIVER=elixir ./chaos.sh tpc-fleet`), drove the whole **6→4096-tenant sweep from ONE process, zero errors at every step** — no ≤128-clients/proc cap, no multi-process orchestration (one driver bug en route: a connect+seed thundering herd crashed it at ≥2048, fixed with a per-worker connect stagger + retry; the fleet processed every query at every attempt — ~3.4–4k tps CPU-bound on this VM, spread ≤1.15× out to 4096; a parameter-matched host A/B has the Elixir driver **1.6–2.8× faster** than Python in its clean range and error-free where one Python process collapses at ≥128 clients — `docs/reviews/tpc-fleet-elixir-driver-2026-07-24.md`; the Elixir driver also covers **tpcc** now (all five value-feeding txns + the W-sweep, tpmC parity with Python) plus a **`tpcc-fleet`** multi-tenant sweep (one 1-warehouse TPC-C per tenant, 16→4096 tenants error-free, aggregate tpmC ~25.6k-peak, even per-node partition ≤1.12×), which surfaced a **Filo.Client resilience fix**: a `:closed` connection — e.g. an LB recycling an idle client keep-alive after N requests — is transparently retried with the **same baton** (resume the Hrana stream, exactly-once via the baton seq) instead of abandoning a held stream mid-transaction), still **no intra-shard convoy** (contrast the single-shard TPC-C lock convoy); absolute txn/s is single-host-bound — the horizontal "millions" throughput axis is the even per-node split, not the one-box aggregate — `docs/reviews/tpc-fleet-2026-07-23.md`. **All pre-2026-07-23 tpc-fleet absolutes (e.g. the 07-11 run's ~40 tps) are obsolete**: they were ~95% LB-502 reconnect overhead from an nginx `Connection: close` upstream-keepalive bug, fixed in both LB configs; the old "moderate concurrency by design" rig caveat is retired with it — `docs/reviews/lb-502-fix-2026-07-23.md`). **EVERY capacity and throughput number above was measured with A2 replication OFF, and as of 2026-08-14 they do NOT hold with it on.** First measurement of the two together (both arms, one rig, one session, `tpc-fleet 16,64,256,1024`): replication off ran every step clean at **2,918 / 4,081 / 4,644 / 4,374 txn/s, 0 errors, spread 1.21×**; replication on cost **~25% throughput where it worked (2,164 / 3,041 / 3,505)** and **did not complete the 1024-tenant step at all** — it OOM-killed a node (`OOMKilled=true`, exit 137) on a 94 GiB VM with no container memory limit, and that step produced no result. Split is **Oban queue-draw, not LB hash** (migration jobs come from one Postgres queue), even at 1.07× for 300 jobs but legitimately lopsided for a handful. The run also found a **reproducible stuck-lease bug** (~1 in 300, different tenant each run): a coordinator lease that outlives its coordinator on a *live* node is never stealable (liveness is the node's heartbeat, and the migrator acquires under a different owner string), so the job snoozes forever in `scheduled` with **no error, no quarantine, `failed: 0`** — that tenant serves normally but can never migrate, and the deploy gate never converges. A client touch on the owning node clears it. **ROOT-CAUSED AND FIXED 2026-08-04, confirmed on the rig (4 runs at 299/300 before, 2 runs at 300/300 after).** The bug was in `release_lease` itself, not in any caller: the release is a conditional `DELETE … If-Match: <the etag we last wrote>` and a **412 was reported as `:ok`**, collapsing two opposite situations — "the lock is someone else's" (correct no-op, finding #22) and "the lock is STILL OURS at a different etag" (a leak reported as success). The release now re-reads on a 412 and finishes the delete when the lock is still ours; the decision lives in `Fathom.Shard.Storage.resolve_stale_release/4` rather than inside a backend, because every etag-carrying backend must make it identically AND because the default suite's backend is `Fathom.Test.FaultyStorage` — a policy implemented privately per backend would only ever be tested against the double. **Why #9/#11 did not close it:** both fixed CALLERS that released with a stale lease, so any rotation whose result the caller never received still leaked. **Why it was heartbeat-mode-only:** legacy's `Fence.check` does a `renew_lease` PUT on the way into the drop and #9's fix threads that refreshed lease back, so legacy accidentally self-heals a rotation from any source; heartbeat mode does no renew and carries the stale etag straight into the release — which is exactly why the rig hit it every run and the legacy-only suite never could. Three OTHER real lock-leak paths were found and fixed on the way, none of which was this bug (each has a discriminating test; the rig reproduced the straggler again after each): `flush_then_drop/1`'s two "keep the local copy" branches (transient flush error; fence couldn't confirm ownership) kept the **lock** as well as the copy, and an **exception between `acquire_lease` and the built state** skipped the release entirely (the hazard `shard.ex`'s own comments describe — #33 had fixed one instance inside `fork_evidence/2`, but `resolve_fork`/`revalidate_takeover`/`promote_pull` still ran unrescued storage calls in the coordinator). Also still open: the migration snooze is unbounded and silent, so any other cause of a long-held lease stays invisible. `docs/reviews/fleet-rollout-2026-08-04.md`. See the § Chaos testing two-layer split in `docs/deploy-cluster.md` and the runs in `docs/reviews/chaos-run-2026-07-05.md`. **The cluster phase (S1–S8) is complete** — LB partition, S3 lease/heartbeat fence, crash/partition contract, observability, directory-off-hot-path, and lease-RPS measurement all shipped (see the Status in `docs/deploy-cluster.md`); what remains cluster-side is Phase 2 (below). **Node shutdown is two phases, and the stop grace has to cover both** (expert review 2026-11-07 #58): `Application.prep_stop/1` runs the bounded `Shards.drain_all/0` (`DRAIN_LB_SETTLE_MS` + `DRAIN_ALL_BUDGET_MS`), and only then does the supervisor teardown run — Edge listeners (Bandit's 15 s `shutdown_timeout`, up to three of them), each straggler coordinator's `SHARD_SHUTDOWN_MS`, the Recorder's 30 s, Oban's 15 s grace. **Local-disk observability + warm-cache back-pressure (review 2026-08-01 #36).** *(Update: the warm cache was removed 2026-09-14 with WarmFollower; the gauge now covers the `data` and `replica` dirs, and the free-space floor guards A2 follower seeds — `Replication.Follower.headroom?/2`. ## Restore drill: the procedure, not just the object (review 2026-08-01 #48)

**Restore drill: the procedure, not just the object (review 2026-08-01 #48).** `verify/2` pulled, `quick_check`ed and compared `user_version` — proving the stored BYTES are readable, but never invoking `Tenants.fork/2`, never cold-opening a coordinator from those bytes, never touching the directory reconcile. So the chain an operator runs under maximum pressure had only ever executed in unit tests. `RestoreDrillJob.run_full_drill/1` (gated `:restore_drill_full_sample`, `RESTORE_DRILL_FULL_SAMPLE`, **off by default** and deliberately a much smaller sample than the read-only drill, because a fork is a full object copy) forks each sampled shard to a scratch tenant, **compares user-table row counts against the source** — a fork that produced an empty database would pass `quick_check` and prove nothing — and drops it. Distinct failure classes (`:fork_failed`, `:restored_mismatch`) because "the recovery path is broken" wants a different response from "this object is corrupt". Scratch tenants are **hard-deleted** (`Directory.hard_delete/1`), never `Tenants.delete/1`: that tombstones, and one tombstone per sample per run would grow the admission-path `Tombstones` ETS set without bound — the routine that proves recovery works would degrade the hot path. **Snapshots** also gained a health signal at all: they are storage objects with no directory row, so `sample_for_drill/1` never saw them and the one class of data a point-in-time recovery reaches for was the one class nothing checked; they are now verified alongside the shard that owns them (`[:fathom, :restore_drill, :snapshot_result]`). Separately, AGENTS.md's own migration-gate item (c) — cross-version tolerance — finally has a test (`test/fathom/cross_version_tolerance_test.exs`), driven over the real Hrana wire and labelled as the tripwire it is rather than a regression test.
## Background scan gate: non-flush whole-shard scans (expert review 2026-10-29 #3)

**Background scan gate (`Fathom.Shard.BackgroundScanGate`, expert review 2026-10-29 #3).** Every exqlite NIF is a dirty-IO job, so one `PRAGMA integrity_check`, `INSERT … SELECT` or `CREATE INDEX` holds one of the `+SDio` (10) threads for the whole scan, and tenant statements share that pool. `ScanGate` (`SDio - 2`) bounds only the FLUSH scans; the migration replay (`Copy.migrate_chain`, 10 workers on the `:migrations` queue), `verify_migrated`, the restore drill (`integrity_check` + row counts) and the tenant export's `integrity_check` were ungated. They now take a permit from a SEPARATE node-wide gate: default `div(SDio, 4)` = 2, `BACKGROUND_SCAN_PERMITS` / `:background_scan_permits` (`0` = off), released on holder death by monitor. Separate on purpose: sharing `ScanGate`'s count would let a rollout starve flushes (RPO) and a flush wave starve a rollout; `ScanGate`'s permit count and every flush path are untouched, and `test/fathom/shard/background_scan_gate_test.exs` asserts the two gates do not block each other. **Unlike `ScanGate` a timed-out waiter does not scan anyway** (the flush must not fail; these scans must yield): a migration takes its permit in `ShardMigration.run/3` BEFORE `with_lease` drains the live coordinator, and holds it through the replay and `verify_migrated`. It waits `:background_scan_wait_ms` (120 s; the tenant is still served while it waits) then gets `{:error, :background_scan_busy}`, which `ShardMigrationJob.transient?/1` classifies as environmental, so the job snoozes without burning an attempt, the same shape as a held lease. `verify_migrated` passes busy through rather than reporting `:migrated_copy_corrupt`. A tenant-facing caller waits seconds, not minutes: the `:inline` migrate-on-touch checkout 3 s (`with_wait_ms/2`, then it degrades to the async job like `:shard_busy`), the admin export 10 s (then a 503). The restore drill runs **2 workers, not 8**, and each worker holds ONE permit for its whole shard. The per-shard deadline starts only once that permit is held (`bounded/4`); the wait is bounded by the Oban job timeout instead. **Deliberately not gated:** `Ledger.check_file` (reads the small `django_migrations` table, not the shard), `Snapshots.restore`'s integrity check (an operator's DR action must not fail on a busy gate), the S3 pull/PUT and `File.cp`. `with_permit/3` and `queued/2` are re-entrant within one process (`acquire/2` is not). **First version, corrected 2026-10-31 (review of e5f45291):** the replay and `verify_migrated` each waited for their own permit INSIDE the lease, so a busy node kept a drained tenant answering `:shard_migrating` for up to two waits per attempt, and each snooze re-did the drain and the S3 pull. The drill counted queue time against its per-shard deadline, so a rollout holding the gate got healthy shards killed and recorded as `"error"`. Cost of the fix: a node runs at most `cap` migrations at once, S3 pull and upload included. Tests: `background_scan_gate_migration_test.exs` (busy before the drain; the permit is kept through verify) and `restore_drill_job_test.exs` (queue time is not deadline time). **The finding's impact is unmeasured**; the default is derived, not swept. If a rollout is observed to stall behind the gate, raise `BACKGROUND_SCAN_PERMITS` before raising `+SDio`, which the 2026-07-25 sweep showed costs throughput.
## Data migrations + `atomic = False` — the transform seam (review 2026-08-01 #26)

**Data migrations + `atomic = False` — the transform seam (review 2026-08-01 #26).** The engine replays the template's SQL verbatim, so a `RunPython` backfill crossed the wire as literal DML carrying **the template's row values**. `Capture` flagged that and capped HEAD, leaving exactly two options — approve it (replay the template's rows onto every tenant, the corruption the flag prevents) or never advance, with every later migration stacked behind it. `AddField` + `RunPython` is the most common two-step Django migration, so this was certain in month one. **Three parts, per the finding's own order.** (1) **Legibility:** `requires_review` was one boolean, so the status API could say `pending_review: [7]` and nothing more. New `review_reason` / `review_detail` columns + `Migrator.review_block/1` report WHY a version is held and spell out the options with their consequences — and `status/0` exposes them in a NEW `review_blocks` field rather than changing `pending_review`'s type, because `migration_controller_test` failing on `pending_review == [2]` was the published control-plane endpoint pointing out that a field changing type is a consumer break. Releases captured before this re-derive their reason from the statements, so an already-frozen fleet gets the explanation on upgrade. The **dashboard** half followed (2026-08-06): `Fleet.migrations/0` carries `review_blocks` and `/admin/migrations` gets a **Held for review** tile plus a *"Rollout held"* panel above the burndown — reason, the flagged statements, and both options with their runnable commands. **Deliberately read-only**, and not merely a smaller scope: `attach_transform` cannot be a button (module + deploy + allowlist), while `approve_review` is the fleet-wide corruption the flag exists to prevent, so a panel offering only the dangerous half of a two-way decision biases toward it — contrast `AdminDirectoryLive`'s Delete, which is destructive but per-tenant and unambiguous. `admin_live_test.exs` pins the absence of a click handler inside `#review-blocks` so the next person to add one reads the moduledoc first. (2) **The transform seam:** a release may carry a `transform` — a module implementing `Fathom.Migrator.Transform` (`run(conn, shard_id)`) that `Copy.migrate_chain/4` runs **inside the same transaction, after the DDL**, so a failing backfill rolls the DDL back with it rather than leaving a column full of NULLs that every version stamp agrees is fine. **The allowlist (`:migration_transforms`) is the security boundary**: a release row is data written by the capture path, whose template AGENTS.md already calls a fleet-wide poisoning vector, so resolution never calls `String.to_atom`/`to_existing_atom` — being a loaded module is not permission. Transforms are resolved BEFORE any file is copied, so an unregistered one fails before doing work. `attach_transform/2` refuses a release still carrying flagged DML (else the version runs both the literals AND the transform) and refuses a version held for a **gap** (a transform cannot conjure DDL the fleet missed). (3) **`atomic = False`:** capture cannot see it by construction — autocommit, no transaction to hook — so `mix fathom.check_migrations <path>` is the pre-flight CI gate (error on `atomic = False`, warn on `RunPython`/`RunSQL` naming the transform path), with the gap detector kept as the late backstop. Transactionality was verified to discriminate: moving the transform after `COMMIT` fails two tests. `docs/django-migrations.md` carries the operator walkthrough.
## Scheduled snapshots + GFS retention (review 2026-08-01 #18)

**Scheduled snapshots + GFS retention (review 2026-08-01 #18).** `Fathom.Snapshots.create/2` was a correct, well-fenced primitive that **nothing ever called on a schedule**, and nothing ever expired a `@snap-<id>` object (`RetirementJob` drops `@<version>` only). Since the live durable object is overwritten every `:shard_flush_interval_ms` (default 5 s), the practical recovery capability for **logical** corruption — a bad deploy, a bad backfill, which `docs/durability.md` itself calls the more common incident — was **zero**: "restore tenant acme to 09:00" had no answer, the largest gap against the Postgres-on-RDS baseline fathom replaces. Two fleet-singleton Oban crons close it, **both off by default**: `Fathom.Snapshots.ScheduleJob` (hourly) snapshots up to `:snapshot_schedule_sample` shards chosen by `Directory.sample_for_snapshot/1` — **active, flushed since their last snapshot, least-recently-snapshotted first**, keyed off a new `last_snapshot_at` column — and `Fathom.Snapshots.RetentionJob` (hourly, +30 min offset) applies `:snapshot_retention` (`%{hourly: 24, daily: 7, weekly: 4}`, or `SNAPSHOT_RETENTION="24h,7d,4w"`). **The selection predicate IS the design:** every snapshot is a server-side object COPY, so cost tracks *writes* rather than tenant count and a million cold tenants cost nothing; `last_snapshot_at` is stamped **only on success**, so a failed snapshot stays at the head of the rotation instead of being marked done for a full cycle. **The safety property:** retention only ever deletes what the scheduler created — `ScheduleJob` labels its snapshots `auto` and `Retention.plan/3` refuses anything else, so an operator's `Snapshots.create(id, label: "pre-migration")` is invisible to the automatic policy (automatic creation and automatic deletion are deliberately the same set; expiring a manual snapshot would delete exactly the backup someone took because they were worried). Retention counts **populated** periods, not wall-clock ones (a week of downtime must not expire the history it protects), buckets on the **ISO week year** (2027-01-01 is ISO 2026-W53), and keeps a future-dated snapshot rather than dropping it (clock skew). `plan/3` is a **pure function** with its own exhaustive suite — bucket boundaries are where this goes wrong and none of it needs an object store; `RetentionJob` is a thin shell that lists, plans, deletes, with `dry_run: true` to rehearse. Both gates verified to discriminate (breaking `auto?` fails 3 tests incl. the end-to-end one; removing the flush predicate fails the cost-control test). The **RPO for logical corruption is the snapshot cadence, not the flush interval** — documented beside the node-loss RPO in `docs/durability.md`.
## Django parity is MEASURED, four ways (2026-08-05)

**Django parity is MEASURED, four ways (2026-08-05).** The fourth is `test/fathom/django_wire_parity_test.exs`: everything else stops at `Fathom.Shard.Connection`, but `django-libsql` reads Hrana's explicit type TAG (`{"type":"integer","value":"12"}`), not the SQL — so a UDF returning INTEGER inside SQLite that went out tagged `text` would reach Django as a string, and `Duration(...) * 2 == timedelta(...)` would quietly stop being true. Invisible at the `Connection` layer, where the value is already right. It drives `Filo.Plug` as a client does and asserts the tag. **Everything OTHER than the UDFs is identical by construction** — fathom runs the same SQLite — which is why the UDF surface was the whole compatibility problem. "Exact compatibility with Django" is a claim that has to be checked, not asserted, and all three suites generate their expectations by RUNNING the reference rather than hand-writing what it is believed to do. (1) `native/fathom_udf/tests/oracle.rs` — 12,501 cases from Django's own `_sqlite_*` functions. (2) `native/fathom_udf/tests/re_oracle.rs` — **3,444 cases from CPython's `re.search`**, because Django's `__regex`/`__iregex` ARE `re.search`. (3) `test/fathom/django_sql_parity_test.exs` — **42 whole queries run against a real Python `sqlite3` connection with Django's UDFs registered exactly as `django/db/backends/sqlite3/base.py` registers them**, requiring identical rows AND identical `typeof()`. The third is the strongest and catches what per-function comparison structurally cannot: result TYPES, which ROWS a `WHERE` returns, GROUP BY/ORDER BY, NULL columns. **`regexp` was rewritten as a result** (`src/pyre.rs`): Rust's `regex` crate rejects lookaround and backreferences (ordinary Python, so a queryset errored where Django returned rows) and — the dangerous half — compiles `$` and returns the OPPOSITE answer, because Python's `$` also matches before a trailing newline. `re.search("^[a-z0-9-]+$", "a-slug-1\n")` is True in Django and was false here: a slug/username validator silently returning the wrong rows on any text that arrived from a form or a file. Fixed with `fancy-regex` plus a small Python→Rust token translator (`$`→`(?=\n?\z)`, `\Z`→`\z`, `(?P=name)`→`\k<name>`) written as a scanner, not a `String::replace`, so `[a$]` and `\$` survive. Both oracles were verified to DISCRIMINATE by re-breaking the `$` rule (10 regex cases and 3 whole queries fail). Engine surface separately probed clean on a **tenant** handle: savepoints (Django's nested `atomic()`) roll back correctly, and `table_info`/`foreign_key_list`/`index_list`/`index_info`/`foreign_key_check`/`table_xinfo`/`sqlite_master`, JSON1, window functions, `LIKE` case-folding and `COLLATE NOCASE` all work. **Exactly two differences remain and both are deliberate**: `STDDEV_POP`/`VAR_POP` over a NULL-containing column and `VAR_SAMP` over one row, where **Django RAISES and fathom answers** (its aggregate step is `list.append`, so `statistics.pstdev` gets a `None`). Not reproduced on purpose — that is Python-library behaviour, not intended Django semantics, and matching it means shipping a crash on any `StdDev` over a nullable column. The direction is what matters and is asserted in the parity test: **every query that works on Django works here**; only queries that ERROR on Django behave differently.
## Django UDF compatibility — `native/fathom_udf` (review 2026-08-01 #19)

**Lookaside cannot be shrunk from the extension (perf review 2026-10-14 #2, measured).** Each open shard holds ~156 KB of SQLite memory per connection, and the obvious lever, `sqlite3_db_config(SQLITE_DBCONFIG_LOOKASIDE, …)` in `sqlite3_fathomudf_init`, does not work. The extension is loaded with `SELECT load_extension(…)`, so its init runs inside a live statement whose VDBE holds lookaside slots, and SQLite refuses to resize while any slot is in use: rc 5 (BUSY) on every handle. Every SQL-driven hook has the same problem. A registered auto-extension does return 0, but `openDatabase` calls `setupLookaside` AFTER the auto-extensions run and overwrites it (a `db_status` probe shows LOOKASIDE_HIT unchanged; the counters come back in the highwater out-parameter). `SQLITE_CONFIG_LOOKASIDE` returns MISUSE once exqlite's NIF has initialized SQLite. The only lever is a custom exqlite build: `EXQLITE_SYSTEM_CFLAGS=-DSQLITE_DEFAULT_LOOKASIDE=0,0` measured 156 → 112 KB per connection (−29%), but uncached `prepare` went 4.5 → 9.5 µs. Not adopted (2026-10-15): the prepare cost and a custom build in every environment outweigh ~45 KB per open shard. Don't retry the shrink from the extension.

**The extension is not optional with replication on** (expert review 2026-11-07 #24). Without it a tenant handle opens `:skipped`: SQLite's built-in `wal_autocheckpoint=4000` owns the WAL-hook slot, `Session.ensure_registered/2` latches `registered: :unavailable` and keeps shipping and acking, and a commit crossing 4000 frames runs a PASSIVE checkpoint that can restart the log before the Session reads the previous commit's frames (the 2026-10-15 #1 window). So `Application.check_udf_extension!/0` refuses a prod node with no extension and `:replication_enabled` on, and `ALLOW_NO_UDF` deliberately does not override it; the choice is build the extension or `REPLICATION_ENABLED=false`. **The boot check proves loadability, not presence** (2026-11-07 #42): `check_udf_extension!/0` calls `Extension.open_mode/0` in prod (arming the auto-extension at boot, before any tenant connects), and a present-but-unloadable artifact refuses the boot whatever `ALLOW_NO_UDF` says. `Extension.arm_outcome/3` is the pure decision behind arming: only a control failure that names the missing `sqlite3_fathomudf_control_init` symbol (an artifact built before r8 #14) may fall back to `:per_open`; any other control failure is returned as an error and NOT cached, so a transient EMFILE/ENOMEM on the first open can no longer pin the node to per-open loading for its life (the old fallback keyed on ANY failure, and `loads_per_connection?/1` returned a failed probe's `{:error, _}`, which is truthy). A permanent failure is not negatively cached either (each open retries two `:memory:` opens and a `dlopen`), because the boot check now catches that class before traffic.

**Engine PRAGMA guard — `native/fathom_udf/src/pragma_guard.rs` (review 2026-10-08 #1, tier b).** The tenant PRAGMA allow-list in `Fathom.ShardExecutor` is a text parser, and five of its defects shipped as live bypasses (a 200-byte window, `main . name`, a leading `;`, `EXPLAIN PRAGMA`, a `;` inside a comment — the last let a `:ro` token set the process-global `hard_heap_limit`). The extension's set-once `fathom_pragma_guard(names, pinned)` installs a `sqlite3_set_authorizer` callback that sees each pragma as SQLite parsed it and DENIES an assignment (value non-NULL) whose name is not allowed; every READ is allowed. `names` is `ShardExecutor.tenant_pragma_assignable/0` (allow + introspect + operator `:tenant_pragma_allow`, minus the deny list), so the two gates share one list; `pinned` is the exact `[schema.]name=value` assignments fathom itself sends on a tenant handle after open (pooled reuse, the lazy TEMP cap). **One authorizer slot:** it replaces exqlite's, so it also denies ATTACH/DETACH. **Tenant handles only** — VACUUM INTO is an internal ATTACH, so a guarded coordinator snapshot would break every flush. Installed LAST in `Connection.open/2`; a failure to install with the extension loaded fails the open; with the extension absent, tenant handles keep exqlite's attach/detach authorizer. **Traps:** (1) the policy is fixed at open, so a runtime `:tenant_pragma_allow` change reaches only handles opened after it (a pooled handle keeps its open-time list until it is closed); (2) any NEW pragma fathom sends on a tenant handle after open must be added to `pinned_pragmas/0`, or it is refused as "not authorized".

**Django UDF compatibility — `native/fathom_udf` (review 2026-08-01 #19).** Django's SQLite backend registers **54** functions on every *client* connection; under `django-libsql` the SQL is compiled by **fathom's** SQLite, where they did not exist — so CRUD worked and the first `__year`/`__date`/`Trunc*`/`__regex` lookup raised `OperationalError`, against the flagship "point an unchanged Django app at it" claim. (TPC-B and TPC-C use only builtins, which is why neither harness ever caught it.) All 54 now resolve: 19 from SQLite's `SQLITE_ENABLE_MATH_FUNCTIONS` build, **35 from `fathom_udf`** — a Rust **loadable SQLite extension** (`cdylib`, `rusqlite`'s `loadable_extension`), loaded by `Fathom.Shard.Extension` on every connection. **The finding's own recommendation was impossible**: "register via exqlite's scalar-function registration" needs an API exqlite 0.37.0 does not expose (no `create_function`, no scalar/aggregate registration, anywhere in `Exqlite.Sqlite3`/`Sqlite3NIF`); what it *does* expose is `enable_load_extension/2`. **Rust over C** because six of the 35 take a `tzname` and need a timezone DATABASE server-side — and those are the ones ordinary apps hit first (`USE_TZ` has defaulted to `True` since Django 5.0, the version `django-libsql` pins) — so `chrono-tz` compiles tzdata into the binary and there is no `/usr/share/zoneinfo` dependency; in C that piece is the whole project. **Security posture:** extension loading is arbitrary code execution on a multi-tenant engine, so the sequence is **enable → load ours → disable**, on every handle (`:ro` included), with a failure to re-disable failing the OPEN rather than degrading; `extension_test.exs` asserts the tenant-side `not authorized` rather than trusting the sequence, and was verified to fail when the disable is removed. Loaded BEFORE the `:attach` authorizer, since tenant handles are the ones running Django's SQL. **Fidelity is generated, not asserted by hand:** `native/fathom_udf/tests/oracle.rs` replays **12,501 cases whose expectations come from running Django's own `_sqlite_*` functions** (`tests/oracle/generate_cases.py` vendors the reference with provenance; JSONL, ~69 KB in git). That caught **seven real bugs the hand-written tests missed** — `django_format_dtdelta` returning TEXT where Django returns a number for `*`/`/` (so `WHERE d*2 = 12` would silently stop matching), an i64 `checked_mul` that would have WRAPPED in the release build, the empty string being NULL alone but an ERROR with a timezone (Django's `try` only wraps `typecast_timestamp`, and `""` returns None *without* raising), `date - timedelta` negating the delta's `.days` FIELD rather than the delta, `cast_date` on a bare date erroring because `datetime.date` has no `.date()`, the diff functions erroring rather than NULLing (they have no `try` at all), and a bare-hour tz offset that only parses on some Python versions. Deliberate divergences, both toward safety: aggregates **skip NULLs** (Django's `list.append` step feeds `None` to `statistics.pstdev`, which raises) and a degenerate group returns NULL rather than raising, matching PostgreSQL. **Cost, measured same-tree on/off:** +39 µs on stream open (374 → 413 µs), per-query unchanged (90 → 91 µs) — and ~21 µs of the original +70 was a `File.exists?` stat per open, now cached in `:persistent_term`. Build is `mix compile.fathom_udf`, wired into `compilers:` AFTER `Mix.compilers()` (the task is defined in this project, so `:elixir` must compile it first); it **skips rather than fails when cargo is absent**, printing a line, so a Rust toolchain is not a requirement for every contributor. `SQLITE_EXTENSION=false` disables; the chaos Dockerfile and CI both install Rust so neither silently tests a fathom without it. Operator view: `docs/quickstart-django.md`.
**A2 checkpoint ownership — the WAL hook steps aside for a replicated file (review 2026-10-15 #1).** The finding: a stream commits, *then* calls `Session.commit`, and any checkpoint in between (the hook's 4000-frame PASSIVE, the coordinator's post-snapshot PASSIVE, a tenant's `PRAGMA wal_checkpoint(PASSIVE)`) let the next writer restart the log and erase the commit before the Session read it — acked quorum-durable, on no replica. Reproduced for all three sources on a real shard (`test/fathom/shard/replication_unshipped_checkpoint_test.exs`). **The fix that looks obvious and is wrong:** a "shipped watermark" the checkpoint consults — check-then-checkpoint races a commit that lands in between, and it is backfilled with the rest. The fix is SQLite's read marks: pin a read snapshot, read the header after it, checkpoint only if the quorum's ack positions cover it, still pinned (PASSIVE never backfills past a held reader; a restart needs everything backfilled). The extension keeps a refcounted set of replicated files (`fathom_wal_replicated(path, ±1)`, which answers the canonical KEY — release with that key: releasing by a path whose symlinked directory no longer resolves leaked the entry and stopped hook checkpoints for that file forever, review follow-up M1); the hook skips them, the tenant authorizer refuses them `wal_checkpoint` and refuses tenants the function. The Session checkpoints at the same threshold in a task that holds the pin **and a coordinator checkout** (closing a connection on the shard's files is only safe while the coordinator cannot drop them — the last close unlinks `-wal` by path), off the reply path (inline it could time the committer out, follow-up M2). Trade recorded in the Session: past 4× the threshold with a failing quorum the pinned checkpoint runs anyway and `prev_extent` (which now counts what the Session read) re-seeds followers that lack the frames. Known: on a busy shard the flush's checkpoint rarely finds the header covered (it reads outside the Session) — the Session threshold bounds the WAL there; and a stream dying between its SQLite commit and `Session.commit`, followed by an idle close-time checkpoint, can still erase never-read frames.

**A2 follower restart with an empty `-wal` — what the `.db` alone holds (review 2026-10-15 #4 follow-up).** `Follower.recover/3` rebuilds each replica from its WAL header, and `Wal.read/1` answers `:empty` for an empty or absent `-wal`, so such a replica was not recovered at all: its position query answered `nil`, which the #4 floor counts as a DEFINITE "nothing" and which loses every ranking. The `.db` can hold the acked tail: the absorb before a reset checkpoints the outgoing generation into the `.db` and truncates the WAL (synchronous=FULL), and a BEAM crash before the new generation's bytes land, or an OS crash that loses those unsynced bytes, leaves `.db` + empty WAL. Reproduced: F absorbs five rows, its WAL is emptied, a staler peer G holds two; the survivor pulled G (`test/fathom/shard/replication/follower_empty_wal_recovery_test.exs`). **Fix (the safe rule: never answer a definite position lower than the durable state may hold):** the absorb records `<shard>.db.position` = `"<lineage> <ordinal> <extent> end"` — the ordinal only when the WAL header's salt is the one the state's ordinal belongs to, and the extent from SQLite's own count (a PASSIVE checkpoint before the TRUNCATE; the WAL's salt/commit-marker claim has no checksums and over-claims past a broken frame, the 2026-10-15 #15 measurement). It is invalidated (truncated in place, datasynced under `REPLICATION_FSYNC`) before anything moves the `.db` — an absorb or a seed install — and written only after, because a STALE record would under-claim, the dangerous direction. Recovery adopts it only for an empty WAL and only at the lineage the replica still has; otherwise an empty-WAL replica recovers **torn** (in memory): `:torn` to a query, not counted, never ranked, re-seeded on its next push — what an unrecovered replica's `:unknown_shard` already asked for. A follower that never held the shard has no `.db` and still answers a definite "nothing", so fresh followers cause no refusal storm. The pull carries it too: a `.db`-only source used to offer its empty WAL's offset 0, so the puller installed `{lineage, ordinal, 0}` and the recheck refused it; it now offers the recorded offset (and aborts if its state moves mid-stream, since `:empty == :empty` cannot see a `.db` swap), and the puller records the same position. Promotion of a `.db`-only replica needs nothing new (`Promote.copy_wal/3` already skips an empty WAL; `frames_match` claims 0). Cost: the reset push's absorb goes ~335 → ~415 us p50 (one fd held across the checkpoint, a 20-byte header read, the PASSIVE count); the first draft's `Wal.read` + stat + `File.write` added ~140 us and was cut. Appends are untouched. Not covered: a `.db`-only replica built by a primary's empty-WAL seed (its `.db` position was never stated, so it stays unrankable before and after a restart, as it was), and a header-only WAL whose ordinal file names another salt (recovered unrankable, not counted — safe, not improved).

**A2 follower rows are derived on first use, not at boot (expert review 2026-10-21 #5).** `Follower.init/1` used to derive a row for every replica on disk (`recover/3`) before returning: measured 150-300 µs per replica on macOS with a warm page cache (1,000 replicas 215-311 ms, 8,000 replicas 1.2-2.1 s), O(replicas), and since `Fleet` starts in the data plane ahead of `Edge`, the node's Hrana and /health listeners waited on it too. A node holding ~667k replicas (a million-shard fleet on three nodes) would refuse everything for minutes after each restart. After the idle sweep (2026-10-20-2027 #11) `state_of/2` already re-derived a missing row under the shard lock through the same `derive_state/3`, so the boot pass was dropped: init now listens in ~3 ms regardless of replica count, the first `state_of/2` of a replica costs ~140-190 µs, and a post-listen `handle_continue` (one directory listing, ~25 ms at 8,000 replicas) reaps stale seed temps and erases tombstoned replicas. Two seams had relied on every row being resident and were closed with it: the busy-lock path of `rederive/2` read the files with no tombstone check (now refuses a deleted tenant, as the locked path does), and `put_state/3` on a non-resident row assumed "untorn, lineage 0" (now reads the torn marker and lineage sidecar), which would have left a stale torn marker behind an untorn lineage-0 seed install. The equivalence argument is in the comment above `Follower.recover_shard/3`; pinned by `test/fathom/shard/replication/follower_lazy_boot_test.exs`. Trades accepted by the user 2026-10-21: the rebalancer warm set (`replica_shard_ids/1`) starts empty after a restart and refills with traffic; a deleted tenant's replica bytes stay on disk until the post-listen pass, refused meanwhile.

**A2 recovery: a failed pull refuses the open, it does not fall to the object (expert review 2026-11-07 #4).** `Recovery.choose/4` says a peer is provably ahead of the object and the `N−Q+1` floor is met, so the peer holds quorum-acked history the object lacks. `Recovery.pull` answered `:none` on EVERY failure (connect refused or closed by the follower's 256-connection accept cap, the source aborting or its `:changed_during_pull`, the flat 60 s timeout, THIS node's own `begin_seed` refusing on its disk floor, a tombstone, a lineage mismatch), which is the same value as "no peer is ahead": `decide_from_fleet` fell to the stale object with no window, and the first flush re-stamped over the only copies of the tail. A failed *promotion* already refused (Jepsen 2026-10-24); a failed pull is that decision one step earlier. Now it routes through `Recovery.error_window/3` (refuse inside `:replication_recovery_underquorum_window_ms`, best-effort and error-logged after). Three traps: (1) **the window row must outlive the settle.** `settle/7` cleared the per-shard row on every floor-met decision; with the pull after it, each retry of a persistently failing pull would be a fresh first refusal and the refusal would never end. The row is now cleared by the decision (`decide/8`) for every outcome but a pull, and by a pull only on success (pinned by `recovery_pull_failure_test.exs` "the window is bounded"; reverting the order fails it). (2) **the fallback is a peer ranked EXACTLY equal to the winner, never a lower one.** The winner is the best offer among those consulted and so carries every acked write the floor guarantees; a lower-ranked peer that is merely ahead of the object may lack that tail, and pulling it would turn a refusal into a quiet loss (`pull_alternates/5`). (3) **`begin_seed`'s silence is right for a primary's seed and wrong for a recovery pull.** A refused primary seed leaves that shard's RPO at the object, which is correct; a pull's bytes ARE the tail. `begin_seed(.., pull: true)` returns a typed `%{failed: true, refusal: :disk_floor | :tombstoned | :stale_lineage | :replica_busy}` entry that `Recovery` turns into `{:error, {:seed_refused, reason}}` at once (no streaming into a refused sink, no second peer: it would meet the same refusal). Ties between equal peers are now spread by `phash2({shard_id, node_key})` (deterministic per shard, so two recovering nodes agree; a failover wave no longer sends every pull to the highest `node_key`). **Parked: the concurrent-pull gate (the review's (d)):** it is a new bound on a path whose per-open cost is unmeasured, the existing `SeedGate` was itself measured to shed writes when on, and the refusal window plus the 3 s refusal cache already pace retries. Three pre-existing tests (`replication_recovery_test.exs` "ANOTHER tenant's bytes", "truncated stream", "source that aborts") were VACUOUS: their fake peers offered no `wal_ordinal`, so `Promote.fresher?/2` refused the offer and no pull ever ran (and with no window table they could not have seen a refusal); they now offer a rankable position, create the table, and assert the pull was requested.

**A2 recovery: `choose/4` never returns a TORN local replica (expert review 2026-11-07 #2).** `choose` ranks on `{lineage, ordinal, offset}` and `rank/1` never read `torn`, so a torn local copy (every replica after an OS reboot, `Follower.hold_torn_after_reboot`; a failed promotion's fence) that tied or out-ranked a peer returned `:local`. `decide_from_fleet` then refused it (`Promote.fresher?(%{torn: true}, _)` is false) and fell through to the stale object: no pull, no log, no refusal, while the peer held the acked tail, and the first flush re-stamped over it. The comment that justified the shortcut ("the winner is already strictly ahead of the object, so a local copy at least equal to it is too") is false exactly where `fresher?/2` has non-order clauses (torn, lineage 0, ordinal 0); the fix is the review's one-liner, `fresher?(local, stamp) and rank(local) >= rank(pos)`, and the comment now says why. The review warned it is NOT sufficient alone: the tie then becomes `{:pull, peer}`, and a torn local from a failed promotion carries the raised lineage, so the pull hit `stale_lineage_seed?` and degraded silently. That is why it landed after the failed-pull refusal (#4) and before the lineage change (#3(b)). Pinned by `replication_recovery_test.exs` (pure `choose/3` over torn positions that tie, trail and out-rank the peer, plus a real-socket pull replacing a torn local).

**A2 promotion: a failed publish un-fences the replica, a failed verify does not, and a recovery pull is not a deposed primary (expert review 2026-11-07 #3).** `Promote.stage/4` copies the replica pair then `fence_for_promotion/3` writes `torn: true` and the new owner's lineage durably, BEFORE verification and the publish PUT, so a deposed owner's push cannot land under the copy. Nothing lifted it when the PUT then failed (store pause, 412 because the object moved, ENOSPC), and the Jepsen 2026-10-24 refuse-and-retry then met a replica torn at the NEW lineage over the OLD bytes: unrankable, and the peer holding the same tail at the old lineage could not refill it because `stale_lineage_seed?/2` refused its seed as "below the replica's lineage". The refusal window only converted "serve stale now" into "serve stale after one window" (the test recorded the gap: "NOT asserted: that the retry then recovers the tail"). Two separable parts, each with its own mutation-checked test in `promote_on_open_test.exs` (both liveness modes, the mode asserted): **(a)** `fence_for_promotion` now returns `{:ok, %{prior:, fenced:}}` and a publish that fails or raises calls `Follower.unfence/3`, which under the shard lock restores the PRIOR row iff the row still equals the fenced one. **The review's amendment is load-bearing:** restore the prior row, never merely clear `torn` with the raised lineage kept: rank is lineage-first, so a row claiming the new lineage over old bytes would out-rank a peer that really holds more of the old lineage, and the retry would promote the shorter copy. The deposed-owner push window after the restore equals the window before the attempt (and a coordinator registered on the node refuses wire frames anyway, `coordinated_here?/2`). Not restored past a successful publish (the tail is the object) or on the local-rename failure (which raises and abandons the open). **(b) A verify failure keeps the fence, deliberately (a deviation from the review's "any failure after the fence").** `checkpoint_and_verify` fails on a bad WAL checksum, `quick_check`, an unreadable WAL or an open/checkpoint error: those bytes are unverifiable, and restoring them would make the retry choose `:local` over a peer with a good copy and fail the same way until the window ended (the very loop #2 closed from the other side). They wait to be replaced by a pull, which is why `begin_seed(.., pull: true)` no longer applies the lineage fence to a TORN higher-lineage row; an UNTORN higher-lineage row still refuses it (typed `:stale_lineage`), and a wire seed is unchanged (`seed_lineage_fence_test.exs`). The operator path (`Promote.promote/2`) takes the new `{:ok, _fence}` shape but does not un-fence on its later failures: it can only fail after a rename onto the live path, and an operator retry is refused by `ensure_no_local_copy/1` anyway (follow-up, not a regression). Test-fixture traps found on the way: with replication off the open claims no lineage (`open_lineage/2` is `:disabled`) so the fence raises nothing and the scenario is unreachable, and with the lineage/ordinal wire gates off a peer's offer reads unrankable so recovery never pulls; the new tests turn all three on only AFTER the fixture is built.

**A2 follower: a replica that exists but cannot be read answers torn, not "nothing" (expert review 2026-11-07 #18).** `Follower.derive_state/3` returned `nil` whenever `Wal.read/1` errored, and a position query maps `nil` to the `have = 0` frame that `Recovery.answered/3` counts as a DEFINITE answer toward the `N−Q+1` floor. A replica holding the acked tail behind a damaged `-wal` header (the zero-filled header an OS crash can leave: `{:error, :not_a_wal}` for a file of 32+ bytes; or `:emfile` under fd pressure) therefore let the recovering node reach the floor on "nothing"s, choose `:none` and open from the stale object. The empty-WAL branch of the same function was already fixed for this class (2026-10-15 #4 follow-up); this one was missed. Now `derive/3` answers TORN (silent to a query, unranked, never counted, re-seeded on its next push) when the `.db` exists and the WAL read errors, and a follower that never held the shard, or holds a stray `-wal` with no `.db`, still answers a definite "nothing" (the documented requirement; pinned by a control test). **Trap, the review's own amendment:** only the deterministic damage (`:not_a_wal`) is cached as a torn row; a transient error (EMFILE, EIO, an `:eacces` that clears) is answered torn from the files each call and NOT inserted, because a cached torn row would poison a replica that may be the only holder of the tail until a re-seed forced by a passing error. That needed `recover_shard/3` to return the row rather than a boolean (the caller used to re-read ETS for it, which cannot see an uncached row). The transient test uses a directory in place of the `-wal` (`{:error, :eisdir}`) as the portable stand-in for EMFILE. Pinned by `test/fathom/shard/replication/follower_unreadable_wal_test.exs`.

**A2 primary: a tenant commit is never acked on a blind wal-index or an empty follower set (expert review 2026-11-07 #10, #17).** Two ways `ship_and_settle`'s `{:nothing, state} -> ack_if_owned` arm (the "nothing left to ship" ack) answered `:ok` for frames no replica held. **#10 — the blind round.** With an `-shm` fd held and the cursor's salts unchanged, an unusable wal-index (three torn reads, a short or zeroed `-shm`) makes `Wal.read_held/2` report the cursor's OLD extent `E_old` (`walk_or_hold/6`'s "an older extent is a safe under-claim"). True for "what to ship next", false for "is THIS caller's commit covered": every follower already held `E_old`, so `Primary.plan/3` planned `:nothing` and the commit whose frames `(E_old, E_new]` were never read was acked quorum-durable; `covered?/2` against the same header let the pinned checkpoint, and the idle-close verdict, backfill them too. Now `read_held` tags such a header `blind: n` (key present ONLY then, so the readable-index path returns the exact map `read/2` does and pays nothing), `Session.read_commit_header/3` re-reads a tenant round up to 3 times (the torn window is sub-microsecond) and otherwise fails the commit `{:error, :wal_index_unreadable}` (a retryable 503 and a `QuorumFence` mark in the executor: the commit IS locally durable), and `covered?/2` / `checkpoint_verdict/1` refuse a blind header. Catch-up and idle-close rounds ack nobody and keep the hold. **The fix that looks obvious and is wrong:** walk the WAL for the extent when the index is blind — the walk trusts a frame HEADER and over-counts a torn frame, the hazard the hold was introduced for (round-4 durability review 2026-10-20 F2), and the cursor would keep the over-count. Each re-read spends one of `@max_blind` (8), so a PERMANENTLY unusable index still degrades to the walk after about two failed commits, the existing "never expected" fallback, instead of failing every write forever. **#17 — the empty set.** `ship_planned/5` reads "no plans" for both "every follower already holds the extent" and "there are no followers"; with `Fleet.shippers() == []` (`Fleet.init/1`'s `publish([])` before `Membership` publishes, `Membership.terminate/2`'s retraction while the Session tree is up) a write held on this node's disk alone was acked. A fleet with ZERO followers is not a legitimate single-node configuration here: `Fleet.validate_quorum!/0` refuses to boot replication with no followers and `Membership` refuses any set of `q` or fewer, so an empty set is only ever a transient window. `do_commit/4` now refuses a tenant commit with `{:no_quorum, :impossible}` when `length(shippers()) <= quorum()` (it used to RAISE `q >= n` inside the commit for `0 < n <= q`); catch-up and idle-close cycles are unchanged. Pinned by `test/fathom/shard/replication_blind_index_test.exs` and `replication_empty_set_test.exs`, both liveness modes.

**A2 primary: a refused push leaves no phantom in-flight entry; a hidden quorum failure still fences reads (expert review 2026-11-07 #44, #73).** **#44.** `Session.send_round/7` records `inflight[F]` for every planned follower BEFORE sending. When the node byte budget (`Budget.reserve/2`, `REPLICATION_MAX_QUEUE_BYTES`) or a shipper's mailbox bound refuses, `Shipper` answers `{:reject, shard, :overloaded, 0}` to the caller and sends nothing, and `reconcile/2` KEPT the entry on the reasoning that `:overloaded` means "the follower is still on the hook for an EARLIER push" (true of `:already_in_flight`, false when this very round created the entry). The next commit then saw `map_size(inflight) != 0` with no free follower and waited out its deadline for replies that were never coming (~`2 * timeout()` per shard, on every follower the overload touched). Now `reconcile/2` has an `:overloaded` clause that drops the entry unless the Session re-sent over a stale entry (`repeated`, tracked in `send_round/7`, empty in steady state). **Two things the review prescribed that are wrong:** testing `Map.has_key?(waiters, shard)` before `overloaded?/1` in `Shipper` so that `:overloaded` "always means nothing outstanding" cannot work, because the byte-budget refusal is decided in the CALLER (`Shipper.push/2`), which cannot see the shipper's waiters; and adding `:overloaded` to `@settled_rejects` would re-break the 2026-08-20 #27 case (a genuinely outstanding earlier reply whose expectation is the only thing that lets `:offset_mismatch` correct the follower's position). Same class, fixed: a `Shipper` does not trap exits, so a swap's `DynamicSupervisor.terminate_child/2` never ran `terminate/2` and its outstanding waiters were never answered; `Fleet.stop_shipper/1` now calls `Shipper.retire/1` first (`:disconnected` to every waiter). Trapping exits instead was rejected: the writer is `spawn_link`ed, and a trapping shipper would swallow its `EXIT` instead of restarting cleanly. Pinned by `test/fathom/shard/replication_overloaded_refusal_test.exs` (a real overload through `:replication_max_queue_bytes`, both liveness modes) and `replication_shipper_retire_test.exs`. **#73.** With `REPLICATION_DEFERRED_WAL_SYNC` on, a round whose quorum FAILED and whose fdatasync also failed (or was still pending) answered only `wal_sync_failed`: `gate_on_wal_sync/4` discarded the quorum verdict, and the executor deliberately does not mark on a failed local sync (it has its own fence, the poison). But the poison refuses ACKS, not reads, and an `{:open, _}` failure does not even poison, so `confirm_quorum/3` was never armed and reads of the locally committed, unreplicated write kept being served (Jepsen finding 7, reachable again under the flag). `run_commit/6` now calls `QuorumFence.mark/1` itself when the round's verdict was an error and the gated reply is `wal_sync_failed` — only the Session knows both. **Executor dirty accounting covers the ERROR return (expert review 2026-11-07 #5).** `ShardExecutor` bumped `WriteCounter`, signalled `:became_dirty`, marked the transaction as having written and shipped to the A2 quorum only in the SUCCESS branches, on the assumption that an error return commits nothing. **S3 lease: an ambiguous steal PUT carries its own marker, and a failed steal-touch's rollback keeps the steal watch (expert review 2026-11-07 #6, #60).** A steal is two writes — the lock PUT (`{us, epoch+1}`), then the data-object touch that makes a zombie's already-fenced `If-Match` flush 412 — and `Req` never retries a PUT, so a lock PUT whose reply is lost surfaces as an error for a lock that EXISTS. Pre-fix the retry's `acquire_existing/4` read a lock naming itself and took the same-owner reclaim: no steal-touch, no `took_over`, no `prev_owner`. A stalled zombie's flush could still land after our pull; promote-on-open skipped the takeover ask (a WARM local copy skipped promotion entirely — the Jepsen 2026-10-24 `WarmTakeoverPromoteTest` shape, re-opened by a lost reply); the previous owner's empty answer counted toward the recovery responder floor. **The mechanism is an in-body marker**: `Storage.pending_steal/3` puts `touch_pending: true` and `prev_owner` (plus what the success path would have put on the lease from the stolen lock: `released_by`, a clean marker's `touched_from/touched_to`) in the SAME single PUT, so the lock says what it is whatever happens to the reply, and `S3.resume_steal/7` redoes claim + touch and returns the lease a completed steal returns. A renew rewrites the body from `Map.take(lease, [:claim])`, which clears the marker; heartbeat mode never renews, so it can outlive a completed steal and a same-incarnation reopen then redoes the touch (conservative: one more touch, takeover decisions run for a lock this node already held). **The rollback is the belt, not the mechanism**: on an ambiguous steal PUT `roll_back_steal/4` rewrites a lock that is still exactly ours to `{dead owner, epoch + 2}` — never a delete (the next acquire would be a fresh create at epoch 1 with no touch) and never back to `epoch` (a backward jump) — but it cannot close a PUT that is merely DELAYED (it reads the pre-steal lock, no-ops, and the late PUT lands after it) and it fails exactly when its own read fails in the brownout that lost the reply; the test that makes that read fail is the one that pins the marker. `restore_lock/4` also read a failed `get_lock` as "nothing to roll back" (`_ -> :ok`): it now retries the read and reports the stranded lock, and its replacement keeps the dead lock's `released_by`/`touched_*`/`dirty`, which the rollback used to drop. **#60:** the rollback rewrite changes the fingerprint the clock-free steal watch keys on (`{epoch, expires_at_ms, etag}`) and `watch_since/3` restarts on ANY change, so every transient touch failure cost the retry another full `ttl + steal_margin` (35 s in prod) for a hold this node had already watched sit unchanged. `Storage.carry_steal_watch/4` re-keys the entry across our own rewrite, keeping its start; only the LOCK half of the key moves, so a renewing heartbeat or any other change to the lock still restarts the watch (both pinned). **Harness** (the prerequisite — the doubles could only fail BEFORE a write applied): `S3EtagStore.inject/4` (`apply: true` performs the request and discards the reply, `after:` stages "the write landed, and from then on reads fail", `times:`), `set_missing_if_match_status/2`, `error_body/2`, pinned by `S3EtagStoreFaultsTest`. Tests: `s3_lease_ambiguity_test.exs` (both dead-owner heartbeat shapes), `steal_watch_test.exs`, the takeover-facts cases in `StorageContract`.

**S3 lock PUT maps AWS's conditional-write statuses (expert review 2026-11-07 #11).** `put_lock/3` mapped only 412. AWS answers a conditional PUT (`If-Match`) against a key that no longer exists with 404 `NoSuchKey` (MinIO says 412, which is why it was invisible there) and a concurrent conflicting request with 409 `ConditionalRequestConflict`; both surfaced as `{:s3_put_status, _}`, which every caller reads as "transient, retry". A deposed owner whose lock the stealer cleanly released (DELETED) therefore never self-fenced: `Fence.revalidate` turned the 404 into `:skip` forever, the shard served stale reads and refused every commit once its write fence armed, re-PUTting the lock every ~1-11 s. Now `put_lock/3` maps 404 `NoSuchKey` to `:precondition_failed` (so a renew is `:superseded`, a marker release is `:ok`, a rollback is a no-op) and 409 to the retryable `{:transient_lookup, :conditional_conflict}`; `create_lock/2` maps 409 the same way (a 404 there stays a plain error: a missing bucket). **The mapping is NOT inside `Fence.revalidate`**: the legacy flush fence and the legacy renew share the hole. **404 is only superseded when the body says `<Code>NoSuchKey</Code>`** (`no_such_key?/1`): S3 also answers 404 for `NoSuchBucket`, and mapping every 404 would make a mis-pointed or deleted bucket self-fence every shard that writes and quarantine its dirty data. The same body check now guards the data flush's fenced-PUT 404 clause, which had the identical latent conflation; `s3_fenced_put_404_test.exs` used to answer a BARE 404 and expect `:superseded` and pinned the defect (it now says so, and pins that a bare 404 is not trusted). A store that answers a bare 404 with no error document therefore never self-fences on a deleted key — the strict reading is deliberate, and the boot probe (which accepts 404 or 412) does not look at the body. Tests: `s3_lock_put_status_test.exs` (legacy and heartbeat fence modes), `ContractS3AwsTest` (the whole `StorageContract` against a double that answers like AWS).

**A failed lease acquire may have written the lock (expert review 2026-11-07 #26).** The lease create is one optimistic `PUT If-None-Match: *` that `Req` never retries, and its reply can be lost after the store applied it: `acquire_lease` returned `{:error, reason}` for a lock that existed and named THIS live node, `open_coordinator` stopped on `{:lease_unavailable, reason}` with no lease in state, and nothing released it — every peer read `{:held, us}` and a failover, migration or handoff was refused until this node happened to open the shard again (the migrator is a foreign owner even on this node, which is why it was quiet). `Fathom.Shard.reconcile_failed_acquire/4` now calls the new `Storage.release_if_owned/2` callback, which reads the lock and acts only when it names exactly this incarnation's owner, by `Storage.stranded_release/1`: a plain first-create lock (epoch 1, no claim, no marker) is DELETED; a lock still carrying the interrupted-steal marker becomes a CLEAN released marker naming the previous holder (never a delete — epoch-1 unfenced create); **anything else is KEPT**. **The review's recommendation (release any lock naming us, keeping its claim) was narrowed on purpose**: a lock at a higher epoch or with a claim can be this node's own ordinary lock from before the failed acquire — a coordinator that crashed while the node stayed up — and while it names a live node it is what keeps peers out of a shard whose local copy holds acked-but-unflushed writes; turning it into a marker hands that shard to the first peer to ask. For the same reason **only a COLD open reconciles** (no local `.db`): a warm open whose create landed keeps healing the old way, on this node's next open. Skipped where the failure proves nothing was written (`{:transient_lookup, _}` read blips, `:corrupt_lock`) except `{:touch_failed, _}`, whose lock write landed first. Narrows the window, does not close it: a PUT that is merely delayed can land after the read saw no lock. Harness: `FaultyStorage` `:acquire_lands_then_errors` (the lock is written and the caller is told it failed; `:acquire` fails before writing), pinned by `FaultyStorageLockFaultsTest`. Tests: `shard_acquire_lands_then_errors_test.exs` (both liveness modes, FaultyStorage and S3 over `S3EtagStore`, plus the warm and no-write cases), `stranded_release_test.exs`, `StorageContract`.

**A lapse revalidation skipped behind an in-flight flush is re-armed when the flush ends (expert review 2026-11-07 #12).** `handle_info(:revalidate_lapse, %{flush_task: t})` skips while a flush runs, justified by "the flush runs its OWN `Fence.check`". **The lease release is retried and its failure surfaced (expert review 2026-11-07 #13).** Every drop path (`release_plain/1`, `release_clean/1`, `release_keeping_claim/2`, plus the open-failure releases) ended in ONE conditional `DELETE … If-Match` (or the released-marker PUT) whose `{:error, _}` the callers ignored; `Req` retries only GET/HEAD, so a reset, a timeout or a 5xx stranded the lock behind this node's live heartbeat — a handoff target got `{:shard_held, source}`, the migrator snoozed with `failed: 0` and nothing logged, until this node reopened the shard. `release_with_retry/3` now runs the release in a task on a 50/200/800 ms ladder under `release_budget_ms/0` (a quarter of the settle budget, 5 s by default; the first drop upload holds up to `settle_yield_ms/0` and the retried upload half of it, inside `:shard_shutdown_ms`). A retry is safe only because each attempt is the same FENCED request resolved against the lock's current state: a lost-reply DELETE retries into a 404, a changed lock 412s into `resolve_412_release` and is left alone, a marker PUT retries into a 412 → `resolve_412_marker` → `:not_ours`. **Wrong alternatives, recorded:** deleting unconditionally removes a stealer's fresh lock (2026-08-01 #22); switching the marker to a plain DELETE re-creates the epoch-1 unfenced create (`S3StealTouchRollbackTest`). **The drop's retried upload is bounded like the first (expert review 2026-11-07 #49).** `retry_drop_upload/1` (a 412 on the drop PUT with the lock still ours) ran its two HEADs and `upload_for_drop/1` inline in the coordinator: checkpoint + `quick_check` + compress + a PUT with no deadline of their own (S3's client timeouts alone are 30 s send + 15 s receive), on top of the first attempt's `settle_yield_ms/0`, against a `:shard_shutdown_ms` that kills terminate outright; checkouts then failed hard instead of retrying onto a fresh coordinator. `bounded_retry_upload/1` runs the re-fence and the upload in one task under half the settle budget (the review asked to bound the HEADs by the "remaining budget"; one task over the whole sequence does that without threading a deadline through `Storage`); a timeout is `{:error, :drop_flush_timeout}`, which the existing `other` arm turns into keep-local-and-release, as the first upload's timeout does. **`Shards.flush/1` does not answer `:ok` when the coordinator self-fenced with the call queued (expert review 2026-11-07 #50).** `flush_pid/3` mapped every `{{:shutdown, _}, _}` exit of the `:flush_now` call to `stopped_clean/1`, which answers `:ok` unless a local copy survived. **One owner-string builder: the previous-incarnation cleanup uses the node key (expert review 2026-11-07 #31).** `Heartbeat.owner/0` is `<node_key>#<nonce>` since 2026-10-15 #17, but `clear_previous_incarnation/0` (the boot-time proof-of-death for this node's own previous incarnation) kept building the predecessor as `<node()>#<nonce>`. **A heartbeat node never opens a coordinator in legacy mode by accident; a legacy renewal failure starts the fence clock (expert review 2026-11-07 #59).** `acquire_gen` is fixed at open (non-nil = heartbeat, nil = legacy) and was sampled as `if Heartbeat.running?(), do: Fence.generation(), else: nil`, where `Fence.generation/1` maps ANY exit to nil. The Heartbeat registers its name before `init/1` does its storage I/O (`clear_previous_incarnation`) and is unregistered between a crash and the supervisor's restart, so an open that overlapped either latched LEGACY for the coordinator's whole life: no lapse subscription, the Session ack ungated, and — the second half — a failing legacy renewal only logged. **Chosen shape: refuse, don't upgrade.** `sample_acquire_gen/0` runs first in the open (before the fork-evidence and pull tasks, still before `acquire_lease`); when the generation cannot be read and the node is CONFIGURED for the heartbeat (`Heartbeat.configured?/0`, the one reader of `:heartbeat_server`, default true, which `Application` now also uses) the open stops `{:shutdown, {:heartbeat_unavailable, :down | :booting}}`, a retryable 503 (`ShardExecutor.open_error/1`) with nothing acquired. The review's alternatives: "upgrade at the first revalidate" has no sound trigger (a legacy coordinator receives no lapse broadcast) and would have to prove no steal happened while it was legacy, the very proof the pre-lease baseline exists to give; refusing costs one client retry for the length of a Heartbeat restart. `heartbeat_server: false` (tests, dev) keeps legacy. **The legacy renew-failure clock:** `apply_renew_result({:error, _})` now calls `note_not_valid/1`, so a failing per-shard renewal starts the write-fence clock on a CLEAN shard (previously only a dirty shard's flush `:fence_skip` did, so a read-mostly legacy shard on a cut-off node never fenced and the first write after the steal window was acked); the re-check timer reads "still set" as "no renewal has succeeded" and the next successful renewal clears it. It starts at the first failed renewal, ttl/3 after the last success, so it arms ttl/3 early, the same early direction as the heartbeat clock. Tests: `shard/liveness_mode_latch_test.exs` (refused when down, refused when registered-but-dead, 503 mapping, heartbeat and config-off controls) and `cluster/write_fence_timer_test.exs` (the clean-shard legacy renewal case, including the lift).

**Every typed open refusal is classified in `ShardExecutor.open_error/1` (follow-up to the 2026-11-07 batch D).** `{:pull_failed, _}`, `{:local_stat_failed, _}` and the `:pull_temp_missing` / `:sidecar_corrupt` reasons the pull carries had no clause, so a client got a 500 `FILO_OPEN_FAILED` for refusals that clear on a retry (an SDK treats a 500 as permanent). The rule now: a refusal a retry can clear is the retryable 503 `FILO_UNAVAILABLE` the other transient refusals use (`FILO_RECOVERING` stays the recovery refusal window, which arrives as `{:open_failed, %UnderQuorum{}}`, including the failed peer pull of batch C); `{:pull_failed, reason}` takes the class of its `reason` and an unlisted `reason` is retryable; the two that need an operator, `:sidecar_corrupt` and `:no_provenance` (a warm file whose provenance cannot be trusted and could not be quarantined: `Materializer.await_pull/3` refuses rather than adopt an unknown lineage), get a stable NON-retryable `FILO_SHARD_UNRECOVERABLE` 500, distinct from the unclassified `FILO_OPEN_FAILED`. Also classified: `{:retained_claim_failed | :retained_claim_unavailable, _}` and (#59) `{:heartbeat_unavailable, _}`. **Deliberately still a 500:** a raw exception in `{:open_failed, exception}` (including the promotion's `raise "promoted object published but …"` for a failed sidecar write or local rename) is a code/data fault by the existing rule; typing those raises would be a change to `PromoteOnOpen`, not to this mapping. The open_error/1 mapping runs only on an open that has already failed, never on a successful stream, so this change is not on the hot path. `shard_executor_open_error_test.exs` is the table of every reason (status + code) plus a drift guard that reads `materializer.ex`, `promote_on_open.ex` and `retained.ex` for literal `{:error, <tag>…}` reasons and fails when one is neither classified nor listed with a reason. The benchmark harness setups (`Bench`, `Bench.StorageIO`, `Scale`) boot no supervision tree and so no Heartbeat; they now set `heartbeat_server: false` explicitly, the same legacy topology they always measured, because a heartbeat-configured node refuses that open (#59).

## Bench + scale harnesses

**Bench + scale harnesses.** `mix fathom.bench` (+ `scripts/benchmark.sh`, `scripts/perf_history.jsonl`, the `scripts/commit_with_bench.sh` regression gate) measures the hot paths; `mix fathom.scale` measures cold-open at real size, node density (`--ramp`), warm density (`--warm-density`), lease-renewal load (`--lease-rps`), and hot-spot detectability (`--hotspots` — the Phase-2 §B rebalancing evidence: Zipf-skewed load read back through `Fathom.ShardLoad`); `mix fathom.rpo` (`Fathom.Rpo`) quantifies the **loss window** — it sweeps `:shard_flush_interval_ms` × write rate and reports lost rows/seconds on node loss (survivor cold-opens the last flushed object) plus a process-crash-loses-nothing check (`synchronous=FULL`), the in-process complement to `deploy/chaos/chaos.sh soak` (see `docs/durability.md`). ## Memory: blocks are not RSS (expert review 2026-10-21 r7 #3)

`:erlang.memory/0`, `served_kb_per_shard` and the soft-heap accounting all sum allocated **blocks**. SQLite's page caches live in `driver_alloc` multiblock carriers, interleaved across connections, and a carrier goes back to the OS only when it is completely empty. Measured on Linux (colima, kernel 6.8, aarch64, ERTS default allocator flags), 400 connections each with a full 2 MB cache: closing 3 of 4 leaves `:erlang.memory(:total)` at 260 MiB and `PRAGMA shrink_memory` on the survivors at 58 MiB, while RSS stays at **931 MiB** (the high-water mark) until the last connection closes. So "2.1 MB to 5 KB per idle handle" (pooled-idle shrink) is **reusable headroom inside the allocator, not RSS**. `memory_breakdown` now reports `allocated_carriers`, `allocated_blocks`, `driver_carriers`, `driver_blocks`, `driver_fragmentation` and (Linux) `rss`; judge density by `rss` and `driver_carriers`, not by `system`. If SQLite is ever moved to the C allocator (`:exqlite, :disable_erlang_allocator`), the `driver_*` gauges read 0 and `rss` is the only truth.

## Host writeback + tail attribution (expert review 2026-10-29 #1, #17)

**The tail is a host setting, and the BEAM cannot see it.** Every `synchronous=FULL` commit fsync waits behind kernel page-cache writeback, and fathom's unfsynced follower writes fill the cache fast, so a large-RAM host on default `vm.dirty_*` batches writeback into 30 s / 60 s bursts (chaos rig, 94 GB VM: p99 598 ms, 1.1-1.2 s windows; `vm.dirty_background_bytes` = 1 GB: p99 417 ms, flat windows; `docs/reviews/tpc-fleet-repl-on-2026-10-26.md`). **Lower is not better**: 256 MB (p99 485 ms) and 64 MB (p99 762 ms, 2,273 txn/s) were worse than 1 GB. The warning and the docs say "measure", and 1 GB is the rig's number, not a recommendation for another host. `Fathom.Application.check_vm_dirty_background!/1` is the warn-only prod boot check (threshold 2 GB, twice the only measured-good value; `Fathom.Host.Proc` holds the pure parsers). Its gauge, `fathom.node.vm_dirty_background_bytes`, comes from the poller (`Measurements.host/0`), not the boot check: the metric reporters attach after the preflight, so a boot-time `:telemetry.execute` would be dropped.

**Trap: do not "just add `sync_file_range` pacing".** The constant-writeback arm was worse (220 vs 175 ms, same report). **Trap: `long_schedule` does not see dirty NIFs**, which is where an fsync blocked behind writeback sits; read `fathom.node.run_queue.dirty_io`, `fathom.node.io_pressure.*` and the opt-in `FSYNC_PROBE` for that. `:erlang.system_monitor/2` is VM-global, so `Fathom.Host.SystemMonitor` refuses to take it over from another owner. The probe file `.fsync_probe` is a dotfile in the shard data dir on purpose: shard ids cannot contain `.`, and every data-dir enumerator keys on `<id>.db` or skips leading-dot names.
